02｜Harness论文主张组合泛化能力

来源（X） · @Xudong07452910 · 2026-11-21 11:40

模型越来越强，Harness 迟早会被吃掉，这篇论文给了个相反的看法。

以前搭 Harness，更多是在给能力不够的模型兜底。alex zhang 他们的新论文认为，现在模型强了，Harness 的作用变成了把模型已有的能力组合起来，让它能处理更长、更复杂的任务，甚至是训练里没见过的任务。

我觉得最有意思的是这个思路：把长任务拆成很多次小调用，让每一次调用都落在模型熟悉的范围里。这样训练时就不用跑完整条很长的流程，用合成任务加模拟的工具调用和子 Agent，单独训练其中一次调用就行，省数据也省时间。

自己做 Agent 产品下来，感觉也差不多。模型升级以后，Harness 里确实有不少东西可以删掉，但怎么拆任务、怎么调度子 Agent，这些设计会更重要。

目前论文、代码和数据都开源了，做 Agent 的朋友可以去翻翻。

引用内容

alex zhang @a1zhang

中文译文

Harness曾经是弱LLM的拐杖。从2026年起，随着模型能力的增强，harness现在提供了一种机制，用于组合LLM已有的和新的能力，使其泛化能力远超其训练环境。

在我们的新论文《LM Harnesses are Compositional Generalizers》中，我们探讨了各种harness抽象如何使LM系统通过对现有LLM能力进行组合，在任务长度、任务策略、递归任务深度等方面实现泛化。这些抽象提供了一种更高效的数据利用训练方式，尤其适用于长任务——通过使轨迹保持在局部分布内（LID），即让所有单次LLM调用都处于分布内。

对于需要很长时间才能执行完毕的任务，这意味着我们甚至可以进行替代harness训练，即用纯合成任务——包含虚假的工具调用和子智能体——来训练单次LLM调用，而不是执行非常长的harness流程。

一个常见的观点是LLM会吸收harness并使其过时。我们不同意，我们认为我们尚未充分探索harness所能提供的价值。

完整的论文、日志、代码库和数据已公开：https://www.alphaxiv.org/abs/2611.harness-cg

与 @SOURADIPCHAKR18 @lateinteraction 合作

原文

Harnesses used to be a crutch for weak LLMs. In 2026 and onward, with stronger models, harnesses now offer a mechanism for composing an LLM’s existing and new capabilities to generalize well beyond their training environments.

In our new paper, LM Harnesses are Compositional Generalizers, we explore how various harness abstractions enable LM systems to generalize over task length, task strategies, recursive task depth, and more through composing existing LLM capabilities. These abstractions provide a means for more data-efficient training, especially over long tasks, by keeping trajectories locally in-distribution (LID) — i.e., shaping all individual LLM calls to be in-distribution.

For tasks that take a very long time to roll out, this implies that we can even perform surrogate harness training, meaning we train an individual LLM call instead of doing the very long harness rollout, using purely synthetic tasks, with fake tool calls + sub-agents!

A common idea floating around is that LLMs will absorb harnesses and make them obsolete. We disagree, and argue that we haven’t sufficiently explored what harnesses can provide.

The full paper, logs, codebase, and data are available: https://www.alphaxiv.org/abs/2611.harness-cg

03｜谷歌发布Harness工程六步实践

来源（X） · @hanakoxbt · 2026-11-21 05:34

中文译文

Google的团队发布了一份关于Harness Engineering的9页PDF。prompt engineering被一个公式取代了：

Agent = Model + Harness

关键在于：同一个Claude Sonnet，同一个基准测试，只有harness不同。

这套方法论包含六个步骤：

步骤1 -> 添加指南
AGENTS.md、规则文件、约束文档。里面的每一行都是一个曾经发生过、不会再次出现的旧故障。

步骤2 -> 添加传感器
linter、测试、验证脚本。智能体在人类看到输出之前就先对自己的输出打分。

步骤3 -> 构建agentic循环
规划、执行、验证、修复。重试有上限，预算有上限，卡住的智能体会把问题上报。

步骤4 -> 外化记忆
模型每次会话醒来时大脑空白。harness持有状态、决策和产物。

步骤5 -> 强制执行权限
用哪些工具、多少次写入、哪些操作需要人工。安全性存在于harness中，而不是prompt中。

步骤6 -> 接入可观测性
每次工具调用、每一分钱、每次重试都会被记录。一旦行为出现偏差，警报立即触发。

结果：智能体不再是一个demo，而开始成为基础设施。

每一次故障都变成永久性修复，所以下一次运行会比上一次更聪明。

这就是一个你拿来炫耀的智能体和一个客户付钱让你持续运行的智能体之间的距离。

一个harness给你一个可靠的循环。把几个连接起来，你就得到了图工程（graph engineering），其中一个智能体的故障成为另一个智能体的传感器。

这份PDF止步于harness。图（graph）是它之后的层。

原文

Google's team dropped a 9-page PDF on Harness Engineering. prompt engineering got replaced by one formula:

Agent = Model + Harness

the catch: same Claude Sonnet, same benchmark. only the harness changes

the playbook runs six steps:

step 1 -> add guides
AGENTS.md, rule files, constraint docs. every line in there is an old failure that can't happen twice

step 2 -> add sensors
linters, tests, validation scripts. the agent grades its own output before a human ever opens it

step 3 -> build the agentic loop
plan, execute, verify, fix. retries capped, budget capped, and a stuck agent hands the problem up

step 4 -> externalize memory
the model wakes up blank every session. the harness holds the state, the decisions and the artifacts

step 5 -> enforce permissions
which tools, how many writes, what needs a human. safety lives in the harness, not the prompt

step 6 -> wire observability
every tool call, every dollar, every retry gets logged. a trip wire fires the moment behavior drifts

the result: the agent stops being a demo and starts being infrastructure

each failure becomes a permanent fix, so the next run opens smarter than the last

that's the distance between an agent you show off and one a client pays you to leave running

one harness buys you a reliable loop. wire several together and you get graph engineering, where one agent's failure becomes another agent's sensor

the PDF ends at the harness. the graph is the layer after it

07｜AI Harness新手先做三件事

来源（X） · @xiaomovps · 2026-11-21 16:50

刚开始使用 AI Harness，我建议先做好这 3 件事，比安装一堆插件更有用

最近我在研究 Pi Agent、Claude Code、Codex 等 Harness 的时候，发现一个很有意思的问题

虽然每个 Harness 的设计和功能都不一样，但是很多基础的使用方法其实是相通的

我结合自己的使用经验和官方资料，总结了 3 个比较实用的小技巧，尤其适合刚开始接触 Harness 的新手

1、先配置好 AGENTS.md 项目规则

这是我觉得最基础的一步

可以直接让 AI 分析自己的项目，然后帮你生成 AGENTS.md，把项目结构、技术栈、开发规范，以及需要特别注意的地方记录下来

这样后面执行任务的时候，AI 就能更好地理解你的项目，不需要每次都重新解释

注意，Claude Code 主要使用 CLAUDE.md，不同 Harness 的配置文件可能不一样

推荐阅读：OpenAI 官方 AGENTS.md 配置指南

https://developers.openai.com/codex/guides/agents-md

2、根据需求配置常用的 Skills

我不推荐新手一开始就安装一大堆 Skills

可以先从自己最常用的功能开始，比如浏览器操作、代码审查、文档处理等，把一些重复性的工作交给 Skills

后面有新的需求再慢慢扩展就可以了

推荐阅读：Agent Skills 官方入门文档

https://agentskills.io/home

3、养成先规划、再执行、最后验证的习惯

这也是我觉得最重要的一点

特别是遇到复杂任务的时候，不要直接让 AI 开始修改代码

可以先让它分析需求、制定计划，然后按照步骤执行，最后让它自己运行测试，检查任务有没有真正完成

当然，简单任务没必要搞得这么复杂

推荐阅读：Anthropic Claude Code 最佳实践

https://code.claude.com/docs/en/best-practices

与其说这是三个使用技巧，不如说是对 AI 资料和信息的整理，很多时候 AI 的能力就取决于你给的资料，针对这个资料，能反馈出多少东西，就取决于你花了多少时间整理

每一个点看起来都比较简单，而且都比较容易上手，真正缺乏的就是，你会不会在真正的使用环境当中去使用这些技巧，当你真正地融入到你自己的任务当中

你也会发现其实用好一个 AI，也是如此的简单

引用内容

小墨同学 @xiaomovps

AI Agent 的 Harness，到底是越简单越好，还是越复杂越好？

看到 Reddit 有一个有意思的讨论：Harness到底是复杂一点好，还是简单一点好？

一位开发者做了 35 次对照测试，发现单 Agent + Skills 和多 Agent 在测试任务上的完成质量差不多，但是多 Agent 的成本高了 62%，执行时间也接近两倍

评论区也出现了两种不同的观点

一部分人认为，现在模型的能力已经足够强了，没必要把所有任务都拆成多个 Agent，反而增加了上下文传递和协调成本

另一部分人则认为，如果面对大型代码库和复杂项目，多 Agent 的并行执行、独立审查和分工依然很有必要

看到这个讨论，我又想到了最近一直在研究的 Pi Agent

其实 Pi 的设计就很契合其中 一条极简的路线，核心只有几个基础工具，剩下的能力交给开发者自己扩展

而 Claude Code、OpenCode 这些 Harness，则提供了更多开箱即用的能力

这也让我开始思考，到底是应该尽可能简化 Harness，让模型自己发挥能力，还是应该把更多功能和规则放到 Harness 里面？

说实话现在我没办法给出答案，如果让我选我可能会更偏向于极简，因为Pi Agent是我实打实在用的，而且也帮我节省了很多额外的Token消耗

极简的 Harness 更容易理解和改造，可以根据自己的需求慢慢扩展，但是很多功能也需要自己维护

复杂的 Harness 虽然会增加一些开销，但在权限管理、任务调度和执行稳定性方面，也能替我们解决不少问题

如果你也想了解，可以看看这篇Harness设计指南：https://journal.daniellopes.dev/p/what-is-an-agent-harness
