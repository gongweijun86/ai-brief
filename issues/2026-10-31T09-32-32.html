06｜RAG用目录树索引替代向量相似检索

来源（X） · @_avichawla · 2026-10-30 15:26

中文译文

RAG 与无向量 RAG 的清晰对比讲解！

在标准 RAG 架构中，文档被切分为文本块，经过嵌入处理后存入向量数据库。查询同样经过嵌入，然后将最相似的 top-k 文本块送入 LLM。

问题在于：相似性和相关性回答的是不同的问题。

举例来说，同一家公司的五份年报很可能每年遵循相同的模板，只有数字会发生变化。

因此，一个关于 FY2022 的问题可能和 FY2025 的文本块距离同样近，LLM 可能会用错误年份的数据来回答。

交叉引用还引入了另一个问题。如果一个文本块提到"参见附录 G"，但其内容与附录 G 中的表格毫无相似之处，那那张表格将永远无法进入 top-k。

无向量 RAG 抛弃了嵌入模型和向量数据库，用 LLM 推理来替代相似性搜索。

预处理阶段将每份文档的版面解析为一个目录树索引。每个节点包含一个章节标题、其页码范围和一段简短摘要，整棵树可以放入 LLM 的上下文窗口中。

在查询时，LLM 同时接收查询和这棵树。它阅读章节标题和摘要，挑选出最可能包含答案的几个章节。

例如，关于债务的问题，它可能会选择"财务摘要"章节以及"附录 G"，因为附录 G 的摘要显示债务详情就在那里。

系统随后提取这些完整的章节，并检查证据是否充分。

↳ 如果足够，LLM 就基于完整章节给出答案，并附上页码引用。
↳ 如果不够，它就回到树上，展开更多节点。

LLM 还能看到对话历史。所以如果你先问了关于资产的问题，接着追问"负债呢？"，它就会回到同一份报告中。

代价在于，现在每次查询都需要在树上进行 LLM 调用。

在同样的查询中，top-k 向量搜索会更便宜（虽然不保证同样准确），而且树状结构只在文档确实有结构化层次时才发挥作用。

因此两者适用于不同的数据：

↳ 对于像申报文件、合同和手册这样长且结构化的文档，使用树结构。
↳ 对于大量短小、互不相关的文本，继续使用向量数据库。

原文

RAG vs. Vectorless RAG, clearly explained!

In a standard RAG setup, documents are split into chunks, embedded, and stored in a vector DB. The query gets embedded too, and the top-k closest chunks go to the LLM.

The problem is that similarity and relevance answer different questions.

For instance, five annual reports from one company can likely follow the same template every year, and only the numbers can change.

So a FY2022 question can lie just as close to an FY2025 chunk, and the LLM might answer from the wrong year.

Cross-references introduce another problem. If a chunk mentions "see Appendix G" but looks nothing like the table in Appendix G, that table will never make it to the top-k.

Vectorless RAG drops the embedding model and the vector DB, and replaces similarity search with LLM reasoning instead.

The preprocessing step parses each document's layout into a ToC tree index. Every node holds a section title, its page range, and a short summary, and the whole tree fits in the LLM's context.

At query time, the LLM gets the query along with the tree. It reads the section titles and summaries and picks the few sections most likely to hold the answer.

For example, for a question about debt, it might pick the "Financial Summary" section and also "Appendix G", because its summary says the debt details are there.

The system then pulls those full sections and checks whether the evidence is enough.

↳ If it is, the LLM answers from the full sections, with page citations.
↳ If not, it goes back to the tree and opens more nodes.

The LLM also sees the chat history. So if you ask about assets and then follow up with "what about liabilities?", it goes back to the same report.

The trade-off is that every query now runs LLM calls over the tree.

Top-k vector search will be cheaper in that same run (although not guaranteed to be as accurate), and the tree only helps when documents have real structure.

So the two suit different data:

↳ Use a tree for long, structured documents like filings, contracts, and manuals.
↳ Stick with a vector DB for lots of short, unrelated text.

07｜Proton称AI已写90%代码

来源（X） · @PlusLibQ · 2026-10-30 21:27

中文译文

Proton CTO 于九月发给其工程师的一份精彩的亲 AI 备忘录。这是我读过的关于开发者职业正在发生什么的最清晰的文本。非常技术人文主义。我没有读这场风波中的其他内容，但面对这份文本，没有任何理由感到愤怒。

它从一个简单的问题出发：既然每个人已经在使用 LLM，为什么生产力没有爆发式增长？

他的第一个回答涉及工程师如何看待自己的角色。他们把 AI 当作加快编码速度的工具。这是一个框架性错误："你的工作已经从根本上改变了。它不再是写代码，LLM 也不是为了帮你更快地写出更好的代码。你的工作是帮助 LLM 更快地写出更好的代码。"

因此，每位工程师都变成了一个管理者，其下属是 AI agent。而一个好的管理者不会整天黏在团队身边："一个当领导去开会时就没人工作的团队，不能算是真正的团队。"目标是让 AI 独立且长时间地工作，并且每次反复失败都触发一次对所有人都有益的修正。

他的第二个回答涉及瓶颈。如果 CI、代码验证和代码审查仍然维持人工节奏，加快代码编写毫无意义。"当我们消除一个瓶颈时会发生什么？另一个会取而代之。"必须从头到尾重新设计流程。他甚至写道，大多数人工代码审查将不得不消失。当成本发生变化时，最佳实践也会改变：如果编写和维护测试几乎不再需要成本，就没有理由再少写测试了。

他也以不天真的方式为人类的价值辩护。"LLM 很快。你很慢，但你承载着一生的经验、判断力和理解力。"工程师仍然要对同事负责，"以一种模型永远无法承担的方式"。

而他的结论是："'编程'已死。工程没有死，专业知识也没有死。你过去的工作已不复存在。你作为建设者的新工作将使你能做得更多、产生前所未有的影响——前提是你抓住这个机会。"

据他所说，Proton 在十月份 90% 的代码是由 AI 编写的。工程师成为虚拟团队的负责人，写作者成为虚拟编辑部的主编。这对开发者已经为真的事情，在未来几年内将成为许多其他职业的现实。这是需要把握的巨大机遇。

原文

Superbe mémo pro-IA du CTO de Proton, envoyé à ses ingénieurs en septembre. C’est le texte le plus clair que j’aie lu sur ce qui arrive au métier de développeur. Très techno-humaniste. J'ai pas lu tout le reste de l'affaire, mais il y a 0 raison de se scandaliser face à ce texte.

Il part d’une question simple. Si tout le monde utilise déjà des LLM, pourquoi la productivité n’a-t-elle pas explosé ?

Sa 1ère réponse porte sur la manière dont les ingénieurs voient leur rôle. Ils utilisent l’IA comme un outil pour coder plus vite. C’est une erreur de cadre : « Votre travail a fondamentalement changé. Il ne consiste plus à écrire du code, et les LLM ne sont pas là pour vous aider à écrire du meilleur code plus vite. Votre travail est d’aider le LLM à écrire du meilleur code plus vite. »

Chaque ingénieur devient donc un manager dont les subordonnés sont des agents. Et un bon manager ne passe pas ses journées collé à son équipe : « une équipe où personne ne travaille quand le chef est en réunion ne serait pas vraiment une équipe ». L’objectif est que l’IA travaille seule et longtemps, et que chaque échec répété déclenche une correction qui profite à tous.

Sa deuxième réponse porte sur les goulots d’étranglement. Accélérer l’écriture du code ne sert à rien si la CI, les validations et la revue de code restent au rythme humain. « Que se passe-t-il quand on élimine un goulot ? Un autre prend sa place. » Il faut repenser les processus de bout en bout. Il va jusqu’à écrire que la plupart des revues de code humaines devront disparaître. Même les bonnes pratiques bougent quand les coûts bougent : si écrire et maintenir des tests ne coûte presque plus rien, on n’a plus de raison d’en écrire peu.

Il défend aussi l’humain sans naïveté. « Le LLM est rapide. Vous êtes lent, mais vous portez une vie entière d’expérience, de jugement et de compréhension. » L’ingénieur reste responsable devant ses collègues « d’une manière qu’un modèle ne pourra jamais l’être ».

Et sa conclusion : « La “programmation” est morte. L’ingénierie ne l’est pas, ni l’expertise. Votre ancien job n’existe plus. Votre nouveau job de bâtisseur vous permettra d’en faire plus et d’avoir plus d’impact que jamais, si vous saisissez l’opportunité. »

Selon lui l’IA a écrit 90 % du code de Proton en octobre. L’ingénieur devient le chef d’une équipe virtuelle, l’écrivain le rédacteur en chef d’une rédaction virtuelle. Ce qui est déjà vrai pour les dev va devenir vrais pour tant d'autres métiers dans les années à venir. Immense opportunité à saisir.
