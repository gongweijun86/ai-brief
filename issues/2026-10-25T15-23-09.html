08｜Sub-Agent 拆分与反向合并实践

来源（X） · @xbquan · 2026-10-25 11:24

A➗最近探讨了 Sub-Agent（子智能体）的适用场景与架构设计实践。

本毛球觉得有以下四点可以学习！！

一、何时引入子 Agent？

1、上下文过载：Token 膨胀导致主 Agent 注意力涣散、效果骤降；

2、可并行执行：任务具备独立的上下文环境，支持并发推进；

3、工具与指令冲突：主 Agent 挂载工具过多导致选错，或多项系统 Prompt/约束产生逻辑互斥。

二、如何合理拆分？

遵循上下文边界清晰的原则进行切分。

像独立调研、接口明确的模块开发、独立单体验证等闭环任务，均适合交由子 Agent，执行完毕后仅向主流程汇总精简结论。

三、交互与控制流

1、主流模式（工具化调用）：主 Agent 将子 Agent 视作普通 Tool 驱动，自身保持全局把控，全权负责与用户的交互。

2、移交模式（交接对话）：仅当子 Agent 必须获取特定领域的交互输入、需直接面向用户时，才移交对话控制权。

四、何时需要反向合并？

若多个子 Agent 之间频繁前后接力、严重依赖共享上下文，往往是“过度拆分”。

此时更合理的做法是：收拢为一个 Agent，将固化流程编排为 Skills/Workflows，原子操作收纳为 Tools，最后通过端到端 Eval（评测集）闭环验证性能与召回。
