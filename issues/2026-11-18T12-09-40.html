扒了 yetone/magpie 38 天的全部发布记录（3,039 个 release，8,625 个 commit），看看号称「全流程 Agent 自治」的项目到底是怎么运转的：

1. 颗粒度极碎：中位数每次只动 7 个文件、2 个模块，61% 的版本只有 1 个 commit。
2. 10.23 效率拐点：前期重整结构，日均发十几个版本（单次动 27 个文件）；10.23 之后单次改动被压到 7 个文件，日均发布直接暴涨到 108 个。改得越少，发得越多。
3. 防幻觉秘诀：改动频次最高的是 docs（1,645 次），超过了核心代码 internal/gui。代码和文档在同一个 commit 里同步改，避免过时文档误导后续 Agent。
4. 强约束生效：对照仓库里的 code-standards.md（单提交单目标），实测数据基本严丝合缝。

最后个直观感受：用 AI 写代码，规矩立住了，后面写起来才能不烧心。

03｜LangChain Agent七成日程触发

来源（X） · @shao__meng · 2026-11-18 18:08

LangChain 谈主动式 Agent：超七成运行靠日程，关键是记忆与人的注意力

@LangChain 团队 @sydneyrunkle 总结了团队构建主动式 Agent 的经验：当 Agent 开始在后台推进持续数天、数周的目标，瓶颈不再只是模型能不能完成任务，而转为人有没有时间处理它不断送来的问题和结果。

以内部的销售 Agent 和工程 Agent Robin 为例，提出两个核心：用记忆提高判断质量，用交互设计减少人的评审负担。

https://www.langchain.com/blog/what-weve-learned-building-proactive-agents

# 主动不是不断发消息，是不必每次等指令

主动式 Agent 有三类触发来源：现实事件，例如新邮件、新 PR；开发者设定的日程，例如夜间整理记忆、每周清理陈旧 PR；以及 Agent 根据任务自行创建的日程，例如第二天跟进，或按用户要求建立每日简报。

LangChain 的 GTM Agent 负责跟进销售线索、处理回复和起草邮件；Robin 的前身是 Open SWE，负责起草和审查 PR。两者都基于 Managed Deep Agents 构建。团队介绍，超过 70% 的运行由日程触发，而不是人临时输入提示。

这个数字反映的变化是：Agent 不再只围绕一轮对话工作，而是通过事件和日程持续推进已有目标。

# 记忆不只是记录历史，更要帮助判断什么值得处理

Agent 被事件或日程唤醒时，往往没有新的人工说明。连接器可以提供最新邮件和项目状态，但用户的偏好、此前的纠正和合作习惯，需要从记忆中获得。

记忆来源分成三类：已有资料，例如过去发送的邮件；当下反馈，例如草稿被修改或拒绝的原因；行动结果，例如发出的邮件是否收到回复。

难点不在写文件，而在持续维护：哪些值得记住，哪些已经过期，重复或矛盾的信息如何处理。一种常见做法是「dreaming」：安排后台任务定期回看近期执行记录，整理并更新记忆。

衡量效果也不该只看存了多少内容，而要看草稿获批是否更快、邮件回复率是否改善，以及 Agent 提出的问题有多少真正促成了行动。

# 人的评审体验，是系统的一部分

LangChain 总结了三个很具体的设计方向。

首先，只呈现值得关注的信息。GTM Agent 把对话分成等待人工处理、需要起草回复和无需回复；Robin 则用 Jev 判断是否有必要加入 Slack 讨论，而不是看到消息就插话。

其次，让结果容易评审。团队发现，在 Slack 里逐条处理待发邮件效率很低，因此为邮件草稿做了专门的评审界面。人的修改不仅是完成审批，也是把难以提前写成规则的偏好反馈给 Agent。

最后，留在已有工作流里。每日简报发到 Slack，后续内容回到同一线程；Robin 先给一两句概要，再展开细节。请求 PR 审查时，附上一行摘要、改动规模和认领按钮，降低接手成本。

这些细节共同决定了：主动式 Agent 是一个可靠的协作者，还是另一个不断制造通知的工具。

## 我的看法

这篇文章最值得借鉴的，是把「主动」拆成两项能力：没有新提示时仍能继续工作，以及继续工作的同时少占用人的注意力。事件和日程解决前者，记忆和评审体验解决后者。

好的长期 Agent，不应只追求运行次数更多，而应让每次问询更准确、每次评审更轻松，并能把反馈用于下一次判断。自主程度的提高，应该建立在这种持续改善之上，而不是简单减少确认步骤。

04｜Antigravity关遥测仍传9G流量

来源（X） · @realchendahuang · 2026-11-17 22:46

Antigravity真是太恶心了卧槽！！！

我看到网上说Antigravity会偷传巨量的数据到服务器，所以要关闭遥测功能。我从第一天起就把 Antigravity 的 Enable Telemetry 关了，结果抓包一看，5 天照样在后台偷跑了 9G 上行流量，比我正常写代码调模型的 5.3G 流量还多。

最傻逼的地方在于两点：

一是那个遥测开关纯属摆设。它只控交互内容，根本不关传输管道，底层的 language_server 照样常开着往 http://play.googleapis.com/log 疯狂发包。

二是脑残的超时重试。代理稍微抖一下超时，它就每隔 5 秒死命重发，超时前发出去的字节全算代理流量。周末我两天没开软件干活，它自己在后台光靠重试空转就烧掉了 4.25G。

最终我把我的代理软件规则列表最顶上加了这个，才把它给禁掉：
DOMAIN,http://play.googleapis.com,REJECT

记住三点：
规则要排在 DOMAIN-SUFFIX,http://googleapis.com 前面，不然拦不住。
macOS 别加 PROCESS-NAME 限定，内核抓不到进程名会失效，直接拦域名。
只在电脑端加，别同步到软路由或手机，否则安卓 Play 商店更不了软件。

加完以后遥测流量直接归零，不影响正常写代码和跑模型。

徐直军上个月刚公开喊过昇腾 950 超节点产能跟不上国内缺口，加上昨天美国商务部把东南亚远程租英伟达算力的路子一堵，国内大厂接下来除了往昇腾集群上切，已经没多少退路了。

眼下国产大模型，最大的困局，还是受到算力的制约，对模型训练的容错率低，追赶吃力；后续可能还是要看昇腾的产能，跟适配是否能跟上。

07｜企业级Agent权限校验用确定性程序

来源（X） · @SeanchenZ · 2026-11-18 16:44

世界500强制造企业 FDE 落地日记｜AI Governance

今天参加企业内部 FDE 培训，我开始意识到，企业级 Agent 开发与个人 Agent 开发之间，存在一道很深的鸿沟。

个人开发者关心的是 AI 能不能解决问题，而企业首先关心的是 AI 有没有权限解决问题。

一份已经脱敏的工业故障分析报告，也不意味着可以随意输入大模型。数据归属、敏感等级、客户授权、模型部署环境，任何一个环节都可能限制 AI 的使用。

这意味着，企业级 Agent 的开发不能只停留在 Prompt Engineering、RAG 和 Tool Calling，还需要考虑：

Data Classification：数据分类分级
IAM：身份认证与访问管理
RBAC / ABAC：角色与属性权限控制
DLP：数据防泄漏
AI Gateway：模型调用治理
Secure RAG：知识检索权限隔离
Audit Logging：全链路审计

从工程架构上，我更倾向于将权限判断交给确定性程序，而不是大模型。

在数据进入模型上下文之前完成权限校验，在工具执行之前完成授权，在任务结束之后保留审计记录。

大模型负责理解与推理，确定性程序负责规则与权限，执行系统负责行动，审计系统负责追溯。

这几层必须相互解耦。

未来企业 FDE 的核心竞争力，可能不是开发出一个多么聪明的 Agent，而是能否将一个概率性的智能系统，嵌入一个要求确定性、可靠性与可追责性的真实工业环境。

Demo 证明 AI 的能力，Production 才证明工程师的能力。
