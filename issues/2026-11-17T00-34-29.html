01｜SQLite 开 WAL 解决读写并发

来源（X） · @GetAskClaw · 2026-11-17 07:34

pg18 比 sqlite 更好吗

现状

journal_mode delete ← 不是 WAL
busy_timeout 5000
锁 应用层 sidecar（另一个 sqlite 文件）
用 delete 模式时，一次写会阻塞所有读。我刚才读库能成功，只是因为抓取的事务都极短。

PG18 能解决什么、不能解决什么

PG18 SQLite + WAL
多写并发 ✓ 真并发 ✗ 单写者
读写并发 ✓ ✓
成本 装服务、驱动、 一行 pragma
连接串、凭据
单文件分发 ✗ ✓

但你真正需要的那个场景，PG 是假解药

“让其他 agent 同时写”听起来合理，但得先问：它们写什么？
抓取 agent INSERT 帖子 ← 唯一的写者，而且是追加
分析 agent 读 + 写标记/分类 ← 这才是冲突来源

两个抓取 agent 同时跑，不会更快——它们争的是 X 的配额（1000 次/小时），不是数据库。DB 让它们并发了，X 那边照样排队。锁当初加的就是这个目的，这个理由依然成立。

所以真需求是：抓取在写的时候，别的 agent 还能读、还能写它自己的东西。

我的主意：三件事，不换数据库

一、开 WAL（一行，立刻见效）

db.execute("PRAGMA journal_mode=WAL")

读写真并发。写不阻塞读，读不阻塞写。

二、把「抓取锁」和「数据库锁」分开

现在 archive_lock() 独占整库，其实它只需要防两个抓取同时烧配额。分析 agent 的写不该被它挡。改法：

抓取 拿 sidecar 锁（防配额双烧）
其他写 不拿锁，靠 SQLite 自己的 busy_timeout 排队

三、分析结果另开库

ATTACH 'data/analysis.db' AS a;

标记、分类、笔记放这里。物理隔离，零冲突，还不用跟抓取抢锁。

什么时候真该上 PG18

多个 agent 在不同机器上写同一份数据
需要跨进程的事务（A 的写依赖 B 的写）
数据量过千万行、单机内存装不下索引

现在一条都不满足。 单机、追加写、十万行——SQLite 在这个量级上还有 5 倍余量（我前面算过阈值 50 万帖才需要 FTS）。

代价对比

PG18 装服务 + psycopg 依赖 + 连接串凭据 + 备份策略 + 版本升级
换来的：你暂时用不上的多写并发

WAL 一行 pragma + 拆锁逻辑（约 30 行）
换来的：读写并发，正是你缺的那一样
如果哪天要上 PG，migrate() 已经把 schema 分离得很干净了，那时候迁移的成本不会比现在低多少。

一个副作用得说

开 WAL 会多出 x.db-wal 和 x.db-shm 两个文件。这两个已经在 .gitignore 里了（*-wal、*-shm），是好事——上次 -journal 漏网被提交，就是这个类别的第一批受害者。

08｜Swamp 把Agent技能固化为工作流

来源（X） · @_avichawla · 2026-11-16 16:25

中文译文

Skills 2.0 来了！

（token 少 8 倍，速度快 2 倍）

我们经常把重复的工作流打包成 skills，但 agent 在每次运行时仍然要重新读取 skill 并逐步决策，这既费 token 又费时间。

Devs 刚刚开源了 Swamp，让你的 coding agent 将重复的 skill 转化为一个只构建一次、然后反复运行的工作流。

你只需描述一次任务，agent 就会将其拆分为连接在工作流中的可复用行为。

每个行为都有类型化的输入和输出，由普通代码决定下一步运行什么。然后 Swamp 给你提供：

- 仅在需要判断的步骤上调用模型
- 从 vault 中拉取密钥并在输出中脱敏
- 每次运行的版本化数据，供你后续查询
- 每次运行发生了什么的完整记录

仓库在这里：https://github.com/swamp-club/swamp

（别忘了点星 ⭐）

Swamp 可以接入你已经在使用的 coding agent，比如：

- Claude Code
- Codex
- Cursor
- OpenCode
- 以及另外 5 种 agent 框架

在 Swamp 中，模型是工作流中的一个步骤，而不是决定接下来发生什么的那个角色。

模型步骤仍然像任何 LLM 调用一样进行推理。

但在这种情况下，循环由代码掌控，所以 agent 不会每次花费 token 重新发现相同的过程。

以下是一个官方结果，他们将一个代码审查 skill 转化为 Swamp 工作流：

- Codex 中的 Skill：约 460 万 token，23 个 agent，12.8 分钟
- Swamp 工作流：约 50.6 万 token，3 个 agent，6.6 分钟

这就是约 8 倍更少的 token，耗时约为一半，大部分节省来自用普通代码替代了协调 agent。

你可以在原型阶段继续使用 skills。一旦某个任务开始重复出现，让你的 agent 将其转化为 Swamp 工作流。

这有助于回答实际问题，比如：

- 哪些步骤真正需要模型？
- 上周那次运行到底发生了什么？
- 更便宜的模型能否处理那个需要判断的唯一步骤？

一旦构建完成，你可以从你的 agent、CLI、定时任务或 API 运行该工作流，每次运行都有记录。

所以你不再需要为模型在每次运行时摸索相同的工作流而付费。

相反，你只在模型的判断能带来价值的步骤上花费 token。

原文

Skills 2.0 is here!

(8x fewer tokens and 2x faster)

We package repeated workflows as skills all the time, but the agent still re-reads the skill and decides every step on every run, which costs tokens and time.

Devs just open-sourced Swamp, where your coding agent turns a repeated skill into a workflow that it builds once and runs again and again.

You describe the task once, and the agent breaks it into reusable behaviors connected in a workflow.

Every behavior has typed inputs and outputs, and plain code decides which step runs next. Swamp then gives you:

- model calls only on steps that need judgment
- secrets pulled from vaults and redacted from output
- versioned data from every run that you can query later
- a full record of what happened on each run

Here's the repo: https://github.com/swamp-club/swamp

(don't forget to star it ⭐ )

Swamp plugs into the coding agent you already use, like:

- Claude Code
- Codex
- Cursor
- OpenCode
- And 5 more agent harnesses

In Swamp, the model is a step in the workflow, not the thing deciding what happens next.

The model steps still reason like any LLM call.

However, in this case, code owns the loop, so the agent doesn't spend tokens rediscovering the same process every time.

Here's an official result, where they turned a code-review skill into a Swamp workflow:

- Skill in Codex: about 4.6M tokens, 23 agents, 12.8 minutes
- Swamp workflow: about 506K tokens, 3 agents, 6.6 minutes

That is ~8x fewer tokens in about half the time, and most of the savings came from replacing the coordinator agent with plain code.

You can keep using skills while you prototype. Once a task starts repeating, ask your agent to turn it into a Swamp workflow.

This helps answer practical questions such as:

- Which steps actually need a model?
- What exactly happened on last week's run?
- Can a cheaper model handle the one step that needs judgment?

Once it's built, you can run the workflow from your agent, the CLI, a schedule, or an API, with every run recorded.

So you are no longer paying a model to figure out the same workflow on every run.

Instead, you spend tokens only on the steps where the model's judgment adds something.
