Moon Dev 开源的 TradingView MCP，内置 16 个 MCP 工具，支持 Claude Code 和 Claude Desktop。

以前用 AI 写 Pine Script，还得自己复制代码、粘贴到编辑器、编译检查，出错了又要重新修改。

6️⃣ 策略回测分析：调用 Strategy Tester，读取收益、回撤、胜率和交易次数

做 TradingView 指标、Pine Script 或 AI 量化开发的，这套值得自己试一下。

02｜RAW-RAG原始检索胜过复杂记忆系统

来源（X） · @QuantumTransf · 2026-10-31 17:34

我们可能从一开始，就把 Agent Memory 想得太复杂了

最近一篇论文《Is Complex Agentic Memory Always Needed?》做了一个很有意思的实验：

不做 Memory Extraction，不做复杂的知识图谱，也不让 LLM 在写入时反复总结、更新记忆

只保留原始对话历史，在需要的时候检索出来，交给 LLM 自己推理

结果呢？

在 LoCoMo、LongMemEval 等四个 benchmark 的 7 组测试设置中，这套简单的 RAW-RAG 方案拿下了 6 组第一，最多领先对比的最强 Agentic Memory 系统 5.53 分

这恰好也是我们开发 Obelisk 时一直坚持的思路

我们认为，Agent 不应该只能看到别人替它总结好的「记忆」

因为一次代码修改背后的原因、一次失败的尝试、几个决策之间的依赖关系，都可能在总结和信息提取的过程中丢失

与其猜测未来什么信息值得记住，不如保留完整历史，让 Agent 在真正需要的时候自己去找

所以我们做了 Obelisk：

一个开源的 Coding Agent Session 检索系统

它可以直接查询 Claude Code、Codex、Hermes、Pi、Opencode 等 Agent 的历史 Session，包括对话、工具调用、Subagent 和工作流。

不依赖 Embedding，也不需要预先从历史中提取 Memory
基于 SQLite FTS5 和 Agent 主动查询，让 Agent 能够重新找到过去的原始证据

比如：

- 为什么当初要这样设计这段代码？
- 上一个 Agent 的任务进行到哪里了？
- 我们之前尝试过哪些方案，为什么失败？
- 这个项目的架构是如何一步步演变的？

Memory 不应该是一份不断被改写的摘要，而应该是一段随时可以追溯的历史

也许下一代 Agent Memory 的关键，不是让 Agent 更努力地记住，而是让它拥有找回过去的能力

Obelisk 完全开源：
https://github.com/tommy0103/obelisk

论文：https://arxiv.org/abs/2610.30755

我某些朋友用的国产安卓手机，前不久被当地公安打电话，要求卸载 X 和 Telegram，因为我其中一个朋友的小米 14 已经 root 了，我觉得因为梯子配置不当导致的 DNS 泄露，或者别的原因，可能性不大，我就重点排查手机上会上报应用列表的应用

关于系统安全组件的录屏采集功能，分辨率 720 × 1280，24 fps，固定竖屏尺寸。相关的流程如下：
取得系统录屏对象
→ 录制约 3 秒屏幕画面到私有缓存文件
→ 读取整段 MP4，转为 Base64
→ 加密后上传小米云端
→ 等待返回“是否风险”
├─ 未命中：删除临时片段，延时 2 秒后继续录制，重复上述行为
└─ 命中：保留一份片段供反馈，显示警告并停止服务

这些应用，SystemHelper 貌似是和 SIM 卡激活相关的，系统安全组件貌似是和反诈相关的，但是都具有高度的数据上报属性。没有 root 的机器，这些组件是无法卸载或者提取的，并且我也暂未分析这两个 APP 卸载之后，会不会自己下载回来。

04｜服务商每分钟RPM查询致CPU满载

来源（X） · @williamlong · 2026-10-31 17:37

我发现我的一台小服务器总是定时CPU百分之百，用AI查询了一下，原来是服务商每一分钟定时跑一个程序，大约每 1 分钟就执行一次 rpm -qa | grep dmidecode（枚举全部已装包再查 dmidecode 是否存在），而且一次并行跑 3 个实例。rpm -qa 本身要遍历整个 RPM 数据库、非常慢，单核机器上 3 个一起跑就是 约 3 秒的 100% CPU，每分钟一次。我让AI把服务商这玩意儿停了，CPU也恢复正常了。

05｜DeepSeek Superagent用Router加Worker分层

来源（X） · @janxin · 2026-10-31 20:41

DeepSeek Harness 团队分享了他们关于 superagent 的思考：

这篇文章探讨的是一种叫 Super-agent 的智能体架构。它的核心目标是让 AI 能像人类员工一样，持续在线、同时推进多项任务，而不是每次都要人重新交代背景。Super-agent 的目标就是让 AI 从“对话工具”进化成“自主员工”。

文章给出的解法是把系统拆成几层：

双层架构：Router + Worker
系统被拆成两个角色。Router 是“前台接待”，负责接收所有消息并判断该交给谁处理；Worker 是“后台员工”，接到任务后自己闷头干。如果所有任务都挤在一个模型里处理，一来上下文会爆炸，二来一个耗时任务会堵住所有后续请求。拆开之后，Router 轻量快速，Worker 专注执行，互不干扰。这样，你在群里 at Agent 说“帮我查一下上周的销售数据”，Router 收到后把任务派给数据查询 Worker，同时你还能继续问“顺便看看这周的排期”，Router 又派给日历 Worker，两个任务并行跑。

事件驱动：不是每句话都要处理
系统不是对每条消息都调用大模型，而是先设一套规则过滤器。比如群聊里有人发“哈哈”“好的”，直接放过去；只有涉及任务、提问、at Agent 的内容才触发 AI 判断。这是因为群聊里 90% 的消息都是闲聊，如果每条都过一遍大模型，成本高、响应慢，还会让 Agent 变得“话多烦人”。用规则筛掉噪音，把模型资源留给真正需要判断的内容。

按需读取上下文
Agent 不会把整个聊天历史都塞进模型，而是只取最近几轮关键对话。更早的历史存到外部数据库里，当模型需要引用某条旧消息时，通过引用链去检索。这是因为大模型的上下文窗口再大也是有限的，塞满历史不仅浪费 token，还会让模型注意力分散，回答质量下降。比如你三天前让 Agent 记了一个需求，今天问“那个需求怎么样了”，Agent 不会把三天聊天记录全读一遍，而是直接去数据库找到那条需求记录，精准回答。

异步执行
Agent 接到耗时任务（比如生成一份几十页的报告）后，会在后台跑，前台立刻返回“正在处理，稍后通知你”。你该干嘛干嘛，不用盯着转圈。如果每次都要等模型跑完才能继续对话，用户体验极差。异步是让 Agent 真正“多任务并行”的关键。用户不需要知道任务什么时候跑完，Agent 跑完了自然会通知。

存算分离：本地轻量，云端重算
Agent 的会话状态（比如当前任务进度、上下文）存在数据库里，计算（模型推理）放在云端。本地只装一个轻量程序，用来连接代码仓库、文件系统这些工具。如果所有计算都在本地跑，普通电脑根本扛不住大模型。如果所有状态都存在云端，断网就全丢了。存算分离让两者各司其职——本地负责“连接”，云端负责“思考”。用户换设备、断网重连，Agent 的状态不会丢，因为状态在数据库里，不在本地内存里。

Super-agent 这套架构的核心思路就是：别让 AI 什么都自己扛，把听、想、做、记”拆开，各找最合适的工具来干。 这样它才能像一个人一样，同时处理多件事、记住上下文、不被打断、也不打断你。

Thorsten Ball @thorstenball

中文译文

下一个问题：你为什么还在用分支？

我们谈过了 PR。如果你从第一性原理重新思考的话，我不认为它们还有意义了。

当然，如果你只是用它们来触发 CI，那没问题，继续吧。那是一个庞大的 commit，不是一个 PR。但如果是为了强制代码审查？知识共享？得了吧。

但你们中有些人说："我们用 PR 是因为我们用分支！我喜欢把我的东西放在分支上。"

我要告诉你们的是：你不需要分支！你可以直接推送到 main。

这叫做基于主干的开发（trunk-based development），其背后的理念是真正的持续集成：你持续地将你的更改集成到主干，也就是 main 分支上。

这个概念已经存在很久了，它是可行的。就在昨天，我还和一个在拥有 400 名工程师的组织中使用过它且没有任何问题的人交谈过。Ruby 这个项目就使用基于主干的开发。

核心理念是你要避免长期存在的分支。它们不好，因为分支会发散，合并会变成一件麻烦事。你不想让常规操作变成一件麻烦事。

即使在我使用 PR 和分支的团队工作时，我也认为一个分支存在超过一两天是一种坏味道。

但当我与其他人分享这个想法时，我经常会收到类似这样的回复：

"好吧，那对你来说很好，但不行。我的东西，我正在做的工作，那不能在 main 上完成。它需要在分支上！它有一个数据库迁移，它改变了底层的结构、架构，它重构了这里、修改了那里。它还不能放到 main 上！我需要在最后把它们全部合并。"

然后我会说：

"不，我几乎可以把任何东西以小 commit 的形式持续合并到 main。你要把它拆分开。先添加那一列，合并它，部署它，现在它上线了，可以用了，很安全。

先添加那些辅助函数，合并它们，把它们上线。

想从旧模式 A 迁移到新模式 B？不要一次性全部做完。先添加依赖，然后一个一个地将 A 迁移到 B，安全地进行。"

如果它能以一个大型变更的形式合并，我敢打赌它也能以小的增量步骤合并到 main 上。

是的，确实有例外情况，但那只是 0.5% 的情况，而不是 50%。

但这种做法确实有一个真正的问题：它很难！

你需要做很多"元编程"工作：确保这个小的第一步变更能够编译、运行且测试通过，合并它，把它上线，监控它；然后做下一个小组件，确保它可以工作并把它上线；然后可能推送一些还未使用的死代码，添加一个功能标志，添加一个配置变量；或者同时让两种配置都能工作，等等。

这意味着有时候在一个又大又臃肿的分支上做反而更容易。但又大又臃肿的分支是有风险的！

一个持续流动的系统比一个断断续续启动和停止的系统更安全。

但是——你猜到了——好消息来了：

现在，有了 AI 代理，所有这些繁琐工作都不再是繁琐工作了！

代理非常擅长添加功能标志，非常擅长拆分代码，非常擅长追踪三个变更并将它们一个一个地合并、观察它们逐步上线。它们非常擅长让两种配置同时工作一天。它们非常擅长逐个迁移。

换句话说：现在在 main 上直接工作并确保所有东西都持续集成、持续可用，比以前容易了 10 倍。

现在确保系统持续流动变得容易了。

而且你看，我不是来劝你切换到基于主干的开发的。这只是让你读这篇文章的借口。（但同时，嘿：试试吧！推送到 main 惊艳极了。）

我来是为了让你重新思考你开发软件的方式。

不要只是用代理来替代你的打字。

把代理当作它们本该成为的魔法代码编写机器来使用。所有因为涉及写代码而变得困难的软件开发工作——甚至是那些元编程工作——都变得更加容易了。

你现在可以去摘星星了！但你需要抬头看。

Next question: why are you still using branches?

We talked about PRs. I don't think they make sense anymore, if you rethink them from first principles.

Yes, if you only use them to trigger CI, then sure, go ahead. That's a fat commit, not a PR. But for mandatory code review? Knowledge sharing? C'mon.

But some of you said: "we use PRs because we use branches! I love to keep my stuff on branches."

And I'm here to tell you: you don't need branches! You can just push to main.

It's called trunk-based development and the idea behind it is true continuous integration: you continuously integrate your changes with the trunk, the main branch.

It's been around for a while, it works. Just yesterday I talked with someone who said they've used it in an org with 400 engineers, without any issues. Ruby, the project, uses trunk-based development.

The main idea is that you want to avoid long-lived branches. They're bad, because branches can diverge and merging can turn into a thing. And you don't want routine operations to become a thing.
