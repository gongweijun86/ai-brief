02｜YOLO将智能眼镜改为物体识别设备

来源（X） · @HeLi8866 · 2026-11-15 14:22

我的天，这太疯狂了！！😱

有人用 Opus 5.5，把自己的智能眼镜改成了能识别物体的 AI 设备！

任何带摄像头的智能眼镜都能接上，戴上之后会当场报出看到的人、车和各种物体。

这套东西免费、开源，普通 Mac 就能跑。

下面是完整步骤：

step 1 → 一条命令装上 YOLO：pip install ultralytics

step 2 → 戴上眼镜，给自己的 Mac 打一通 WhatsApp 视频通话

眼镜看向街道，Mac 上就能看到同样的画面

step 3 → 在 OBS 里捕获通话窗口，并打开 Virtual Camera

这样眼镜传来的画面，会像摄像头一样出现在 Mac 上

step 4 → 对着这路画面跑追踪：yolo track model=http://yolo26n.pt source=1 show=True

每个物体都会带上框、标签，还有一个会跨帧跟着它走的 ID

step 5 → 只留下你关心的类别：classes=0,2,16 对应人、车和狗，conf=0.5 用来去掉没把握的判断

step 6 → 写一小段 Python，用 macOS 的 say 把看到的内容念出来，再经 BlackHole 这类虚拟麦克风送进通话：car on your left。声音会直接进到你耳朵里

step 7 → 用自己的东西来训练：你的产品、工具、自己的狗。把 coco8.yaml 换成你标好的照片，再跑 yolo train

step 8 → 导出到手机：format=coreml 给 iPhone，format=tflite 给 Android，这样以后可以不用再靠 Mac

底层大致是这样：

→ YOLO 对每一帧只看一遍，并在这一遍里找出所有物体，所以够快，能跟上实时视频

→ 追踪（默认是 ByteTrack）会让同一只狗即使走到树后面，也还是原来那个 ID

→ 80 种物体开箱就能认，不必先训练

仓库地址：
https://github.com/ultralytics/ultralytics

有兴趣的话可以自己试一下

03｜Tabbit从截图点击转向写代码

来源（X） · @yibie · 2026-11-15 11:10

从点坐标到写 Playwright 的转向记录

这是 Tabbit 团队一年半做浏览器 agent 的复盘：让模型看截图点页面，成功率停在 60% 左右；模型能稳定写代码后，路线一夜翻转。结尾在带货自家浏览器，结论都带立场。

阶段一：60% 和几百种组合。团队把 DOM 压成上百种标签、裁掉不可见元素，一年测了几百种模型加 harness 组合，仍卡在慢和点不准：Claude 3.5 Sonnet、Opus 在真实截图上也漂几十像素；Seed 1.8 点击强但下拉框常错、智力弱，Seed 2.0 的 GUI 反而退步；Gemini 3.5/3.6 Flash 内部测评不如 Claude 3.7 Sonnet。

阶段二：一个 for 循环。单次轶事，没有对照组。一次后台配置手工估计一个多小时，Codex Chrome 扩展不到半小时做完、十分钟检查无一遗漏；跑通第一条后，200 多条配置用一个 for 循环约两分钟灌完。它主要默默写代码，首选 Playwright，视觉坐标和 CDP 只做兜底。

阶段三：多赢一次，省一半 token。Tabbit CLI 用自家 BU Bench V1 比三家：25 题乘 3 次共 75 次，同一模型，reviewer 模型判定。Tabbit 正确率最高，但只比 Codex Chrome 多一次成功，原文写「不能据此宣布全面的能力差距」。差距主要在成本：每个正确答案的输入 token 比 Codex Chrome 少约 49%、比 Agent Browser 少约 61%，P90 耗时 220.6 秒对 489.0 秒。这是成本指标，不是准确率差距。

最终方案：Playwright 优先的 Tabbit CLI。2026 年 8 月推出，Agent 经 CLI 控制真实浏览器，保留页面、变量和进度，复用登录态，在后台干活、不抢窗口。首选 Playwright，底层需求再下沉 CDP；Browser Use 一派相反，让模型直写原生 CDP。两边都认可 Coding Agent Harness 最成熟，分歧只在抽象层多高。

阶段四：Jev 的反证。165 张截图上，Jev 判状态准确率 95.2%，与 Kimi K3 持平，延迟 0.76 秒对 8.54 秒；36 道定位题 Jev 对 35 道、K3 全对。但放进 10 个任务，118 步里只有 2 步由 Jev 决定，K3 调用没减少；先规划再让 Jev 点击没触发，Jev 实际 0 次点击。作者明说样本小，不能据此断言 Jev 无效。

单步延迟只有 K3 的约十一分之一、判断持平，长程里却只拿到 2 步决策权。单步更快，不等于长程更快。

05｜Grok Bot以机器人组织团队工作

来源（X） · @0xlangeai · 2026-11-15 16:59

Grok Bot 想做的不是更好的聊天框，而是让你能创建一组 AI 同事。

YC Lightcone 这期请来了 Lauren Tan 和 Roman Ugarte。从第一行代码到上线，只用了七周。现在它已经被做进 X 的默认私信里。

几个核心设定：工作围绕机器人来组织，而不是围绕聊天或文件；这些机器人要用和你一样的工具，得有自己的电脑，不能只靠 MCP；它们应该一直在线，主动把事从待办里拿掉，而不是等你去催。

给得越多，它就越深。先给小任务，再给一个结果，再把一整份工作交给它。

内部已经有不少这样的用法。市场团队把机器人接到广告后台，用它们自己的登录和预算去做测试。支持团队让它复现问题、处理工单。更意外的是，最早用得最疯的一批居然是小企业：招不到会计，几个小时之内，就多了一名把记账做得很稳的新员工。

Roman 的组织方式也很清楚：一个机器人只专心一件事。领域专家把机器人搭好，再共享给全公司。

Lauren 把这套能力叫做「外循环」。以前她要先去 Slack 把问题聊清楚，再把上下文复制给 agent。现在她把 Grok Bot 加进 Slack，在工作真正发生的地方直接 @ 它。

片子里有一条几乎是黄金标准的例子。Lauren 和同事 Samantha，加上她的机器人 Potato，在一个大约 200 条消息的 Slack 线程里做完了一个功能。Potato 拉起 Cursor Cloud Agent，那个 agent 自己跑应用，做完原型再带着视频和截图回来。整条链路里，他们甚至没有打开 Cursor。Lauren 后来连那个 PR 都没读，只看产物。

她以前一个月大约 2000 多个 PR，现在已经超过 4000。Roman 说，真正的瓶颈已经不是做功能的时间，而是团队有没有对齐：路线图是什么，什么叫好。东西经常已经做出来了，但不能见一个合一个，否则产品会变成弗兰肯斯坦。

执行越来越便宜。你可以拉起一百个编程 agent、一百个 Grok 机器人去攻一个问题。片子里的判断是：接下来差的往往不是执行失败，而是规格没写清楚，目标没定义清楚。
