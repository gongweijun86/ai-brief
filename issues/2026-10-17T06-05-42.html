01｜Anthropic七层代码审查工程实践

来源（X） · @vikingmute · 2026-10-17 11:46

昨天还在说 Code Review 的实践，今天Anthropic就写了一篇文章详细描述它们 Code Review 的工程实践：
https://claude.dev/blog/solving-code-review-at-anthropic/

非常受用，可以好好读一下，核心观点是：代码多到人读不过来之后，人已经不 review 代码了，而是追求花最少的时间 并且回滚和事故又不增加

一个改动要过七层检查，几点也很有趣：

1 让 Agent 提 PR 之前先自证 证明做完了 测试 截图 等等

2 每个 PR 都有 AI review diff，对照整个仓库和 PR 的意图来审 多个 agent 同时找 bug 再由另一组投票，多数认定是真问题才发出来 纯风格类的意见直接丢掉 这个和我的 review-forge 的思路非常类似

3 按风险决定要几个人批 低风险不用人批准自动合并，普通功能一人批 最高风险的路径要两个人（我怀疑这步骤真的那么有用吗？人能看过来吗）

4 merge queue / feature flag / 灰度发布 先给内部员工用， 快速发现 快速回 feature flag 不用部署就能关掉

里面还有一个非常实用的思路 正好解答昨天多 agent review 的问题：

review 要能收敛，agent 写 agent 审，有可能可以互相折腾个没完，文中说有个 PR 一夜之间来回改了五十多轮 git blame 一看，59% 被反复标记的都是第一轮时就已经存在的老代码

所以他们加了几条规则：最多三轮，超过就让作者退一步重新想方案 几轮之后只审新增的 diff 已经提过的意见不再重复。

02｜Agent提示词从402行减至15行

来源（X） · @sleepy0x13 · 2026-10-17 11:05

Anthropic 在一堂 4 小时的免费工程课里，把一个 Agent 的 System Prompt 从 402 行砍到 15 行，任务通过率反而从 62% 提升到了 92%。

这套教程信息量挺大，我把最值得学的几个技巧整理了一下，建议收藏。

1. Prompt 怎么写（00:15）

别上来就写一堆指令。先建立 Eval，覆盖正常任务、边界情况和失败案例，再根据结果修改 Prompt。

业务规则、角色、数据和输出格式分开写。数学计算交给代码工具，复杂任务可以采用 Generate → Evaluate → Repair，让模型生成、检查、修复。

2. Claude 为什么越用越笨（33:21）

视频拿库存 Agent 做实验：402 行 Prompt、12 个工具、3 个子 Agent，通过率只有 62%。

优化方法：

Tool 负责执行明确动作，例如查询、计算
Skill 按需加载业务知识，不要全部塞进 System Prompt

Subagent 留给需要独立上下文的任务

大量数据用 Python 处理，只把结果返回模型
改造后通过率提升到约 92%，Token 消耗也下降了。

3. Anthropic 内部怎么用 Claude（1:33:39）

一个很实用的产品开发流程：

先让 Claude 反过来采访你，问清需求中的模糊点，生成产品规格。

然后根据规格制作多个可预览的 HTML 方案，让人直接比较和修改。

开发完成后，用 Schema、Fixture、Invariant 定义验收条件，再通过 Playwright 自动检查页面。

简单说，就是让 Claude 从需求讨论一直参与到最终验证。

4. 自动化和长期记忆（2:29:24–3:18:59）

Routines 可以按时间或事件触发任务，比如每周检查合并的 PR，自动提出文档更新。

Memory Store 负责跨会话保存信息，Dreaming 则负责定期整理历史记忆、去重和更新索引。这部分属于 Managed Agents 的能力。

05｜Paperclip管理多Agent协作

来源（X） · @sitinme · 2026-10-17 10:30

Claude Code 开了五六个终端，一个在重构，一个在补测试，一个在写文档，过半小时回来，已经分不清哪个窗口在干嘛，电脑一重启，上下文全没了。

更怕的是失控。某个 agent 陷进死循环，一晚上烧掉几百美元 token，第二天看账单才发现。

Paperclip 换了个思路，agent 既然越来越像员工，那就给它们开一家公司。

它是一个 Node.js 服务加一个 React 后台，Claude Code、Codex、Cursor、Gemini CLI、OpenClaw 都能接进来当员工。

有组织架构，有汇报线，有预算，你坐在董事会的位置上批方案、看账。

引用内容

sitin @sitinme

如果把 Claude Code、Codex、Cursor、OpenClaw 这些 AI Agent 看成一个个“员工”，那 Paperclip 做的事情，更像是给它们装了一套公司操作系统。

它不负责让模型变聪明，而是解决 Agent 一多以后最麻烦的问题：

谁负责什么、任务做到哪了、有没有重复干活、花了多少钱、哪些操作需要人工批准、出问题以后能不能追溯。

Paperclip 里面可以真的搭一套“AI 公司”：有 CEO、有工程师、有研究员，可以设置上下级关系、任务、目标、预算、审批和工作区。

Agent 通过 heartbeat 定期醒来领取任务，执行完再把结果和日志写回去；预算到上限还能自动暂停，重要操作可以先交给人审批。

我觉得它最值得关注的，不是网上说的“零人公司”，而是它开始解决一个越来越真实的问题：

当你同时跑 5 个、10 个甚至更多 Agent 时，真正的瓶颈已经不是模型能力，而是管理和协调。

当然，这东西也不是装完就自动赚钱。Agent 越多，Token、调试、权限、验收和维护成本都会跟着上来。

比较靠谱的玩法，是先用 1 个 Company + 1 个 CEO + 1~2 个专职 Agent 跑一条很窄的流程，看看它到底有没有帮你减少协调时间。

如果只是偶尔用一个 Codex 或 Claude Code，Paperclip 可能有点重；但如果已经开始让多个 Agent 并行做开发、内容、运营或者增长，它就很值得研究了。

从零接 Claude API，最耗时间的不是写功能，是搞清楚「这东西到底该怎么搭」：会话怎么存、工具怎么挂、agent 跑崩了怎么续。claude-quickstarts 把这些都做成了能直接跑起来的完整项目——客服机器人、金融数据分析、浏览器自动化、能自己写代码的 agent，每个都带自己的 README 和配置说明，你照着改比对着文档猜快太多。

最值得翻的是 computer use 那两个：一个是让 Claude 直接操作桌面的 demo，另一个是在原生 macOS 上的参考实现，提示缓存、服务端压缩、批量工具调用、沙盒化 shell、轨迹记录这些门道全写进代码里了。另外还有一个把 Managed Agents Sessions API 包成九个工具的 MCP server，stdio 和 Streamable HTTP 两种接法都给了。

与其对着文档猜，不如先把官方的示例跑一遍。
