06｜四项AI使用习惯提升Agent效率

来源（X） · @I_am_oil_oil · 2026-10-30 21:53

分享一下我平时使用 AI 的四个高效小习惯：

1. 用语音输入代替打字。手打字慢的时候很容易偷懒少给背景，用语音就能快速把上下文说清楚。而且内容是发给大模型看的，有一点错别字和口头语也不影响它理解，不需要自己再校对一遍。

2. 写文章时让 AI 采访我。直接让 AI 按大纲写会有很重的 AI 味，自己写又容易思绪零散。我会让 AI 每次问我一两个问题，我用语音回答，并要求它先把我的原话一字不改地存成底稿，最后只基于原话梳理结构和改错别字，避免多次加工写出 AI 味。

3. 用最省事的方式给 AI Agent 提供上下文。现在的 Agent 能自己看网页、读写文件和跑命令，所以做调研、装复杂工具直接丢官方文档链接就行，遇到报错直接发截图，改前端页面就直接点选并复制元素的上下文，不用自己手动搬运信息。

4. 多任务并行，把重复的事做成 Skill。现在 Agent 会自己做验证，单次任务耗时变长了，我一般会同时开五六个任务并行跑。另外像做封面、加字幕这种每天重复的工作，跑通两三天后我就会做成 Skill，并在日常使用里持续迭代。

文章链接：https://book.oiloil.org/articles/ai-efficiency-habits

07｜JiTTests合并前写测试拦74个bug

来源（X） · @frxiaobei · 2026-10-30 23:41

Meta 昨天讲了他们怎么让 LLM 在代码合并之前写测试抓 bug，叫 JiTTests。

它和常见的 AI code review 思路有点区别。

他家是这么做的： AI review 读代码说出哪里可能有问题；JiTTests 针对这次改动生成能跑的测试，直接跑出新旧行为的差异。
然后几个模型一起判断是不是误报，再加一层固定规则兜底，排在前面的才再去找工程师。

Meta 给了一组数据，上半年在合并前拦下 74 个严重隐私 bug，推给工程师的问题里有六成是真问题。

我对那层固定规则比较感兴趣。
LLM 的判断每次都可能不一样，他们专门配了一个确定性的判断器压着，这和我自己搭流水线的习惯一样，能用固定脚本的地方就不交给模型自由发挥。

这里另一个变化是人的位置。工程师不再一条条看测试了，改成定标准然后看整体结果。这个跟我们现在的做法就一样了。

08｜Google技术写作课免费开放

来源（X） · @immersivetran · 2026-10-30 09:21

谷歌内部工程师上岗必修的英文文档写作课，其实官方一直对外完全免费公开，甚至连账号都不用登就能直接学。

它就是 Google Technical Writing One，一套专为工程师打磨的“技术英文除杂指南”。

对于想要学习英文写作的同学也很推荐！

1️⃣ 改写被动句（Active voice）：很多技术文档读起来累，往往是塞满了各种由被动语态堆砌的模糊主语。课件会带你对比 The file was deleted by the script. 与 The script deleted the file.，教你一眼找出无主句并精准还原操作主体。

2️⃣ 消灭悬空代词（Ambiguous pronouns）：文档里出现 this、that 或 it 很容易让读者产生歧义。课程直接给出强制替换法：每次出现这类代词，后面必须紧跟具体名词（如把 This causes an error 改为 This misconfiguration causes an error）。

3️⃣砍掉废话长句（Short sentences）：带你像做 Code Review 一样审视句子，拆分复合从句，把一段 60 词的冗长逻辑拆成两个单核句子加一个清晰的列表。

建议两类朋友直接上手试一试：
开源项目作者 / 海外业务工程师：打开“Active voice”和“Short sentences”两节，对照你的 README 或 PR 描述，亲手重构一段。

想提升技术英语表达的开发者：先看课件里的“Before”反例，尝试自己动手改写一遍，再展开官方的“After”对比句式差异。

整套 Pre-class 预习课件完全公开免费，页面提供网页端学习，不强制登录，零门槛直接看。
