01｜Agent工程七成后端三成不确定性

来源（X） · @antiAIvo · 2026-11-02 21:16

Agent 工程，我的感觉是七成后端，三成在处理不确定性

七成后端很好理解
主循环是状态机，工具调用是 RPC
记忆是存储和缓存，长任务是队列和工作流
再加上沙箱、权限、可观测性
这也是为什么大厂的 Agent 工程师很多是后端转过去的

三成的不确定性
Agent 的核心组件是概率性的
同一个请求跑十次，结果可能都不一样
处理这种不确定性，主要靠两样东西
1. Harness，运行时约束，让agent跑的稳
2. Eval，用数据集打分，判断改动是变好了还是变坏了

03｜Agent代码审查转向实测与形式化验证

来源（X） · @chasen_liao · 2026-11-03 12:04

有的时候你让多个 Agent 互相对抗式审查代码，很多时候就是在浪费 token！！🤯

土豆姐发现 Agent 审查代码时很容易陷进细枝末节，花了大量 token，最后产出的可能只是一堆看起来很严谨的意见

更何况，有时候拿来审查的模型能力还比较弱，也没有写代码时的完整上下文，让它硬找问题，很容易给你一些似是而非的建议，最后还得你自己判断

这种感觉有点像以前做 Test-driven development，有时候测试写了一大堆，看着全绿就安心了，但测到的东西未必是用户真正会遇到的问题

说白了，就是在拿 token 买安心

土豆姐现在更倾向于把这些 token 用在实际运行验证和形式化验证上，这个思路我觉得很值得学

比如让 Agent 真的把应用启动起来，走一遍用户操作，检查界面、日志和实际产生的数据，而不是看完代码就说「应该没问题」

遇到并发、重试这种边界难测的场景，再挑出一条关键规则，用形式化方法检查它在明确的模型和范围内是否成立

当然，测试通过不代表没有 bug，形式化验证也只能保证它覆盖到的性质

Agent 生成的东西越来越多，怎么验证它做的东西能不能用，本身就是一门很深的学问，值得我们多花时间研究

04｜datetime兼容老版本解析Z时间串

本地 3.12 跑得好好的，部署到一台 3.10 的老机器上，解析工具返回的时间直接 ValueError: Invalid isoformat string😶

06｜RAGFlow论文称检索先于索引

来源（X） · @QuantumTransf · 2026-11-03 12:35

又一篇论文开始挑战我们对 Agent Memory 和 RAG 的传统认知了，最近这方面的工作真的不少

前几天分享了 RAW-RAG 这篇论文，相信让不少人印象深刻：仅仅保留原始历史，在需要时检索并交给 LLM 推理，就能击败不少精心设计的 Agentic Memory 系统

而现在，RAGFlow 团队又发表了一篇新论文《Context as Infrastructure》，从另一个角度讨论了同一个问题：

我们真的需要那么复杂的检索架构吗？

给不了解 RAGFlow 的朋友介绍一下：这是一个在 RAG 领域颇有影响力、工程背景非常扎实的团队，核心成员有深厚的数据库和搜索引擎研发经验，其联合创始人金海也曾主导 Milvus 的早期研发

所以，当这样一支团队开始重新审视 Embedding、索引结构与 Agent Harness 的关系时，我觉得尤其值得关注

论文提出了一个很有意思的观点：

Retrieval is a harness problem before it is an index problem.

检索首先是 Agent Harness 的问题，其次才是索引的问题

在实验中，仅使用 BM25 / grep，配合能够自主查询、阅读、调整检索策略的 Agent Harness，就在 BrowseComp-Plus 和 FRAMES 上分别取得了 85% 和 91% 的准确率

是的，不需要 Embedding，也不需要预先构建知识图谱

更有意思的是，在 FRAMES 的实验中，额外引入复杂的知识结构，并没有带来可检测的准确率提升

这让我再次想到了我们开发的开源项目 Obelisk，它的做法是为 Coding Agent 提供历史 Session 检索能力，基于 SQLite FTS5 保留并索引原始对话和工具调用记录，而不是预先将历史转换成一套复杂的 Memory

更重要的是，我们同样认为，检索应该是 Agent 自己能够控制的过程，而不只是由一个 Retrieval Pipeline 决定哪些信息应该进入上下文

因此，Obelisk 通过 Code Mode 为 Agent 提供可编程的检索接口，让它能够自主决定查询条件、组合检索操作，并根据结果继续探索历史

我们提供检索能力，而不替 Agent 预先决定它应该记住什么

但这里就引出了另一个问题：

既然简单的检索方案已经能够达到很高的准确率，我们是否真的不再需要那些复杂的数据结构了？

我觉得恰恰不是这样，而这也是这篇论文最有启发性的地方

论文发现，精心组织的证据结构虽然未必能够进一步提高准确率，却能够显著减少检索时消耗的 Token

换句话说，复杂结构的价值，未必在于让模型回答得更正确，而可能在于让系统以更低的成本找到正确的信息

这本质上是一个 Scale 和 Workload 的问题
当数据规模增长几个数量级，检索延迟、索引维护成本、查询复杂度和上下文开销，都可能改变最优的系统设计

一套在个人 Session 历史上表现优异的检索方案，未必适合拥有数十亿条记录、复杂权限边界和高并发查询需求的企业系统。

我们不应该为了追求简单而否定复杂性，也不应该在尚未证明必要性时就引入复杂性。

而这又回到了我一直以来对 Agent Memory 的一个基本判断：

Raw History should be the Source of Truth.

我们可以在原始历史之上构建索引、维护派生视图，或者引入更复杂的结构来优化检索

但这些结构应该是服务于查询的，而不应该通过有损的信息转换，取代那些真正发生过的历史

因为无论检索系统如何演进，Agent 最终都应该能够回到原始证据，重新理解过去发生了什么，而不是只能相信某个 Memory System 预先替它总结好的结论

所以我觉得，RAW-RAG 和这篇新论文，实际上正在从不同角度指向同一个值得探索的方向：

我们需要的可能不是一套越来越复杂的「记忆系统」，而是一套能够扩展、能够追溯、能够让 Agent 自主查询的 Retrieval Infrastructure

这也是我们希望通过 Obelisk 探索的方向

- 这个项目的架构是如何一步步演变的？

Memory 不应该是一份不断被改写的摘要，而应该是一段随时可以追溯的历史

也许下一代 Agent Memory 的关键，不是让 Agent 更努力地记住，而是让它拥有找回过去的能力

07｜AI短片先做首尾帧再生成视频

来源（X） · @MinLiBuilds · 2026-11-02 17:14

很多短剧也是这么做的。

复刻了一条大话西游 x Tibo × Poteto 的 CP 视频💗

不少人问怎么做的，分享一下这次的MV工作流。

我这次主要分了 7 步：

1. 先剪辑，再拆镜头

先把视频节奏剪好，再拆成适合 AI 生成的短片段。

镜头拆得合理，后面更容易生成，也方便单独返工。

2. 人物定妆

先固定人物的脸型、发型、服装和体态，生成多角度参考图。

人物一致性是第一关。脸都没固定好，后面换什么视频模型都没用。

3. 逐镜头生成首尾帧

按照镜头构图、人物站位、表情和动作，制作每个片段的首尾帧。

这一步值得多花时间。

4. 生成完首尾帧，一定要他妈的检查！

这一步特别重要。

你喂进去的图片有问题，结果肯定不好。

5. AI 写提示词

GPT、Gemini、Claude 都可以。

重点描述动作、表情和运镜，别只会堆 8K、电影级画质这种关键词。H3很吃提示词，让AI写即可，告诉他是H3.

6. 最后才是视频生成

人物、首尾帧、提示词都准备好了，再选择合适的视频模型。

有问题就针对单个镜头返工，不要整段推倒重来。

7. 后期统一电影质感

统一调色、曝光、锐度、颗粒感，再处理声音、音乐和剪辑节奏。

否则单个镜头都很好看，拼起来却像七部不同的电影。

🚀 这次最大的收获：

先把图片做好，再用提示词控制动作，最后才交给视频模型。

08｜用布局专有名词精准控制AI排版

来源（X） · @awe0_io · 2026-11-02 15:34

跟 AI 说「布局好看一点」
结果整页每个区块都换了个排法？
因为你没讲清楚要换哪一种布局。

其实这些布局都有名字，直接告诉 AI 就好：

1. Hero Section：首屏大横幅，一打开就是一张大图加一句话，像商店门口的大招牌，先告诉你这是干嘛的。
2. Bento Grid：便当格，大格子小格子拼在一起，像便当盒，一格装一个东西，看着满但不乱。
3. Masonry：瀑布流，卡片像水一样一列列往下流，每列长短不一样，越刷越多。
4. Split Screen：左右分屏，屏幕从中间切开，左边放图，右边放字，两边对照着看。
5. Sidebar Layout：侧边栏布局，左边一条竖菜单，右边是正文，像书旁边一直贴着目录。
6. Full-width Section：通栏，一整条颜色从左铺到右铺满屏幕，像横幅拉满，专门放最重要的一句话。

下次直接说：「首页用 Hero Section，功能区用 Bento Grid，文章列表用 Masonry。」

一句话，AI 就知道每一块该怎么排。
