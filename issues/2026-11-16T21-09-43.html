02｜Agent开发十条高频Prompt技巧

来源（X） · @Khazix0918 · 2026-11-16 17:59

翻了一下最近两个月，我用Agent干活最爱说的几句Prompt：

1. 从第一性原理出发，找到最本质原因，修复一下。

2. 先问一些不清晰的问题，对齐我的喜好，然后再出3版方案。

3.不要默认我提出的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来

4. 不要只考虑这个改动产生的直接效果。继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。

5. 其他领域里有没有类似的方案，用跨领域的方式全面思考，找到最优解。

6. 先假设你当前认为最合理的方案是错误的。站在最强反对者的角度，寻找能够推翻它的证据、反例和边界情况。然后重新评估方案，看看有没有更好的解法。

7. 深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。

8. 假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。

9. 全面分析最近XX天里的所有的PR，找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。

10. 全面复盘最近XX时间的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者Skill，避免我们反复支付同样的成本。

04｜Grok Bot靠确定性约束量产PR

来源（X） · @0xlangeai · 2026-11-16 22:01

Lauren Tan 也叫 Potato，在 SpaceXSI 做 Grok Bot。她这场演讲一开场就问，你有没有看过别人写的代码，心里想这不都是 slop。她想说服的是，这些 slop 是可以炼成金的。

软件工程师现在的工作，就是想清楚怎样在大幅提高产量的同时，把代码质量稳住，最好还能再提高一点。

她花了六个月，才走到一个月能往生产环境合进去几千个 PR，而且很多是睡着时合上的。上个月她一个人合进了 3000 个。Grok Bot 团队上个月合进了 11000 个。十月大约有 227 人至少贡献过一个 PR，客户端大概每天都会切出一个新的稳定版。被回滚的比例反而更低了，稳定在大约 0.5%。启动、打字、打开新对话、切换对话，都比刚上线时更快。

核心不是盲目信任，而是去建设 agent 的环境，让你能够相信它们会把事情做对。

她用一张倒金字塔来排该把时间花在哪。最下面两层是确定性的，直接用代码本身：好的 API 设计、架构、重构，以及 lint、类型系统、编译器和测试。再往上才是运行时验证和形式化验证。最上面才叠一点点规则、skills、agents.md。每次纠正 agent，先想能不能做成一条确定性检查，而不是再往 agents.md 里加一行。写进代码里更可复现，也更能信。

因为代码库就是 agent 最大的输入之一。以前一天也许只审三个同事的 PR，现在这个数字更像是 300。每个工程师背后，都可能是一支几百、甚至几千个 agent 的队伍。权宜之计、反模式、过时代码，下一个 agent 很容易直接抄走。

他们为 Grok Bot 做的客户端框架叫 Dune，可以把它想成 Electron 应用里的 Next.js。真正起作用的是约束。凡是要用好就得特别讲究分寸的东西，最后往往都会变成 slop。最典型的是 React 里的 useEffect，他们直接禁止在产品代码里用。

目录结构也在传上下文。Grok Bot 和 Dune 有两个顶层目录，electron-renderer 和 electron-main，它们之间的 import 会被依赖图分析和 lint 直接禁止。这是从 Cursor 这个 Electron 应用里学来的教训：agent 经常把主进程代码 import 进渲染进程，结果就是长任务和卡顿。

agent 还喜欢用快速补丁，再用注释给自己找理由。到了 Grok Bot，他们禁止了 99% 的注释，因为注释太容易过时，也无法被强制执行。lint 会直接让 agent 去修根因。这样做得足够多次，审查要盯的东西就会越来越少，甚至可以让 agent 自己合并它们的大多数 PR。

验证也在改审查方式。他们现在的 code review，已经大幅收成主要看视频、截图、图示和形式化验证。运行时验证说白了，就是让 agent 自己把代码跑起来。他们还在用 TLA+ 对主要用户流程做模型检测，用 Lean 去证明某些算法，已经找到了不少 bug。片子里也说了，这当然不是银弹，还在试验。

有个叫 Cindy 的人，六个月前还没法信任自己的 agent，因为一些很细的 bug 被合进了代码。六个月后，她说每天 70% 的 token 都花在验证上。Lauren 自己也是这样。她觉得测试和验证正在进入黄金时代，不是因为方法变新了，而是过去贵到用不起的深度，现在用得起了。

如果你内层的编码循环本身就在产 slop，那把这条循环自动化，只会产出更多 slop，然后还得不断往这个问题上砸更多 token。所以先改代码库，先加 lint，先把旧的反模式清掉，先把验证做扎实。有了这些地基，再去搭工厂，很多事情才会突然变得可能。

等准备好了，她把 Grok Bot 当成搭外循环的方法。连接器、例程、Cursor Cloud Agents、projects，可以编排上百、甚至上千个 agent。一个例子是，每切出一个新版本，Grok Bot 就会自动拉起一个新的 Cursor project，像真实用户一样去跑整个应用，找到 bug，开出修复 PR，再自动合并。敢这样，是因为代码库已经足够好，大多数产品代码已经不再需要很深的人工审查。

06｜Home Repo统一管理Agent指令

来源（X） · @vincemask · 2026-11-16 20:35

个人多仓库 Agent 工作流：Home Repo 方案。

这个思路来自 Matt Pocock 分享的 Home Repo 模式：用一个独立仓库集中管理 Agent 指令、Skills、工具和项目知识，让 Agent 能够理解多个代码仓库并完成跨项目任务。

一个统一入口，多个独立仓库，两种工作模式。

1. 日常单仓库开发：直接进入业务仓库运行 Agent。

2. 跨仓库需求：从 Home Repo 启动 Agent，统一分析和协调修改。

3. 个人规范和通用 Skills：集中管理。

4. 项目架构、构建命令和技术约束：仍然保留在业务仓库。

5. Git、依赖和发布流程：各仓库独立维护。

这样既能实现跨仓库协作，也能避免所有 Agent 都获得过大的修改范围。

引用内容

Matt Pocock @mattpocockuk

中文译文

很多人问我："你是怎么让 agent 同时处理多个仓库的？"

我有一个非常简单的解决方案——Home Repo（主仓库）

我有一个单独的仓库（主仓库），里面存放了我所有的 skills、steering 文件、wiki 等等。

我在主仓库中运行我的 agent，然后在 AGENTS.md 中添加指向其他仓库的说明：

```
For skills, clone mattpocock/skills to ~/repos/skills.
For Sandcastle, clone mattpocock/sandcastle to ~/repos/sandcastle
```

这极其简单，但效果出奇地好。主仓库让你可以：

1. 把所有 steering 文件和工具集中在一处
2. 有一个统一的地方运行所有 agent
3. 对多个仓库进行全局性的修改

我相信你也会喜欢的。尽情享用吧！

在几乎所有公司都在教员工怎么用 AI 一键生成现成答案的时候，华尔街最赚钱、技术品味也最硬核的量化交易巨头 Jane Street 反手在 GitHub 上开源了他们内部的 janestreet/agent_skills 仓库，其中冲上 HN 榜首（712 分）的技能叫 Socratic Tutor（苏格拉底式导师）。

点开这份只有几百行的 SKILL.md，你能看到顶级工程团队对“AI 让人脑退化”这件事有多警惕。它给大模型立下了几条极其严苛的铁律：

只要你对它说出 teach me、quiz me 或 drill me，它被绝对禁止直接给你讲课或甩出长篇解释。它必须先拆出 4 到 10 个子技能树，每次只问你一个问题，连摸底带追问，把你在每个子技能上的真实水平钉死在 0 到 5 级（0 级是闻所未闻，3 级是在提示下能做对，5 级是不靠任何提示且隔轮复习依然对答如流）。

在教学循环里，哪怕你答错了，它也不准直接告诉你正确答案，而是必须顺着你的错误推理反问一句：如果按你说的这样，那当边界条件变成 X 时会发生什么？ 逼你自己推导出矛盾点。直到连续两轮卡死，它才允许给一个最小化的脚手架提示，而且一旦给过提示，这道题就绝不算你掌握（最高只能记 3 级）。在随手一问就能拿到几千字总结的今天，这种故意给大脑制造阻力、逼人自己走完推导闭环的提示词设计，反而成了最稀缺的工程资产。

08｜Git单事提交规范优化Agent上下文

来源（X） · @bozhou_ai · 2026-11-16 11:37

推荐大家在自己的全局记忆里面，都加上下面这一段提示词，让AI把每一件事情都做一个Git版本，我实测下来，效果非常好，Commit记录就是给到Agent最好的一个上下文。

# Git 提交

- 一个提交只做一件事（一句话说得清），按事切分，不按文件数；做完且测试通过就自己提交，不用问。标题要用"和"连起不相干的事，就拆开。
- 不提交半成品和没过测试的改动；格式化、改名不和逻辑改动混在一起。
- 标题用中文一句话写具体变化；正文只写代码里看不出来的：为什么改、依据、放弃的方案、已知没做的。
