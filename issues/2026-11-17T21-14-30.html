02｜Google 提出自改进记忆系统

来源（X） · @omarsar0 · 2026-11-17 22:39

中文译文

Google 关于 RSI 的一篇炸裂论文。

（收藏起来）

他们提出了一种在 harness 层面实现持续递归自我改进的方法。他们还为 harness 优化器提出了自己的自我改进记忆系统。

这清楚地凸显了追踪记录以及在你的 harness 中拥有一个功能性、自适应且结构化的持久记忆系统的重要性。

他们表明，当 harness 优化器记住它为什么做出过去每次编辑时，10 次持续运行中有 9 次得到改进。

他们讨论了一个常见问题：当你更换模型或基准测试时就会出现。一个由 Opus 进化来的 harness 在 Gemini 上起步得分 68.41，低于纯种子 harness 的 73.89。

自我改进记忆（Self-Improvement Memory）将过去的编辑按照它们所解决的 harness 问题进行分组。对于每次编辑，它存储推理依据、预期结果、观察结果和评估上下文。提案者和选择者在做出新更改之前都会读取它。

在包括从 Terminal-Bench 2.1 到 Terminal-Bench 4 的四个领域中，SIM 在六个跨数据集设置和四个从 Opus 到 Gemini 的设置中都优于仅从 harness 继续的方案。在十次编码运行中，它平均增加 2.36 分（p=0.003）。

如果你在自动进化 harness，请将每次编辑的原因和结果与代码一起存储。

原文

Banger paper from Google on RSI.

(bookmark it)

They propose an approach for continual recursive self-improvement at the harness level. They also propose their own self-improving memory system for the harness optimizer.

This clearly highlights the importance of traces and having a functional, adaptive, and structured persistent memory system in your harness.

They show that a harness optimizer improves 9 of 10 continued runs when it remembers why it made each past edit.

They discuss that a common problem shows up when you change the model or the benchmark. An Opus-evolved harness started at 68.41 on Gemini, below the 73.89 of the plain seed harness.

Self-Improvement Memory groups past edits by the harness problem they addressed. For each edit, it stores the rationale, predicted outcome, observed outcome, and evaluation context. The proposer and the selector both read it before making new changes.

Across four domains, including Terminal-Bench 2.1 to Terminal-Bench 4, SIM beats continuing from the harness alone in six cross-dataset and four Opus-to-Gemini settings. Across ten coding runs, it adds 2.36 points on average (p=0.003).

If you evolve harnesses automatically, store the reasons and results of each edit next to the code.

中文译文

自回归 LLM 对比扩散 LLM，清晰解读：

（一个热门的 LLM 面试问题）

生成 500 个 token 并不总是需要 500 个顺序解码步骤。

自回归模型一次扩展一个 token 的响应。掩码扩散模型可以同时预测多个位置，然后重复该过程以完成响应。

两者都可以使用 transformer 组件，如嵌入、注意力和前馈层。它们的注意力模式和训练目标不同。

1) 自回归 LLM

在标准自回归解码中，每次前向传播为下一个 token 产生一个概率分布。

选中的 token 被追加，生成从那个更长的序列继续。

因果注意力防止一个位置访问未来的位置。因此，较早的 token 表示在新 token 到来时保持不变。

这使得它们的 KV 可以被缓存和重用。

一个 500 个 token 的响应通常需要 500 个顺序的 token 生成步骤，尽管诸如推测解码之类的技术可以减少昂贵的模型前向传播。

2) 扩散 LLM

在下面所示的掩码扩散方法中，生成从与提示词一起的掩码输出位置开始。

一次去噪过程使用双向上下文为多个位置预测候选 token。

通过基于置信度的采样，选中的预测被保留，其他位置在后续步骤中保持掩码状态。

模型逐步填充序列。它不一定会生成一个完整的草稿然后反复重写每个 token。

一些实现按块生成，而不是一次性处理整个响应。

每一步可以确定多个 token，使得步骤数少于输出 token 数。步骤预算同时影响速度和质量。

这里存在一些工程上的权衡。

双向注意力使得标准的自回归 KV 重用变得更加困难。一个 token 的表示在周围位置更新时可能发生变化，即使该 token 本身保持固定。

因此，缓存取决于架构和解码策略。例如，块扩散可以在已完成的块之间支持 KV 缓存。

更少的步骤也不保证更低的延迟。每一步可能处理多个位置，因此总计算量和实现方式都很重要。

双向条件化还支持填充文本或代码中的空白。

我在另一篇分析中介绍了 KV 重用在自回归解码中如何工作。

它涵盖了预填充期间缓存了什么、解码期间缓存如何增长，以及为什么在长上下文下它成为主要的内存瓶颈。

原文

Autoregressive LLMs vs. diffusion LLMs, clearly explained:

(a popular LLM interview question)

Generating 500 tokens doesn't always require 500 sequential decoding steps.

Autoregressive models extend a response one token at a time. Masked diffusion models can predict multiple positions together, then repeat that process to complete the response.

Both can use transformer components such as embeddings, attention, and feed-forward layers. Their attention patterns and training objectives differ.

1) Autoregressive LLMs

In standard autoregressive decoding, each forward pass produces a probability distribution for the next token.

The selected token is appended, and generation continues from that longer sequence.

Causal attention prevents a position from accessing future positions. Earlier token representations therefore stay unchanged as new tokens arrive.

That allows their KV to be cached and reused.

A 500-token response normally requires 500 sequential token-generation steps, although techniques such as speculative decoding can reduce expensive model passes.

2) Diffusion LLMs

In the masked diffusion approach shown below, generation starts with masked output positions alongside the prompt.

A denoising pass predicts candidate tokens for multiple positions using bidirectional context.

With confidence-based sampling, selected predictions are retained while other positions remain masked for subsequent steps.

The model progressively fills the sequence. It doesn't necessarily produce a complete draft and repeatedly rewrite every token.

Some implementations generate block by block rather than processing the entire response together.

Multiple tokens can be finalized per step, allowing fewer steps than output tokens. The step budget affects both speed and quality.

There are some engineering tradeoffs.

Bidirectional attention makes standard autoregressive KV reuse harder. A token's representation can change when surrounding positions are updated, even if that token itself stays fixed.

Caching therefore depends on the architecture and decoding strategy. Block diffusion, for example, can support KV caching across completed blocks.

Fewer steps also don't guarantee lower latency. Each step may process many positions, so total computation and implementation matter.

Bidirectional conditioning also supports filling gaps in text or code.

It covers what gets cached during prefill, how the cache grows during decoding, and why it becomes the main memory bottleneck at long context.

05｜Multi-Agent 设计模式成本权衡

来源（X） · @UPing123zzz · 2026-11-17 15:03

为什么一个 Agent 明明能完成的任务，非要拆成五六个 Agent；明明一条固定 Workflow 就能解决的业务，非要搞一个 Manager Agent，再配几个 Worker，最后加个 Supervisor 管理所有人。

整个架构看起来特别牛逼，但真正上线以后，Token 成本上去了，响应速度变慢了，出了问题反而更难排查。

这篇关于 Multi-Agent Design Patterns 的文章，我觉得特别值得研究。

它把多智能体系统拆成六种设计模式，而且没有只讲功能，还讨论了每种架构背后的成本和价值。

首先是 Sequential，顺序执行。

一个任务接着一个任务做，适合步骤之间存在明确依赖的场景。

然后是 Parallel，并行执行。

几个相互独立的任务同时处理，最后汇总结果。它可以缩短等待时间，但也会带来并发配额、资源竞争和结果合并的问题。

再往后是 Hierarchical，层级式架构。

由一个 Manager Agent 负责拆解目标、分配任务，再交给不同的专业 Agent 执行。

听起来像是在组建一支 AI 团队，但问题是，管理本身也是有成本的。

主 Agent 需要理解任务、委派工作、传递上下文、检查子任务结果。你多引入一个管理层，就多了一层可能发生错误的地方。

还有 Generator–Critic。

一个负责生成，另一个负责审查，发现问题以后再修改。

这个模式确实可能提高结果质量，但如果没有明确的评测标准，所谓审查也可能只是让另一个模型换个角度胡说八道。

两个 Agent 意见一致，不代表答案一定正确。

Human-in-the-Loop 则是把关键决策留给人。

比如招聘 Agent 可以自动读取简历、生成分析报告，但涉及正式修改招聘状态、发送面试邀请的时候，仍然需要明确的权限和审批机制。

最后是 Composite，把多种模式组合起来。

复杂业务确实可能同时需要顺序执行、并行任务、动态委派、结果验证和人工审核。

但我觉得这里最容易出现的错误，就是把复杂架构本身当成了技术成果。

举个最简单的招聘 Agent。

解析简历、提取岗位要求、生成匹配评分、检查结果、交给 HR 审核。

这几个步骤如果流程已经明确，完全可以用普通后端代码加 Workflow 完成。

批量简历可以通过任务队列并行处理，评分由模型负责，业务规则通过程序校验，最终结果交给 HR 确认。

为什么非要让每一步都变成一个 Agent？

模型自主决策是有价值的，但不是所有步骤都需要模型自主决策。

更值得研究的是，什么时候需要一个 Agent，什么时候需要多个 Agent，什么时候一条确定性的工作流反而更可靠。

原帖后面还提到了 MCP 和 A2A，这两个协议我觉得也很容易被混淆。

MCP 主要解决 AI 应用怎么连接工具和外部数据，A2A 则主要解决独立 Agent 系统之间怎么通信、委派任务和协作。

但接入 MCP，不代表工具调用就自动安全。

使用 A2A，也不代表多个 Agent 就天然拥有共享记忆、统一权限和可靠的任务恢复。

协议解决的是交互标准，真正的业务可靠性仍然需要系统自己实现。

所以我越来越觉得，多智能体工程真正值得研究的，不是 Agent 数量，而是增加一个 Agent 到底能产生多少实际收益。

任务成功率提高了吗？整体延迟下降了吗？

Token 和工具调用成本增加了多少？

出了故障还能不能准确定位和恢复？

如果这些指标都没有改善，那所谓更先进的多智能体架构，可能只是在花更多的钱完成同一件事情。

现在 AI 编程工具越来越强，开发几个 Agent、写一套编排代码确实已经不难了。

但能把系统做复杂，不代表有能力把复杂度控制好。

真正的工程判断，是你知道哪些任务应该并行，哪些任务必须顺序执行，哪些决策适合交给模型，哪些操作应该由确定性代码和人工审批负责。

别最后做了一个十几个 Agent 协作的庞大系统，结果还不如一个设计合理的单 Agent 稳定。

Multi-Agent 从来不是越多越好。

真正有价值的架构，是用必要的复杂度，换来可以被验证的业务收益。

如果复杂度增加了，但价值没有增加，那就不是技术升级，只是技术上的自我感动。

我们的软件工程面试正在改变（一点点）

过去几年，大语言模型改变了软件的构建方式，在 Jane Street 也不例外。如今我们大多数工程师每天都在用它们，不仅写代码，还读代码、调试代码、做代码评审，以及做很多与代码无关的事。

我们最近在一期播客里聊过 AI 在开发中的用法，也在一篇关于形式化方法的文章里谈到 agent 式编程如何重塑我们的工作方式。

但我们的编程面试一直没变。今天我们问软件工程师的问题，和多年来问的还是同一种风格：和一两位面试官坐下来，一起编程解一道题，边做边聊。

这种方式一直很管用，核心目标也没变：我们想看你怎么解决问题、怎么组织工作、怎么沟通，以及怎么在合作中追求优秀的软件开发。但工作的形态已经变了，我们觉得面试也该跟着变。既然生成代码比以往任何时候都更便宜，工作的其他部分就显得更重要了：对“该做什么”的品味、选择能经得起时间的抽象、确保做出来的东西确实正确，等等。

所以今年夏天，我们开始在校园招聘的 onsite 里试行几种新的面试形式。大体上，它们写代码的部分更少，更偏高层面的东西：软件设计、验证代码的质量、结构和意图，以及用 LLM 生成代码。大多数轮次仍将是传统编程面试，不借助 LLM 进行。

我们知道这听起来很含糊，但这是故意的：这些形式还在演变，我们不想今天详细描述一个六个月后可能就变了样子的东西。

有几点值得了解：

不是每次 onsite 都有这些新轮次，来了之后我们会提前告诉你会遇到什么。

其余流程不变。如果你读过我们以前关于面试的文章，那些内容依然准确。

我们觉得 LLM 在日常工作中非常有价值，但也明白不是每个人都有丰富的 LLM 使用经验。你不需要有一套很成体系的 agent 工作方法也能在我们的流程里表现好。归根结底，我们要找的是对构建软件有出色直觉的人，而评估这一点我们觉得不需要 LLM。

不同的人把 LLM 融入工作流的方式和程度各不相同，我们不要求你有特定的配置，也不要求你事事都用它们。我们在意的是你对自己用的工具想得清楚：它们擅长什么、在哪里不足、什么时候该换别的工具。

和一段时间以来一样，更有经验的候选人的面试会更多样，涵盖从产出软件、设计系统到讨论过往工作等多种形式。

和往常一样，我们会继续迭代，有更多可说的会再写。
