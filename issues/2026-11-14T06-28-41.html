01｜e2e 框架 Agentic 测试五条实践

来源（X） · @hungryturbo · 2026-11-14 12:12

AI 时代的 e2e 测试该怎么做?

最近 GitHub 斩获 13.8k Star，刚拿了 800 万美金融资的开源 AI 测试框架 e2e，其创始团队技术布道师 Kacper Kapuściak 写了一篇非常扎实的工程实践，下面总结几条核心内容：

1、测用户意图目标，而非前端实现，越过 DOM 节点与 test-id 绑定，直接用自然语言向 Agent 下达具体，收敛的业务意图。由 AI 自主感知界面完成选日期，点生成等交互，哪怕前端重构组件库，测试照样稳定。

2、废弃拖慢 CI 流水线的固定 Sleep 读秒，改用带超时上限的 AI 动态条件等待。忽略Loading 消失这类弱的 UI 信号，直接等上月报表已打开可查看等强业务状态，并将负责异步加载的动态等待，与只抓拍当前画面的瞬时断言严格解耦。

3、执行 Agent 汇报点击完成，不能代表报表没空数据或串数据，更不能让大模型盲猜什么才是正确的画面。必须先从后端 API 查出真实任务列表作为唯一真值源，再调用独立的 AI Judge，严格比对屏幕渲染明细与 API 底账。

4、严禁测试用例之间产生顺序依赖，开跑前通过可复用的 Fixture 调接口独立构造专属工作区与测试数据，跑完后在生命周期钩子中自动清理还原，确保单测重试或并发执行绝对幂等。

5、将“生成报表，下载 CSV，发邮件”拆成命名清晰的独立原子测试。一旦断言失败，框架自动打包故障追踪轨迹，涵盖前置步骤、应用日志、Agent 推理上下文与屏幕快照，不仅人类能秒级定位，更能直接喂给 Coding Agent 自动修 Bug。

传送门：http://e2e.com/blog/5-tips-for-writing-good-agentic-tests

02｜风控检测跨区用户的十二种手段

来源（X） · @AyakaAteliers · 2026-11-14 10:48

总有一些自以为是觉得自己最聪明的程序员，作为最顶级的安全工程师不妨给你们透露一下大概有什么途径可以检测你们这些小白

1. SSH ：终端 SSH_CONNECTION 这个环境变量，包括你的真实 IP，不信 echo 一下
2. 远程桌面：常见远程桌面把你们机器上日志收集一下就能知道真实 IP 是啥了，再不济 dump tcp connection 看应用程序也能筛一下远程 IP
3. 全局你顶不住 ICMP 的包，说白了 ping 都能检测出来你的 src IP
4.接一个远程命令下发执行器，服务端提前准备好若干检测命令，周期性无规律下发，客户端你是逆向天才都不知道干了什么
5. 顶着 300ms 的请求时延，好难猜啊，在哪啊，ping 三点根据时延确定一下大致地区
6. GPS 读一下就行了定位，读不出来的默认扣风控分
7. 网卡型号设备，WiFi 监管域读一下标识码
8. 服务器增加一个分类器，对于疑似不支持地区的用户维护一个封禁词表，把类似大厂内部域名的包名记录进来
9. 检测到了异常并不马上封号，一点点扣掉用户账号的风控分数，低于阈值就要求 KYC
10. 营造出封号没有规律的假象，定期收割即可
11. Agent 每天叮着 X 上各类防封教程博主，自迭代更新检测机制，有截图的识别里面可以抓到的账号信息
12. 周期 Pull 用户 GitHub Readme 检测一下自述地区

05｜Swamp 工作流省下九成 Token

来源（X） · @NpieAI · 2026-11-14 12:09

同一个代码评审，token 从 460 万降到 50 万，时间从 12.8 分钟砍到 6.6 分钟。

问题不在模型，在技能的用法。我把重复流程写成技能，agent 每次跑都要重新读一遍技能、重新决定每一步该怎么走。等于每跑一次，都要花 token 把流程从头想一遍。

Swamp 的办法是反过来的：让写代码的 agent 把重复的技能一次性搭成工作流，搭好之后反复跑。

每个步骤的输入和输出都是事先定好的，下一步走哪条由代码决定，不由模型临时想。模型只在真正需要判断的那几步才出场。

Swamp 官方公布的一组实测是这样：同一个代码评审技能，在 Codex 里跑要花约 460 万 token、23 个 agent、12.8 分钟；改成 Swamp 工作流后，约 50 万 token、3 个 agent、6.6 分钟。

省得最多的一块，是把协调这活儿从 agent 手里交给了代码。

流程跑第二遍的时候，就不该再花 token 想流程——判断请模型，流程交给代码。

我的做法是这样：
第一，新任务第一次跑，照常用技能，先跑通。

第二，同一个任务跑到第二遍，就让 agent 把它改成工作流。

第三，改的时候先问三个问题：哪几步真的需要模型判断？上周那次跑到底发生了什么？需要判断的那一步，换个便宜模型行不行？

一句话：技能是草稿，工作流才是定稿。

你手里现在跑得最勤、每次都要重新讲一遍的那个流程，是哪一个？

08｜OrbStack 稀疏文件卡死系统迁移

来源（X） · @chijianqiang · 2026-11-13 17:46

之前老 Mac 装了 OrbStack，使用迁移助理的时候遇到了这个大坑，真是被这个软件气死了，他妈的。

https://shivankaul.com/blog/migration-assistant-sparse-files

我的新 Mac 是 4T，旧的是 2T，迁移系统的时候居然告诉我空间不足。苹果也是够弱智的。啥原因呢？这里：

新 Mac 的存储容量是旧机的四倍，迁移却报“没有足够的可用空间来完成迁移”。真正原因是 OrbStack 留在 ~/Library/Group Containers/HUAQ24HBR6.dev.orbstack/data/data.img 的一个虚拟磁盘镜像：它只有 6.5 MB 实际占用，但逻辑大小 8.0 TB。

• 作者用两条命令把这个矛盾量化出来：sudo du -sh ~ 得到 282G，sudo du -shA ~ 得到 8.3T。在 1 TB 的 SSD 上出现 8.3 TB 的表观体积，说明有文件在尺寸上“说谎”。
• 定位方式：sudo du -hA -d 2 ~ | sort -h | tail -30 按表观大小聚合排序，锁定到具体文件后，再分别用 du -hA（8.0T）和 du -h（6.5M）复核。
• 删除该镜像后，第五次运行 Migration Assistant 在 3 小时内完成。OrbStack 自己的 FAQ 也提到这个 8 TB 文件，并说明稀疏文件会干扰 Migration Assistant。

这老哥迁移了五次，我迁移了两次，目前在进行第三次，说起来苹果的迁移助理也真是傻叉。
