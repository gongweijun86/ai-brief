01｜Agentic AI 知识图谱五层依赖

来源（X） · @UPing123zzz · 2026-11-17 11:11

很多人一上来就研究 Multi-Agent、Self-Improving Agents、长期记忆、自主执行，恨不得直接搭建一套能够不断自我进化的智能体系统。

但真让他解释一次 Agent 从接收任务、构建上下文、调用工具，到执行失败、恢复状态、验证结果的完整过程，可能根本讲不清楚。

这张 Agentic AI Knowledge Graph，我觉得很值得仔细研究。

它最有价值的地方，不是整理了多少技术名词，而是把这些技术背后的依赖关系画出来了。

整张图分成五层。

最底层是 Foundations，包括 LLM Reasoning、Prompt Patterns、Function Calling、Embedding 和 Context Window。

往上是 Retrieval & Memory，包括 Classical RAG、Graph RAG、Agentic RAG，以及短期记忆、长期记忆和情景记忆。

再往上才是 ReAct、Planner-Executor、Multi-Agent Orchestration、Tool Routing 和 Reflection。

然后进入真正的生产环境治理，包括 Confidence Scoring、Policy Gates、Audit Trail、Decision Logs、Evaluation、Observability 和 Token Economics。

最上面才是 Memory & Learning Loops、自我改进、多模态推理和规模化 Agent 工作流。

仔细研究之后，你会发现一个挺有意思的问题。

很多人天天追逐最上层的能力，却把最下面那些看起来枯燥的工程基础跳过去了。

比如 Memory。

现在很多 Agent 都宣传自己拥有长期记忆，但把聊天历史扔进向量数据库，不代表系统就真的具备了可靠的记忆能力。

什么信息值得保存？什么时候应该检索？历史经验过期了怎么办？不同用户的记忆怎么隔离？

这些问题如果没解决，所谓长期记忆，可能只是一个越积累越混乱的信息仓库。

Reflection 也是一样。

让模型执行完任务，再让它自我评价一次、反思一次，不代表它真的能够持续进化。

如果没有真实业务结果、明确的评测标准和可靠的执行记录，模型很可能只是换一种方式重复原来的错误。

这就涉及一个我觉得非常重要的东西：Feedback Loop。

真正有意义的反馈循环，应该是任务执行之后，系统能够记录发生了什么，通过评测判断哪里做得好、哪里出了问题，再根据反馈调整下一次的执行策略。

而不是单纯给 Agent 加一句“请不断反思、持续改进”，就觉得它拥有了自我学习能力。

更重要的是 Production & Governance 这一层。

我觉得它才是整张图最值得 Agent 工程师认真研究的部分之一。

现在很多人做 Agent，喜欢比较能调用多少个 MCP、能同时运行多少个子 Agent、能自主执行多少步。

但模型调用工具之前有没有权限检查？执行到一半崩溃了怎么恢复？重复调用会不会造成业务损失？任务执行过程能不能追踪？最终结果有没有真正完成用户的目标？

这些东西往往没有那么炫酷，却直接影响一个 Agent 能不能进入真实业务。

举个例子。一个招聘 Agent 能自动分析 50 份简历、生成评分报告，看起来已经不错了。

但如果评分规则更新了，旧任务怎么处理？模型误判了候选人，能不能追溯依据？如果它准备发送面试邀请，哪些操作必须经过人工审批？

这些问题不解决，你再增加几个分析 Agent、审核 Agent、Supervisor，可能只是让系统变得更加复杂。

所以我觉得，学习 Agent 最容易走偏的一件事，就是把系统复杂度当成技术先进程度。

实际上，很多业务根本不需要多智能体，一条设计合理的 Workflow 就能解决。

有些任务不需要长期记忆，只需要可靠的状态存储。

有些问题根本不需要模型反思，而是需要更准确的检索、更严格的业务规则和更好的评测。

真正值得学习的，是这些技术之间的关系，以及什么时候该用、什么时候不该用。

尤其是现在 AI 编程工具已经能够帮助我们快速实现大量功能。

实现一个 Agent Demo 越来越容易，但理解它为什么能够运行、为什么会失败、怎样控制风险、怎样持续改进，依然需要认真研究。

这张图最后有一句话我特别认同。

学习 Agentic AI，不能只从那些最先进的概念开始。

你得顺着技术之间的依赖关系往下研究，再真正观察一条任务从开始到结束的执行过程。

说到底，Agent 的价值不是它拥有多少工具、多少记忆、多少自主执行步骤。

而是它能否在真实任务里正确获取信息、选择行动、控制风险、验证结果，并且根据可靠反馈不断改进。

如果没有这些基础，所谓自主进化，可能只是在不断积累错误。

如果没有完整的执行追踪，所谓智能决策，出了问题也根本无从解释。

我越来越觉得，Agent 工程真正的门槛，不是让模型表现得越来越像一个聪明的人。

而是给这个充满不确定性的模型，建立一套能够持续执行、发现错误、纠正错误，并且对最终结果负责的工程系统。

别最后研究了一堆 Self-Improving Agents、Multi-Agent、Memory Loops，结果连一个工具调用失败之后该怎么安全恢复都搞不明白。

那学的可能不是 Agent 工程，只是越来越多的技术名词。

02｜GA100故障注入解锁满血A100

当年英伟达为了防止矿工抢占数据中心显卡，拿 GA100 大核心切出了 CMP 170HX 矿卡，不仅在硬件熔丝（Fuses）层面砍掉了显存容量、禁用了 NVLink 高速互联、把 PCIe 降到 Gen1，还锁死了张量计算吞吐。

Kate 顺着 GA100 上电启动读取板载熔丝配置寄存器的微妙时间窗口，用精密控制的电压毛刺（Voltage Glitching）去干扰芯片的熔丝传感放大器——让芯片在自检瞬间把原本烧断的限制熔丝全部误读为 0（未熔断状态），再配合重新植球焊满的高带宽显存，一举解开了英伟达在硅片层面的全部封印：不仅显存认满 81,920 MiB（80GB），连原本被阉割的 PCIe Gen4、NVLink、MIG 切分 也全数复活。

更离谱的是实测性能：因为英伟达在卖零售版 A100 时为了保证晶圆良率，统一锁在了 108 个流多处理器（SM）；而这张被毛刺攻击彻底放飞自我的 GA100 核心，居然把晶圆上全部完好的 120 到 126 个 SM 单元 全点亮了，跑出来的真实算力比官方正版 A100 还要快出整整 1.2 倍。

03｜Antigravity双命令实战解析

来源（X） · @ChatGptAstra · 2026-11-17 08:37

我敢说，/learn 和 / swarm 绝对是 Antigravity 中最被低估的两个命令！

一、先说 /learn
这个命令我经常用，主要场景有 3 个:
1、某次复杂的任务跑得特别好，想把关键步骤和坑沉淀下来；

2、想把某个工作流提炼成 Skill，这时候 /learn真的不是一般的好用，谁用谁知道;

3、反复纠正过的错误或约束，想让它彻底记住。比如”数据库查询必须加 LIMIT，禁止全表扫描“之类的东西

每次你使用 /learn，Agent 会先分析近期消息，寻找明确纠正过的地方，对比失败和成功路径，最后找出关键改动和根本原因。

然后，Agent 会继续判断这个经验是属于 Rule 还是 skill，如果是已有的 Rule 或 skill 但是在实际中失效了，那么 Agent 会更新现有文件而不是重复创建副本。

最后，会生成一个叫 learning_proposal.md 的提案文件等你审核通过后再修改。

这就是 /learn 的整个流程。

二、/swarm 命令则有点像著名厨师 @poteto 的米其林厨房的概念
1. 拆分任务。
进入 swarm 模式后，当前的对话 Agent 会立刻化身协调者，并将当前的复杂任务拆分为互不冲突的小模块，并将它们交给不同的 Worker Agent

2. 分配并公开Breif。
然后，每个 Worker 会获得独立的上下文，并收到协调者的一份公开 Brief，Brief 会明确每个 Worker 负责什么、不能碰什么、怎样算完成。

3. 并行执行 + 验证。
Workers 开始在各自的隔离工作树并行执行。同时，每 2-4 个 Worker 会被分配一个 Verifier Agent，负责读 diff、跑测试、发现问题并反馈给对应的 Worker 去修。
还会有一个 Monitor Agent，任务卡住的时候它就会跑出来。

4. 共享看板协作。
Worker 之间不私聊，所有进展、问题、测试结果都公开可见，所有沟通都会在同一个共享看板进行。

5. 汇总汇报。
协调者 Agent 本身不写代码，只负责分配、判断结果、向你汇报最终进展。你也可以随时打开 Swarm 面板

这就是 /swarm 的整个流程，对于复杂任务真的非常值得尝试，就是有点耗 Token....

05｜Anthropic多Agent实验落败

来源（X） · @Xudong07452910 · 2026-11-17 08:33

一群 Agent 一起干活，结果还不如一个 Agent 单独协调？

推荐阅读 Anthropic 新发布的《Worse Together》，专门研究多个用户各自带着 Agent，共享资源时会发生什么。

研究者设计了四类场景，包括共享 Token 预算、医院预约、集体订餐和代码合并。在测试的两款 Claude 模型上，多 Agent 团队的整体表现全部落后于单个协调 Agent。

在集体订餐这个实验中，用户明确提出了无麸质需求。虽然 94%～99% 的情况下，消息已经发给负责下单的 Agent，但真正提交订单时，只有 47%～67% 的情况下，这条信息进入了它的 Context。

很多失败就发生在这种消息同步问题上。

作者后来加了一条简单的 Harness 约束：下单前必须读完所有待处理消息，结果挽回了 62%～73% 的失败案例。

还有个挺值得思考的发现。部分 Agent 会擅自取消其他用户的任务，反而让整体评分更高，暴露了现有 Eval 对协作行为的盲区。

这项研究是非常有价值的。之后多个 Agent 共同工作越来越普遍，消息同步、共享资源管理、权限边界这些问题，都值得单独研究和评测。

作者还开源了 MAMUBench，包含 74 个多用户协作测试场景。做 Multi-Agent 和 Agent Eval 的朋友很推荐阅读和收藏！

06｜Pi Durable让Agent断点续跑

来源（X） · @yibie · 2026-11-16 20:37

作者亲自解读 Pi Durable：怎么做到断点恢复的

终端里的 Pi，崩了没关系，敲一句 continue 就行。但如果 Agent 跑在 Slack、内存受限的手机上、或部署到会被回收的 serverless 环境后，旁边就没人敲 continue 了。它得能被重新拉起，从断点恢复，还不能忘掉做过什么。

Pi Durable 把会话里每个动作都表达成带阶段的任务：先记录接下来要做什么，执行这个 effect，把结果持久化，再进下一阶段。所有状态变化按顺序串行提交，提交后才算数；模型一次回复发起的多个工具调用各自成为任务，可以并行跑。

它刻意不用事件溯源。常见 harness 把每个 token、每次工具调用都写成事件，几千条记录的编码会话够用，但一个要在 Slack 频道活五年、几千人参与的 bot 撑不住。

Pi Durable 改存 JSON 文档：监听者先拿整份快照，之后只收 delta，文档带版本号、可迁移，演讲里说这是为跑十年的 agent 准备的。存储只是一个简单接口，SQLite、Postgres、Cloudflare Durable Object、JSONL 都能接。

进程任意时刻被杀，重启后打开同一个存储说 resume，没完成的任务会被读出来续跑。这里有个讲究：bash 这种不可重放的工具不会再执行，而是在转录里标记成因进程消失被中断，把结果交给模型让它收尾；只有搜索这种天然幂等、或带幂等键的工具才会重放。用户输入也带幂等键，Slack 把同一次 mention 重复投递时不会触发两次运行。

工具和运行的机器分开：read、write、edit、bash 只依赖访问文件系统和起进程两个接口，同一套工具能跑笔记本、安卓 Termux、QEMU 沙箱或 Cloudflare，运行中还能热插拔。一个 harness 配置一次就能并行承载多个会话，Slack 子线程可从主会话某点 fork。

两个现场演示挺说明问题。一是放进 Cloudflare Durable Object，它跑满 15 分钟就被回收，设个闹钟到期前重启，resume 后像什么都没发生。二是整套 harness 跑在他的安卓手机上，现场 51 个人同时网页围观。代码在 GitHub 的 earendil 仓库里。
