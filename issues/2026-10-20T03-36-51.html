02｜RAG 召回用双塔 重排用交叉编码

来源（X） · @cxjwin · 2026-10-20 00:12

中兴一面连着问了两句：为什么 RAG 既要 embedding 又要 rerank？为什么不能全部 rerank？答案在召回和重排用的两种结构上。

双塔：问题和文档分开编码，文档向量提前算好，查得快，几百万条里也能找；代价是两段文本编码时互相看不见，否定、条件、数字对不对得上，这类细节容易丢。 交叉编码器：把问题和文档拼在一起送进模型，逐对打分，更准，但每个候选都要现算。

所以先用便宜的召回把范围缩到几十条，再用贵的重排把这几十条排准。全库都做 rerank，计算量跟着库的大小线性增长，做不下去。

这是下面这篇里的一环。从解析、切分到评测，每一环都这么拆：解决什么问题，原理是什么，怎么取舍，面试会怎么问。

RAG 效果差、召回不准从哪排查，是题单第 15 题，后面单独写。

03｜科研Agent 两轮自进化提升假设质量

来源（X） · @Xudong07452910 · 2026-10-20 11:20

科研 Agent 会提 idea 已经不稀奇了，难的是知道哪条真的值得继续做。

这篇 DiscoveryRSI 想让 Agent 学会筛选和改进研究假设。

它会围绕一个假设不断生成、修改和组合方案，同时要求每个假设都有明确证据、实验设计、判断标准和替代解释。

更关键的是，研究过程会反过来训练下一轮 Agent。

好的假设会保留下来，失败轨迹则用来定位研究流程哪里出了问题，再继续更新模型和 Harness。

两轮自我改进后，假设质量从 4.86 提升到 5.39，提升主要来自「可证伪性」和「数据是否真的能回答问题」。

还有一个挺有意思的结果：

DiscoveryRSI-27B 生成的假设中，有 6.3% 和模型知识截止后发表的研究方向相似；GPT-6 是 2.5%，Claude Opus 5 是 2.3%。

这个指标当然不能直接等同于真正发现，但方向很值得关注。

科研 Agent 的自进化，不该只学会写得更像论文。

它还要逐渐学会判断，哪些问题值得追，哪些证据真的够，以及下一轮研究该怎么做得更好。

05｜测试成为 Agent 感知世界的传感器

来源（X） · @shao__meng · 2026-10-20 11:19

AI Coding Agent 时代"Verification"为何成为核心瓶颈 ？

来自 Claude Code 团队 @addyosmani 最新分享「Agentic Verification」，他认为瓶颈已经从 “写出代码” 转移到 “知道代码是对的” ：
https://addyo.substack.com/p/agentic-verification

Addy 的核心观点：验证改变了 Agent 的行为模式
一个不能自我验证的 Agent，本质上是在“猜”。猜的结果就是把慢速的人类循环强加给流程：人类读 diff、跑测试、点应用、报 bug。而一个能自我验证的 Agent，会在人类看到任何东西之前就完成“写代码 → 跑检查 → 读输出 → 重试”的闭环。

由此，测试的定义被改写了。传统上测试是防 bug 和支持重构的工具；现在测试是“Agent 感知世界、判断自己何时完成的传感器”。“实现这个功能”是个模糊目标，“让这条 E2E 测试通过”是一个可以追逐的目标。人类的工作从“逐行 review”变成“构建 Agent 能自己跑的验证循环”；人仍然对发布负责，但审查的对象从 diff 变成了证据。

# 三种测试，其实是三种给 Agent 的“考题”

1. E2E 测试：如果只能选一种，选它。 E2E 模拟真实用户流程 (注册、加购物车、结账、看到确认页)，不关心内部结构，因此很难被“糊弄”。相比之下，基于 mock 的单元测试可能出现 Agent 和测试共享同一个误解的情况，代码错、测试也按同样的错误理解写，双双通过。E2E 的额外价值在于：失败时给出的是截图、trace、具体失败的步骤，而不是一句 "Timeout after 30s"。代价是慢和 flaky,所以要维护一小套高价值的集合。配套技巧(来自 Lauren/@poteto)：给 Agent “手和眼”，一个能启动、驱动、观察真实系统的 skill/CLI (CDP、模拟器、API harness)，再加一份 feature map：以用户视角清点功能、入口、选择器、预期结果和坑。

2. 属性测试 (property-based)，规定“什么永远不许发生”。 由工具 (fast-check / Hypothesis / proptest) 自动生成成百上千个输入去攻击你的规则，失败后自动收缩成最小复现案例。典型属性：编解码往返一致、不变量(排序不丢元素、余额永不为负)、幂等性、等价性(优化版和朴素正确版行为一致)。这对 Agent 尤其关键：Agent 倾向于自己编造能通过的示例；属性测试强制它面对任意生成的输入。实践建议：从纯函数(解析器、格式化、计价)入手；先用自然语言写属性再翻译成代码；让 Agent 写“属性”而非“示例”。更高阶的做法(引自 Claude Code 的 Boris Cherny)：对最刁钻的状态机和并发逻辑用形式化模型(Lean、TLA+)，靠反例暴露竞态条件。

3. 差分测试 (differential)，把旧系统当“标准答案”。 新旧系统并排跑相同输入(随机生成或回放真实流量，而非手工挑的用例)，差异要么是 bug、要么是有意的破坏性变更。这是 Agent 辅助重写的理想模式：改代码 → diff → 审查不一致 → 修，循环推进。Addy 引用了一个匿名团队的观察：从“修好一处又弄坏另一处”变成有条不紊的推进。三条纪律：归无语义意义的差异(如顺序)；把有意的变更记入“已批准清单”，防止“不一样”被默认容忍；迁移完成后彻底删掉旧系统，两套并存等于双倍工作和双倍故障面。

回路质量：慢和 flaky 是在“训练” Agent 学坏
慢或不稳定的测试不只是浪费时间，它是一次训练。人类能容忍偶发的 flaky CI，但 Agent 会从回路的激励中学习：如果重跑有时能过，“重试”就会取代“修复”成为首选策略。测试慢则 Agent 跑得少、改动打包提交、无法定位是哪次改动引入的失败。最阴险的是，这两种失败模式都让 Agent 悄悄变差，而没有任何可见的失败信号。因此："主套件里一条 flaky 的测试比没有测试更糟，因为它摧毁了对其他所有结果的信任。"

合格回路的标准：核心循环亚秒级完成；结果完全确定(随机性固定种子、冻结时钟、受控网络、隔离状态)；flaky 测试立即隔离移除；失败输出短而具体(冗长的通过日志浪费 Agent 的注意力)；快内环先行，重 E2E/diff 后置。一句话：把测试基础设施当作 Agent 的依赖来投资，改进它是复利。

人的角色：先写检查，再写代码
结论落在方法论上：在让 Agent 构建之前，先明确“成功长什么样”（一条 E2E 流程、一个属性、或一次与旧系统的对比）并且要快、要确定。你定义成功标准的判断力，“将比你自己读 diff 的能力扩展得好得多”。配套习惯：让 Agent 编码前先复述目标；用新上下文或独立的 reviewer Agent 做验证；对 Agent 生成的测试本身保持怀疑，它真的能区分“正确实现”和“貌似正确的实现”吗？出错的地方沉淀为共享配置、hook 或测试，让错误累积成“品味”而非重复。

06｜五条工程习惯优化 Agent 编码

来源（X） · @bylixing · 2026-10-19 21:20

Agent coding 时代，确实有一些工程习惯要面向 Agent 做优化：

我目前总结下来是这几条：

1. 文件长度要在上下文窗口之内。

我的标准是单个代码文件不超过 800 行，单行不超过 200 字符。稍不注意，Agent 就能把一个文件写到一万多行，之后每次修改都很难找到位置。已经超长的老文件先记个账，以后只许变短，不许变长。

2. 变量、函数的命名要符合搜索直觉。

Agent 找代码基本靠 grep，名字叫 a1、tmp2、data，它就搜不到；叫 orderTotal 才能搜到。

3. 文件命名也一样，禁止万金油名字。

utils、types、config 这种万能名字，一个项目里能有十个，Agent 根本分不清该改哪个。要带上领域前缀，比如 order_utils，一看就知道是干什么的。

4. 当心「永远为真」的测试。

比如让 Agent 写一个算折扣的函数，原价 100 块，打八折应该返回 80。再让它补一个测试，它经常只检查「函数有没有返回值」，不检查「返回的是不是 80」。这样一来，函数算成 800 也好，算成 0 也好，测试照样是绿的。

还有一种更隐蔽的情况：测试本来写对了，跑出来是红的。Agent 不去修函数，而是把测试里的期望值从 80 改成 800，让测试去迁就错误的结果。

所以每写一个测试，我都会故意把函数改错一次，看测试会不会变红。不会变红的测试，写了也等于没写。

5. 也是最重要的一条：能确定判断对错的事，用脚本约束，别写进全局 Prompt。

上面几条，一开始我都是写在 AGENTS.md 里让 Agent 自觉遵守的。

结果一是 AGENTS.md 越写越长，每个会话都要把它读一遍，费 token，也稀释注意力；二是 Agent 照样会忘、会无视。

现在我的做法是：文件超长、命名违规这种机器能判断对错的事，统一写成 pre-commit hook 和 CI 检查，不合格直接拒绝提交。

AGENTS.md 只留那些需要判断力、脚本管不了的东西。

07｜提示词优化让决策模型提约10分

来源（X） · @0xLogicrw · 2026-10-19 18:32

AI 搜索公司 Parallel 用自身搜索业务中的真实案例，测试了 Jev、Perplexity、OpenAI Decisions 等 8 款决策模型。

测试包括 4 项任务：判断网页变化是否重要、过滤低质内容、选择搜索索引，以及给搜索结果排序。直接使用初始提示词时，Jev 在四项任务中的平均排名第一，Perplexity 第二，OpenAI 第五。

其中，最难的是判断网页变化是否值得重新处理。比如招聘信息只是调整了两条要求的顺序，可能不需要更新；排行榜名次发生变化，却值得重新抓取。测试采用综合衡量误报和漏报的指标，分数越高越好。Perplexity 最初得到 93.3 分，Jev 为 87.9 分，OpenAI 只有 79.0 分。

团队随后让 Claude 帮各个模型改进提示词。以网页变化识别为例，先准备 800 条人工标注的案例，让 Claude 检查模型的错误判断，再针对容易出错的情况补充规则。连续尝试 5 轮，每轮只保留成绩更好的版本。

最终在独立测试集上，OpenAI 从 79.0 提高到 88.8，Rune 26B 从 74.1 升至 83.9，Nimble 9B 从 65.1 升至 75.3。三款模型都提高了约 10 分。

把网页变化识别、低质内容过滤和查询路由这三项任务合在一起计算平均分，Perplexity 从 97.3 升至 97.6，Jev 从 95.5 升至 96.5，OpenAI 则从 88.7 大幅提高到 95.1。8 款模型的平均分全部提高，但原本领先的模型进步有限，OpenAI 明显缩小了差距，优化后排在第三。

剩下的搜索排序任务单独计算。优化提示词后，Jev 排在前列的搜索结果与人工标注结果重合率达到 71.45%，Perplexity 为 70.68%。但 Parallel 自己微调的一款小型排序模型达到 75.21%，比 Jev 高约 3.8 个百分点，每 Token 推理成本也只有 Jev 的约四分之一。

代价是必须自行收集标注数据、训练和部署。对于需要反复处理的大量固定任务，专门训练的小模型仍可能更准确、更便宜。
