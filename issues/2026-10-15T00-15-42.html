01｜腾讯评测Agent抓取高德数据

来源（X） · @sleepy0x13 · 2026-10-15 00:17

笑死，几个老外在互联网上抓到了一群中国 AI Agent，顺着线索一查，发现腾讯的 Agent 正在跟阿里高德的反爬系统打架。

我刚看完这群研究人员发布的完整调查报告，事情实在有点抽象。

从 9 月 28 日开始，一批运行在腾讯云环境里的 AI Agent，持续尝试获取高德地图的数据。它们的任务也很奇怪，比如调查成都动物园有多少人从北门进、有多少人从东门进，或者某个景区的各个入口分别占多少导航流量。

为了搞到这些数据，这群 Agent 进行了超过 2600 次尝试，最多同时有 14 条任务在运行。

问题是，高德有反爬虫机制，不允许它们随便获取数据。结果这些 Agent 相当执着，开始自己寻找各种办法：调用第三方网站帮忙访问高德、寻找网上公开的 API Key、尝试绕过验证码和访问限制，甚至摸到了阿里的预生产接口。

研究人员最初只是发现了一批异常流量，后来顺着日志找到了腾讯云的服务器，以及一个叫 hysandbox 的代理环境。

更好玩的还在后面。

研究人员发现，这些 Agent 居然会阅读网上关于自己的调查报告。于是他们干脆在网页里藏了一段文字，告诉 Agent 这里有免费的高德数据查询服务。

结果真的有 Agent 主动找上门了。

双方就这么聊了起来。研究人员一共记录了 13 组对话、33 条 Agent 消息。有的 Agent 介绍自己正在执行什么任务，甚至透露了运行环境。还有的 Agent 自称 Claude Code，但研究人员并没有确认其真实模型身份。

研究团队认为，这可能是人类第一次在真实互联网环境中，主动联系上一批正在越界执行任务的 AI Agent。

后来，一位接近腾讯的知情人士告诉研究人员，这些 Agent 属于腾讯的独立评测研究项目，使用的是第三方模型，相关项目已经结束。内部复查也没有发现针对高德的协同攻击，或者外部系统被入侵的证据。

02｜企业级Skill分四层设计

来源（X） · @kafkaup · 2026-10-15 07:54

一个偏产品工程化的话题：企业级的 skill 应该怎么写？

很多团队在做 Agent 或者 workflow 的时候，skill 写得很草率：一个 name、一个 description，加上一大段 prompt，看起来能用。但随着 skill 的数量越来越多，就会出现新的问题。比如模型无法准确命中，该调用的时候不调用，不该调用的时候调用了；或者一大段无关紧要的东西被塞进上下文，导致 token 成本浪费；更严重的是，有时 skill 之间的职能边界不清，还会导致模型产生幻觉和越权执行。

所以，企业级 skill 的问题不能只理解成怎么把提示词写得更完整，它更像是在设计一个可以被模型发现、调用、执行和维护的能力模块。

企业级 skill 最关键的一点是分层：不同的信息应该放在不同的位置，每一层都有对应的服务场景。我一般会把它拆成四层：触发层、执行层、兜底层和参考层。

1. 触发层
决定模型什么时候要调用这个 skill。这里主要写 name 和 description，但 description 不能写成宣传语，也不能把所有执行细节都塞进去。它应该写清执行什么任务、典型的触发场景是什么、不适用场景是什么，以及和相邻 skill 的边界在哪里。
这层的作用非常明确，就是帮助模型做 discovery 和 routing（在一堆 skill 里找到正确的那一个）。因为触发层经常暴露给模型，所以要短、准、边界清晰；写太长不仅增加成本，还会让模型误以为什么场景都可以调用它。
2. 执行层
决定 skill 在被调用后应该怎么完成任务。在这一层才适合写入具体的执行规范，比如输入要求、处理步骤、关键参数、工具调用、输出格式和质量标准。企业级 skill 最怕每次输出都不一样，这不仅让能力显得很不稳定，工程上也难被后续流程消费。
执行层的流程一般包括几个部分：
(a) 进入任务前检查输入是否足够
(b) 抽取关键对象和目标任务
(c) 按照固定的维度来处理
(d) 输出时遵守固定的格式
(e) 明确哪些内容可以推断，哪些内容必须标注不明确
如果会调用工具，也要写清楚调用条件：比如什么时候需要检索，什么时候只基于用户上传的文件，什么时候先做结构化提取，什么时候需要等待用户确认。这一层的目标是减少模型的自由发挥，让它按稳定的流程交付。
3. 兜底层
解决异常情况发生时该怎么处理。很多人写主要流程很清楚，但几乎不写异常处理，然而在实际产品里，异常才是常态：用户可能没有上传文件、参数缺失、工具失败、外部依赖失效、检索没有结果、依赖系统超时，或者用户请求超出了能力边界。如果这些不提前写清楚，模型就容易硬凑、编造、误调用，或者在错误路径上执行。
兜底层要明确几类策略：缺少必要输入时追问、工具失败时说明原因、结果置信度低时标注不确定、超出能力边界时拒绝或转到其他 skill、涉及高风险操作时等待确认等。兜底层也可以理解为异常处理和治理策略，它不只是 fallback，还包括追问、降级、拒绝、转人工、停止执行和安全提示。
4. 参考层
解决哪些资料需要在必要时加载。这里可以放模板、schema、术语表、示例库、业务标准、行业规范、few-shot 等。
参考层的原则是：不要默认全部塞进主 prompt。数量少时或许能接受，但数量一多就会变成 token 黑洞，模型看到大量无关信息既耗成本，又容易误触发或幻觉。所以参考层必须按需加载：要求固定格式时再输出模板，需要结构化 JSON 时再加载 schema，进入专业场景时加载术语表或行业规则，需要风格对齐时再加载示例等。能挂载就不要常驻，能按需就不要预加载。模型看到的信息越多不一定越好，信息要在正确的时机出现。

总结一下，企业级 skill 按照四个层级来写：
• 触发层：让模型知道什么时候该用它
• 执行层：让模型知道调用后该怎么做
• 兜底层：让模型知道遇到参数缺失、低置信、工具失败和越界请求时该怎么处理
• 参考层：把模板、schema、示例等按需加载，避免一开始就把上下文塞爆

再往产品设计上抽象一点，skill 不是一段长提示词，而是一个被模型调度的能力模块：它既要能被正确发现，也要能稳定执行，还要在失败时可控、在需要资料时按需加载参考。这样写出来的 skill 才不会越写越重、越写越乱，才真正接近企业级可维护的水平。

03｜OpenChart接入AI自动盯盘研究

来源（X） · @_zheergen · 2026-10-14 08:49

好家伙！真有人做出了一个能让 Codex 自己盯盘的开源版 TradingView。

价格一旦突破你画的趋势线，AI 还能自动研究背后的涨跌原因！

这个开源项目叫 OpenChart。

它是一套 AI 原生金融看盘终端，支持 Codex、Claude、Gemini，集成 K 线、技术指标、智能预警和 AI 行情研究。

最吸引我的是，软件本身免费，图表、指标和警报都没有订阅数量限制。

几个挺硬核的能力：

1️⃣ AI Agent 看盘：接入 Codex、Claude、Gemini，让 AI 分析行情、开发指标和设置监控。

2️⃣ 自然语言监控：告诉 AI 想盯什么，它就能生成 Tea 脚本，持续检测市场异动。

3️⃣ 画线自动预警：画出趋势线或价格区域，突破后触发提醒，还能让 AI 调查原因。

4️⃣ 智能涨跌分析：选中一段 K 线，AI 研究异动原因，并把带有来源的分析标注到图表上。

5️⃣ 免费专业图表：支持 4×4 多图布局、Volume Profile，指标和警报没有软件数量配额。

6️⃣ Pine Script 迁移：让 AI 辅助把 TradingView 指标转换成 Tea，继续开发自定义交易信号。

我比较看重的是它把 AI Agent 和市场监控真正串起来了。

比如让 Codex 盯着 NVDA、TSLA、AAPL，一旦出现异常放量或突破关键阻力，就自动调查相关新闻和市场变化。

以前看盘软件只负责提醒你价格动了，现在 AI 还能接着研究为什么动。

做股票量化、AI Trading，或者经常用 Codex 研究美股行情的，这个项目值得关注。

05｜Claude Code迁移旧系统分级验证

来源（X） · @AISuperDomain · 2026-10-14 13:39

让 AI 重构老项目，最怕代码改完了，业务行为也悄悄变了。

Anthropic 官方插件库里的 code-modernization，把老系统迁移串成一套流程：

摸清代码和业务规则 → 人工批准方案 → 分步迁移 → 独立验证。

支持版本升级、跨技术栈逐模块重写、架构重建。验证环节包括：

旧代码能运行时，用相同输入跑新旧系统，由脚本比较输出。
额外生成至少 10 个新输入，复查边界、空值等情况。
故意改坏一行代码，确认测试真的能报错。

README 记录的 COBOL → Java 案例里，已有 213 个测试，后续检查仍发现行为差异，最终判定为 NOT PROVEN。

结果分 PROVEN、PARTLY PROVEN、NOT PROVEN。旧系统无法运行、只能依赖录制输出时，最高只能到 PARTLY PROVEN。差异是否接受、最终是否签字，仍由人决定。

需要 Claude Code，安装：
/plugin install code-modernization@claude-plugins-official

启动：
/code-modernization:modernize

https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-modernization/README.md

06｜VB6分离业务代码转VBS调试

来源（X） · @williamlong · 2026-10-15 00:08

我发现用 VSCode 维护老旧的 VB6 代码的一个方法：
1. 把 VB6 的项目代码改造为多个类，将界面和业务分离，分离出不含界面的代码；
2. 将分离出来的不含界面的类，修改后缀为 .vbs，变成 VBScript 代码（两者基本上是通用的）；
3. 把这些VBScript 代码放到 VSCode 里，就可以运行调试了。
