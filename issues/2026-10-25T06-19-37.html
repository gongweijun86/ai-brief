02｜Agent4Sci：Skill让提升翻倍

来源（X） · @Xudong07452910 · 2026-10-25 13:04

Claude Opus 做科研时，会把一个几乎人人都在用的调参技巧，当成「创意突破」。

Anthropic 这篇新论文里讲的这个细节很能说明今天的 Research Agent，实验做得越来越好，但还分不清什么才算真正的新想法。

Agent4Sci 把 Claude Code、Codex、Gemini 放进 20 个真实 ML for Science benchmark，让它们直接读论文、改代码、跑实验，再尝试超过论文原本的最好结果。

结果前沿 Agent 在所有 benchmark 上都找到了提升，Claude Opus 平均相对提升 10.4%。

但作者把轨迹拆开后发现，大部分提升来自熟悉的 ML 工程技巧：调超参、换优化器、ensemble、反复局部搜索。

真正的科研判断还比较弱。

它们经常高估一个想法的新颖性，GPU 放着不用，或者很快找到一个有效方向后，就一直在附近刷参数。

作者后来只加了三个很轻量的 Skill：科研构思、实验管理和定时自检。

Claude Opus 的平均提升从 10.4% 涨到 20.1%，Codex 也从 4.4% 涨到 8.1%。

所以 Research Agent 现在的瓶颈不在执行，在判断。三个轻量 Skill 就让提升翻倍，说明比起给它更多算力，先给它科研习惯更划算。

对于经常用 Claude Code 或 Codex 跑实验的朋友非常推荐阅读。

📎 arxiv: https://arxiv.org/abs/2610.28763

6️⃣ AI 辅助开发：支持 Codex、Claude Code 快速启动，辅助开发量化研究工具。

原本需要反复打开图表、手动整理的数据，现在可以用代码批量处理。

而且接口本身免费开源，不需要从零开发整套行情和指标连接模块。

06｜pi-famulus让Pi长命令转后台

来源（X） · @Leechael · 2026-10-17 23:02

拖了挺久，分享我做的一个新的 Pi 插件： pi-famulus 。

做它是因为几件事一直烦我：
- 跑个长命令，主 agent 就卡在那等，我也没法跟它接着聊；
- 线上巡检日志，我想让 agent 在旁边盯着，有动静再叫我，而不是我隔一会儿去问一次；
- 我有一个基于 Pi 做的自娱自乐的 Personal Agent，现有的方案对非 TUI 的场景考虑不够，能否持续连续对话很重要 —— 不止是 subagent，background task 也非常重要；
- 在 spawn 多个 subagents 时，最多人使用的 pi-subagents 在我这边的体感很糟糕：TUI 的动画 lagging，让我有主 agent 已经卡住了的错觉。

所以 pi-famulus 做了这几件事：
- 长命令跑超过 20 秒自动转后台，跑完再叫醒 agent，对话不断；
- monitor 盯着输出，有新内容才叫醒 agent，agent 只在旁边观察。说一句"ssh 到服务器一直盯着日志"，它在后台看着，我中途照样能问别的。这对 SRE 做线上生产环境的日志巡检很重要；
- subagent 整台机器最多 8 个（还在调整参数），跑测试的 subagent 可以单独限流，默认最多 2 个；
- shell 和 monitor 交给一个 Rust 写的小 daemon 托管，针对 monitor 还做一个小优化，重复输出不会去反复通知 agent；

是的，我知道这些在 Claude Code 里都能做得很好。但我不想把额度浪费在这种事上，便宜的模型也足够了。

我一般跟主 agent 把方案聊清楚，写代码交给跑便宜模型的 subagent。主 agent 的上下文只留给目标。

虽然用着用着感觉想修正优化的东西还有很多，不过现在可以先发布一轮，欢迎大家来给些意见：

`pi install npm:pi-famulus`

10｜BalanceRoute为MoE路由提速

来源（X） · @jiqizhixin · 2026-10-25 12:36

中文译文

你往推理集群中加了更多GPU。吞吐量应该随之提升——但它增长得越来越慢。在MoE模型服务中（DeepSeek等），多个计算组并行处理请求。每个组处理自己的请求，但每个解码步骤都需要跨组通信。解码是一场同步行进：最忙的组决定节奏，所有更快的组都只能闲着。更糟糕的是，即使请求数量相同，每个组的实际计算负载也不同——所以负载较轻的组会提前完成并等待，一步接一步，默默地吃掉了扩展规模的收益。

香港科技大学周子杰团队与华为2012实验室理论部提出了BalanceRoute，已被NeurIPS 2026接收（ArXiv 2605.06113）。

BalanceRoute首先将问题形式化：它对分布式解码中的同步等待进行数学建模，然后将短期负载预测转化为在线路由决策——将每个到达的请求分配给未来闲置时间最小的组，而不仅仅是最短当前队列长度。在96 GPU的主实验中，BalanceRoute-H配合真实预测器，将解码吞吐量提升了约15%（相比最强基线）。该方法已经部署在双方共建的MaaS推理系统MathBot-Pie中。代码已开源。

结果：BalanceRoute对分布式MoE解码中的同步等待瓶颈进行建模，将负载预测转化为在线路由——在96 GPU上相比最强基线获得约15%的解码吞吐量提升，已部署于MathBot-Pie——来自港科大与华为2012实验室，NeurIPS 2026，代码开源。

BalanceRoute：分布式MoE推理的负载感知路由

原文

You add more GPUs to the inference cluster. Throughput should scale — but it grows slower and slower. In MoE model serving (DeepSeek and others), multiple compute groups process requests in parallel. Each group handles its own requests, yet every decoding step requires cross-group communication. Decoding is a synchronized march: whichever group is busiest sets the pace, and all faster groups sit idle. Worse, even with identical request counts, the actual compute load per group differs — so lighter groups finish early and wait, step after step, silently eating the gains of scale.

HKUST's Zhou Zijie team and Huawei 2012 Labs Theory Division present BalanceRoute, accepted at NeurIPS 2026 (ArXiv 2605.06113).

BalanceRoute first formalizes the problem: it mathematically models the synchronous waiting in distributed decoding, then converts short-term load prediction into an online routing decision — assigning each incoming request to the group that minimizes future idle time, not just current queue length. In the 96-GPU main experiment, BalanceRoute-H with a real predictor improves decoding throughput by approximately 15% over the strongest baseline. The method has already been deployed in the jointly built MaaS inference system MathBot-Pie. Code is open source.

Result: BalanceRoute models the synchronized-wait bottleneck in distributed MoE decoding and turns load prediction into online routing — ~15% decoding throughput gain over the strongest baseline on 96 GPUs, already deployed in MathBot-Pie — from HKUST and Huawei 2012 Labs at NeurIPS 2026, with open code.

BalanceRoute: Load-Aware Routing for Distributed MoE Inference
