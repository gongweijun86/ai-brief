03｜GitLab 未登录RCE波及12年版本

来源（X） · @dotey · 2026-10-22 04:57

GitLab 六周内第三个满分漏洞：不用登录就能控制服务器，2014 年以来的自建版本都要升级

如果你们公司装了 GitLab，得赶紧升级了。10 月 21 日，GitLab 修复了一个满分 10 分的漏洞：在某些条件下，外人不用登录，就能在服务器上运行任意程序。2014 年的 7.0 版到现在，所有自建版本都受影响，10 月 12 日刚打过补丁的也在内。

这是 GitLab 六周里修的第三个满分漏洞，第一个已经被黑客用来攻击。

GitLab 是管代码的平台，很多公司把它装在自己的服务器上，全部源代码、部署用的密钥、自动打包上线的流程都在里面。服务器被人控制，对方就能翻看所有代码、取走密钥，或者悄悄改代码埋后门。

【六周里的三个满分漏洞】

9 月 10 日，GitLab 修了第一个：不用登录就能读取服务器上的任意文件。安全公司 watchTowr 和 Rapid7 发现有人在用它攻击，watchTowr 说可能泄露密码和密钥。美国网络安全机构 CISA 第二天把它列为“已被利用”，要求联邦机构三天内修好。

后两个满分漏洞都出在正则表达式引擎里。正则表达式是描述文本规律的公式，比如“找出所有 11 位手机号”，GitLab 用 Ruby 语言自带的引擎把这种公式翻译成程序。

研究者 joaxcar 一个月里在这个引擎上找出四个能远程运行程序的漏洞：9 月 23 日修了两个，要先登录，9.9 分；10 月 12 日修了一个，不用登录，10 分；第四个就是这次的，也是 10 分。

前三个只影响 19.2 以后的版本。这次的问题是翻译公式时有个数字超出上限，像里程表跑满一样归零（整数溢出），攻击者能借这个错位把自己的指令塞进服务器。GitLab 每个版本都带着这个引擎，所以十二年的版本都跑不掉。10 月 12 日补到的 19.2.8、19.3.5、19.4.2 也照样中招。

【我要不要管，升到哪个版本】

用 http://GitLab.com 网站的不用管，官方说已经修好；GitLab 代管的专属版 GitLab Dedicated 也已修复。要动手的是自己装 GitLab 的公司和个人。

19.5 升到 19.5.1，19.4 升到 19.4.3，19.3 升到 19.3.6，19.2 升到 19.2.9，19.1 升到 19.1.9，19.0 升到 19.0.10。18.11 及更老的版本，统一升到 18.11.13。

GitLab 平时只给最近三个月度版本打补丁，这次破例多补了四条老版本线。版本很老的不能一步跳到 18.11.13，要按规定经过几个中间版本，官方工具能算出要停哪几站：https://gitlab-com.gitlab.io/support/toolbox/upgrade-path/

19.4.3 和 19.3.6 升级时要改数据库，只有一台服务器的会停机一段时间。多台服务器的可以按官方的零停机流程升级。

【这次的被利用了吗】

GitLab 公告没提。The Hacker News 报道说，GitLab 表示没发现被用于攻击的迹象。CISA 10 月 21 日更新的“已被利用漏洞”目录里也没有它。

“某些条件”具体是什么，官方没说，管理员没法靠检查配置排除自己。官方也没给临时缓解办法，升级是唯一确定有效的做法。GitLab 另外发了两条检测规则，管理员可以用来翻日志，看有没有人试过攻击。

GitLab 公告：https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/

原文：https://thehackernews.com/2026/10/critical-gitlab-flaw-cvss-100-could.html

04｜eMudhra 弱私钥证书被浏览器拉黑

来源（X） · @dotey · 2026-10-22 01:29

印度发证机构 eMudhra 8 枚“网站公章”密码小于 256，谁拿到都能冒充任何网站；浏览器已堵上，App 和设备要等更新

你在手机上登录银行、购物网站，地址栏会有一把小锁。这把锁保证你连上的真是这家银行，没有人半路冒充。哪怕连的是咖啡馆里来路不明的 Wi-Fi，有这把锁，别人也看不到、改不了你输入的密码。

小锁的原理像查身份证。网站会出示一张“网络身份证”（行业里叫证书），上面盖着发证机构的章。你的手机和电脑里存着一份可信发证机构的名单，章对得上，锁就亮。

这次出事的是印度发证机构 eMudhra。它有 8 枚章被主流浏览器和系统认可，盖章靠的是一串保密的数字（私钥），本该是 100 多位的随机数，没人猜得到。Mozilla 工程师 Dennis Jackson 说，这 8 串数字都小于 256。安全研究员 Scott Helme 举的例子是 4、56、115，他说不到一秒就算出来了。

Cloudflare 说，拿到这些章的人能给任何网站做假身份证。比如在公共 Wi-Fi 上假扮你的银行，小锁照样亮着，你输的密码、看的内容都可能被截走或篡改。

【为什么影响大】

这些弱密码 2025 年 4 月就生成了，直到 2026 年 10 月 17 日才被研究者 Wayne 发现，挂了一年半，谁都能算。Mozilla 说已有多人各自算出了这些密码，有人还公开了。

浏览器好办。Jackson 的网站显示，Chrome、Firefox 当天就拉黑了这些章，Apple 19 日、Microsoft 20 日跟进，大多在后台自动生效。Jackson 说主流浏览器只认在公开账本上登记过的证书，账本里查不到这些章盖过东西，所以过去用浏览器的人不会中招。

麻烦在浏览器之外。手机 App、公司服务器、路由器、各种联网设备，很多自带一份名单，要等软件更新才会拉黑，老设备可能永远等不到。它们大多也不查那个公开账本，Jackson 说不知道这一年半里它们有没有被攻击过。Cloudflare 说，浏览器只用改一个程序，Cloudflare 自己要改几百个。

eMudhra 回应说，是生成密钥的脚本出错，员工又误用了弱的那套，10 月 18 日已作废这 8 枚章。

【要做什么】

普通人：把浏览器、手机和电脑系统、常用 App 都更新到最新。用 Cloudflare WARP 或 1.1.1.1 App 的，Cloudflare 已发新版，记得升级。

开发者和站长：Cloudflare 提醒，程序里核对证书的可能是网络库、编程语言或操作系统，光升级 SDK 不够，要一路更新到底，再重启服务。更新后如果冒出证书报错，Cloudflare 说别靠关掉证书检查来解决，关掉了，小锁就没用了。

Jackson 做了个自查网站，能测浏览器和程序还认不认这些章，也列了各软件的修复版本：https://emudhra.we-have-a-problem.com/

原文：https://blog.cloudflare.com/emudhra-certificate-compromise/

05｜Cloudflare 全事务检测拦截攻击

来源（X） · @mylifcc · 2026-10-22 05:00

Cloudflare 官方刚刚发布的一篇核弹级安全警报与技术复盘。核心事件是今天（2026年10月21日）刚刚公开披露的 PHP 史诗级底层漏洞——php2shell（编号 CVE-2026-109618 和 CVE-2026-109619）。

4 个最关键的信息点：
• 波及面极广、危害极大（“PHP 界的 Log4Shell”级别）
• 谁发现的？ 由 OpenAI、Wiz、http://Calif.io 和 Quarkslab 联合发现并披露。
• 影响谁？ 影响全球所有运行 PHP 5.4 及以上版本 的 Web 服务器（全球近 70% 的网站都在用 PHP，包括 WordPress、Magento 等底层）。
• 有什么后果？ 攻击者只需发送特殊构造的 HTTP 请求，就能触发 远程代码执行（RCE，直接拿服务器 Shell 权限）、敏感数据泄露 或 拒绝服务（DoS）。而且因为这是 PHP 运行时（Runtime）底层的漏洞，只更新网站代码或 WordPress 插件完全没用，必须升级底层 PHP 版本！
• 技术原理：内存“异常中断”引发的连环车祸
• CVE-2026-109618（未初始化内存使用）： 攻击者发超大/特殊请求把 PHP 内存撑爆（OOM），导致请求处理在一半时被迫中断。PHP 在清理现场时，把还没初始化完的半成品数据当成合法数据去执行，直接被黑客注入代码。
• CVE-2026-109619（释放后重用 / UAF）： 致命错误（Fatal Error）打断请求后，内存虽然释放了，但 PHP 进程还留着指向那块内存的“过期指针”。等下一个正常请求进来复用这个 PHP 进程时，顺着旧指针读到了脏数据，直接导致其他用户的敏感数据泄露或被攻击。
• 真实暗战：漏洞在正式公开前就已经泄漏并遭黑客狂轰滥炸
• 在官方正式解禁前，这个漏洞就已经在暗中泄漏。Cloudflare 监控到了大量在野攻击流量，甚至亲眼目睹黑客在实时变异 Payload（攻击载荷），试图绕过防火墙规则。
• Cloudflare 提前 9 小时 紧急为所有用户（包括 Free 免费版用户）默认上线了 WAF 拦截规则。
• Cloudflare 的大招：首发“全事务检测（Full Transaction Detection）”
• 以前 WAF 防火墙只看“进来的请求（Request）”长什么样，但 php2shell 靠超大请求或异常触发，单看请求很容易误杀正常业务。
• Cloudflare 为此首次推出了 Full Transaction Detection（全事务检测）：同时结合进来的请求信号 + 源站返回的响应（Response）信号。如果发现源站响应里出现了被攻破或内存泄露的特征，WAF 会在响应返回给黑客前的最后一秒把它拦截掐断！

06｜TiDB Cloud 控制面被窃22天

来源（X） · @AnzalAbidi · 2026-10-21 15:05

中文译文

安全领域疯狂的 72 小时。三大事件接连发生：eMudhra、PingCAP（TiDB Cloud）和 PHP。

以下是事件经过和受影响方的简要概述。

1. eMudhra（受信任 CA 泄露）

eMudhra 在 2025 年 4 月生成了 8 个中间 CA 证书（由 Sectigo 交叉签名）。他们 HSM 密钥包装测试脚本中的一个 bug 生成了第二组 P-384 密钥，其私钥是小于 256 的单字节数字。运维人员选择了错误的密钥标签，并将其签名写入了真实的 CA 证书。

其中一个中间 CA 私钥实际上是数字 4。
其余七个分别是：56、66、115、155、156、230、237。

三周后（2025 年 5 月），他们的 CRL 签名开始失败，因为 CRL 签名器使用的是真实密钥而非弱密钥。有人没有去追问密钥为何不匹配，而是将 CRL 签名器切换为使用弱密钥，然后关闭了工单。

• 浏览器安全：Chrome、Firefox、Apple 和 Microsoft 已经阻止了它们，且零个伪造证书进入了 CT 日志。
• 服务器不安全：curl、Python（certifi）、Go 二进制文件和 Docker 基础镜像不检查 CRL。请更新 ca-certificates、certifi 和 Go（1.27.3 / 1.26.10）。
• 10 秒即可在任何服务器上完成检查：
curl https://dv-g3b-emudhra.we-have-a-problem.com/
（TLS 错误 = 安全。200 OK = 仍然存在风险。）

2. PingCAP / TiDB Cloud（10.6 TB 数据泄露）

攻击者在 PingCAP 自己的仓库中发现了已提交的 GCP 和 Azure 凭据。他们搭建了一个 TiDB Cloud 生产控制平面的复制流，连续 22 天每 6 小时导出一次完整数据库。共 88 次完整导出，零次告警。200 GB 数据已经在种子网络上流传。

除了 413 个私有仓库和从其 Web SQL Editor 记录的 2060 万条客户 SQL 查询外，PingCAP 工程师还将客户机密信息直接粘贴到了 Jira 工单中。

泄露记录中受影响的方：

• 支持工单中暴露的实时凭据：
- Pinterest：其 pingcap-logs S3 存储桶的 AWS 密钥
- CardX / Silverlake（NPCI 关联环境）：备份日志中的 AWS 管理员密钥，拥有对 258 个外部 S3 存储桶的完全访问权限
- DeBank：38 个预签名 S3 URL
• 一个未具名的 AI/开发平台：一个工单中附带了 314 MB 的慢查询日志，其中包含 8,027 个客户实时机密（一个 AWS 根密钥、一个覆盖 1,701 个仓库的 GitHub 管理员 PAT、7,485 个 AWS STS 令牌，以及 192 个 OpenAI/Anthropic/Gemini 密钥）

• 基础设施元数据、VPC CIDR、应用服务器 IP 或合同定价被暴露的租户：
- 科技：Atlassian、Databricks、Airbnb、百度、LINE、Nylas、Persona、PatSnap
- 电商与旅行：http://Booking.com、Shopee、Flipkart、Mercari、ZOZO、AEON、Delhivery、Klook
- 游戏：Capcom、Square Enix、Konami、Bandai Namco、Cygames、Colopl、DMM
- 金融：PayPay、SoftBank、SBI、SB Payment Service、富士通、TOPPAN、中国银行、中国人寿
- 加密货币：Bitget（称其上仅有公开交易日志且他们已经离开）、Pionex、DigiPlus、NFTscan、Chainbase

• 开发者档案泄露（来自 PingCAP BigQuery 中一张购买的 http://reo.dev 数据表）：
- 来自腾讯（3,327）、华为（2,726）、字节跳动（2,475）、AIG（2,140）、万事达卡、Flipkart 和 bKash 的工程师的 24,900 个个人邮箱 + GitHub/LinkedIn 档案。

如果你使用 TiDB Cloud：请轮换你的控制台 API 密钥、数据库密码，以及你曾经粘贴到支持工单中的任何内容。

3. PHP "PHP2Shell"（CVE-2026-109618 和 CVE-2026-109619）

两个 CVSS 9.2 的预认证 RCE 在今天 UTC 14:00 补丁发布之前被泄露。

公开分析将其追溯到 PHP 原生 C 语言 multipart/form-data 会话上传进度处理器（ext/session/session.c）中的一个堆 Use-After-Free 漏洞。

由于 C 层面的 multipart 解析在 index.php 第 1 行之前运行：
• 应用认证、Laravel/WordPress 中间件以及 file_uploads = Off 都无法阻止它。
• 今天只有 PHP 8.2–8.5 获得官方补丁（Shodan 上 59% 的 PHP 服务器运行在已 EOL 的 ≤ 8.1 上）。
• 在你修补 php-fpm 之前：请锁定 php_admin_flag[session.upload_progress.enabled] = off，并在 Nginx/Apache/Cloudflare 层面阻止意外的 multipart 请求。

Crazy 72 hours in security. Three major incidents dropped back-to-back: eMudhra, PingCAP (TiDB Cloud), and PHP.

Here is the short version of what happened and who got hit.

1. eMudhra (Trusted CA compromise)

eMudhra generated 8 intermediate CA certificates in April 2025 (cross-signed by Sectigo). A bug in their HSM key-wrapping test script created a second set of P-384 keys where the private keys were single-byte numbers under 256. Operators picked the wrong key labels and signed them into real CA certs.

One of the intermediate CA private keys was literally the number 4.
The other seven: 56, 66, 115, 155, 156, 230, 237.

Three weeks later (May 2025), their CRL signatures started failing because the CRL signer was using the real keys instead of the weak ones. Instead of asking why the keys didn't match, someone switched the CRL signer to the weak keys and closed the ticket.

• Browsers are safe: Chrome, Firefox, Apple, and Microsoft already blocked them, and zero rogue certs hit CT logs.
• Servers are not: curl, Python (certifi), Go binaries, and Docker base images don't check CRLs. Update ca-certificates, certifi, and Go (1.27.3 / 1.26.10).
• 10-second check on any server:
curl https://dv-g3b-emudhra.we-have-a-problem.com/
(TLS error = safe. 200 OK = still vulnerable.)

2. PingCAP / TiDB Cloud (10.6 TB breach)

Attackers found GCP and Azure credentials committed inside PingCAP's own repos. They set up a replication feed of TiDB Cloud's production control plane and exported the entire database every 6 hours for 22 straight days. 88 full exports, zero alerts. 200 GB is already out on torrents.

Beyond the 413 private repos and 20.6M customer SQL queries logged from their web SQL Editor, PingCAP engineers were pasting customer secrets into Jira tickets.

- Gaming: Capcom, Square Enix, Konami, Bandai Namco, Cygames, Colopl, DMM
