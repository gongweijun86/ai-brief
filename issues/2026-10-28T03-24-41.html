01｜AI辅助设计强调全局约束与克制减法

来源（X） · @yanliudreamer · 2026-10-28 07:44

多看看英区文章，打破信息茧房💪

这篇“如何用AI设计”狠狠共鸣了！
1️⃣始终从全局出发，而不是局部修补。
先梳理所有约束条件，再探索能够同时满足这些条件的解决方案，必要时重新审视和调整约束。如果跳过这一步，设计很容易沦为被动修补问题，最终拼凑出一个缺乏整体性的产品。

2️⃣学会做减法
AI Agent 总喜欢添加多余的文案，分割线和图标。对于每一个设计元素，都要反问自己：它真的有存在的必要吗？

3️⃣在设计工具中迭代，而不是直接在代码里打磨。
使用能够精细控制设计的工具，一次生成 3–4 个不同方案进行比较。避免陷入原型引力Prototype Gravity，因为已经在真实代码库中投入了大量精力，就不自觉地沿着现有方案不断优化，而忽略了其他可能性。

4️⃣用组件和设计系统保持一致性。
充分利用现有组件库和设计系统，确保整个产品在视觉和交互上保持统一，而不是每个地方都重新造轮子，最终形成拼凑感。

5️⃣借鉴成熟的 UX，用自己的审美做判断。
参考同类产品中已经被验证的交互模式，不必重新解决别人早已解决的问题。在此基础上不断探索自己的审美偏好，观察并反思自己对不同方案的直觉反应，持续迭代，直到设计真正让自己满意。

好的 AI 辅助设计，不是让 Agent 不断生成更多东西，而是通过全局思考、主动做减法、探索多个方案，以及持续训练审美判断力，让设计变得更完整、更克制、更有一致性。

02｜温度0仍非确定需分层排查

来源（X） · @king1818888 · 2026-10-28 10:08

最近看到一份很硬核的《2026 AI 工程面试 100 题》，非常有启发。

它完全不考“什么是注意力机制”这类死记硬背的八股文，每一道题都是从线上最真实的工程事故切入。

排在第一道（Q1）的场景，几乎每一个做过大模型上线的团队都被业务方拷问过：

“你的客服助手明明以 temperature = 0 运行，但同一张工单在不同日子却得到了不同的回答。PM 认为这是 Bug，要求你必须修复。你如何排查？又能向他们承诺什么？”

很多刚接触大模型的工程师面对这个问题，第一反应容易是心虚：“这是偶然 Bug，我保证调回去让它回答一模一样。”——但这恰恰暴露了对底层工业级系统的缺乏经验。

资深 AI 工程师会从两个层面给出毫无破绽的回答：

一、如何排查？（区分“假随机”与“真随机”）

1. 排查“伪不确定性”（Prompt 真的完全一样吗？）：
• 系统提示词里是否暗中注入了动态当前时间？
• RAG 检索返回的 chunk 顺序、时间戳或相似度得分是否发生了微小漂移？
• 多轮对话的历史裁剪（Truncation）逻辑在不同会话中是否一致？
• 工具调用的 Schema 注册顺序在不同实例启动时是否有差异？

2. 排查底层“真不确定性”（为什么 temp=0 依然不能保证 100% 一致？）：
• 浮点数的非结合律：GPU 并行计算时，(a+b)+c 与 a+(b+c) 在底层存在微小的浮点舍入误差。线上高并发服务为了吞吐都会开动态批处理（Dynamic Batching），同一个请求在不同的 Batch 组合、不同的线程块调度下，输出的 Logits 会有极轻微的扰动。当两个词的概率极其接近时，就会触发不同的分支；
• 集群硬件与路由漂移：商业 API 背后是由成千上万张不同架构的 GPU（A100、H100）构成的集群。路由到不同机房、底层推测解码（Speculative Decoding）或算子版本的微小升级，都会破坏字对字的一致性。

二、你能向 PM 承诺什么？

工业级架构师的思维，永远是把“含糊的安抚”升级为“可衡量的确定性约定”：

1. 承诺“决策稳定性”，而非“措辞一致性”：
明确告诉 PM：大模型作为生成系统，天生无法承诺跨硬件、跨并发环境下的字对字完全一致。但我们承诺“核心业务逻辑的一致性”——退款就是退款，拒绝就是拒绝，理由核心要点一致。

2. 关键业务路径做确定性收敛：
不要指望模型在自由文本里算账或做最终审批。涉及订单金额、退款权限等关键动作，强制使用 JSON 严格模式（Structured Outputs），并交由下游确定性代码做业务规则校验。

3. 建立基准测试与 SLO 指标：
拉出一套包含 1,000 张典型历史工单的 Golden Benchmark。向团队承诺明确的稳定性指标（例如：“在基准测试集上，核心业务决策的一致性达到 99.8%”），并在 CI/CD 中作为上线拦截门禁。

如果把这 100 道题通读一遍，你会发现一个贯穿始终的准则：
优秀的 AI 工程师从不指望模型完美，而是在充满非确定性的生成模型外，包裹上一层绝对确定性的工程防御层。

这 100 道题涵盖了 Prompt 工程、RAG 检索、Grounding 评测、Agent 可靠性、微调选型、推理性能、系统设计和安全成本等 8 大核心领域。

接下来我会把每个板块挑出最具代表性的生产事故题做逐一拆解。对工业级 AI 落地感兴趣的朋友可以先点个关注。

04｜Anthropic多智能体待解四大难题

来源（X） · @dotey · 2026-10-28 07:49

Anthropic 平台工程负责人 Katelyn Lesse：上千个 AI 智能体一起干活，还缺程序员解决四个难题

AI 越来越会写代码，很多程序员开始怀疑自己的手艺还值不值钱。Anthropic 平台工程负责人 Katelyn Lesse 10 月 25 日发文说，她看到的情况正相反：接下来一两年，AI 想做成大事，得先靠程序员解决一批新问题。她说，现在是当工程师最有意思的时候之一。

Lesse 在 Anthropic 负责平台工程，据她接受 Kleiner Perkins 访谈时的介绍，团队约 200 人。她此前在 Stripe 和 Betterment 带过工程团队。这篇文章发在她的个人博客和 X 上，X 上阅读量约 61 万。

【这些问题从哪来】

AI 智能体，就是能自己调用工具、一步步完成任务的 AI 程序。Lesse 说，它最早只是聊天框，人盯着一问一答；后来模型能独立干更久、更难的活，开始搬到云端运行；再往后出现了多智能体系统：一个总管 AI 把任务拆开，分给一批助手去做，还有的 AI 专门负责打分、提建议。

她说，现在已经有人在搭由成千上万个智能体组成、连续工作不停的系统，用来做科研、新发现和硬件设计。规模一上来，就冒出了四类新问题。

【难题一：服务器怎么安排】

现在大部分软件跑在 Kubernetes 上，这是一套给服务器排班的系统，擅长管“一模一样的副本，哪个挂了换一个顶上”。Lesse 说智能体正好相反：每个都是独一份，记着自己干到哪了；大量时间在等模型回话、等工具、等别的智能体或等人回复，闲多久说不准，忙起来又可能一下冒出几千个。

Google 上个月开源的 Agent Substrate 就是冲这个问题做的。据 Google 官方博客，它能让闲着的智能体休眠、把资源腾出来，需要时半秒内唤醒。Lesse 说这块还有大量问题没解决。

【难题二：谁在干活，能干什么】

很多智能体用的是人的账号和权限，系统得分清某个操作是人做的，还是 AI 替人做的。更难的是授权：一个系统替你连干几周，你怎么事先讲清它能做什么、不能做什么？智能体之间互相派活时，一个智能体凭什么相信另一个？Lesse 说，确认身份可以借用现成技术，比如用很快过期的临时凭证代替长期有效的密钥；授权这块基本还是空白。

【难题三：一个被骗，全队遭殃】

Lesse 说，最近几个月，尤其最近几周，软件漏洞冒出来的速度超过了业界修补的速度，很多出在大量系统依赖的核心软件里。本月 PHP、GitLab、Node.js 就接连发布了严重漏洞的修复。上千个智能体跑在这些软件上，还要写来路不明的代码、读来路不明的网页，没修好的漏洞就危险得多。

多智能体还多一层风险：一个智能体被网页里藏的恶意指令骗了，可能把指令转给同伴，甚至写进共享记忆，让后来的智能体也照做。她的建议是让每个智能体在严格隔离的“沙箱”里干活，好比实验室把每份样本放进独立的密封箱，一个出事不会传染整屋。

【难题四：跑偏了要能叫停】

系统得记下每个智能体做了什么，而且任何智能体都改不了自己或别人的记录。还得有一个总闸，监控一发现问题，就能把整个系统一次停下，收回所有权限。Lesse 说最难的是判断系统有没有跑偏：一个智能体反复尝试访问不在白名单里的网站，可能是在搞破坏，也可能只是太想把任务做完。

文章最后，Lesse 对正在焦虑的工程师说，这些领域大多还没有现成答案，值得钻进去学、形成自己的判断。

08｜Open Code Review开源

阿里巴巴开源了内部使用两年的 AI 代码审查工具 Open Code Review。

据项目介绍，这套工具曾供数万名开发者使用，累计发现数百万个缺陷。它支持检查 Git Diff、定位具体代码行，还内置了空指针、线程安全、XSS、SQL 注入等问题的检测规则。

具体效果仍需结合实际项目验证。

10｜多Agent任务控制在小时粒度更稳

来源（X） · @Stephan_Talk · 2026-10-28 10:52

分享下我在多 Agent 管理时的一点经验：

1. 不要把任务切分的太细，重点放在设计和验收

正如宝玉老师所说，管多 Agent 正如管人一样。新的技术管理者最容易陷入的误区就是事无巨细的管，导致自己最容易成为瓶颈

管 Agent 也是，如果每个 Agent 的执行粒度是几分钟的话，很快人的脑袋就晕了，上下文切不过来，也容易管出问题

我目前体会是每个任务控制在小时粒度（长的话有几小时的）是最舒服的，这就需要设计阶段多花些时间和 Agent 调研和讨论，形成文档化的共识后让它去慢慢跑。与此同时我再切到下一个 Agent 讨论和布置任务

2. 验收要落在实处，“多少测试用例绿了” 不能说明任何问题

Agent 在跑长程任务后很容易跑出几十上百个单元测试，这些不是质量证据，甚至不能说明 spec 的遵从度。只有从设计角度出发，写一套符合需求的端到端验证，拿到验证证据才算数

这方面特别推荐使用 pstack 的以下两个元技能（用来创建skill的skill）：
/create-verification-skill
/create-formal-verification-skill

第一个能帮你创建一个 e2e 测试的基础设施、以及当前项目的功能地图，根据功能地图进行真实的e2e测试：

https://x.com/i/grok/share/80ddfc71cee84f488488e2373dcf754d

第二个是对第一个测不到的地方的补充，比如无法枚举的测试、并发竞态条件等，用形式化验证来做数学证明，确保复杂状态的正确性

相对应的 lauren 还提供了两个维护更新这两个skill的元skill，简单说就是项目功能在不断迭代过程中，验证类的skill也要随项目不断更新才行

3. 与多 Agent 的沟通方式：不要打乱自己的节奏

刚开始管理多 Agent 的时候，我开很多窗口，一有 Agent 完成任务了我就切过去看，很快证明这样马上就会乱成一坨

多 Agent 管理必然是异步沟通的方式，这有点像是 CPU 的时间片切换，不应该一有消息就马上切，而是 Agent 异步通知 → 我看到通知了 → 等我把手头的一个检查点工作做完 → 再切过去接收

Agent 永远是在挂起等我反馈，而我只有做完当前“线程”的阶段性事务才会切我的注意力过去

目前我的窗口极限大概就3-4个，这和当前 AI 的长程能力也息息相关（如果未来Agent可以按天高质量交付了，这个窗口数就能扩大）

4. 反模式：单任务不要过大

按照当前的前沿模型能力，我认为单任务最长控制在小时级别是合适的，到天级别很容易跑歪

之前我跑了一个几天的长程任务，跑完发现一堆问题，最后还是不得不全部回滚了

这还是上面说到的原因：当前最前沿模型的能力，我的感觉还到不了天级别

上下文窗口、幻觉、自动压缩、指令遵从性等等，会让 Agent 在长程任务上的问题会逐渐放大到不可控

14｜ETH仅将指数时间压缩为次指数

来源（X） · @MrRyanChi · 2026-10-27 19:08

很多人看到 OpenAI 刚刚用 AI 证伪了指数时间假设（ETH）

所以，OpenAI要毁灭人类现有的社会秩序了吗？未来是不是 Token 够多，我们就能解决任何问题了？

今天这篇炒的很热的 @OpenAI 的ETH解法论文，普遍大众认知似乎是

1 - PNP问题解决了，所以AI 解决一切万物的时代到来了
2 - 大加速时代来了，万物的解决方案都可以被计算了

仔细花了一个小时细读研究，发现其实并没有大家想的那么夸张。这里简单解释下几个关键概念：

----------------------------------

首先，到底什么是 P vs NP 问题？

我在 16 岁左右刚开始学习算法工程时，曾对 P vs NP 特别痴迷。因为如果它被解决，就说明宇宙万物只要使用足够的算力，就能瞬间获取答案。

简单来说，它的核心是：“可以在多项式时间内【验证】有解决方案的问题，是否等于可以在多项式时间内【获得】解决方案？”

即，可以在多项式时间内证明有解决方案的问题，是否等于可以在多项式时间内获得解决方案。

什么是多项式时间？

简而言之，任何算法都可以边简化为 o(n)，o(n^2) 等等多项式方程，n 是数据的规模，o 则可以通过 n 计算出所需要的计算时间。

换言之，如果 P = NP，则一切事物都可以被计算，相当于人类拿到了宇宙的“作弊码”。

从今往后，只要token够多：

• 我们可以瞬间反向推导，研发出治愈任何绝症的特效药。

• 研发火箭，AI 能在几秒钟内穷尽无数可能，抓出那一个完美的发射方案。

• 物流优化、AI 训练、天气预测……全部可以通过砸Token在几秒内解决

----------------------------------

但是，如果正如主流科学界认为，P ≠ NP，那么很多问题就没法在多项式时间内，而是在指数时间内完成。

什么是指数时间？

指数时间就是说 order of complexity 不是o(n^c)，而是 o(2^n)一类的形式。变量 n 每增加 1，计算量就会直接翻倍。

而存在这类指数时间，且无法转化为多项式时间的问题，就意味着有些问题就算你一直烧Token，也不知道什么时候才能获得解法。

现实中，新药研发的蛋白质折叠、保护你网银安全的 RSA 加密算法，全都是顶级的指数时间难题。就算你把全地球的算力烧干，计算机算到太阳系毁灭也拿不到答案。

一旦 P = NP 成立，指数时间问题可以通过算法工程转化为多项式时间问题，人类可以靠AI创造一切，也可以毁灭并破解一切。

----------------------------------

那么，这次的ETH问题和PNP问题的联系在哪里呢？

大家都在提的点，就是ETH问题证明了3SAT这个指数时间问题有更好的解决方案，所以似乎解决了PNP。

但实际上并不是如此。即便3SAT这个指数时间案例被证伪，PNP仍然没有解决。

为什么？因为这次的ETH问题，本质上是将 o(2^n) 指数时间，转化为了 2^{O(n/\sqrt{\log n})} 这个次指数时间，而这仍然不是多项式时间。

随着n的数量增大，order of complexity的结果仍然会爆炸式增加，只是它不是指数性，而是“次指数性”的。本质上，AI 只是把时间从“几百亿年”缩短到了（比如）“几亿年”。

当然，这也不是说这件事情本身不值得警惕。因为 AI 已经提出了一种人类未曾想到的减少指数时间的方案。

那么，随着 AI 进一步发展，很多原本被判了死刑、认为 “不可能算得更快” 的经典难题，全部重新变成了未解之谜。

也就是说，“指数时间无法成为多项式时间” 这一假设，仍然有被推翻的可能，不过，并不是现在。

就像另外一个 “ETH” 的V神 @VitalikButerin 前段时间针对 ECDSA 算法存在被 AI 攻破的可能性这件事情发表的那句话一样：

在任何数学结构上，比起“刚好只有 3 种解决方案”，“存在隐藏的第 4 种”更有可能。
