02｜Harness 论文提出组合泛化训练法

来源（X） · @Xudong07452910 · 2026-11-21 11:40

模型越来越强，Harness 迟早会被吃掉，这篇论文给了个相反的看法。

以前搭 Harness，更多是在给能力不够的模型兜底。alex zhang 他们的新论文认为，现在模型强了，Harness 的作用变成了把模型已有的能力组合起来，让它能处理更长、更复杂的任务，甚至是训练里没见过的任务。

我觉得最有意思的是这个思路：把长任务拆成很多次小调用，让每一次调用都落在模型熟悉的范围里。这样训练时就不用跑完整条很长的流程，用合成任务加模拟的工具调用和子 Agent，单独训练其中一次调用就行，省数据也省时间。

自己做 Agent 产品下来，感觉也差不多。模型升级以后，Harness 里确实有不少东西可以删掉，但怎么拆任务、怎么调度子 Agent，这些设计会更重要。

目前论文、代码和数据都开源了，做 Agent 的朋友可以去翻翻。

引用内容

alex zhang @a1zhang

中文译文

Harnesses曾经是弱LLM的拐杖。从2026年及以后，随着模型变得更加强大，harness如今提供了一种机制，通过组合LLM已有的和新的能力，实现远超其训练环境的泛化。

在我们的新论文《LM Harnesses are Compositional Generalizers》中，我们探讨了各种harness抽象如何使LM系统通过组合现有LLM能力，在任务长度、任务策略、递归任务深度等方面实现泛化。这些抽象通过使轨迹保持在局部分布内（LID）——即让每一次LLM调用都处于分布内——提供了一种更数据高效的训练手段，尤其是在长任务上。

对于需要很长时间才能展开执行的任务，这意味着我们甚至可以进行代理harness训练，也就是说，我们训练单次LLM调用，而不是进行非常长的harness展开，使用纯合成任务，配合假工具调用+子agent！

一个常见的观点是LLM将吸收harness并使其过时。我们不同意这一观点，并认为我们尚未充分探索harness所能提供的东西。

完整论文、日志、代码库和数据均可获取：https://www.alphaxiv.org/abs/2611.harness-cg

与 @SOURADIPCHAKR18 @lateinteraction 合作

原文

Harnesses used to be a crutch for weak LLMs. In 2026 and onward, with stronger models, harnesses now offer a mechanism for composing an LLM’s existing and new capabilities to generalize well beyond their training environments.

In our new paper, LM Harnesses are Compositional Generalizers, we explore how various harness abstractions enable LM systems to generalize over task length, task strategies, recursive task depth, and more through composing existing LLM capabilities. These abstractions provide a means for more data-efficient training, especially over long tasks, by keeping trajectories locally in-distribution (LID) — i.e., shaping all individual LLM calls to be in-distribution.

For tasks that take a very long time to roll out, this implies that we can even perform surrogate harness training, meaning we train an individual LLM call instead of doing the very long harness rollout, using purely synthetic tasks, with fake tool calls + sub-agents!

A common idea floating around is that LLMs will absorb harnesses and make them obsolete. We disagree, and argue that we haven’t sufficiently explored what harnesses can provide.

The full paper, logs, codebase, and data are available: https://www.alphaxiv.org/abs/2611.harness-cg

04｜Agent 写码只需部分理解靠测试兜底

来源（X） · @dotey · 2026-11-21 08:27

Sean Goedecke 在个人博客发文说，在大型软件项目里，程序员只理解自己负责的那一部分代码是正常的，而且这已经是能做到的最好状态。

确实如此，我基于原文稍微解读和引申一下。

很多人说 AI 写不好程序，因为 AI 不能完整理解代码库，但实际上在大的软件项目中，程序员只理解自己负责的一小部分代码是常态。

想象一下，新人去接手一个历史复杂项目，那么他们短时间只可能理解一部分代码，但这并不妨碍他们去维护项目。

那么以前怎么保证不理解完整代码不会改出问题呢？还得要靠自动化测试来兜底。

一个好的项目，需要配合好充分的自动化测试覆盖，这样就算新手去修改代码，也不至于把正常运行的系统搞崩溃，毕竟改出问题了自动化测试是无法通过的。

并且为了防止新人乱改，还会有 Code Review 配合，这本身也是很好的知识传承手段。

现在让 Agent 干活也是如此，让 Agent 在一个会话上下文中理解整个项目是不现实的，它永远只能部分理解项目，但这并不妨碍 Agent 去修改运行程序。

要保证 Agent 干活的质量，同样也要通过验证手段兜底，自动化测试是必须的，但也无法过度依赖，因为有些测试可能本身就是有问题的；

Code Review 现在也很难保证了，毕竟代码量太大了，人根本看不过来，只能是让 AI Review 大部分代码，人只 Review 最重要的部分。

另外一个有效手段就是让 Agent 自己提供证据，比如我最近最常用的手段就是让 Agent 截图，在开发新功能的时候让它提供新功能截图，修改 bug 的时候提供改之前和改之后的截图对比。

让 Agent 截图，最近还挖掘出来一个用法：就是让 Agent 自己去模拟 API 响应数据，动态生成各种不同场景的截图，都不需要服务端配合，虽然我还没搞明白它是怎么去模拟的。

05｜斯坦福 Agent Harness 实战作业

来源（X） · @GitHub_Daily · 2026-11-21 08:00

看了不少 Agent 教程，也跟着敲完一个能调工具的小 Demo，真要自己从头搭一个，还是不清楚循环、工具、记忆该怎么拼到一起。

斯坦福今年秋季开了一门 Engineering AI Agents 课，课号 CS329Z，第一次作业的代码放出来了，题目就是从零搭一套 Agent Harness，也就是包在模型外面负责调工具、跑循环的那层程序。

作业拿一家公司的邮件存档当素材，先写邮件优先级分类、每日摘要、关键词检索和邮件问答，再把这些接成一个能调工具、跑命令、带记忆的 Agent。

GitHub：https://github.com/cs329z/assignment1-harness

测试分两种，一种不调模型，专查空回复、格式错乱、工具报错这些异常处理。另一种真调模型打分，光分类那题就要调 60 次模型，跑一分钟左右。

最后还有一轮模拟测试，几个预设角色轮流来跟我们的 Agent 对话，看它能不能把事办成。

每次调用模型都会记账，还能自己设预算上限，循环跑飞了会先停下。

我觉得这份作业比看一堆教程管用，测试把要求写得很死，哪里没做对一跑就知道。想把 Agent 底层弄明白的，可以照着做一遍。
