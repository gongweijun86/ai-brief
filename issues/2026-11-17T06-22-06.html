03｜Agent 授权提示词校验执行权限

来源（X） · @0xChonsy · 2026-11-17 07:24

中文译文

我*了

SpaceX AI 工程师 Lauren Tan 分享了她让 agent 工作与团队决策保持一致的方法：

把下面这段粘贴到你的 agent 里，用来根据权限验证操作

提示词：

request.bind {
origin := [SLACK_THREAD]
requester := [REQUESTER]
repo := [REPO]
goal := [TASK]
acceptance := [OBSERVABLE_RESULT]
grants := [EXISTING_AUTHORIZATIONS]
paths := [PERMITTED_EDIT_PATHS]
stop_when := [LIMIT_OR_BLOCKER]
}

authority.resolve {
IDENTIFY 从授权上下文中识别 requester
READ 读取仓库规则和源线程决策
RESOLVE 解析允许的操作、目标和所需审批
CHECK 检查宿主工具和实际访问权限
KEEP 使未解决的权限保持显式

ASSERT 理解 != 授权
ASSERT 通过检查 != 发布审批
REUSE 复用现有授权而不再次请求
}

action.inspect {
verb := [PROPOSED_ACTION]
target := [FILE_SERVICE_OR_RESOURCE]
effect := [EXPECTED_STATE_CHANGE]
authority := [SUPPORTING_GRANT]
source := [REQUEST_OR_DECISION_LINK]
}

action.route {
ALLOW 当以下条件满足时：
请求者的权限覆盖该操作
目标和效果保持在范围内
所需的工具和访问权限可用
适用的审批条件已满足

CLARIFY 当以下情况时：
目标或验收标准模糊
指令相互冲突
缺失的上下文会改变正确的操作
可用的已授权来源无法解决该问题

ESCALATE 当以下情况时：
需要额外的权限或访问
敏感基础设施、数据库或部署工作缺乏审批
变更扩展为不相关的设计重构
产品或发布决策仍未解决
}

context.sync {
ASSIGN 指定一个负责的任务所有者
ATTACH 附加线程链接、仓库约束和验收检查
COORDINATE 在并行编辑前协调共享文件
REFRESH 当团队反馈改变任务时更新简报
RETAIN 保留支持每次范围变更的消息
REASSESS 重新评估受修订需求影响的检查
}

worker.cycle {
PIN baseline.commit
PIN baseline.worktree_diff
SAVE 保存复现输入、环境设置和预期结果
PRESERVE 保留不相关的变更和回滚路径

READ 阅读相关实现
TRACE 追踪调用和数据流
SEPARATE 将观察与假设分开
REPRODUCE 在选择修正方案前先复现
PATCH 打上一个逻辑上内聚的补丁
RUN 运行实际应用
REPLAY 重放受影响的场景
INSPECT 检查输出、错误和产生的状态

ON 不匹配 -> 诊断原因 -> 修正 -> 重放
ON 缺少前置条件 -> 记录阻碍因素和下一步操作
ON 命中停止条件 -> 停止并返回收集到的证据

CLEAN 只清理本次运行创建的资源
KEEP 保留证据产物
}

proof.match {
build -> 编译器和构建输出
behavior -> 执行的用户路径和观察到的结果
performance -> 等效的基线和候选配置文件
quality -> 类型、lint、依赖检查和相关测试
intended_flow -> 状态图与实际执行行为的对比
acceptance -> 团队针对所请求的产品结果进行评审

CONTROL 控制配置文件构建、输入、工作负载和缓存状态
CAPTURE 为交互和时序变化录制记录或追踪
USE 使用截图记录可见状态

ASSERT 导入分析建立的是边界，而非执行时间
ASSERT 录制覆盖了所演示的场景
ASSERT 测试建立的是实际被检查的属性
ASSERT 技能需要可用的工具和正常工作的流程
}

check.record {
requirement := [ACCEPTANCE_ITEM]
commit := [TESTED_COMMIT]
worktree := [TESTED_DIFF]
environment := [BUILD_AND_REQUIRED_STATE]
execution := [COMMAND_OR_ACTIONS]
expected := [REQUIRED_OBSERVATION]
observed := [ACTUAL_RESULT]
exit_code := [VALUE_IF_APPLICABLE]
artifacts := [EVIDENCE_PATHS]
status := PASS | FAIL | NOT_RUN
blocker := [MISSING_PREREQUISITE_IF_ANY]
}

result.route {
PASS -> 保留当前证据并准备所需的评审
FAIL -> 修正已证实的原因并重新运行受影响的检查
NOT_RUN -> 说明前置条件、责任人和下一步操作

ON 代码或环境变更时：
REASSESS 重新评估先前的证据
RERUN 重新运行假设或依赖项已变更的检查

ASSERT evidence.commit == returned.commit
ASSERT evidence.worktree == returned.worktree
}

repository.maintain {
FIND 找出重复的修正和过时的实现示例
ENCODE 将稳定需求编码到 API 或自动化检查中
MAKE 让诊断信息能识别违规行为和支持的恢复方式
VERIFY 验证该约束能捕获原始失败
VERIFY 验证允许的行为仍然成功
MIGRATE 迁移过时的示例
PRESERVE 保留有用的设计理由
AVOID 避免由宽泛的模型批评驱动的不相关重构
}

return to_thread {
revision := 已测试的提交和工作区状态
change := 内聚的 diff 或 PR
checks := 各项结果和执行记录
artifacts := 截图、录制、日志和追踪
limits := 未覆盖的用例、阻碍因素和不确定性
decisions := 未解决的产品或发布问题
next_action := 责任人和所需的操作

RETURN 将结果返回到原始线程
SEND 仅在该操作被授权时发送消息
FOLLOW 遵循仓库的评审和合并策略
}

autonomy.expand {
REQUIRE 在更广泛的委派前要求可重复的验证
DEFINE 定义权限、隔离和停止条件
KEEP 保留决策日志和回滚选项
EXPAND 仅在批准的权限范围内扩展
}

04｜EvoX Harness 适配因模型而异

来源（X） · @Xudong07452910 · 2026-11-17 11:34

六套 Agent Harness 的整体评测，第一名和第二名只差 0.3 个百分点。可一旦按底层模型拆开，几乎每个模型的第一名都不一样

EvoMap 的新论文《EvoX》讨论的就是这件事：Harness 和模型合不合得来，可能比 Harness 的整体排名更重要。

论文提出「The Second Policy」，把 Harness 看成 Agent 的第二套策略。模型负责理解任务、规划行动，Harness 负责把决策落地，包括修正工具调用、执行中断后接着跑、核验结果是否真的完成。

团队用自建的评测框架 Contrast，在 6 个模型、6 种 Harness、5 个 Benchmark 上统一测了一遍。整体成功率 EvoX 56.2%，Pi 55.9%，几乎打平。

拆到单个模型就很分散了。Opus 5 上 Claude Code 第一，GPT-6 Astra 上 Codex 第一，Sonnet 5 上 Pi 第一，DeepSeek 上 Hermes 第一。EvoX 在 GLM-5.3 和 Kimi K3 上领先最明显，比其他五种 Harness 的平均值分别高 10.7 和 7.9 个百分点。

对于 Harness Engineering 来说，关注模型与运行时策略之间的适配是非常重要的。

单独评估模型或 Harness 的平均表现，可能都会遗漏重要信息。真正值得研究的是，不同模型究竟需要什么样的执行策略，以及能否根据模型特性动态调整 Harness。

📎 arXiv: https://arxiv.org/abs/2611.15006

05｜Agent 用执行 Trace 回放排障

来源（X） · @zcswl7961 · 2026-11-16 15:03

给刚接手 Agent 项目的同学一句实在话：先记执行过程，别急着换框架。

听一个做平台化 Agent 的朋友说，他们接手第一版时，出问题只能翻聊天记录，谁在第几步改了分区口径、哪次工具结果被截断，全靠当事人回忆。

后来只加了一层最笨的东西：每次工具调用记下关键输入、返回结果和当时的口径版本，Trace 能按任务回放到那一步。就这一层，排查时间从一整晚缩到一顿饭的工夫。

“换框架解决的是它会不会跑，回放解决的是它为什么停。”

框架半年一换，执行过程这层记录却一直要留在自己的系统里。模型给的答案是概率的，账得是确定的。

你们现在能回放一次失败的任务，还是只能重跑一遍碰运气？

06｜Code-Graph-RAG 图谱查代码

来源（X） · @bkdgiffug · 2026-11-16 23:50

维护大型代码库时，最头疼的往往不是写代码，而是理清代码之间的关系：函数被谁调用、模块如何关联、改一处会影响哪些地方。

GitHub 上的 Code-Graph-RAG 提供了一个新思路：把代码结构和调用关系转换成知识图谱，存入图数据库，再通过自然语言查询整个项目。

它支持 Python、TypeScript、Rust、Go、Java、C/C++ 等十多种语言，混合语言项目也能统一分析。

除了自然语言问答，还支持：
分析函数调用和模块依赖
检测死代码
按结构模式搜索和替换
提供代码优化建议
修改前预览变更内容

另外，它还能作为 MCP Server 使用，接入 Claude Code、Codex 等 AI 编程工具。

面对复杂项目，想让 AI 不只是看文件，还能理解代码之间的关系，这个工具值得关注。
🔗 https://github.com/vitali87/code-graph-rag
