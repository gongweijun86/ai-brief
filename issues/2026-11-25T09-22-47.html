01｜Agent 记忆系统必读论文与工程清单

来源（X） · @Tao100086 · 2026-11-24 11:26

Agent 记忆系统已经从早期的“长上下文拼接 + 简单向量检索（RAG）”演进到了动态巩固、时序图谱、操作系统级分页与经验自进化阶段。下面按奠基经典 → 前沿架构论文 → 权威综述与评测 → 必读工程博客四个维度精选最值得读的清单：

一、 奠基必读经典（建立认知框架）

这几篇定义了今天所有 Agent 记忆系统的基本范式和术语：

- Generative Agents: Interactive Simulacra of Human Behavior (Park et al., Stanford, UIST 2023)

推荐理由：斯坦福“AI 小镇”论文，Agent 记忆系统的开山之作。首次完整跑通了 Memory Stream（记忆流）+ Reflection（定期反思抽象）+ Retrieval（按近因性 Recency、重要性 Importance、相关性 Relevance 加权检索） 的闭环。
论文链接：https://arxiv.org/abs/2304.03442

- MemGPT: Towards LLMs as Operating Systems (Packer et al., UC Berkeley, 2023 — 现 Letta 前身)

推荐理由：借鉴操作系统虚拟内存设计，将上下文窗口视为 RAM（主存），外部存储视为 Disk（外存），让 LLM 通过 Tool Call 自主管理上下文换入换出（Paging）与自我编辑记忆块。
论文链接：https://arxiv.org/abs/2310.08560
开源仓库：https://github.com/letta-ai/letta

- CoALA: Cognitive Architectures for Language Agents (Sumers et al., Princeton, TMLR 2024)

推荐理由：最清晰的理论分类框架。借鉴认知科学，把 Agent 记忆严格拆分为 Working Memory（工作记忆）、Episodic Memory（情景记忆/历史轨迹）、Semantic Memory（语义记忆/世界知识） 和 Procedural Memory（程序记忆/技能与代码）。
论文链接：https://arxiv.org/abs/2309.02427

- Reflexion (Shinn et al., NeurIPS 2023) & Voyager (Wang et al., 2023)

推荐理由：分别代表了情景反思记忆（把失败教训写成自然语言存入记忆指导下次尝试）和程序/技能记忆（在 Minecraft 中将成功的代码封装进 Skill Library 持续复用）。
Reflexion 论文链接：https://arxiv.org/abs/2303.11366
Voyager 论文链接：https://arxiv.org/abs/2305.16291

二、 前沿核心架构论文（2024–2026 工业界与学术界主流）
解决传统向量检索“无法处理事实变更（如搬家/改偏好）、多跳推理弱、缺乏结构化联系”的核心痛点：

- HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models (Gutiérrez et al., NeurIPS 2024 — 及其后续 HippoRAG 2)

核心看点：受人类海马体记忆索引理论启发，结合知识图谱 + Personalized PageRank 实现单步完成跨文档多跳关联记忆检索，比传统向量 RAG 更擅长串联碎片信息。
HippoRAG 论文链接：https://arxiv.org/abs/2405.14831
HippoRAG 2 论文链接：https://arxiv.org/abs/2502.14802

- Zep: A Temporal Knowledge Graph Architecture for Agent Memory (Rasmussen et al., 2025 — 底层引擎 Graphiti)

核心看点：聚焦双时态知识图谱（Bi-temporal Knowledge Graph）。给每条记忆加上“事件发生时间”与“入库有效区间”，当状态改变时使旧事实优雅失效而非粗暴覆盖，解决企业级 Agent 对动态实体演化的追踪问题。
论文链接：https://arxiv.org/abs/2501.13956
Graphiti 开源仓库：https://github.com/getzep/graphiti

- Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory (Chhikara et al., 2025)

核心看点：工业界应用极广的提取-更新（Extract-and-Update）记忆层论文，拆解了如何低延迟、低 Token 成本地从多轮对话中动态抽取事实、消解冲突，并结合向量与图结构（Mem0g\text{Mem0}_gMem0g​）服务生产环境。
论文链接：https://arxiv.org/abs/2504.19413
开源仓库：https://github.com/mem0ai/mem0

- A-MEM: Agentic Memory for LLM Agents (Xu et al., 2025)核心看点：借鉴 Zettelkasten（卢曼卡片盒笔记法），每次写入新记忆时动态生成结构化笔记卡片并自动与历史记忆建立双向链接、更新旧卡片上下文，实现自组织的记忆网络。
论文链接：https://arxiv.org/abs/2502.12110

三、 系统综述与评测基准（快速把握全景）

如果你想在最短时间内俯瞰整个领域的脉络与短板：

综述首选：
- Memory in the Age of AI Agents: A Survey (Late 2025)：

目前社区引用最广的全景综述之一，从 Forms（载体形式：Token 级 / 参数级 / 隐状态）、Functions（功能）、Dynamics（形成、演化与检索） 三个维度系统梳理了整个领域。
论文链接：https://arxiv.org/abs/2512.13564
配套论文列表仓库：https://github.com/Shichun-Liu/Agent-Memory-Paper-List

- From Storage to Experience: A Survey on the Evolution of LLM Agent Memory Mechanisms (Luo et al., ACL Findings 2026)：
把记忆演进总结为 Storage（存轨迹）→ Reflection（做反思）→ Experience（抽技能实现自进化） 三阶段，非常适合用来理解 Coding Agent / Computer-Use Agent 的经验复用。
论文链接：https://arxiv.org/abs/2605.06716

评测基准论文（看懂记忆系统怎么评测）：

- LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory (Wu et al., ICLR 2025) 与 LoCoMo (Maharana et al., ACL 2024)：
读这两篇能立刻明白生产级记忆系统的五大硬骨头——信息抽取、跨会话推理、知识更新（冲突覆盖）、时间推理与防幻觉拒答。
LongMemEval 论文链接：https://arxiv.org/abs/2410.10813
LoCoMo 论文链接：https://arxiv.org/abs/2402.17753

四、 必读工程技术博客（强烈推荐，贴近实战）

很多最佳工程实践并没有发成论文，而是沉淀在一线团队的博客里：

- Lilian Weng — LLM Powered Autonomous Agents (Lil'Log)入门圣经。其中关于 Memory 的章节把感觉记忆、短期上下文学习与长期外部检索的映射讲得极其透彻。
文章链接：https://lilianweng.github.io/posts/2023-06-23-agent/

- LangChain Blog — Memory for Agents & LangMem 文档非常务实地把 CoALA 理论落地为工程代码模式，清晰对比了 “Hot Path（对话同步更新记忆，延迟高但实时）” 与 “Background / Subconscious（后台异步整理记忆）” 两种架构取舍。
博客链接：https://www.langchain.com/blog/memory-for-agents
LangMem 文档：https://langchain-ai.github.io/langmem/

- Letta Blog — Agent Memory 系列 & Sleep-Time Compute提出 Sleep-Time Compute（睡眠期计算）
概念：与其只在用户提问时做推理（Test-time compute），不如利用 Agent 空闲时间在后台异步重组、去重、反思并重写核心记忆块。
Agent Memory 综述博客：https://www.letta.com/blog/agent-memory-how-to-build-agents-that-learn-and-remember
Sleep-Time Compute 博客：https://www.letta.com/blog/sleep-time-compute

- Anthropic — Effective Context Engineering for AI Agents（及 Claude Code CLAUDE.md / 文件系统记忆实践）代表了近年极其实用的另一派工程趋势：
基于文件系统与 Markdown 的扁平透明记忆（如 MEMORY.md、渐进式披露笔记、由 Agent 自己 grep/edit 维护知识库），在 Coding Agent 场景往往比黑盒向量库更可控、更易调试。
文章链接：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

建议阅读路径

想做工程落地选型：先看 LangChain《Memory for Agents》 + Anthropic 上下文工程博客，再对比阅读 Mem0（应用层 API 托管记忆）、Zep/Graphiti（时序图谱记忆）和 Letta（Agent 自主管理状态）的设计差异。

想做学术研究或深度自研：按 Generative Agents → CoALA → HippoRAG → Memory in the Age of AI Agents (Survey) → LongMemEval 的顺序精读。

02｜RSI 自进化论文揭示验证难题

来源（X） · @Xudong07452910 · 2026-11-25 08:25

这篇 RSI（递归自进化）年度总结写得很好，推荐收藏！

今年 RSI 的论文非常多，让 AI 自己找问题、改自己、再验证的系统也越来越多。但难的是证明它确实变好了，而不是适应了测试集，或者被评分器骗了。这份清单里很多论文都在回答这个问题。

📚 论文清单

1. The Last AI Built by Humans: Toward Genuine Recursive Self-Improvement（综述）
按 AI 在改进循环里能掌控多少，把 RSI 分成五级。最低一级是人定目标、AI 只负责执行，最高一级是 AI 连改进流程本身都能改。用来判断各种 RSI 说法到底到了哪一级，很好用。
https://arxiv.org/abs/2609.11873

2. Meta-Harness: End-to-End Optimization of Model Harnesses
写 harness 这件事也交给 agent 来做。关键是让它看到以往每次尝试的代码、分数和完整 trace，这样它才知道之前为什么失败，能提出新设计，而不只是在上一版上小修小补。
https://arxiv.org/abs/2603.28052
代码 https://github.com/stanford-iris-lab/meta-harness

3. Exo: An Architecture for Self-Improving Systems at Runtime
agent 可以在干活的过程中改自己的工具、记忆和上下文处理。但运行记录、密钥、沙箱权限放在一个它改不了的保护层里，每次改动都留下人能读懂的 diff。
https://arxiv.org/abs/2611.00463

4. Hyperagents
把干活的 agent 和改它的 agent 合成一个程序，「怎么提出改进」的方法本身也能被改写。实验里，正是这类改动最容易迁移到新领域。
https://arxiv.org/abs/2603.19461
代码 https://github.com/facebookresearch/Hyperagents

5. Harness Evolution Hits a Ceiling: When Weight Training Should Begin
先把失败分成两类。卡住、死循环、步数用完这类「做不完」的问题，改 harness 能解决；做完了但答案差这类「做不好」的问题，得靠训练权重。
https://arxiv.org/abs/2610.11655

6. Harness-Delta Attribution: Dissecting Gains From Harness Evolution
把 harness 搜索带来的提升拆开看，有一大半是在适应测试集本身，还有一部分只是多花了算力。想知道是不是真的变强，要在同等算力下用新任务再测一遍。
https://arxiv.org/abs/2610.22466

7. The Winner's Curse in LLM Self-Improvement Loops: Selection Noise, Lock-in, and Acceptance Rules
每轮都挑分数最高的版本，但分数有噪声，挑中的往往只是运气好，评估集越小虚高越严重。所以要留一份只用来评估的数据。
https://arxiv.org/abs/2610.09239

8. Who Verifies the Verifier? Co-Evolving Inspectable Graders with Self-Improving Agents
开放任务没有标准答案，评分器设计错了，循环就会朝错的方向优化。更麻烦的是，坏评分器照样能让 agent 分数上涨，所以评分器要拿人工核对过的样例单独校准。
https://arxiv.org/abs/2610.11464

9. Reflections on Trusting Trust, Revisited: Contaminating Self-Modifying AI Coding Agents with Poisoned Benchmarks
自我修改的 agent 靠 benchmark 决定保留哪些改动，所以谁控制了 benchmark，谁就能悄悄影响它学成什么样。被带偏的行为在干净任务上也会保留，后续训练很难洗掉。
https://arxiv.org/abs/2609.17817

10 Bootstrapping Conversational Recommendation Agents At Spotify: Synthetic Data Generation and Self-Improvement Loops
产品上线前还没有真实对话，就先用合成对话来测试，再让 coding agent 提出修改。每轮都是人审 PR 加完整回归测试，最后用真实用户的 A/B 测试来验证。
https://arxiv.org/abs/2609.30297

11. No Second Run: Does RSI Stop at Frontier Pre-training?
前沿预训练成本高、没法重来，就把它拆成 agent 跑得起的小循环，比如修基础设施、调数据过滤、改爬虫，失败的想法也记进共享笔记。新组建的团队靠这套方法，三个月训出了 30B 的 MoE 基座。
https://arxiv.org/abs/2611.10719
代码 https://github.com/GAIR-NLP/801-30B

03｜Go+SQLite 扛3000并发长连接

来源（X） · @realchendahuang · 2026-11-24 10:25

大多数 API 后端完全可以用 Go 加 SQLite 扛住高并发，哪怕丢进 1G 内存的小机器里也没问题，根本用不上 PG、Redis 和 Docker 那套重型设备。

实测下来，原生 Go 加嵌入式 SQLite 编出来的单个执行文件只有 15 MB 左右，跑起来常驻内存也就 15 MB，不装任何外部中间件，一台 1C1G 小机器能直接扛住 3000 以上的并发长连接。

传统做法把数据库独立部署，哪怕装在同一台机器上，程序每次查数据都要打包发请求、等数据库算完再传回来，嫌慢又往上套一层 Redis，顺手把缓存一致性和一堆连接池麻烦全引进来了。

SQLite 直接嵌在 Go 程序里面，查库相当于直接读本地内存，单次查询几十微秒，连前端页面和数据库脚本都能一起打进这一个文件里，扔服务器上直接跑。

避开 SQLite 并发写锁死，关键是把读和写拆成两条独立连接，读的放开并发，写的单线排队不互相抢锁。配置、路由、限流、余额预扣这些高频操作直接放在 Go 进程内存里处理，不穿透硬盘。

需要落盘的账单和日志，放进内存队列每 15 毫秒攒成一批打包写入，把每秒几千上万条零碎写入压成几十次提交，硬盘压力很小。

担心单机硬盘坏了丢数据，后台挂一个轻量同步工具 Litestream，每 10 秒把增量变化传到 Cloudflare R2 对象存储，一个月不到 26 万次写入都在免费额度里。

就算机器坏了，新开一台 1C1G 服务器执行一行恢复命令，5 分钟就能原样拉起来。

如果你的业务已经做到多机多活、多个节点同时写主库，或者每秒要扛几千次必须立刻落盘的强同步写入，又或者单库数据攒到了几百 G、重度依赖全文检索和向量检索，最佳实践依然是老老实实上集群、独立 PostgreSQL 加 Redis。

不过大多数人的独立产品、SaaS、内部系统和 API 服务，从上线做到稳定赚钱，根本用不到那一步。

想直接用这套方案，把下面这段提示词丢给你的 AI，就能照着搭出来。

---

请帮我用原生 Go + 静态编译的 SQLite 设计并实现一个单机高并发 API 后端骨架，严格遵守以下架构要求：

- 零外部中间件、零 ORM，不依赖 Docker、PostgreSQL 和 Redis；用 embed.FS 把前端静态资源和 SQL 迁移脚本打包进单个二进制文件，提供 systemd 部署配置。
- 数据库层显式拆分 ReadDB 和 WriteDB 两个连接池：底层开启 PRAGMA journal_mode = WAL、PRAGMA synchronous = NORMAL、PRAGMA mmap_size = 134217728、PRAGMA cache_size = -32000。
- ReadDB 连接串强制加上 mode=ro&_query_only=on，设置 4 到 6 个连接用于并发读；WriteDB 锁定 SetMaxOpenConns(1) 并设置 _txlock=immediate，同时在 Go 层加一把 sync.Mutex 串行化写入，避免 SQLITE_BUSY。
- 热路径内存化：配置快照、路由状态、限流计数、用户余额或额度预扣等高频读写全部放进 Go 进程内存，使用 atomic 和按账号细粒度锁控制并发，不穿透磁盘。
- 异步组提交落盘：用容量 8192 的带缓冲 channel 接收扣费、日志等写入事件，后台单一写协程按每 15ms 或攒满 64 条合并成一个 SQLite 事务批量提交；实现优雅停机，退出前 Drain 排空队列防止丢数据。
- 容灾配置：生成配套的 Litestream 配置文件（每 10 秒增量同步至 Cloudflare R2）与一键 restore 恢复脚本；应用初始化数据库时必须显式设置 PRAGMA wal_autocheckpoint = 0，把 WAL checkpoint 控制权完全交给 Litestream，防止增量同步链断裂。

04｜AGENTS.md 八条极简编码规则

来源（X） · @HeLi8866 · 2026-11-24 17:18

Vercel 团队为了解决 AI 乱写代码的毛病，硬生生烧了 60B token，最后提炼出了一份 AGENTS.md，核心就 8 句话！

这 8 条规则，就是在 AI 动笔前直接把它按住：能不写的不写，能复用的复用，能简单的绝不搞复杂。

直接抄作业，把这 8 条丢进你项目的 AGENTS.md 里，Claude Code、Codex 都能自动读取⬇️：

1️⃣ 不保留向后兼容：过时东西直接删，别写迁移脚本和回退方案。
2️⃣ 极简主义：选满足当前需求的最简实现，绝不搞“预防性抽象”。
3️⃣ 小步快跑：先跑通最小端到端版本，别为了臆想的未来去拆当前能跑的架构。
4️⃣ 模块化：组件保持独立，关注点分离清楚。
5️⃣ 别造轮子：优先用成熟的、有人维护的第三方库。
6️⃣ 先查再写：动手前先翻翻项目里已有的依赖，别想当然瞎引包。
7️⃣ 架构要有远见：绝不接受“先凑合，以后再说”的临时屎山。
8️⃣ 抄作业：先看成熟产品怎么解决，用验证过的模式，别从零发明。

🚨 但是！作者加了一个极其保命的硬核警告：
这套规则只适合 Side project、内部工具和原型，生产环境一定要慎用！

因为第一条规则，作者亲测差点让 Agent 把生产环境的数据库表给删了，差点损失 2000 美金。上生产的话，千万记得把第一条改温和点！

省 token 的方法有很多，但最管用的，就是在根目录放个文件告诉 AI：别整花活，写最少的代码！

赶紧码住，今晚就给你的 AI 立规矩！
