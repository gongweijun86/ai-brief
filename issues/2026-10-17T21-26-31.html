01｜asd-STE100 受控英语改写提示

来源（X） · @kafkaup · 2026-10-18 04:41

航空和国防业有一套强制的受控英语标准 ASD-STE100，存在的理由很直白：一条飞机维修指令被看错，是会死人的。规则就那几条——一个词只准一个意思、用主动语态、只用简单时态、一句话只给一条指令、不许省词。

asd-ste100-skill 做的事，是把这套纪律搬给另一类读者：读上游 agent 输出、读 tool description、读报错信息的模型。它的理由也说得通，下游 agent 和当年那个非母语机械师处境一样，没有回传通道，没法反问"你指的是 X 还是 Y"。

以前写 tool description，很容易写成 README 里那种句子：这个工具会尝试在各个已配置的后端之间同步状态，如果检测到冲突，可能会根据已设置的策略自动处理，否则就暴露出来人工审查。一句话里塞了三个条件分支，模型按哪条走全看运气。

接上 skill 之后，它会逐句标出违规项：被动语态且施事不明、一句多指令、名词堆叠过长、现在完成时、分号、营销形容词、堆叠的模糊限定词，然后拆成四个短句重写，同时要求不丢掉任何事实、条件和范围限定。如果缩短会损失精度，它保留长句并标注取舍，而不是悄悄简化。输出默认只给改写后的正文，想看依据就问 show the diff，它才列出规则对照表。

两种模式：Strict 用于流程、报错、tool description；STE-flavored 用于 README 和 PR 描述，保留句式纪律但不锁词表。

代价要说清楚。仓库里的 scripts/ste-lint.py 只做结构检查，不比对原文和改写、不验证语义是否保留，零告警只代表结构规则没命中。短语动词也只认 spin up、reach out 这类固定一小串，take off the panel 就能混过去。它自己的 SKILL.md 都要带 baseline 41 才跑得干净，作者直接写在 README 里了。

04｜Claude Code 项目状态页自更新

来源（X） · @TiagerBao · 2026-10-17 21:28

Claude Code 现在可以把整个项目直接变成一个“实时状态页”了。

Anthropic 官方这个插件叫 project-artifact。

它会读取你的：
GitHub 仓库、PR、CI、Review
项目 tracker
设计文档

然后生成一个可以分享给团队的私有 Claude Artifact。
重点不是做一次汇报，而是它会记住数据来源。

以后直接执行：
刷新工件
它就会重新拉取 PR、CI、审查状态，更新同一个页面，并告诉你这次发生了什么变化。

页面会自动整理：
项目概览、成功标准、工作流、下一步行动，以及有内容时才出现的风险、计划、FAQ。
它还会按 1.0、1.1、2.0 给 PR 分组，把依赖关系直接展示出来。
拉取失败的数据会标记为 stale，不会自己猜；PR 里的文字也只当数据，不当指令执行。

这比每周手动写一次项目周报实用多了。

安装：
/plugin install project-artifact@claude-plugins-official

运行：
/project-artifact

07｜AI Coding 落地六类工程范式

来源（X） · @xulijian1994 · 2026-10-17 11:33

Vibe Coding 玩到最后，拼的可能不是模型，而是软件工程基本功。

最近一直在思考一个问题：Claude Code、Codex 越来越强，代码生成速度已经不是瓶颈了，但为什么项目越做越大，反而越来越难维护？

尤其是复杂业务系统，前期 AI 写得飞快，后期改一个需求，可能牵扯十几个文件，修一个 Bug 又引入三个 Bug。

我觉得问题不完全在模型，而在于我们缺少一套真正适合 AI Coding 的工程范式。

目前比较值得了解的有这么几类：

1. SDD（Spec-Driven Development，规格驱动开发）

先写清楚需求、技术方案、任务拆分，再让 AI 编码。

核心是把自然语言需求变成结构化 Spec，降低 AI 自由发挥的空间。

代表工具：OpenSpec。

适合需求复杂、开发周期长、需要跨会话持续开发的项目。

但 SDD 解决的是「做什么、怎么执行」，不代表生成的架构一定合理。

2. TDD（Test-Driven Development，测试驱动开发）

先定义测试，再实现功能，最后重构。

在 AI Coding 场景下，我觉得 TDD 的价值反而被放大了。

因为 AI 最大的问题不是不会写代码，而是经常写出「看起来正确」的代码。

有了测试，至少能让 AI 的实现过程形成反馈闭环。

不过测试本身也可能写错，不能把测试通过等同于业务正确。

3. DDD（Domain-Driven Design，领域驱动设计）

这是我认为复杂业务系统尤其值得重视的部分。

SDD 管流程，DDD 管业务边界。

比如开发一个 ERP 系统：

库存、采购、销售、财务应该如何划分？

哪些逻辑属于库存领域？

哪些数据可以跨模块访问？

哪些操作必须通过领域服务完成？

如果这些边界不明确，AI 很容易把业务逻辑写得到处都是。

DDD 的核心价值不是增加多少抽象层，而是让业务边界清晰、模块职责稳定。

当然，不是每个小项目都需要完整的 DDD。

4. Context Engineering（上下文工程）

这是 AI Coding 特有的重要能力。

很多人觉得模型上下文越长越好，但上下文长度不等于有效信息质量。

项目越大，历史对话、无关代码、过期需求越容易干扰模型。

我更倾向于：

- 用 AGENTS.md / CLAUDE.md 记录项目级约定
- 用模块级规则约束局部实现
- 用独立文档记录关键架构决策
- 每次任务只提供必要的上下文
- 跨会话依靠文档恢复状态，而不是依赖聊天记录

核心就是让 AI 在正确的上下文里做正确的事。

5. Workflow / Harness（工作流与执行约束）

这类方案解决的是执行过程的稳定性。

比如：

需求分析 → 方案设计 → 人工确认 → 任务拆分 → 编码 → 测试 → Review。

Superpowers、Trellis、PStack 等工具都可以作为研究对象。

它们的价值在于减少遗漏，让开发过程更可重复。

但必须认识到：Workflow 不能替代架构设计。

流程执行得再标准，如果一开始模块划分就错了，最后仍然可能是一座结构规范的屎山。

6. Project Rules / Skills（项目规则与技能沉淀）

我觉得这可能是个人开发者最容易落地的一种方式。

通用 Skills 可以提高效率，但真正有价值的，是根据项目不断沉淀自己的规则。

比如：

- Controller 不直接操作数据库
- 跨模块调用必须通过明确接口
- 新增 API 必须补充契约和测试
- 修改公共组件前必须检查调用方
- 数据库结构变更必须提供迁移脚本

这些规则不需要一开始就写得非常复杂，而是随着项目不断迭代。

最后，我觉得还有一个很重要的判断标准：可重建性。

假设今天把项目代码全部删除，只保留需求文档、架构设计、接口规范和测试用例。

你能不能让另一个 AI 会话重新实现出业务行为基本一致的系统？

如果完全做不到，说明很多关键知识其实只存在于代码和聊天记录里，并没有真正沉淀下来。

当然，这不是要求每次生成完全相同的代码，而是业务行为、模块边界和核心约束能够被复现。

我的观点是：

SDD 管需求，TDD 管正确性，DDD 管架构，Context Engineering 管信息，Workflow 管执行，Rules 管约束。

它们不是互相替代的关系，而是不同层面的工程能力。

对于简单的小工具，直接 Vibe Coding 完全没问题。

但对于需要长期维护的商业项目，最终还是得回到软件工程本身。

AI 可以替我们写代码，但不能因为代码生成成本降低，就忽略设计成本。

未来真正拉开 AI Coding 差距的，可能不是谁的 Prompt 更厉害，而是谁能把软件工程经验转化成 AI 可以稳定执行的规则。

大家现在用 Claude Code 或 Codex 开发项目，主要采用哪种范式？有没有真正能长期坚持使用的工程化方案？

今天看到，JetBrains 给 Pi 做了一个 GUI 客户端🔥

从我的角度来说还是命令行最舒服，但是GUI、TUI才是大众更能接受的表现形式。

如果想把Pi 分享给更多的人，GUI这条路总要有人来跑一跑。

JetBrains 给 Pi 做的 GUI 客户端，叫做ThinkRail，底层的引擎还是 Pi，比如模型、skills、压缩还是交给Pi自己管，但是外面多了一层能看的工作区。

这次的GUI 我觉得比较有意思的点有三个：

1.、聊天、编辑器、终端摊在一个界面里
不用来回切窗口，改哪看哪，Agent 在干什么一眼能跟上。

2. 一个仓库能开多个工作区
每个 Agent 单独一条 git worktree，界面上并排跑，main 不会被一起改乱。这才是多 Agent 能看懂的 GUI，不是多开几个对话框。

3. 规格和改动都能看见
Spec graph + diff 在界面上，中间态不会只剩最终结果。想回溯，不用翻一堆日志。

虽然命令行的形式符合 Pi 这条极简路线，但是在复杂的工作当中，如果有人帮我配置和安装好对应的功能，我想大家也会很高兴，最主要的是终于有一条能把人留住的 GUI 路径。

使用什么是你的权利，但是社区给你提供不一样的选择，这和Pi的理念不谋而合
