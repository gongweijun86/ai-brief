02｜Anthropic归纳六种Agent模式

来源（X） · @0xTrackmind · 2026-11-15 00:51

中文译文

这篇 Anthropic 论文真是他*的金矿

Anthropic 展示了他们构建 AI agent 的完整方式。大多数还在构建 agent 的人至今还没读过它。

秘诀在于：几乎没有人需要一个"真正的" agent。他们需要的是最简单的可行模式。

里面包含的 6 种模式：

模式 1 → 增强型 LLM

一个模型 + 工具 + 记忆。
从这里开始。大多数"agent"应该到此为止。

模式 2 → 提示链

任务 → 步骤 1 → 检查 → 步骤 2 → 检查 → 完成。

模式 3 → 路由

输入 → 分类 → 发送到合适的提示（或更便宜的模型）。

模式 4 → 并行化

拆分 → 同时运行 → 合并。
或者运行 3 次 → 投票。

模式 5 → 编排器-工作者

一个模型规划 → 派生工作者 → 合并它们的返回结果。

模式 6 → 评估器-优化器

生成 → 批评 → 修复 → 循环直到通过。

只有当以上模式都不适用时 → 才是一个真正的 agent：一个带有工具、停止条件和人工检查点的循环。

他们甚至把整份指南打包成了一个提示。粘贴到 Claude Code 里，它会为你选择模式，然后构建出来。

6 种模式。1 个提示。0 过度工程。

收藏这篇。

原文

the secret: almost nobody needs a "real" agent. they need the simplest pattern that works.

the 6 patterns inside:

pattern 1 → augmented LLM

one model + tools + memory.
start here. most "agents" should stop here.

pattern 2 → prompt chaining

task → step 1 → check → step 2 → check → done.

pattern 3 → routing

input → classify → send it to the right prompt (or the cheaper model).

pattern 4 → parallelization

split → run at once → merge.

pattern 5 → orchestrator-workers

one model plans → spawns workers → merges what they return.

pattern 6 → evaluator-optimizer

generate → critique → fix → loop until it passes.

only when none of these fit → a real agent: a loop with tools, a stop condition and a human checkpoint.

6 patterns. 1 prompt. 0 overengineering.

03｜Chord成为Pi分布式对象运行时

来源（X） · @fttt007 · 2026-11-15 11:00

Chord 是 Pi 生态中的分布式对象运行时，负责对象的组织、访问、通信、状态和生命周期管理。

Pi Durable 则构建在 Chord 的部分基础能力之上，专注于持久化 Agent 执行，包括对话管理、模型调用、工具执行、任务恢复等。

简单来说：

Chord 解决对象如何运行和协作，Durable 解决 Agent 如何持久化执行和恢复。

两者配合，让 Pi 不仅能运行 Agent，还能构建能够长期运行、崩溃恢复和持续演进的 Agent 系统。

引用内容

kayce @fttt007

今天深入学习了 Pi 生态中的 Chord v2，最大的收获是理解了它的核心定位：分布式对象运行时（Distributed Object Runtime）。

Chord 不只是一个插件系统，它负责让不同进程中的对象能够创建、运行、通信和管理自己的生命周期。

今天重点理解了几个概念：

Object：类似于 Python Class 创建出来的实例，是一个真正拥有数据、方法和生命周期的运行实体。
Host：Chord 系统中的运行节点，具有逻辑身份和运行实例。它通常对应一个进程，但不等于进程。
Runtime：负责管理 Host 中对象的创建、激活、引用和生命周期。
Host Kind：定义节点的类型。
Host Address：确定具体要访问哪个节点。
Link：连接不同 Host，让它们能够通信。

举个例子：

Server Host 想访问 Session S2 中的 Notes Object：

先通过 Host Kind 确定节点类型，再通过 Host Address 找到具体节点，最后通过 Link 建立通信，访问目标对象。

我越来越觉得 Chord 最有价值的地方在于：

它把原本需要开发者自己处理的对象创建、资源管理、跨进程通信和生命周期管理，统一交给 Runtime 协调。

这也是理解 Pi 如何构建复杂、可持续运行的 Agent 系统的重要基础。

05｜Harness由4B模型自动进化

来源（X） · @damkina7 · 2026-11-14 21:33

中文译文

这篇论文简直令人震撼！

中国研究者发表了一篇 6 页的论文，其标题足以让每一个 AI agent 构建者停下来思考：

《Harness 工程的终结》

核心论点极其尖锐：
一个手写的 harness 只是一个人在某个下午的猜测，被发布到生产环境中后就无人问津数月。

论文提出了一个架构上的反转：
大模型保持 100% 冻结。harness 围绕它自主进化。

以下是精确的 4 步循环：

→ 步骤 1：运行时执行失败被捕获为结构化 trace
→ 步骤 2：一个轻量级 4B 编辑器读取出错内容并生成 8 个候选 harness diff
→ 步骤 3：所有 8 个候选都在一个保留的评估套件上执行
→ 步骤 4：得分最高的那个编辑存活到 v(n+1)；其余 7 个被删除

为什么这颠覆了软件工程：

1. 框架变成了一次性的
你不再维护脆弱的编排框架。harness 每一轮都由一个 4B 参数的编译器重写。

2. 人的工作缩减为一件产物
你不再编写 agent 逻辑或调整提示。你唯一的输出是评分集：那些标准答案基准问题。

3. 考试就是工作
如果你无法度量差异，你就无法构建 harness。竞争优势从你写 agent 代码写得好不好，转向你设计评估门槛有多严格。

一句话总结：
停止为 agent 写代码。先写考试，让循环来写 harness。

阅读下面的完整论文拆解 ↓

原文

This paper is absolutely mind-blowing!

Chinese researchers have published a 6-page paper with a title that should give every AI agent builder pause:

"The End of Harness Engineering"

the core thesis is brutal:
a hand-written harness is just one human guess on one afternoon, shipped to production and left unread for months.

the paper proposes an architectural inversion:
the big model stays 100% frozen. the harness evolves around it autonomously.

here is the exact 4-step loop:

→ step 1: runtime execution failures get captured into structured traces
→ step 2: a lightweight 4B editor reads what broke and generates 8 candidate harness diffs
→ step 3: all 8 candidates are executed against a held-out evaluation suite
→ step 4: the single highest-scoring edit survives into v(n+1); the other 7 are deleted

why this flips software engineering upside-down:

1. frameworks become disposable
you stop maintaining brittle orchestration frameworks. the harness is rewritten every round by a 4B parameter compiler.

2. the human job shrinks to one artifact
you no longer write agent logic or tweak prompts. your only output is the scoring set: the ground-truth benchmark questions.

3. the exam is the job
if you can't measure the delta, you can't build the harness. competitive advantage shifts from how well you write agent code to how rigorously you design evaluation gates.

the takeaway in one sentence:
stop writing code for the agent. write the exam first, let the loop write the harness.

13｜Agent项目TypeScript占七成

来源（X） · @meow2149 · 2026-11-15 01:24

这段时间介绍和拆解过的agent相关项目，我重新翻了一遍，一共20个，其中TypeScript写的占了70%。

具体是：TypeScript 14个，Rust 3个，Go、Swift、Python各1个。

统计时按主要开发语言归类，每个项目只算一次，混合语言的项目也只算在主语言下。

一、TypeScript：14个，占70%

▪︎ T3 Code：把Claude Code、Codex等agent接进一个统一的工作台，管理任务、会话和代码改动。

▪︎ Orca：为agent开发做的IDE，集成了并行任务、Git Worktree、代码编辑和diff审查。

▪︎ Paradev（原名Superset）：给每个任务分配独立的工作区，可以同时跑多个coding agent。

▪︎ Emdash：多agent开发环境，可以自选工具和模型供应商，并行处理任务。

▪︎ Paseo：在桌面、手机和浏览器上都能访问电脑里的coding agent。

▪︎ Parallel Code：把多个coding agent放进同一个界面，每个任务用单独的Git Worktree。

▪︎ CodexHost：把Pi、Claude Code这些工具接进Codex Desktop。

▪︎ Conductor：在Mac上用独立工作区并行跑agent，改动和代码审查都集中在一处看；官方公开的桌面端技术栈包括TypeScript、React和Tauri。

▪︎ Pi Coding Agent：可扩展的终端编程agent，也提供模型调用、agent循环、终端界面等基础组件。

▪︎ Oh My Pi（OMP）：从Pi分出来的增强版，加了Hashline编辑、语言服务和调试等功能。它有一部分核心组件是Rust写的，但仓库主语言还是TypeScript。

▪︎ Cindy：把Claude Code、Codex和Pi放进同一套任务界面，换台设备也能接着干。

▪︎ Claude-Mem：记录agent的工作过程并整理成记忆，在后续会话里补上相关上下文。

▪︎ DeepSeek dsh-superagent：面向GitHub仓库的研究原型，接到任务后在独立会话里处理，最后通过回复或PR交付。

▪︎ Paperclip：管理agent团队的角色、目标、任务、权限、预算和运行记录。

二、Rust：3个，占15%

▪︎ Herdr：管理coding agent的终端、会话和运行状态，把多个agent放进同一个工作空间。

▪︎ Runner：让多个终端agent围绕同一个任务协作，各自的终端界面都保留着。

▪︎ agent-desktop：让agent能操作桌面应用，通过系统的无障碍接口读取界面、定位元素、执行操作。

三、Go：1个，占5%

Magpie：统一管理不同agent用的模型和账号，用本地网关做协议转换、模型路由和切换。

四、Swift：1个，占5%

cmux：macOS原生的终端工作区，基于Ghostty，带垂直标签、分屏和agent通知。

五、Python：1个，占5%

Hermes Agent：可以部署在电脑或服务器上的个人agent，支持工具调用、长期记忆、Skill和定时任务，还能接入消息平台。

为什么TypeScript这么多？看完这批项目，原因其实挺明显。

这份名单里，工作台、桌面客户端和开发环境占了一大半。这类应用要处理模型调用、子进程、流式输出、会话状态、文件、Git和审批，最后还得做成好用的界面。

这些环节用TypeScript基本都能串起来：界面用React，应用逻辑交给Node.js或Bun，桌面端有Electron和Tauri，要做移动端还有React Native，前后端之间共享类型和协议也方便。

Cindy就是个典型例子，桌面端用Electron，移动端用Expo和React Native，中间还有一层共享能力。

Rust这几个项目更贴近终端、桌面和系统接口，渲染、资源占用、进程生命周期和底层调用都得认真处理，用Rust很合理。

当然，这个比例跟我的选题有关。我介绍的多是开发者工具和工作台，不能拿它当整个agent生态的语言排名。

不过至少能看出来，做agent应用时，界面、状态管理、跨端开发和工程组织这些经验都能直接用上。

前端这几年学的东西，到了agent这里，还真没白学。
