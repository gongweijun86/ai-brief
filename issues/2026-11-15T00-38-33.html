02｜NVIDIA Dory 复用层比肩9B模型

来源（X） · @_avichawla · 2026-11-14 18:26

中文译文

NVIDIA 发布了一款新的循环 Transformer：

不是堆叠更多层，而是将相同的层运行多次，使一个 4B 模型能像 9B 模型一样思考。

以下是它的工作原理：

在标准 Transformer 中，每个 token 都会通过一个解码器块堆栈一次，每个块都有自己独立的权重。

所以如果你想要一个更深的模型，你就需要添加更多的块，参数量随深度增长。

NVIDIA 的 Dory1.0-4B 通过复用其一部分层来解耦这两者。

模型被分为三个部分：

> 输入块由 8 个块组成，运行一次，将 token 转换为隐藏状态 x。

> 循环块由 20 个共享块组成，运行 k 次，k 的范围可以从 1 到 4。

> 输出块由 8 个块组成，在最终状态上运行一次，随后是 LM head。

在每次通过循环块之前，x 会被加回当前状态，然后对总和进行 L2 归一化。

这使得每次通过时都能看到原始的 token 表示，而不是每次只看到上一次通过产生的结果。

下图中的两个模型都存储了 36 个块的权重。

标准 Transformer 对每个块应用一次，而 Dory 在 k=1 时应用 36 个块，k=2 时应用 56 个块，k=4 时应用 96 个块，即来自同一 checkpoint 的 72、112 和 192 个物理层。

额外的深度在推理和 agentic 任务上确实有帮助：

> SWE-bench Verified：

- 1 次循环 → 50.3
- 2 次循环 → 59.5
- 4 次循环 → 61.8

> 12 项基准测试平均分：

- 1 次循环 → 35.17
- 2 次循环 → 39.67
- 4 次循环 → 40.60
- 且在 2 次或更多循环时，超越了 Qwen3.5-9B、Gemma 4 12B 和 Gemma 4 26B-A4B。

更多循环意味着每个 token 需要更多计算量，但 4 循环模型在 agentic 任务上输出的 token 数量也少了 1.3x 到 2.5x。

因此 2 次循环端到端的总计算量实际上只是 1 次循环的 1.03x 到 1.25x，这就是 NVIDIA 推荐将 2 作为默认值的原因。

默认情况下，Dory 为每次循环保留独立的 KV cache，所以在 4 次循环时，循环层会存储 4 倍的 cache。

为了避免这种情况，它可以只保留最后一次循环的 cache，这使用的 KV 内存与普通模型相同，只有微小的精度变化。

有一点需要注意：循环帮助模型基于它已有的知识进行推理，但不会添加新知识。

例如，在 AA-Omniscience 等任务上，无论运行 1 次还是 4 次循环，准确率都保持在 10.0，而在 GPQA 等知识密集型任务上，Dory 仍然落后于 Qwen3.5-4B。

论文在这里：https://arxiv.org/abs/2611.03998

话虽如此，循环消耗多少内存取决于 KV cache 的处理方式，所以我写了一篇关于 KV cache 工作原理的完整详解。

它涵盖了 prefill 期间缓存了什么内容、cache 在解码过程中如何增长，以及为什么它在长上下文时成为主要的内存瓶颈。

原文

NVIDIA released a new looped transformer:

Instead of stacking more layers, it runs the same layers multiple times so a 4B model can think like a 9B one.

Here's how it works:

In a standard transformer, every token passes through a stack of decoder blocks once, and each block has its own weights.

So if you want a deeper model, you add more blocks, and the parameter count grows with the depth.

NVIDIA's Dory1.0-4B decouples the two by reusing a chunk of its layers.

The model is split into three parts:

> An input block of 8 blocks runs once and turns the tokens into a hidden state x.

> A recurrent block of 20 shared blocks runs k times, where k can be anywhere from 1 to 4.

> An output block of 8 blocks runs once on the final state, followed by the LM head.

Before every pass through the recurrent block, x is added back to the current state and the sum is L2-normalized.

This keeps the original token representation in view on every pass, instead of each pass only seeing what the previous one produced.

Both models in the diagram below store 36 blocks of weights.

The standard transformer applies each block once, while Dory applies 36 blocks at k=1, 56 at k=2, and 96 at k=4, i.e., 72, 112, and 192 physical layers from the same checkpoint.

The extra depth is actually helpful on reasoning and agentic tasks:

> SWE-bench Verified:

- at 1 loop → 50.3
- at 2 loops → 59.5
- at 4 loops → 61.8

> 12-benchmark average:

- at 1 loop → 35.17
- at 2 loops → 39.67
- at 4 loops → 40.60
- and with 2 or more loops, it beats Qwen3.5-9B, Gemma 4 12B, and Gemma 4 26B-A4B.

More loops implies more compute per token, but the 4-loop model also writes 1.3x to 2.5x fewer output tokens on agentic tasks.

So 2 loops end up costing only 1.03x to 1.25x the compute of 1 loop end to end, which is why NVIDIA recommends 2 as the default.

By default, Dory keeps a separate KV cache for every loop, so at 4 loops the recurrent layers store 4x the cache.

To avoid this, it can keep only the cache from the last loop, which uses the same KV memory as a normal model with only a small change in accuracy.

One thing to note here is that looping helps the model reason over what it already knows, but it does not add knowledge.

For instance, on tasks like AA-Omniscience, accuracy stays at 10.0 whether you run 1 loop or 4, and on knowledge-heavy tasks like GPQA, Dory still trails Qwen3.5-4B.

Here's the paper: https://arxiv.org/abs/2611.03998

That said, how much memory looping costs comes down to how the KV cache is handled, so I wrote a full breakdown of how KV caching works.

It covers what gets cached during prefill, how the cache grows during decoding, and why it becomes the main memory bottleneck at long context.

Read it below.

11｜Capgemini 按验证结果算AI成本

来源（X） · @antgrasso · 2026-11-14 22:02

中文译文

你选择了一个更便宜的 AI 模型。很好。但你确定省了钱吗？Capgemini 警告说，错误和人工审查可能会改变最终的账单。

Token 价格很容易比较。更难的部分是弄清楚组织为获得结果实际花费了什么。

微型博客 by @antgrasso

考虑一个为产品目录准备描述的营销团队。一个 AI 模型每次请求花费更低。另一个花费更高，但它的草稿可能在发布前需要更少的修改。

团队需要比较每条获批描述的总花费，包括核查产品信息所需的工作。

每次请求价格更高的模型最终可能反而是更经济的选择。

Capgemini 称这种衡量方式为 Cost Per Verified Outcome（每经验证结果成本）。它将比较从 token 消耗转移到经过验证的业务结果的成本上。

但即使是一个经过验证的结果，也需要产生足够的价值来证明公司为获得它所花费的成本是合理的。

#AIEconomics #AIManagement

原文

You chose a cheaper AI model. Good. But are you sure you saved money? Capgemini warns that errors and human review can change the final bill.

Token prices are easy to compare. The harder part is working out what the organization spends to get a result.

Microblog by @antgrasso

Consider a marketing team preparing descriptions for a product catalog. One AI model costs less per request. Another costs more, but its drafts may need fewer revisions before publication.

The team needs to compare what it spends for each approved description, including the work required to check the product information.

The model with the higher price per request could turn out to be the less expensive choice.

Capgemini calls this measure Cost Per Verified Outcome. It shifts the comparison from token consumption to the cost of a verified business result.

But even a verified result needs to produce enough value to justify what the company spends to obtain it.

#AIEconomics #AIManagement
