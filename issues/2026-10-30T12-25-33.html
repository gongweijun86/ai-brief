01｜FDE 做企业 AI 定制重在可复用

来源（X） · @UPing123zzz · 2026-10-30 17:09

最近听到几个人讨论 FDE 和企业 AI 落地的商业模式，我觉得有些话虽然不太好听，但特别现实。

现在很多人觉得，有了 Codex、Claude Code，再配上各种 Agent 和 Skill，一个人就能给企业做系统、做自动化、做数字化转型。听起来特别美好，一个人就是一家公司，甚至还可以把自己包装成超级个体。

但实际去接触客户以后，你会发现企业定制开发根本不是写完代码就结束的事情。

需求可能随时变化，客户可能自己都说不清楚到底想要什么。你今天解决了一个问题，他明天又提出三个新的需求。系统开发完成了，还要部署、培训、处理权限、解决异常、维护环境。你以为卖出去的是一套软件，最后可能变成了长期给客户做技术支持。

而且 AI 领域还有一个特别麻烦的问题，就是底层平台更新太快了。

你花几个月时间定制开发的功能，可能过段时间某个大厂的产品就直接内置了。你投入大量精力做出来的东西，客户突然发现普通订阅软件也能完成，那你就得重新解释自己的方案到底有什么独特价值。

我听到一个判断是，对个人或者小团队来说，现阶段做标准化培训、小型项目，可能比直接承接大型企业 AI 改造更容易控制成本。这个观点我觉得有现实意义，但也不能理解成定制开发一定不赚钱。

关键还是你的交付到底有多少能够复用。

如果每来一个客户，你都要重新设计架构、重新写 Skill、重新配置环境、重新处理各种特殊需求，那营收看起来可能不错，最后却被交付和维护消耗掉大量时间。

但如果你长期服务某个行业，慢慢把知识库、权限管理、工作流、审核机制、部署方案都沉淀下来，新客户来了只需要处理少量差异，情况就完全不同了。

我觉得这也给了想做 FDE 的人一个提醒：千万别只盯着技术实现，商业模式本身也要设计。

这个项目收多少钱？需要交付多久？后期谁维护？客户要改需求怎么办？有没有持续收入？如果平台升级了，系统需要多少维护工作？

这些问题你在接单之前不想清楚，后面很可能就会付出代价。

FDE 这个方向当然值得做，但千万别把它想得太轻松。技术能让一个人交付更多东西，却不能自动解决需求管理、商业定价和客户维护的问题。

会写 Agent 只是入场券，能不能把项目做成一门可持续的生意，才是真正困难的部分。

06｜Droid 1.0 默认程序化工具调用

来源（X） · @0xLogicrw · 2026-10-30 16:10

Factory 发布 Coding Agent 运行框架 Droid 1.0，引入程序化工具调用（Code Mode），并将其设为默认执行方式。AI 可以先编写 JavaScript 脚本，再通过脚本连续调用数百次工具，不用每执行几步就重新请求大模型，从而减少模型调用次数和 Token 消耗。

例如，迁移并核查 151 条 Linear 工单，传统方式预计需要 36 次模型请求、310 万输入 Token。改用 Code Mode 后，实际只需 2 次请求、约 6.1 万 Token，输入 Token 减少约 98%。在更广泛的测试中，使用 Claude Opus 5.5 的任务成本降低约 15%。

Factory 还优化了不同模型的工具调用策略、缓存和任务执行机制。在 Terminal-Bench 4 官方自测中，使用相同的 GPT-6.1 Sol 模型，Droid 比 Codex 高 3.5 分，成功任务成本降低 12%，但耗时增加 10%。

Code Mode 并非新技术。Cloudflare 早在 2025 年 9 月就提出了这一方案，Anthropic 随后也将类似机制用于 Agent 工具调用。今年，DeepSeek Harness、Pi 和 OpenCode 2.0 等开源 Agent 框架也陆续加入支持。
