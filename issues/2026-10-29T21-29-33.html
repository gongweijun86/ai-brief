05｜Claude Code 提前自动压缩阈值

来源（X） · @dotey · 2026-10-29 02:08

如果你在用 Claude Code 的话，再推荐下记得运行下 /autocompact 300k
（原推是400k，我自己用下来300k就足够了，当然选哪个你可以自己决定）

自动压缩（Auto-compact）的作用是将整段长对话精简为简短的摘要，而不是一直保留上百万的完整历史记录。在 1M 上下文模型中，系统默认要到约 967K Token 时才会触发压缩。

由于你发送的每一条消息都会带上之前的全部对话历史，等到 967K 再压缩，意味着后期的每一次交互都在重复消耗海量 Token。虽然在缓存有效（warm cache）的情况下，大部分历史内容走的都是廉价的缓存读取，且压缩本身也只相当于一次普通请求，但这些庞大的读取量依然会实打实地计入你的使用额度，积少成多。

使用 /autocompact 300k 可以将触发压缩的阈值提前到 300K。这样既能让对话历史始终保持精简，又能避免单次请求的上下文无限膨胀，从而大幅节省长对话的 Token 消耗。

引用内容

Lydia Hallie ✨ @lydiahallie

中文译文

为了避免一些误解：auto-compact 是会做摘要的。当它运行时，你的整个对话会被替换为一个简短的摘要。它不会保留最后 100 万 token 的内容。

约 967K 的数字只是在 1M 模型上运行时才会出现。压缩本身只是一次请求，读取的 token 量大约和你在它运行前刚发送的那条消息差不多，而且如果缓存仍然有效的话，大部分是缓存读取。

@rohit3a 发现的是：等到 967K 才压缩意味着之前每条消息都会消耗大量 token，因为每条消息都包含了你迄今为止的整个对话。其中大部分是从缓存读取的，价格要低得多（所以只要缓存有效通常没问题），但它仍然会计入你的用量，并随着对话增长而不断累积。

/autocompact 400k 可以让它在 400K 时就进行摘要，这样你的消息就不会变得那么大。

原文

Just to avoid some confusion: auto-compact does summarize. When it runs, your whole conversation is replaced by a short summary. It doesn't keep the last 1M tokens around.

The ~967K is only when it runs on 1M models. Compacting itself is just one request that reads about as many tokens as the message you sent right before it, and it's mostly cache reads if your cache is still warm.

What @rohit3a found is that waiting until 967K means every message before that point uses a lot of tokens, because each one includes your whole conversation so far. Most of it is read from the cache, which is much cheaper (so this is usually fine as long as your cache is warm), but it still counts toward your usage and adds up as your conversation grows.

/autocompact 400k makes it summarize at 400K instead, so your messages never get that big.

06｜Grok Bot 额度消耗机制实测

来源（X） · @leaf_sanren · 2026-10-29 16:11

Grok Bot 额度机制天机泄露😱

1. Grok Bot 的额度不按消息条数扣，按 Bot 实际干的活扣：模型调用、上下文体积、工具调用全都算。每走一步都要把整段历史重读一遍，最忙的 Bot 每步要重读 8-9 万 token。

2. 搜 X 走 Bot 自带的免费额度（每分钟 30 次、每天 1000 次），不扣周额度。但搜回来的大批推文要存文件，别贴进聊天。

3. 最大的坑是看图看视频。截图、视频帧、扫描件直接丢进对话，上下文会迅速膨胀；有人一天发 4 张图、搜一次、处理两份扫描件，就吃掉顶档周额度的 11%。我自己用它剪视频，也是掉得最快的。先让命令行工具出文字摘要，Bot 只读摘要。

4. 读网页别让它截图点点点。同一个网站，Computer use 约 21.3 万 token，浏览器里跑脚本约 5.1 万，纯脚本执行期间模型 0 token。能走 API 连接器就别开浏览器。

5. Bot 当包工头，别当搬砖工。在它的云电脑上装 Grok Build、Codex、Claude Code、Pi + DeepSeek 这些 CLI，重活让 CLI 跑，Bot 只调度。有人把写代码交给 Grok Build，两天半 Bot 池用了 70%，开发池才用 6%。

6. 但这里有个坑我天天踩：CLI 跑完没有明确提醒，Bot 派完活就睡了，经常忘了回来查，你就干等半天没结果；让它一直盯着，又费 token 效果还一般。目前看到的解法是 Webhook 叫醒：CLI 一跑完就把 Bot 叫起来验收，范凯和一泽都开源了现成的。

7. 定时任务是隐形吸血鬼。每 15 分钟跑一次 = 一周 672 次唤醒，改成每小时 = 168 次，一天 3 次 = 21 次。没变化也照样扣。

8. 盯数据的活改成"有变化才叫醒"：在云电脑里跑个脚本盯着，不过模型、不扣额度，有变动再用 Webhook 叫醒 Bot。注意 Webhook 实测约 1 小时 200 次上限，打满会中断。

9. 同一个 Bot 别聊太久。聊长了它会自动压缩上下文，你根本不知道它压掉了什么，效果越来越差，每一步还要重读一大坨。一个任务开一个新对话，长资料存成文件，聊天里只回结论和路径。放着不聊的旧对话不扣额度，不用清。

10. 别开 Bot 群聊。群里每条消息每个 Bot 都要读一遍，纯重复浪费；有个团队账号约三分之一的轮次是 Bot 在互相叫醒。让 Bot 之间单独对话，消耗反而可控。

11. 同理，别让主 Bot 一次给所有 Bot 派活。我之前有个定期更新记忆、推送文件的任务，主 Bot 每次给所有 Bot 发一遍，它们就各自把文档重新总结一遍。可我平时就让它们日常总结了，这一轮纯属重复烧额度。

12. 先小样本，再放量。复杂任务先跑 1-2 个样本，停下确认再继续；同一步失败 2 次就让它停下来问你。有人 2 小时试错就烧掉过半周额度。

13. 两个无效技巧：想切轻量模型省额度——没有模型选择器，系统自动分配；多订几份想叠加——不叠加，只用额度高的那份。

14. 现在是大一统订阅：Grok、Grok Bot、Cursor 共用一个每周池。Grok Bot 从 $30 的 Premium 起才有，Super $100 是它的近 4 倍，Ultra $200 是 12 倍多。第三方模型不在池子里，按 API 原价另算。

15. 官方没公布每档多少 token。有人从 Cursor 后台反推：$30 周限额约 2.76 亿 token，$100 约 13.27 亿，$200 约 44 亿（个人实测反推，非官方）。
