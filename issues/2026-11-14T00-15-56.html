06｜CanyonOS按智能体独立扩缩容器

来源（X） · @shao__meng · 2026-11-13 08:27

CanyonOS：多智能体工作流可以只给忙的智能体加副本
https://github.com/CanyonCodeCoreAI/canyonos

按智能体扩缩，也按智能体追踪

各智能体很少同时需要同一份容量：规划器很快结束，请求却可能堆在某个研究智能体后面。整应用一起扩，空闲部分也会被加机器。CanyonOS 把每个智能体做成独立的容器服务，自带队列和副本上下限。智能体之间仍写成普通方法调用，由本地控制器转发并立即返回 Future，可以同时发出多路调用，而不必改写成异步代码。扩缩策略写在 scaling.yaml，对每个智能体分别计量：看每副本每分钟完成的请求数，或该智能体全部副本上的排队长度。默认约每 5 秒采样，连续 4 次越线才加减一个副本，大约 20 秒反应一次；缩容会先排空再停。数据库和入口不参与扩缩，副本下限至少为 1。

智能体之间的调用，以及经内置 LLM 网关的模型请求，由平台记下路径、耗时、token 和估算费用，并可导出到 OpenTelemetry。不必在业务代码里加追踪装饰器，但仍要按「一个智能体一个文件」接入，或用转换助手改写 LangChain、LangGraph 项目。可部署到本机 Docker、自有 AWS 或 Kubernetes，模型需提供 OpenAI 兼容接口。

一次演示，以及现在的边界

用官方 portfolio 示例分析了 40% 苹果、35% 微软、25% 英伟达，回看过去一年。跟帖截图是本地 canyonos test：Test passed，约 22.4 秒，价格来源为 yfinance。他写道有 10 个可追踪步骤、两次 LLM 调用，估算费用 0.000184 美元，但截图里看不到这张明细。这些是作者单次自报，不是独立评测。费用按平台价目估算，会用到 LiteLLM 的报价，不是账单原件。已部署接口没有内置鉴权，看板默认关闭登录。

中文译文

多代理工作流存在扩展性问题！

同一工作流中的代理很少在同一时间需要相同的容量。

假设你有一个规划器（planner）、多个研究代理和一个最终综合代理。

规划器可能很快完成，而请求开始在某个研究代理后面堆积。对整个应用进行扩展会在所有地方都增加容量，尽管实际上只有工作流的一个部分需要它。

CanyonOS 是一个开源的、工作流感知的平台，面向多代理 Python 应用，也是你各个代理之间的运行框架。

每个代理作为独立服务运行，拥有自己的队列和副本限制，因此繁忙的研究代理可以获得额外容量，而规划器和综合代理则保持原位。

它还处理代理之间的通信，并让你在请求进来之后能看到整个工作流中发生了什么。

CanyonOS 记录请求所经过的路径，包括它调用了哪些代理、并行分支、模型使用情况、执行时间和预估模型成本。

而且你不需要在整个代理代码中添加追踪装饰器或单独的插桩 SDK。你仍然将工作流与 CanyonOS 集成，但追踪由平台层处理。

我还通过它运行了一个多代理投资组合分析工作流，由不同的代理分别处理三只股票。

单个请求在工作流中产生了 10 个可追踪的步骤，我可以看到哪些代理运行了、LLM 调用发生在何处、每个阶段耗时多久，以及预估模型成本。

对于多代理应用而言，能够独立操作每个代理同时仍能看到完整执行路径，随着工作流的增长变得越来越有用。

CanyonOS 是开源的。GitHub 仓库链接在评论区！

原文

Multi-agent workflows have a scaling problem!

The agents inside the same workflow rarely need the same amount of capacity at the same time.

Say you have a planner, multiple research agents, and a final synthesis agent.

The planner might finish quickly while requests start piling up behind one of the research agents. Scaling the entire application would add capacity everywhere, even though only one part of the workflow actually needs it.

CanyonOS is an open-source, workflow-aware platform for multi-agent Python applications and the harness between your agents.

Each agent runs as a separate service with its own queue and replica limits, so the busy research agent can get additional capacity while the planner and synthesis agents stay where they are.

It also handles communication between the agents and gives you visibility into what happens across the workflow after a request comes in.

CanyonOS records the path a request took, including the agents it called, parallel branches, model usage, execution time, and estimated model costs.

And you don't need to add tracing decorators or a separate instrumentation SDK throughout your agent code. You still integrate the workflow with CanyonOS, but tracing is handled at the platform layer.

I also ran a multi-agent portfolio analysis workflow through it with separate agents working across three stocks.

A single request produced 10 traceable steps across the workflow, and I could see which agents ran, where the LLM calls happened, how long each stage took, and the estimated model cost.

For multi-agent applications, being able to operate each agent independently while still seeing the complete execution path becomes much more useful as the workflow grows.

CanyonOS is open source. Link to the GitHub repo in the comments!
