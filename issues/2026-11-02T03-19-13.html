01｜领域专用小模型新书聚焦本地部署

来源（X） · @Zen_with_AI · 2026-11-02 02:06

推荐一本 @ManningBooks 的新书《Domain-Specific Small Language Models: Efficient AI for local deployment》，《领域专用小语言模型：面向本地部署的高效 AI》作者 Guglielmo Iozzia，2026 年 5 月出版，

书的内容是，做垂直领域的任务，大模型庞大的容量有时反而帮倒忙。用领域数据训练的小模型，跑在普通硬件上，也能在特定任务上做出高质量的结果。

全书 15 章，骨架是：

微调->量化->领域生成->部署服务
（第 2、3 章 -> 第 5、6、9 章，含 ONNX -> 第 7、8 章，生成 Python 代码和蛋白质结构 -> 第 11 到 15 章，含笔记本运行、RAG、Agent）

看目录有两点值得说。一是它把"在自己的机器上跑起来"当成目标，量化、性能分析、安全 API、笔记本运行都有专门章节。二是书里的 RAG 系统和 Agent 只靠小模型，不依赖基础大模型的调用成本。适合熟悉 Python 的 AI 工程师。

02｜MPTCP 漏洞未波及普通 Go 服务

来源（X） · @fishjar · 2026-11-02 01:44

这几天安全圈和科技博主全在疯传一条核弹级预警：任何暴露了 TCP 端口的 Linux 服务器，只要用 Go 写的 Web 服务就会被黑客远程完全接管。

评论区瞬间哀鸿遍野，无数公司的后端运维连夜爬起来打内核补丁。但只要你把 Go 标准库的 net 包源码和 Linux 内核的 socket 机制看一遍，就知道这是最典型的概念移花接木。

这个漏洞（CVE 涉及的内核多路径 TCP 模块）确实存在，严重级别也确实高，但攻击的前提条件被自媒体故意掐掉了。

Go 语言的 net.Listen("tcp", ":8080")，底层调用的是操作系统最原始的 AF_INET、SOCK_STREAM 和 IPPROTO_TCP。
它走的是规规矩矩的单路径普通 TCP 协议栈，根本不会主动去协商 MPTCP。

MPTCP（MultiPath TCP，RFC 8684）在 Linux 5.6 之后确实合入了主线内核，但它是一个必须显式声明的特异协议。
除非你在代码里显式写了 IPPROTO_MPTCP，或者服务器管理员手动在 sysctl 里开启了 net.mptcp.enabled 并且配置了强制路由代理，否则内核根本不会把进来的普通 TCP 握手包扔给 MPTCP 状态机处理。

真正受影响的，是那些跑在移动回传网络、跨多网卡聚合或者特定 CDN 边缘节点上、主动启用了 MPTCP 的特定网关。

普通跑在内网或者反向代理后面的 Go 业务服务，被这波恐慌吓得睡不着觉，纯粹是替概念炒作买了单。

这个名字描述了一种架构关系。Super-agent在执行工作的主agent之上添加了一层，而sub-agent则在其之下添加一层。"Super"并不是对更高级智能的声称。

两层设计回应了一个未解决的记忆问题
关于如何实现长期agent记忆，目前仍没有共识。截至他发文时，DeepSeek Harness本身尚无跨会话的内置长期记忆，不过他暗示这可能会很快改变。
在此背景下，团队将跨任务的持续性和维持任务吞吐量视为长运行agent系统中的一个根本性权衡。
两层架构提供了一种分解该问题的方式。崔并不声称其特定实现是最优的。

该原型仅实现了所提设计的一部分
该代码仓库 dsh-superagent-prototype 仍是一个探索性原型。
文章中讨论的一些想法，包括将计算与状态和执行环境解耦，在DeepSeek Harness中实现仍需要大量工作。因此，发布的代码不应被解读为对每个架构提案的完整实现。

内部验证留下了大量部署问题
崔将系统在内部使用中相对较低的复杂度部分归因于工程和运营场景中有意的简化。
该原型仅在公司内部一个小型、可信的环境中进行了验证。更广泛的部署仍面临第8节中提出的未解决问题：扩展两层架构、超越会话的人机协作、上下文边界与agent间通信，以及安全与隐私。
他的描述将Super-agent呈现为一个需要探索的方向，具有可行的内部经验，并明确了已展示内容的边界。

DeepSeek’s Super-agent: A Final Reviewer Explains the Design and Its Limits
Zhihu contributor @tianyi (崔添翼), from DeepSeek’s product department and one of the final reviewers of its Super-agent design article, explains the proposal’s central trade-off: continuity across tasks versus task throughput.
He credits his DeepSeek Harness colleagues, especially lead author Yujia Qiao, with the main write-up, architecture, code and experiments.

"Super" means a layer above the working agent
The name describes an architectural relationship. A Super-agent adds a layer above the main agent doing the work, whereas a sub-agent adds one below it. "Super" is not a claim of superior intelligence.
Cui explicitly rejects the idea that the team has introduced an entirely new theory. In conversations with other teams, he found similar architectures had already been explored months earlier. The harder challenge, he argues, is identifying and committing to the right long-term direction.

The two-layer design responds to an unresolved memory problem
There is still no consensus on how to implement long-term agent memory. As of his post, DeepSeek Harness itself had no built-in long-term memory spanning sessions, though he suggested that might change soon.
Against that backdrop, the team sees maintaining continuity across tasks and sustaining task throughput as a fundamental trade-off in long-running agent systems.
The two-layer architecture offers a way to decompose that problem. Cui does not claim its particular implementation is optimal.

The prototype implements only part of the proposed design
The repository, dsh-superagent-prototype, remains an exploratory prototype.
Some ideas discussed in the article, including decoupling computation from state and execution environments, still require substantial work to implement in DeepSeek Harness. The released code should therefore not be read as a complete implementation of every architectural proposal.

Internal validation leaves substantial deployment questions
Cui attributes the system’s relatively low complexity in internal use partly to deliberate simplifications in engineering and operating scenarios.
The prototype has only been validated in a small, trusted environment inside the company. Broader deployment still faces the open questions identified in Section 8: extending the two-layer architecture, human-agent collaboration beyond sessions, context boundaries and agent-to-agent communication, and security and privacy.
His account presents Super-agent as a direction to investigate, with working internal experience and explicit limits on what has been demonstrated.

05｜PyTorch pin 提速源于免拷贝

来源（X） · @liumengxinfly · 2026-11-01 22:31

一直没搞明白为啥 pytorch 里的 pin memory 能加速 CPU Memory 和 GPU Memory 之间的传递。

从字面上看 pin memory 就是把内存页锁住不让换出，能避免缺页中断的开销。但是理论上如果关闭了 swap，使用 mlock 锁住内存，内存页一样不会被换出，为啥还需要用一个新的 pin 操作呢？

因为 mlock 只能解决内存页不被换出，解决不了物理地址的变化。在 numa balancing, compaction 和 fork 的情况下，同一个 tensor 对应的物理地址可能发生变化。而 CPU Memory 和 GPU Memory 之间传递使用了 DMA，需要提前提交要迁移的内存页物理地址，如果这个期间发生了这些物理地址变化的操作也回到只传递失败。

但这解释了为什么需要 pin，没有解释为什么 pin 之后性能会好。真实原因是为了避免 DMA 的复制错误，如果不是 pin memory 的传递，CUDA 会额外创建一个 pin memory 的 buffer 把原先的 tensor 复制一份到这个 buffer 然后再 DMA。为什么不原地 pin？因为 pin 需要按 page 操作然后 DMA 后还要 unpin 反而不如额外创建个 buffer 快。

所以所谓的 pin memory 速度快，更多的是因为 pin memory 没有这一部分 DMA 前的准备开销。但 pin 这个动作本身的开销是很大的，每次 pin 其实性能也不好，所以 pytorch 里还有一套专门的池化管理机制，来平摊掉这部分开销。

说了这么半天就想说一个表面的 pin memroy 性能更好其实是个很复杂的权衡，不明就里就去用并不会达到预期的效果。

06｜Mika、DSH Go 解决安卓后台

来源（X） · @xulijian1994 · 2026-11-01 13:29

最近看了两个挺不错的安卓开源 Agent，Mika 和 DSH Go，目前 GitHub 分别有约 2.9K 和 3.7K Stars。

专门翻了一下它们的实现，发现这两个项目都不简单，而且定位还挺不一样的。

先说 Mika，我比较喜欢它的一个设计，就是给 Agent 单独开一块虚拟屏幕。比如我让它去微信整理消息、刷小红书总结内容，或者去 BOSS 直聘处理招聘信息，它可以自己在后台操作，我前台该干嘛干嘛，互不影响。不需要 Root，也不需要一直连着电脑。

它还有几个细节我觉得做得不错。比如一次可以批量执行最多 20 个操作，减少模型来回思考的开销；成功执行过的任务还能保存操作经验，下次遇到类似任务直接复用。再加上定时任务、条件触发，以及 MCP 接入，甚至可以让电脑上的 Codex 去指挥手机干活。

DSH Go 则是另一条路线，我觉得它对开发者更有吸引力。

它直接在安卓手机里通过 PRoot 跑 Ubuntu、Node.js 和 DeepSeek Harness，相当于把一套 Coding Agent 环境搬到了手机上。不仅能在手机本地写代码、执行命令，还能通过 SSH 或 DSH Remote 连接电脑，接着之前的开发会话继续干。

而且它也支持直接控制手机 App，Android 14 以上可以借助 Shizuku 或 ADB 实现后台虚拟屏操作。

看源码时还发现一个有意思的细节，DSH Go 在点击界面元素之前会重新检查目标，尽量避免页面变了还按照旧坐标乱点。对于发送消息、删除内容、付款这些操作，它默认也比较谨慎，会要求用户确认。

Mika 在这方面相对放得开一些，普通操作默认可以直接执行，主要在涉及花钱时要求确认。两种策略各有取舍。

如果让我选，日常手机自动化我会更倾向 Mika，它的功能基本就是围绕让 AI 替你操作手机来设计的。

但如果是我自己平时的开发场景，DSH Go 可能更实用。毕竟我更需要的是随时拿起手机，就能接着电脑上的 Coding 任务继续干活。

这两个项目让我比较期待的一点，是安卓端的 Agent 开始认真解决后台运行、权限管理、任务恢复这些实际问题了。比单纯演示 AI 自动点击手机屏幕有价值多了。
