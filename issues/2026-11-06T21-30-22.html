01｜Agent 记忆架构收敛为九个问题

来源（X） · @Suercha007 · 2026-11-06 13:51

之前做 Agent 的时候，重点研究过记忆架构，当时觉得很复杂，但其实把整个 agent 运行逻辑搞清楚之后，剩下的也就是工程和业务上的事情了。

你只需要弄明白以下的问题，你的记忆架构基本上就不会出问题，用什么框架都无所谓。

无非就是弄明白何时写、写什么、写到哪里、冲突如何解决、生命周期如何管理、召回时机、怎么召回、怎么注入、安全怎么保证、自学习。

其他的，没了。

引用内容

陈大黄 @realchendahuang

目前 AI Agent 记忆的几个主流技术路线基本可以收敛为三类：

第一类是全自动向量与图谱记忆库，典型代表是 OpenViking、Mem0、Letta 这类项目。

实现机制是在客户端挂 Hook 拦截会话，后台用大模型异步抽取实体和事实，存入向量库和图数据库；在每次输入时，通过前置意图分析模型判断是否触发检索，再经重排注入上下文。

优势在于对上层无感，跨工具、跨会话被动积累历史事实，适合多客户端共用一个全局大脑。

软肋是工程链路极长，每次交互前多出至少一次模型推理和向量检索，天然增加一到两秒的物理延迟；自动抽取的碎片缺乏人工校验，容易堆积过期失效的信息；同时向量数据库强绑定特定的 Embedding 模型，一旦换代全库都要重建。

第二类是纯静态结构化文档流，也就是目前主流 IDE 和 Agent 广泛采用的规则文件与 Skills 架构。

实现机制是由人或工程脚本显式沉淀 Markdown 文件，如 AGENTS.md、CLAUDE.md、系统提示词或针对特定任务按需激活的上下文卡片。

优势在于百分之百确定，毫无黑盒幻觉，本地直接加载零延迟，改动走 Git 记录清晰可见。

软肋在于依赖人工维护与分层设计，如果项目过于庞大且规则没有做好按需拆分，容易单次塞入过多上下文导致注意力稀释；且无法自动捕捉跨会话零散出现的个人临时习惯。

第三类是混合投影模式，以本地 Markdown 为唯一真源，把向量检索降级为轻量辅助索引。

实现机制是所有业务事实、架构决策和硬性规则依然落在纯文本文件中，只有在文档量突破百万字、关键词检索难以准确定位时，才在本地挂载轻量向量索引辅助打捞。

优势在于兼顾了纯文本的可控性与语义联想的宽容度，即便索引损坏或换模型，从 Markdown 重新扫一遍就能原地重建。

对于绝大多数独立开发者和中小型项目，个人日常编码与任务执行，第二种纯静态 Markdown 配合 Git 管理是综合体验最好的选择，成本最低且没有意外。

只有当你面对海量跨月、跨工具的松散交互记录，且完全无法靠人工分类归档时，再考虑引入第一类独立的服务型记忆底座。

04｜ComfyUI 换脸换姿换装分段独立跑

来源（X） · @servasyy_ai · 2026-11-06 10:02

发现一个 ComfyUI 宝藏项目！
自带 1499 个头像、1439 种姿势、1407 套服装，全做成了可视化图库！

不用到处找参考图，鼠标点哪张，当场给角色换脸、摆动作、换衣服！

最爽的是三个图库直接接进同一套工作流，选好图、拨一下开关，想单换哪样就换哪样，也能三项一口气全换。

项目里头有几个设计挺讲究：
1、换脸、换姿势、换装，分三段独立跑
三路参考图分开喂，按「换头 → 换姿势 → 换装」串起来，每段各配一个开关。
想保住现在的脸和衣服、只改个动作，单独打开姿势开关就行，再也不用把所有要求全挤进一段提示词里赌运气。
2、Qwen 图像编辑模型打底，精度和速度分开算
演示配置里，挑细节的换头用 Qwen Image 2.1 BF16 保精度，换装直接上 INT8 量化版提速（单段 20 多秒就能跑完），文本编码器搭的是 Qwen3-VL 8B。
姿势阶段还单独挂了 PoseStudio V1.1 LoRA。脸、动作、衣服各管各的，哪一步出问题直接单独调哪一步，不用整张图推倒重来。
3、图库直接连节点，省掉来回找图、上传
头像能按正脸、侧脸、发型筛，姿势和服装支持分类搜索。看中哪张点一下，参考图直接回传进对应节点。

仓库做好了单项替换和三段全流程的 JSON，拖进画布配齐模型就能跑。

我觉得它最顶的地方，是把做角色时最折磨人的重复活儿全收进了一套流程里。拿来做漫画分镜、短剧角色定妆，同一批脸、动作和衣服随时调出来反复组合。

不过也有两个实测边界得注意：
一是换装时偶尔还会有色差（把默认的 20 步往上调能改善），毕竟是局部重绘，别把独立开关当成其他细节绝对不动。
二是代码虽然 MIT 开源，但那四千多张图来自第三方图库，有单独的授权限制，自己用没事，别连图带包拿去商用或分发。

项目地址：
https://github.com/JGRFw/comfyui-aicg3d-PoseSwap

05｜Agent 饱和测试保障语义稳定性

来源（X） · @unclebobmartin · 2026-11-06 21:30

中文译文

饱和测试。我使用 crapper 和 mutator 来确保系统中的每个表达式都被测试覆盖。如果一个表达式被修改，一个或多个测试将会失败。

这过去是不切实际的。我们根本负担不起创建这么多测试。当需求变化时，我们也负担不起修改这么多测试。负担太重了。

现在这变得微不足道了。在 crapper 和 mutator 的鞭策下，agent 们会编写这些测试并让它们通过。当需求发生变化时，他们会编写新的测试并修改旧的测试。

这些都不能证明系统是能工作的。那要靠人类来判断。人类可以使用 gherkin 之类的工具来做这件事，或者使用手工测试。

饱和测试所提供的是语义稳定性。当需求发生变化，需要添加和修改代码时，这些测试确保这些变更不会无意中破坏系统中不相关的部分。

原文

Saturation Testing. I use crapper and mutator to ensure that every expression in the system is covered by tests. If an expression is changed, one or more tests will fail.

This used to be impractical. We simply could not afford to create that many tests. We also could not afford to change so many tests when requirements changed. The burden was too high.

Now it’s trivial. The agents, under the lash of crapper and mutator, will write those tests and make them pass. And when requirement changed, they’ll write the new tests and change the old tests.

None of this proves that the system works. That’s up to humans to judge. Humans can do that with tools like gherkin, or they can use manual tests.

What the saturation tests provide is Semantic Stability. When the requirements change, and code has to be added and changed, those tests ensure that those changes do not inadvertently break unrelated parts of the system.

07｜MCP 全量挂载推高 token 成本

来源（X） · @fishjar · 2026-11-06 12:13

现在整个行业都在言必称 MCP（Model Context Protocol），好像它是某种颠覆性的前沿 AI 黑魔法。

把抓包工具挂在线路上看一眼原始报文，真相朴素得令人发笑：底子就是跑在 stdin 或者 HTTP 上的标准 JSON-RPC 2.0。

客户端发一个 initialize 握手，服务端回一个支持的 capabilities 列表；客户端发 tools/list 查工具，服务端把名字和 JSON Schema 吐回来。

这个协议最大的贡献根本不是技术突破，而是建立了一套工业界公认的接口合同。

但在企业落地时，真正要命的问题才刚浮出水面：每一个挂上来的 MCP 工具，它的参数说明和返回值定义都会原封不动塞进大模型的 Context Window 里。

你挂了 30 个企业内部微服务工具，哪怕这轮对话只问了一句“你好”，两万个 token 的 schema 已经先在后台烧掉了。

协议统一了调用标准，但没有帮你解决 token 账单。把整个系统无脑暴露给 MCP，是当下最昂贵的架构偷懒。

协议拆解参考：https://mcp-explained.com/
