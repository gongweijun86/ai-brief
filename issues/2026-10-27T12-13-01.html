https://pub-sdn-001.mowen.cn/mo/release/mo-agent/Mowen-0.6.0.dmg

墨问 Bots 可以做的事情：

1、创建你的 Bot，为每个 Bot 设置不同的模型和思考等级，Bot 会根据对话自动选择思考等级回复问题和做任务，最高思考等级是用户设定的那个。

2、你可以和 Bot 一直对话，完成任务，不需要像 Agent 那样切换会话，Bot 会智能地管理你的长期上下文和记忆。

3、多个 Bots 之间可以通讯，用户可以让 A 通知 B、C 做自己擅长的任务。甚至，你可以为你的 Bots 们设置一个 CEO。

4、可以拉群，设定群负责人，你和你的 Bots 们就可以在群里做各种各样的协作了。我有日常交流群，咖啡群，Vibe Coding 群和产品群。我可以让 Bot 通过 Herdr 驱动 Codex 和 Cursor 做编程任务，可以让不同模型的 Bot 为我做产品调研，也可以讨论如何制作一杯美味的瑰夏咖啡。

你会发现这和使用单一模型是很不一样的，不同的视角会在讨论中自然呈现，非常有意思。

5、可以用自然语言为 Bots 设定自动任务，比如监控 tibo 的重置消息，每隔三小时看一下墨问动态，工作日定时看盘等等。

04｜百度OCR 2让长文档解析开销恒定

来源（X） · @shao__meng · 2026-10-27 19:13

百度开源 Unlimited OCR 2：超长文档解析，注意力开销尽量不随页数涨

Unlimited OCR 2 是面向「几十到几百页」文档的开源 OCR / 版面解析模型，3B/A0.5B 的 MoE 模型架构：用 SR-SWA 把文本–视觉注意力压到固定大小的工作参考集，再配合按页分块解码，让超长文档能在有限上下文里跑完，并声称逐步解码的延迟和显存几乎不随文档变长而涨。

开源模型：https://huggingface.co/baidu/Unlimited-OCR-2

相对 v1 改了什么
v1（R-SWA）已能做多页端到端解析，但论文写明输入大约卡在 40 页，也因此没上 MarathonDocBench。v2 把解码器注意力升到 SR-SWA（Sparse Reference Sliding Window Attention），并加上 Unlimited-Horizon Decoding；骨干仍是 DeepEncoder + MoE 解码器一路，从 v1 权重再训。口号从「长程」推到「不限程」。

SR-SWA 在做什么（技术报告口径）
长文档会让文本–视觉注意力很贵。R-SWA 管住了局部交互，但远端视觉 token 仍会随页数涨。SR-SWA 的做法是：把交互压进固定容量的工作参考（README 举例 512 tokens）。大致两步：Page Gate 先按页收窄候选；Token Sieve 再对块做摘要打分，用 α-entmax 稀疏路由，只保留 top-k 远端块加局部窗口。解码侧按页切块，页边界重叠 1 页并复用 KV 尾部，避免超长时显存爆掉。作者称百页量级上，逐步速度相对 Full Attention 约 7.0×、相对 R-SWA 约 5.6×。

05｜skill-diet为Skill减重

来源（X） · @shao__meng · 2026-10-27 17:58

[开源 Skills 推荐] skill-diet 给 Skill 减重：用评测保证「更瘦但不更差」

skill-diet 是一个管其他 skill 的 meta-skill：一边把臃肿 SKILL.md 压薄并校对工具是否过时，一边给后续每次改 skill 立规矩；瘦身版只有在「旧 skill / 新 skill / 无 skill」同任务评测里至少不输才会留下。作者 @nicopreme 测试在真实 skill 上可砍 70–80% token，且测出文档里已失效的命令。
https://github.com/nicobailon/skill-diet

Agent 每次用 skill 都会读完整 SKILL.md。常见冗余是：多数任务用不到的细节、模型本就会的常识、写给人看的说明、可用一条原则代替的长列表；教 CLI/API/SDK/MCP 的 skill 还会抄一份工具手册，工具一变就过期。让 agent「更新一下 skill」通常只会越写越长。

它做了两件事
· Put on a diet：重写、修与工具不符之处；只有评测过关才保留瘦版。
· Keep lean：之后每次增补都先过一套门槛，避免教训和代码变更把体积又养回来；相对上次 diet 大约涨 10% 就要再做一轮。

可以直接说：put the deploy skill on a diet / is this skill still accurate for the current CLI? / add this lesson to …。

分层：事实放在「刚好够用」的最低层
· skill description：每个场景一条触发，几乎每个会话
· SKILL.md：几乎每任务都要的规则，启用该 skill 时
· references/：少数任务才要的细节，点到该场景时
· 工具自带 help：flag、合法值、示例，选到那条命令时
· 工具回复 / 报错 / checker：正确名、修法、下一步，调用出错或猜错时

教工具的 skill 还多两步：精确字段名留在工具侧；机械错误优先靠更清晰报错、测试或 linter，而不是再写一段 prose。只用人工触发的 skill 可标 user-only，避免 description 每会话白占配额。

一次 diet 在做什么
测体积与典型任务加载量 →（若教工具）用运行或源码行证明 skill↔工具不一致；从 session log 找高频调用、只把高频写全；看 agent 是否真打开 skill，少打开则把规则下沉到工具报错；必要时裁自家工具 schema（schema 每请求都带）→ 砍模型已知与仅人类需要的文字 → 同任务跑旧 / 新 / 无 skill，瘦版不优于「随机波动可解释」就失败。命令优先写成 agent 会敲的 usage lines（作者给的相对代价：表 1.5×、TS 类型 1.6×、JSON Schema 2.8×、OpenAPI 4.7×）。

之后每次改 skill：停在第一个能处理的步骤
· 先修工具（报错 / check），别堆文。
· 新会话不写也会对，就别加。
· 改已有那一行，别另起一段。
· 放到仍「来得及」的最低层。
· 写规则不写故事（故事进 commit）。代码改了 skill 依赖的名字或行为，同一次变更里改 skill；commit 记前后体积。

06｜Repo2RLEnv生成RL环境

Repo2RLEnv（Hugging Face 开源）和AgentEnv Framework（Scale AI 开源）从不同角度来实现RL环境。

Repo2RLEnv是输入一个 GitHub 仓库，它自动从已合并的 PR、commit 历史中提取任务，生成完整的 Harbor 格式环境（包括沙盒、指令、私有验证器）。验证器直接跑仓库自己的测试用例打分。

AgentEnv Framework（Scale AI 开源）：提供标准化接口定义环境（MCP 工具、沙盒状态）、任务（步骤 DAG）和评分逻辑。可以用插件扩展，把真实应用或模拟工作场景打包成可重复训练的环境。

一些垂直领域可以用AgentEnv Framework这类框架定制RL环境，也会有领域（或是公司）的Repo2RLEnv，根据领域一些特性，工程师做出类似Repo2RLEnv类工具，自动编译出领域的RL环境。这都对传统的数据标注类业务来讲大大的提升了效率，所以硅谷最近出了很多非常小的RL环境团队，大部分都是非常小，但收入很好的。他们就在往这种方向上靠拢。

08｜最终一致性先为每屏定读旧规则

来源（X） · @milan_milanovic · 2026-10-20 14:29

中文译文

最终一致性 bug 在"最终"之前就开始了

当你读到"最终一致"时，通常听起来它只会有一个小延迟。这意味着当写入停止时，副本将会追上数据。

但问题是，在此之前会发生什么呢？

以下就是发生的情况：

𝟭. 𝗥𝗲𝗽𝗹𝗶𝗰𝗮𝘁𝗶𝗼𝗻 𝗹𝗮𝗴（复制延迟）

主节点在每个副本拿到数据之前就确认了写入。从慢副本的读取会返回旧值。

𝟮. 𝗥𝗲𝗮𝗱 𝘆𝗼𝘂𝗿 𝘄𝗿𝗶𝘁𝗲𝘀（读己所写）

写入之后，读取携带该版本。落后的副本需要等到追上为止。

𝟯. 𝗖𝗼𝗻𝗳𝗹𝗶𝗰𝘁 𝗿𝗲𝘀𝗼𝗹𝘂𝘁𝗶𝗼𝗻（冲突解决）

当多个节点接受写入时，两个节点可能在同步之前接受不同的写入。最后写入胜出（Last write wins）会保留一个并 𝗱𝗿𝗼𝗽𝘀 𝘁𝗵𝗲 𝗼𝘁𝗵𝗲𝗿 𝘄𝗶𝘁𝗵𝗼𝘂𝘁 𝗮𝗻 𝗲𝗿𝗿𝗼𝗿（在没有报错的情况下丢弃另一个）。合并（merge）则会保留两者。

𝟰. 𝗤𝘂𝗼𝗿𝘂𝗺（法定人数）

有 3 个副本时，每次写入等待 2 个，每次读取询问 2 个。因为 2 + 2 > 3，每次读取至少能到达一个拥有已确认写入的副本。

𝟱. 𝗛𝗶𝗻𝘁𝗲𝗱 𝗵𝗮𝗻𝗱𝗼𝗳𝗳（暗示移交）

当一个副本宕机时，另一个节点暂存其写入，等副本恢复后将其投递过去。

𝟲. 𝗥𝗲𝗮𝗱 𝗹𝗲𝗽𝗮𝗶𝗿（读取修复）

读取发现某个副本已过时，便将最新值写回给它。

在我们添加读副本之前，应该逐个功能地决定该读取是否允许是旧的。产品列表可以稍有延迟。用户刚保存的个人资料则不行。

在第一个副本上线之前，把每个屏幕的这个决定写下来。

原文

Eventual consistency bugs start before "eventually"

When you read "Eventually consistent", it usually sounds like it will happen with a small delay. And this means that when writes stop, replicas will catch up with the data.

But the question is what happens before this?

Here is what happens:

𝟭. 𝗥𝗲𝗽𝗹𝗶𝗰𝗮𝘁𝗶𝗼𝗻 𝗹𝗮𝗴

The primary confirms a write before every replica has it. A read from the slow replica returns the old value.

𝟮. 𝗥𝗲𝗮𝗱 𝘆𝗼𝘂𝗿 𝘄𝗿𝗶𝘁𝗲𝘀

After a write, the read carries that version. A replica that is behind waits until it catches up.

𝟯. 𝗖𝗼𝗻𝗳𝗹𝗶𝗰𝘁 𝗿𝗲𝘀𝗼𝗹𝘂𝘁𝗶𝗼𝗻

When more than one node takes writes, two of them can accept different writes before they sync. Last write wins keeps one and 𝗱𝗿𝗼𝗽𝘀 𝘁𝗵𝗲 𝗼𝘁𝗵𝗲𝗿 𝘄𝗶𝘁𝗵𝗼𝘂𝘁 𝗮𝗻 𝗲𝗿𝗿𝗼𝗿. A merge keeps both.

𝟰. 𝗤𝘂𝗼𝗿𝘂𝗺

With 3 replicas, we wait for 2 on every write and ask 2 on every read. Because 2 + 2 > 3, every read reaches at least one replica that has the confirmed write.

𝟱. 𝗛𝗶𝗻𝘁𝗲𝗱 𝗵𝗮𝗻𝗱𝗼𝗳𝗳

When a replica is down, another node keeps its write and delivers it when the replica is back.

𝟲. 𝗥𝗲𝗮𝗱 𝗿𝗲𝗽𝗮𝗶𝗿

A read notices that one replica is stale and writes the newest value back to it.

Before we add a read replica, we should go feature by feature and decide if that read is allowed to be old. A product list can be a little behind. The profile a user just saved cannot.

Write that decision down for every screen before the first replica goes live.

当 LLM 生成文本时，每个新 token 都需要完整地遍历一遍模型，而这一次遍历要从内存中读取模型的全部权重。

基础款 M5 的内存读取速度约为 153 GB/s。一个 4-bit 的 9B 模型大约重 5.2 GB。

所以每次遍历产生一个 token 的话，上限大约是 153 ÷ 5.2 ≈ 29 tokens/s，无论 GPU 算得多快。

uzu 突破了这个上限，它每次遍历产生多个 token 而非一个：

↳ 一个小的起草器（DFlash）一次性为接下来的 16 个位置提出候选。

↳ 一个微型适配器（Weaver，56.7M 参数）从左到右在候选中挑选，使猜测组成连贯的文本，并保留几个备选分支形成一棵树。

↳ 9B 模型在单次遍历中检查整棵树，并保留它同意的最长路径。主模型仍然决定最终输出中的每个 token。

Big win for local LLM inference!

This new inference engine runs LLMs 4x faster than llama.cpp:

I ran Qwen3.5 9B on a base M5 MacBook Pro with three engines:

- llama.cpp: 22.0 tokens/s
- MLX: 25.1 tokens/s
- uzu: 92.1 tokens/s

The video below shows all three runs side by side.

The first two numbers don't mean llama.cpp or MLX are badly built. But both are sitting right under a hard limit of local decoding.

When an LLM generates text, every new token needs one full pass through the model, and that pass reads all of the model's weights from memory.

A base M5 reads memory at about 153 GB/s. A 4-bit 9B model weighs about 5.2 GB.

So at one token per pass, the ceiling is roughly 153 ÷ 5.2 ≈ 29 tokens/s, however fast the GPU computes.

uzu gets past that ceiling by producing several tokens per pass instead of one:

↳ A small drafter (DFlash) proposes candidates for the next 16 positions at once.

↳ A tiny adapter (Weaver, 56.7M params) picks among them left to right, so the guesses form coherent text, and keeps a few alternative branches as a tree.

↳ The 9B model checks the whole tree in a single pass and keeps the longest path it agrees with. The main model still decides every token that ends up in the output.

GitHub repo: https://github.com/trymirai/uzu

(don't forget to star it 🌟)

In my run, each pass of the 9B model produced 7.5 tokens on average. Ordinary decoding produces exactly 1.

The weights and kernels are designed around this too. uzu ships its own 4-bit checkpoints, and on M5 chips it runs the verification step on the GPU's int8 matrix path.

uzu is an open-source inference engine by Mirai Labs, written in Rust with Metal kernels. It has Swift, Python, TypeScript and Rust bindings, so the same engine runs inside a Mac or iOS app.
