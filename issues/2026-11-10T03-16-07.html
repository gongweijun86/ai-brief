01｜Claude Fable 5.2 提速降价发布

来源（X） · @sunruichao · 2026-11-10 10:37

Claude Fable 5.2 和 Mythos 5.2 正式发布：升级了什么，谁能用？

北京时间11月10日凌晨，Anthropic 正式发布 Claude Fable 5.2 和 Claude Mythos 5.2，重点提升编程、推理和视觉能力，面向需要长时间推进的复杂技术任务。

除了能力升级，这次还有两个直接影响使用的变化：输出速度比5.1最高快30%，API输入、输出单价下降20%。Pro用户也迎来一周用套餐额度体验 Fable 的机会。

1．两个名字，怎么选？

Fable 5.2 和 Mythos 5.2 采用同一个底层模型，主要区别在安全防护和开放范围。

Fable 面向广泛的付费用户和API客户，但对高风险网络安全、生物研究等任务设有限制。Mythos 则向通过网络安全或生命科学验证计划等审核的机构开放。

普通个人用户，先看 Fable 就行。不能把 Mythos 理解成升级套餐后就能随意使用的另一个档位。

2．订阅用户能不能直接用？

Max、Ultra 和 Team 高级席位：Fable 已包含在套餐中，最多使用每周总额度的50%，与其他模型共用总额度。Fable 消耗额度更快，用完后可以换模型，或另外按量付费。

Pro 和 Team 标准席位：平时需要用额外用量付费。这次限时允许从套餐周额度中使用 Fable，最多占50%，到北京时间11月17日15:59结束。之后恢复原来的付费方式。

免费账号目前不能用。

网页版、桌面端、手机端可在模型选单里手动选择 Fable 5.2，默认模型不会替你切换。Claude Code 需要2.1.321或更新版本；团队和企业账号还要看管理员是否已开放。

这次还给符合条件的老付费账号送了额度重置。Max、Ultra 等符合条件的套餐，按订阅时长获得1至3次；Pro 等符合条件的账号获得1次。重置资格要求在北京时间11月10日02:00前已建立付费账单，团队席位另有加入时间要求。

重置会退回本周已经花在 Fable 上的额度；如果账号有5小时窗口，同时补满该窗口，但不会提高原有上限。入口在“设置→用量→免费重置”，到期时间以页面显示为准。

3．API降价，快模式怎么收费？

标准API价格从每百万输入／输出 Token 的10／50美元，降到8／40美元，输入和输出都降了20%。

可选的快速模式，输出速度最高达到标准模式的2.5倍，价格为每百万输入／输出 Token 16／80美元。

这里的“快”主要指开始输出后的生成速度，不代表等待第一句话、调用工具或完成整个任务都按同样比例缩短。套餐内的体验权益，也不能当作API账户里多了一笔余额。

4．能力升级，具体用在哪？

编程方面：它更适合跨文件修改、复杂迁移、需要反复测试的长任务。在合适的 Agent 工具环境里，还能协调子 Agent 分工，或把简单工作交给较小的模型。

视觉方面：可以结合文字和图片理解材料，例如读取图表、分析工程图。两款模型都支持100万 Token 上下文、最高12.8万 Token 输出；输入是文字和图片，输出是文字，别把“视觉升级”理解成新增生图功能。

推理方面：重点是需要多步分析、持续验证的问题。这些能力能否帮到自己的项目，仍要结合任务和工具环境看。

官方编程评测有个值得注意的比较：Fable 5.2 开 High 档得45.3%，接近 Opus 5.5 开 Max 档的45.5%，单任务花费约为后者一半。

这说明算成本时，不能只看每个 Token 的单价。不过，这是特定评测与设置下的结果，不能直接换算成所有项目都省一半。

5．它已经做成了什么？

一个案例是操作系统原型。工程师交代目标后，Fable 5.2 从空文件夹开始，协调超过1000个子 Agent 连续工作8天，写代码、测试和审查，做出能在笔记本启动、带文件存储和窗口界面的系统。它仍是原型，距离成熟操作系统还有差距。

另一个案例是电子设备。与 Diode 合作时，它完成了语音助手中枢、USB会议扬声器和掌上虚拟宠物的电路、外壳及软件设计，工程师负责实际制造、装配和测试。三款原型都运行起来了，但还没经过量产产品所需的完整验证与认证。

数学方面：约1000个 Agent 在约30小时内完成了费马大定理证明的 Lean 形式化，让计算机逐步检查推导。这不是重新发现费马大定理的证明。详细实验说明还写明，系统提供了定理清单、部分已证明引理和工具环境，不能说成完全没有基础材料。

这些都是官方报告的案例，不能直接当作每个用户都能复现的成绩。

6．现在值得换吗？

Anthropic 自己的建议是：大多数日常编程和知识工作，先从 Opus 5.5 开始；遇到更困难、需要长时间推进的任务，再考虑 Fable。

如果已经符合体验条件，可以拿一个旧模型反复卡住的真实任务试试：看它能不能推进到完成，中间需要多少次纠正，最后花了多少额度。

一次升级究竟值不值，落到自己手头那件一直没做完的事上，会比只看排行榜更清楚。

04｜Pi Durable 隔离每对话 Agent

来源（X） · @fttt007 · 2026-11-09 11:20

学习 Pi Durable：Per-Conversation Agent。

先理解三个核心概念：

Session：整个会话运行环境，可以包含多个 Conversation。
Conversation：一个独立的聊天对话，保存自己的对话记录。
Agent：负责执行任务的 AI 助手，拥有自己的模型、工具、指令和工作目录。

Pi 的设计很有意思：每个 Conversation 都可以拥有自己的 pi.agent 配置。

例如，同一个 Session 中：
Conversation A 是编程助手，可以读取文件、执行命令。
Conversation B 是翻译助手，只负责翻译。
Conversation C 是研究助手，拥有自己的模型和工具。

它们互不干扰，各自工作。

其中：
configure()：修改当前 Conversation 的 Agent 配置。
agent(context)：获取最终生效的 Agent 配置。
未单独设置的配置，继续使用 Host 默认值。

另外，还要区分 Provider Session ID：它是用于关联模型提供商侧会话的标识，不等于 Pi 自己的 Session。

一句话总结：Session 管理整个会话环境，Conversation 管理独立对话，而 Per-Conversation Agent 让每个对话拥有自己的 AI 工作方式。

这就是 Pi Durable 的核心设计思想之一。

05｜Vibe Coding 前先建六份项目文档

来源（X） · @UPing123zzz · 2026-11-09 15:16

现在用 Codex、Claude Code 这些 Coding Agent 写代码，我越来越觉得，真正重要的可能不是 Prompt 写得有多牛逼，而是你有没有能力把一个项目的需求、架构、约束和执行过程管理清楚。

这篇推文提到，在开始 Vibe Coding 之前，最好先准备六份 Markdown 文件：

PRD.md：产品到底要做什么，给谁用。
ARCHITECTURE.md：技术栈、目录结构、系统架构和数据流。
DESIGN.md：界面设计、组件规范、整体视觉风格。
RULES.md：开发规范，以及 AI 绝对不能做的事情。
TASKS.md：把开发任务拆解成可以逐步完成的小步骤。
PROGRESS.md：记录已经完成的工作、遇到的问题和下一步计划。

我觉得这背后反映了 AI Coding 一个特别重要的变化：

代码生成正在变得越来越便宜，但管理代码生成过程的能力，反而越来越值钱。

以前一个开发者要花很多时间写代码，现在你把需求描述清楚，Agent 几分钟就能修改几十个文件，甚至直接把一个产品原型搭出来。

但问题是代码写得快，不代表项目推进得顺利。

尤其是做过稍微复杂一点的 AI 项目之后，就会发现很多时候真正浪费时间的根本不是写代码，而是反复返工。

比如你让 Agent 开发一个系统，第一轮它设计了一套架构，第二轮你让它增加一个功能，它又引入了新的依赖。第三轮修改前端，顺便改了后端接口。第四轮修复 Bug，结果把之前已经正常运行的功能搞坏了。

折腾了几个小时，项目看起来改动了很多，但实际上可能还没有第一版稳定。

更麻烦的是，等你第二天重新打开一个会话，Agent 对项目的理解可能又和昨天不一样了。

你不得不重新解释业务需求、技术架构、之前遇到的问题，以及为什么某些方案不能使用。

这其实不是模型不会写代码，而是整个开发过程缺乏稳定的上下文和约束。

所以我觉得这六份文件真正解决的，不是怎么让 AI 生成代码，而是怎么让 AI 在一个持续变化的项目中，始终知道自己应该做什么。

PRD 解决需求边界，避免 Agent 不断增加没必要的功能。

ARCHITECTURE 解决架构一致性，避免今天用一套方案，明天又推翻重来。

DESIGN 解决界面规范，避免每次修改都重新生成一套视觉风格。

RULES 解决开发约束，明确哪些操作不允许擅自执行。

TASKS 解决任务拆解，让 Agent 每次完成一个可以验证的小目标。

PROGRESS 解决跨会话交接，让下一次执行能够接着之前的结果继续，而不是从头摸索。

把这些东西放在一起，其实就是在给 Coding Agent 建立一套最基本的软件工程纪律。

不过，我觉得这里还有两个特别值得注意的地方。

第一，文档本身不是重点，文档是否真实、准确、持续更新才是重点。

很多人看到这篇文章，可能马上就让 AI 自动生成六份 Markdown，然后觉得自己的项目一下子规范起来了。

但如果这些文档只是模型根据项目名称猜出来的和真实代码根本对不上，那反而可能误导后续开发。

而且不同工具的指令入口也不完全一样。比如 Codex 可以使用 AGENTS.md，Claude Code 有 CLAUDE.md。

所以不是把文件扔进项目根目录，Agent 就一定会自动理解所有内容。

你需要确保它能正确读取，并且知道什么时候应该参考哪些文件。

第二，也是我觉得更重要的一点：不要把写完文档，当成完成了软件工程。

PRD 写得再漂亮，架构图画得再完整，TASKS 拆得再详细，如果最后没有测试、没有代码审查、没有验收标准，项目照样可能是一堆不能稳定运行的代码。

真正可靠的流程应该是：先明确需求，再确定架构，接着把任务拆小，让 Agent 逐步实现。

每完成一个功能，运行对应测试，检查实际修改了什么，再记录结果。

出现问题就定位原因，有必要时回滚，而不是让 Agent 无限循环地修改。

对于稍微复杂一点的项目，还应该配合 Git 分支、Commit、Pull Request、CI/CD。

尤其是现在多 Agent 并行开发越来越普遍，如果没有版本管理和任务边界，多个 Agent 可能同时修改相同的文件，最后连谁改坏了什么都搞不清楚。

AI Coding 下一阶段值得重视的不只是 Prompt Engineering，而是 Context Engineering 和 Spec-Driven Development。

前者解决应该给 Agent 什么上下文，后者解决应该按照什么规格开发和验收。

当然，也没必要把所有事情都搞得特别复杂。

如果只是修改一个小 Bug，没必要先写六份文档。

但如果你准备开发一个需要长期维护的 Agent、RAG 系统、SaaS 产品，或者需要多个 Agent 协作的大型项目，那这些规范的价值就会越来越明显。

说到底，AI 正在降低软件开发的门槛，但没有消除软件工程本身的复杂性。

以前我们花大量时间解决怎么把代码写出来。

现在可能需要花更多精力思考，怎么让 AI 生成的代码符合需求，怎么控制变更，怎么验证结果，以及怎么让整个项目持续迭代。

会让 AI 写代码，只是能力的一部分。能把 AI 的代码生成能力组织成一套可靠的开发流程，才是更值得积累的能力。

以后模型只会越来越强，生成代码的速度也会越来越快。

但需求判断、架构取舍、工程约束、质量验收，这些能力不会因为模型升级就自动变得不重要。

相反，当代码可以被大量生成的时候，知道什么代码值得写、应该怎么写、怎样证明它是正确的，可能才是真正拉开开发者差距的地方。

AI 可以帮你完成实现，但你必须知道自己到底在交付什么。

这也是我觉得从 Vibe Coding 走向真正 AI 工程开发，绕不开的一步。

06｜Indra OCR 纯 CPU 解析文档

来源（X） · @Ryrenz · 2026-11-10 10:02

📄 Datalab 刚开源了 Indra OCR，一个只有约 1M 参数的模型，纯 CPU 就能把 PDF 和图片转成 Markdown。

Indra 10 月中旬才建仓，GitHub 上已经 1600+ star；在 OmniParseBench 上拿到 66.7 分，PaddleOCR PP-StructureV3 是 58.4。

以前想把一堆扫描 PDF 喂给 AI，要么上 GPU 跑大模型，要么用 Tesseract 凑合，表格和多语言一塌糊涂。Indra 不依赖 PyTorch 也不要 GPU，默认模型总共约 76 MB，32 核 CPU 上每秒能处理约 44 页，大约是 Tesseract 的 15 倍。

输出不只是文字，每一行、每一块都带框、标签和阅读顺序，80 多种语言（含中日韩）和手写都能认；数字版 PDF 直接读文字层，只对缺的部分做 OCR。

官方也写明了短板：复杂表格、手写和质量很差的扫描件还认不好。模型权重是修改版 OpenRAIL-M，个人、研究以及融资或营收低于 2000 万美元的初创公司免费用。

文档进 AI 之前的那道坎，现在一台普通服务器就能迈过去。
