01｜DS SuperAgent架构设计思考

来源（X） · @konghayao · 2026-11-02 10:07

关于 DS SuperAgent 的架构设计思考：
1. 首先，我们先了解 peri RCRA Loop 的底层概念。RCRA 在 ReAct 基础上扩充了 MessageQueue 来存放未进入 Loop 的外部消息，可以持久化保证 durable，外部消息只能由这个 MessageQueue 来进入 Loop 内部。

2. 借由 1 的基础，我们可以高度解耦解构消息系统和 Agent 系统。

我们向外设计一个 EventSystem，它用来合并所有的外部系统的输入，所有的 IM 或者是 Github 的 webhook 均由此输入，并管控相应的投递逻辑与权限。并在 Event 来到时做可靠投递，到 Agent 系统就进入了一个 session 的 MQ 里面，两侧只有通信耦合。

消息的过滤其实 jev 非常非常合适，不需要构建代码，只需要构建 Agent 需要监听的方向，进行过滤。

3. 我们先了解 Async Subagent System + Cursor Multitask。

Async Subagent System：主 agent 的 Agent 工具立刻返回一个 agent id 和能够与 subagent 通信的方式，subagent 自动异步执行。
Cursor Multitask：multitasks 是一组提示词，关于主子 agent 如何操作的提示词，保证 Async Subagent System 能够在上下文设计中能够运行。

那么 SuperAgent 人机交互中的大部分都是旧有设计。

关于 Router + Worker 的Agent系统设计，我认为是非必要的。或者说不需要在代码中构建出这个逻辑，传统的 Agent 核心就有这个能力。这个设计中必要的能力是 ，源头是 Cursor 的 Multitask 和一众以 async 优先的 Agent 设计。

Peri 在实现的时侯，已经做到了 Cursor Multitask 的 Agent Mode 设计。能够由门户 Agent 路由与管理多个 Subagent 工作。

4. 关于 Inline & Spill 就是社区里面非常成熟的工具落盘机制 你可以在 CC、Codex、Peri Code、MCode 和 Pi 的源码里面找到。核心是当消息超过阈值，自动放到磁盘，并给出简化的 tool result 和 寻回方式，通过 Agent 的能力就能完成。

5. 多跳检索这个东西，建议是 EventSystem 提供Channel 历史的 list 接口，那么其实让 agent 直接从 list 接口找就行了，多跳检索行为可以简化为系统数据找回，无需对 Agent 系统改造。

6. “计算、状态与环境的分离” 的设计源头是 Claude Managed Agent，社区和各大框架有比较成熟的设计，这里不再展开。

7. Watch Dog 的设计算是普普通通，如果 Agent 系统内部设计的得当，那么几乎 95% 的 error 不会阻挡 agent 的正常运行。

经过我们的统计，LLM API Error 和停机中断是两大核心因素，反而是长久以来云服务开发体系的 Agent 系统本身非常稳定。这两个问题，其中一个是 durable 设计能够解决的，比如 pi-durable 尝试解决停机中断恢复。另外一个则可以由 Agent 系统的进程重试来尝试唤醒，在 L LM API uptime 之后自动继续。

8. 关于遮蔽对人的 session 掌控权：这个方向是对的，在 2027 年初，我们应该面对的问题是如何构建一个人，而不是构建一堆 session。

总而言之，SuperAgent 的这篇文章更像是综述了 Agent 设计工程的成熟设计，但是其中的细节和系统的解耦理解还处于一个实验阶段。可以说循着 SuperAgent 的设计，在社区里面能看到非常多已经成熟的设计，借以扩充整个 Agent 体系的视野。

02｜Holon共享Agent97%非人工触发

来源（X） · @jolestar · 2026-11-02 15:56

几个月前作为 AI Agent 技术顾问参与一个小团队，开始的时候大家各自用自己本地的 Codex / Claude 来开发，个人效率提升了，但协作起来效果就没有那么明显了。于是我尝试把 Holon 部署在服务器上，让大家共用，把 Agent 像团队成员一样加入到协作流中，Holon 成为了一个协作空间。

131 天跑下来，服务器上 6 个共享 Agent 跑了 39,809 个轮次（约 204 亿 Token，完成 3,986 个 WorkItem）。其中 97% 以上的运行都不是人主动去“问”的（59.2% 来自 Webhook 事件直接触发，37.0% 来自内部续跑与复检，人工直接发消息只占 2.88%）。

典型的几个场景：

1. 代码 Review 和合并：跟着 PR、新提交和 CI 变化持续复审，累计审阅了 1,666 个 PR（占 41.7% Token 用量）。
2. Bug report 追踪排查：设备日志上报后直接触发 Agent 还原 trace 现场并写入 GitHub Issue，自动创建了 1,044 个 Issue、897 份调查报告（占 25.5%）。
3. 测试验收：PR 合并后持续盯部署和发包，能自动测的接口自己测，需要上真机的整理好步骤交给测试同学再接回结果，完成了 931 个 Issue 的验收（占 23.8%）。
4. 服务器运维：处理版本发布、监控巡检以及测试环境部署。
5. 数据分析统计：解决产品经理经常需要让开发跑数据的问题，按需求直接跑出产品指标和会话统计。

我整理了一篇文章，总结了几个案例，分享这个实践。总体上来说，AI Agent 要尽量能靠近上下文来源，个人本地的 Agent 很容易接触本地上下文，而团队中，最靠近上下文来源的就是服务器。

当然，不同的团队规模，对安全要求、数据的隔离都有差异，这个例子主要适用于可信的小团队。

07｜Magpie用三条loop持续运维

来源（X） · @MindfulReturn · 2026-11-02 09:59

yetone 这套 Magpie 运维看着朴素，总结下来的方法如下：Claude Code + 官方 Opus，并行三条 /loop——一条盯 GitHub issue/PR 和 Discord（PR 要拉下来真跑才合），一条盯 X 反馈（前面用便宜模型 Jev 先拦一刀省 Token），一条定时清屎山、写教训、拉黑低质提交。人晚上只铲 UI/UX。

三端真机复现（mac + Win + Win 里 Linux VM，Agent 只装一端，跨机走 ssh）；决策靠 Claude Code 记忆 + 仓里设计文档；对外操作全是 browser use；有人问 /loop 比 scheduled task 有啥优势，他直接说「没有优势，能监听就行」。

我这边也在用 Magpie 给 Claude 做本机路由。越看越觉得 OPC 先把「什么算做完」写清楚，再给 agent 一本会升级的错题本，比再堆一层编排管用。

对比：理念类似，不是同一套方法。 都是「事件驱动、先过滤、少打扰人、持续盯仓」；yetone 是 Claude Code 上 3×/loop 手工作坊，DeepSeek SuperAgent 是 DSH 上产品化工单引擎的研究原型插件。

对照：

1. 连续运维：两边都不是一次性会话写码——yetone 整夜养 Magpie；SuperAgent 常驻盯 GitHub（可选飞书），panel 只推「待人工」。
2. 并行：yetone=3 条独立 /loop；DeepSeek=1 个 Router + 多 Worker Ticket（订阅可直通，不经 Router）。
3. 便宜过滤：yetone 用 Jev 拦 X；DeepSeek 用代码 Gate + 模型 Eval（长文称 Fast/Slow，Router 可用更轻模型）。
4. 记忆/错题：yetone 有 LESSONS.md→code-standards；SuperAgent 有 SQLite 工单账本 + 版本化 prompts，无公开错题本升级流水线。
5. 人机边界：两边都把人抬到验收/决策；DeepSeek 默认 observe、Mandate/白名单由宿主强制，yetone 更多靠提示词与人工习惯。
6. 产品角色：Magpie=网关；SuperAgent=Agent 插件本身。别和 Plugin Hub 上另一款 dsh-super-agent（preset 协议）搞混。
