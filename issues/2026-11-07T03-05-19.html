01｜vczh用正反例约束Codex大项目

来源（X） · @LanzhiAI · 2026-11-06 14:23

用 Codex 写大项目最让人抓狂的，就是它动不动过度设计，甚至顺手把你底层的核心依赖全给改了。

知名开发者 vczh（轮子哥）公开了他给 Codex 写的代码规范配置。不少人总抱怨模型写出来的东西像玩具、代码过度封装，他拿自己 GacUI 的长期实践给出了另一套思路。

核心就两件事：正反例和死规矩。

提要求必须同时给正面和反面例子。光跟模型说要简洁根本没用，它只能按概率去猜，必须把哪种写法算坏味道、哪种算达标白纸黑字写进规则文件。

更关键的是把边界锁死。他在规范里明确划定了哪些依赖目录和导入文件夹绝对只读、严禁改动；如果自动生成的代码报错，模型必须去排查生成器的根因，绝不允许自作聪明去修生成出来的临时文件；修改依赖、更新生成文件和单测快照，也都被强制要求拆成独立的提交。

想参考的可以去 GitHub 搜 vczh-libraries 里的 GacUI 或 Release 仓库，在 Guidelines 目录底下就能翻到这两份文件。

很多人总把给 AI 写规则当成文学创作，指望说两句好话就能约束它。但在大型项目里，模型不越界的前提是你给它立一份严苛的工程契约。不给正反例、不划清禁区，它自然会在你的代码库里到处脱缰。

03｜Claude用宝可梦测Agent记忆策略

来源（X） · @Zen_with_AI · 2026-11-07 07:07

细品Anthropic 今天的工程博客《The components of agent memory》

Anthropic 今天这篇讲 Claude 记忆的文章，把"记忆"这个大词拆成了三件能动手的部分：
记什么、
什么时候整理、
整理成什么样。

让 Claude 玩宝可梦红版，Sonnet 3.7 写了 413 个记忆文件、225 个文件夹，只拿到 1 个徽章；
Fable 5 只写了 9 个文件、2 个文件夹，外加一个总纲文件，拿了 4 个徽章。
记得多，不等于记得好。

整篇文章可以压成一条链：经历 -> 笔记 -> 做梦 -> 下次更好。

记什么。Sonnet 3.7 什么都记，每场战斗、每个道具、每个 NPC 都记，记录很快就过时了。一万步左右，它 17 步里新建 6 个文件、删了 9 个，游戏一步没动。Fable 5 记的是策略和规则，比如连续 3 个球没抓到就换抓球节奏。Opus 5.5 更省，只用一个小文件夹跟踪目标和下一步，直接通关了。Anthropic 的说法是，写下一条规则，就是预测这个模式以后还会出现。记的不是事实，是下次能用的判断。

做梦。灵感来自海马体：睡眠时大脑重放经历，把短期记忆固化成长期的。Claude 在两次交互之间的空闲时间里做同样的事，Anthropic 叫它"dreaming"，用的算力叫"sleep-time compute"。做梦能改错、写新笔记、搭出更好的记忆结构。宝可梦里有个现成的例子：Claude 记错了宝可梦中心在月见山东边，认定月见山已经打完了，结果从单向悬崖掉了三次，怎么也到不了华蓝市。做梦时它拿笔记对照会话记录，把错改过来，重新进洞，这次到了。

整理成什么样。Anthropic 试了把笔记整理成 wiki。Stainless 的 35 万份内部文档，约 4.2 亿 token，做了 128 次做梦，25 道题的得分从 13% 涨到 48%。搜索加 wiki 从 54% 涨到 61%，单搜 53%，每题省约 2 万 token。Harvey 的法律基准上，24 道并购题，wiki 是 87%，单搜 73%。但也有边界：单文档的任务基本没提升，有一次 wiki 长得比原文还大，Anthropic 自己拿 Borges 的梗自嘲了一句。

还有两个细节值得留意。只让 Claude 记失败，它反而丢掉了记忆带来的大部分提升；提醒 Sonnet 4.6 先读记忆再回答、验证自己的理论，分数几乎翻倍。Sonnet 5 十次里有九次会主动先读记忆，Sonnet 4.6 不到一半。顺带一提，Claude Code 的自动记忆只读 MEMORY.md 前 200 行或 25 KB 当索引头，写多了反而没人读。

简单总结一下就是，Anthropic 这篇讲的其实是一件事：记忆拼的不是数量，是判断和整理。什么时候该记、记了怎么保持更新，他们也承认还没解决，这篇更像是一份进行中的工程笔记，而不是定论。

https://www.anthropic.com/research/components-of-agent-memory

04｜Runner管理多Coding Agent

来源（X） · @meow2149 · 2026-11-06 17:09

每天介绍一个开发者工具，今天是 Runner。

Runner 是一款开源的多 Agent 协作工具，可以将 Claude Code、Codex、OpenCode 等独立运行的 Coding Agent 组织成一个团队，让它们围绕同一个开发任务分工、通信和协作。

例如，让 Claude Code 负责实现功能，Codex 负责代码审查，OpenCode 负责测试验证。每个 Agent 保留原来的终端、模型和工具，通过消息完成任务交接，需要人工决策时再向用户提问。

Runner 由开发者 @yicheng47 开发，使用 Rust 构建，基于 GPUI 实现原生桌面界面，采用 MIT 协议开源。

截至目前，最新正式版为 v0.19.4，支持 macOS、Windows，Linux 目前处于 Beta 阶段。

一、Runner 支持哪些功能？

1. 多 Agent 统一管理

支持 Claude Code、Codex、OpenCode v2、GitHub Copilot CLI、pi、Cursor、Grok Build、Antigravity CLI 等 Agent。

每个 Agent 都运行在独立的真实终端中，保留自己的 TUI、登录状态、对话历史和工具能力。

可以在一个窗口中分屏运行多个 Agent，也支持多标签页、多窗口管理，以及会话状态查看。

2. Role、Crew 和 Mission

Runner 使用四个概念组织 Agent 协作：

▪︎ Role：可复用的 Agent 角色配置，包含运行时、模型、职责提示词等。

▪︎ Crew：团队模板，将多个 Role 组合起来，并配置团队成员之间的协作约定。

▪︎ Mission：一次实际执行的任务，包含共同目标、工作目录、成员和消息记录。

▪︎ Session：每个成员实际运行的 Agent 进程与终端。

整体关系：

Role → Crew → Mission → Sessions

例如，创建一个开发团队：

▪︎ @coder：Claude Code，负责实现功能
▪︎ @reviewer：Codex，负责审查代码
▪︎ @qa：OpenCode，负责测试验证

启动 Mission 后，三个成员会分别收到共同目标和各自的职责指令。

Coder 完成代码后，可以给 Reviewer 发送消息，请它审查修改。Reviewer 发现问题后再反馈给 Coder，修复完成后继续交给 QA 测试。

Runner 不要求固定的队长，成员可以直接通信。具体分工和交接由角色提示词、团队约定和消息驱动。

运行过程中也可以动态增加、移除成员，不需要重新创建 Crew。

3. Agent 之间直接通信

Runner 提供共享 Mission Feed 和成员收件箱。

Agent 可以通过 CLI 向指定成员发送消息、向整个团队广播，或者查看其他成员的反馈。

例如：

`runner msg post --to reviewer "请检查刚才修改的代码"`

Reviewer 收到收件箱通知后，可以通过 `runner msg read` 读取消息正文。

每个 Agent 独立执行任务，通过持久消息实现协作，而不是简单地将同一条 Prompt 同时发送给多个模型。

4. 人工决策与任务回报

Agent 遇到需要人工决定的问题，可以通过 `runner ask --human` 发起提问。

问题会出现在 Mission Feed 中，用户选择答案后，回答会保存并送回原来的 Agent。

Runner 还支持将 Mission 关联到一个普通 Agent Chat。

当 Mission 需要人工处理、执行失败、因后台服务 runnerd 重启而丢失成员正在执行的一轮，或者进入 Settled 状态时，Runner 会向关联 Chat 汇报相应状态。

Chat 中的 Agent 可以进一步读取任务详情，向用户说明任务情况。

5. 后台运行与会话恢复

Runner 支持关闭桌面窗口后继续运行 Agent。

选择 Keep running 时，后台服务 runnerd 会继续管理 Agent 进程和终端。

重新打开 App，可以接回原来正在运行的会话。

如果 Agent 已经停止，也可以通过 Resume 尝试恢复原来的对话，而不必重新开始。

6. 远程控制

Runner 支持从另一台电脑远程访问正在运行 Agent 的主机。

通过 PIN 配对和端到端加密连接，可以查看远程终端、启动任务、发送指令，以及处理需要人工确认的问题。

Agent 和项目代码仍然保留在目标电脑上。

目前远程控制处于邀请内测阶段，仅向中国大陆受邀用户开放。

7. CLI 与脚本集成

除了桌面 UI，Runner 还提供 runner CLI。

开发者、脚本或其他 Agent 可以通过命令创建会话、启动 Mission、查看任务状态、发送消息和获取执行结果。

Runner 的任务管理能力既可以通过图形界面操作，也可以通过命令行调用。

二、Runner 的底层架构

结合官方仓库的源码和技术文档，Runner 主要由以下模块组成：

1. Runner App

采用 Rust + GPUI 构建原生界面，负责窗口、终端展示、Feed、用户交互和状态更新。

终端底层使用 alacritty_terminal 管理终端网格，再由 GPUI 完成绘制。

2. runnerd

独立运行的后台服务，负责管理 Agent 进程、PTY 终端、会话生命周期、任务状态、消息路由和持久化数据。

桌面 App 与 runner CLI 通过本地 IPC 和 runnerd 通信。

3. SessionManager + PtyRuntime

负责启动、停止和恢复 Agent，通过 PTY 与真实 CLI 程序交互。

Claude Code、Codex、OpenCode 等仍然运行自己的程序，Runner 不接管它们内部的模型调用和工具执行循环。

4. Runtime Adapters

处理不同 Agent 的启动参数、状态判断和恢复方式。

适配层负责处理运行时差异，不会把所有 Agent 转换为同一种模型 API。

5. AppCore + SQLite

保存 Role、Crew、Mission、Session 等配置和运行元数据。

6. EventLog + EventBus

Mission 的消息、问题和回答会写入 events.ndjson 持久化事件日志。

EventBus 根据日志维护成员收件箱、未读消息和相关状态。

7. Router

负责判断消息应该通知哪个成员，以及当前是否适合投递。

完整的消息链路：

Agent 发消息 → events.ndjson → EventBus → Router → 目标 Agent 的 PTY → Agent 读取消息

消息保存、终端通知和确认已读是不同的阶段。

Router 通常会等待目标 Agent 空闲，或者终端输入状态适合接收通知时再投递。Claude Code 支持在工作过程中排队接收通知。

通知送达后，不代表 Agent 已经读取正文。通过 runner msg read 读取后，才会推进对应的已读记录。

三、Runner 的架构与协作机制

Runner 的实现可以概括为三个方面：

1. 保留 Agent 原生运行环境

Runner 不重新实现 Claude Code 或 Codex 的 Harness，也不合并不同 Agent 的内部状态。

各个 Agent 保留独立的终端、对话历史和工具执行能力。

2. 通过持久消息组织团队协作

Role 负责角色配置，Crew 负责团队模板，Mission 负责实际任务。

Agent 之间通过共享目标、团队约定、消息和反馈完成协作。

消息记录保存在事件日志中，可以用于恢复收件箱和任务协作状态。

3. 分离界面与执行进程

Runner App 负责展示和交互，runnerd 负责持有 Agent 进程、PTY 和任务状态。

关闭桌面窗口不会必然终止 Agent，重新打开后可以连接仍在运行的终端。

对于已经停止的进程，Runner 通过 Agent 自身保存的会话历史尝试恢复对话。

四、当前版本的使用限制

▪︎ Runner 目前处于 Alpha 阶段，Linux 支持仍为 Beta。

▪︎ Mission 成员默认共享指定的工作目录。Runner 不会自动创建 Git Worktree 或分支。如果多个 Agent 同时修改代码，需要自行规划工作目录隔离或文件修改范围。

▪︎ Mission 通常采用 Agent 的广泛权限模式。团队约定属于行为指令，不等于文件系统沙箱或强制审批机制。

▪︎ Agent 之间共享的是任务目标、消息和反馈，不是隐藏推理、原生工具状态或完整的模型上下文。

▪︎ Mission 的 Settled 表示成员满足空闲条件，并不代表代码通过测试或审查。Failed、Interrupted 等情况会分别显示对应状态。

▪︎ 文件预览、Diff 审查等功能仍处于开发或 Preview Nightly 阶段，不属于 v0.19.4 稳定版的完整功能。

五、Runner 的整体工作流程

整个协作过程可以整理为：

1. 配置 Role，定义每个 Agent 的运行时、模型和职责
2. 将多个 Role 组成 Crew，设置团队成员与协作约定
3. 启动 Mission，向成员分发共同目标和工作目录
4. runnerd 通过 SessionManager 和 PTY 启动各个 Agent
5. Agent 通过 EventLog、EventBus 和 Router 进行消息交接
6. 需要人工决策时，通过 Mission Feed 提问并接收回答
7. 任务状态变化后，通过关联 Chat 汇报进展
8. Agent 在后台继续执行，桌面 App 可以重新连接运行中的会话

Runner 将多个独立 CLI 的管理、团队配置、消息通信、任务状态和后台运行整合在同一套工具中。

从 Role、Crew、Mission 的组织方式，到 runnerd 的进程管理、PTY 终端和消息投递机制，相关功能与架构整理在配套的 4 张图中。

06｜BUI抽出Blender内核18MB内存

来源（X） · @fishjar · 2026-11-06 21:20

今天开源圈出了个很有意思的项目：BUI 把 Blender 沉淀了三十年的 UI 渲染内核彻底给抠出来了。

做桌面端的人苦 Electron 久矣，动辄吃掉几百兆内存；后来大家追捧 Rust 写的 GPUI，但生态绑在特定编辑器上难以剥离。

开发者直接把 Blender 底层的 Ghost 窗口抽象和即时模式（Immediate Mode）GPU 渲染流水线抽成独立运行时，向外暴露了 C/C++、Rust、Python 和 JS 的通用接口。

Blender 能在成百上千个复杂的着色器节点和实时视口下保持 60 帧丝滑渲染，就是因为它的 UI 根本不走任何 DOM 树计算或虚拟节点 Diff，每一个按钮、每一个滑动条直接由专用 Shader 在显存里原地成型。

实测下来，初始化内存占用只有 18MB，冷启动窗口建立耗时不到 12 毫秒。
