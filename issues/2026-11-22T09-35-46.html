Pi Bot 开源了，Apache-2.0。

Pi Bot 是一个在你自己电脑上干活的 AI 团队：一群有名字的 Bot，可以私聊，也可以拉进群里分工，做计划、跑命令、改文件、互相交接。

09｜Bitwarden自托管检查nginx

来源（X） · @sysxplore · 2026-11-22 16:26

中文译文

如果你自行托管 Bitwarden，请检查你的 nginx 版本，而不仅仅是你的 Bitwarden 版本。

Bitwarden 正在通知自托管用户立即更新到 v2026.11.0。它所捆绑的 nginx web 服务器受到了 CVE-2026-123007 和 CVE-2026-123633 的影响，这两个漏洞可能允许在 nginx 容器内部执行远程代码。一个独立的 Linux 内核漏洞 CVE-2026-72447 可以与它们串联利用，因此请在同一时间窗口内修补宿主操作系统。

问题在于，v2026.11.0 的一些早期拉取版本仍然包含了存在漏洞的 nginx 1.31.8。一位 Bitwarden 员工解释说，nginx 1.31.9 在发布当天就已更新，"因此在 nginx 镜像重建之前拉取的镜像虽然显示为 2026.11.0，但仍然包含 1.31.8。"

请运行 docker exec bitwarden-nginx nginx -v。它应该显示 1.31.9，在 Bitwarden Lite 上则应显示 1.30.7。

原文

If you self-host Bitwarden, check your nginx version, not only your Bitwarden version.

Bitwarden is telling self-hosters to update to v2026.11.0 now. The nginx web server it bundles is hit by CVE-2026-123007 and CVE-2026-123633, which could allow remote code execution inside the nginx container. A separate Linux kernel bug, CVE-2026-72447, can be chained with them, so patch the host OS in the same window.

The catch is that some early pulls of v2026.11.0 still shipped the vulnerable nginx 1.31.8. A Bitwarden employee explained that nginx 1.31.9 landed the same day as the release, "so images pulled before the nginx image was rebuilt reported 2026.11.0 but still contained 1.31.8."

Run docker exec bitwarden-nginx nginx -v. It should say 1.31.9, or 1.30.7 on Bitwarden Lite.

10｜Antigravity经ACP访问合规

来源（X） · @fankaishuoai · 2026-11-22 16:21

官网文档：通过 ACP 方式访问 Antigravity 完全合规。

在Paseo设置Providers里面，打开 Antigravity 直接就可以合规使用了。也是通过ACP方式调用的。

缺点就是不够原生，是Paseo端组装上下文交给Antigravity处理的，但不管怎么说，可以在Paseo里面正常使用 Gemini 4 Neon了。

引用内容

XAIFURA.org @x1fl_

中文译文

【Google 官方、关于 T3 Code 出乎意料的愤怒】

"对误信息已经受够了。让我们说清楚。
在 T3Code 中使用 Antigravity 不会被封禁。"

这实际上是在一举打消人们长期以来对在官方应用之外使用 Antigravity 所持有的警戒感。

【NG 情况】

实际上，Google 官方 FAQ 中确实有一个条目写着"为什么我无法使用 Antigravity 的登录信息来使用第三方软件……？"

其中相当强硬地写道：通过第三方工具或服务访问 Antigravity 属于违反服务条款，可能导致账户被停用或终止。

此外，在其附近还有一条关于 CLI 无头模式（agy -p）的说明，大意是"该功能仅用于直接的脚本或 CI，不支持将其包装在第三方 agent 或应用中，也不支持账户自动切换（个人套餐为不支持）"。

仅凭这些内容来看，认为"从官方应用以外的工具连接过来的都全部违规"也并非没有道理。

【救世主 ACP】
然而，这里其实有一个容易被忽视的要点。

Antigravity CLI 作为官方功能之一，提供了 ACP（Agent Client Protocol）服务器（agy acp）。

这是从 Zed 或 T3 Code 等支持 ACP 的客户端出发，在不修改官方二进制文件的情况下直接调用，并通过标准协议进行交互式通信的"官方正规途径"。

这与提取登录信息（OAuth 令牌）进行代理、或将其嵌入非官方包装器中从背后调用的做法，在机制上有着根本性的不同。

因此，官方这次的主张是：通过 ACP 服务器正常使用的部分是没有问题的。

【为什么会被警戒？】
那么，为什么会出现如此多的不透明感和误信息扩散呢？

最主要的原因在于：
- "官方认可的通过 ACP 进行的集成"
- "构成违反条款的通过第三方工具进行的登录信息盗用和包装器使用"

这两者之间的界线，从外部来看一时难以分辨。

- FAQ 中使用了广泛的表述，容易被理解为"在第三方软件中使用属于违反条款、会被封禁"
- 实际上此前已有不少报告称因使用 OpenClaw 或 OpenCode 等工具而导致账户被限制或封禁
- 像 T3 Code 这样的外部客户端，从外观上看也像是"从外部工具运行 Antigravity"
→ 容易被与 NG 工具群混为一谈

在这些背景因素的叠加下，"T3 Code 也会被封禁"的说法不胫而走，

最终导致 Google 官方这次以"对误信息已经受够了"这样的强硬措辞予以否认。

【Google 公式、T3 Code 関連でまさかの怒り】

「誤情報にはうんざりだ。はっきりさせておこう。
T3Code で Antigravity を使っても BAN されない。」

公式アプリ以外で Antigravity を利用すること自体に、ずっと警戒感がまとわりついていたところを一蹴した、という形になる。

【NG ケース】

実際、Google 公式の FAQ にも「Antigravity のログイン情報でサードパーティ製ソフトウェア ... を使用できないのはなぜですか？」という項目がある。

そこでは、サードパーティ製ツールやサービス経由で Antigravity にアクセスすることは利用規約違反であり、アカウント停止・終了につながる可能性があるとかなり強めに書かれている。

さらにその近くには、CLI のヘッドレスモード（agy -p）についても「直接のスクリプトや CI 向けであり、サードパーティ製エージェントやアプリの中にラップすること、アカウントの自動切り替えは個人プランでは非サポート」という旨の記載もある。

これだけ読むと、「公式アプリ以外のツールから繋いだら全部アウトなのでは？」と思ってしまうのも無理はない。

【救世主 ACP】
ただ、実はここに見落とされがちなポイントがある。

Antigravity CLI には、公式機能として ACP（Agent Client Protocol）サーバー（agy acp） が用意されている点だ。

これは Zed や T3 Code などの ACP 対応クライアントから、公式バイナリを改変せずそのまま呼び出し、標準プロトコル経由で対話的にやり取りするための「公式の正規ルート」。

ログイン情報（OAuth トークン）を抜き取ってプロキシしたり、非公式のラッパーに組み込んで裏から叩いたりするやり方とは仕組みが根本的に違う。

だから ACP サーバー経由で普通に使う分には問題ない、というのが今回の公式の主張になる。

【なぜ警戒される？】
じゃあ、なぜここまで不透明さや誤情報が広がったのか。

一番の原因は、
・「公式が認めている ACP 経由の連携」
・「規約違反になるサードパーティ製ツールでのログイン情報流用・ラッパー利用」
の線引きが、外から見てパッと分かりにくかったことにある。

・FAQ では「サードパーティ製ソフトウェアでの利用は規約違反・BAN 対象」と広く読める強い表現になっている
・実際に過去、OpenClaw や OpenCode などの利用でアカウント制限・BAN の報告が相次いでいた
・T3 Code のような外部クライアントも、見た目上は「外部ツールから Antigravity を動かしている」ように見える
→ NG なツール群と一緒くたにされやすかった

こうした背景が重なった結果、「T3 Code も BAN される」という話が独り歩きし、

今回ついに Google 公式が「誤情報にはうんざりだ」と強い言葉で否定する事態になったのだろう。
