02｜Codex CLI 新增多会话指挥中心

来源（X） · @ai_suxiaole · 2026-11-09 10:09

Codex 同时跑多个任务，几个会话的状态分散在终端里。任务进度、新结果、待处理事项，很难一眼看全。

11 月 6 日发布的 CLI 0.167.0，增加了一个新入口：Agent Command Center。

操作如下：

codex agents --no-daemon

运行后会打开 Agent Command Center，多个 Agent 会话集中展示，有新结果的会话会标记为未读。

日常使用时，可以把互不依赖的任务拆开执行：

一个查资料

一个改页面

一个检查测试

打开 Command Center，集中查看各个任务的结果，检查实际改动和验证记录。

任务显示完成，只代表执行流程结束，不代表代码已经通过验收。

另一个实用更新：

CLI 0.167.0 支持在审批提示中直接展开 Patch。

Codex 要修改自己不熟悉的文件时，展开 Patch 可以查看具体代码差异和修改范围，方便判断是否批准。

04｜g-harness-evals 测成本差

来源（X） · @Smartpigai · 2026-11-09 10:56

同一个 AI 大模型，换一套 Agent Harness，任务完成率可能差不多，成本却能差一倍。到底是谁在浪费 Token？

最近看到 YC CEO Garry Tan 开源的 g-harness-evals，我觉得做 Agent 开发的人真该研究一下。

它不是又一个模型排行榜，而是一套开源的 Agent Harness 横向评测框架。

核心思路很简单：

固定模型、任务和评分标准，只替换 Harness，看谁能以更低成本、更短时间完成任务。

目前已经对 Claude Code、Codex、Hermes、OpenClaw、QM（Pi loop）等 Harness 进行了测试。

而且不只是看官方结果。

如果你自己开发了 Harness，也可以研究它的 Runner 和 Harness 适配实现，把自己的方案接入同一套评测流程，与现有框架做对照实验。

这点我觉得非常有价值。

1. 同模型，不同 Harness，成本差距有多大？

使用 Claude Opus 5.5：

Claude Code：76.3% 成功率，约 $0.22 / 成功任务
Hermes：78.8%，约 $0.24
OpenClaw：76.3%，约 $0.44

这些成功率在当前样本下无法明确区分，但 OpenClaw 的成本点估计接近 Claude Code 的两倍。

研究人员进一步拆解发现：

OpenClaw 相比 Claude Code 的额外成本，约 81% 来自 Prompt Cache Writes。

主要原因是较大的 System Prompt 和 Tool Results 被反复传入上下文。

这其实揭示了 Harness 一个很容易被忽略的问题：

模型本身没变，但上下文组织策略、工具输出长度、缓存复用方式，都可能显著改变最终成本。

2. Skills 和 Memory 并不是装上就一定有效。

项目还专门测试了 Instruction Reliability。

例如，同样一条「先查询记忆」的规则，放在 System Prompt、Startup File、Hook 或 Skill 中，实际遵循率可能完全不同。

Codex 在测试中，对通过 Per-turn Hook 注入的规则实现了 30/30 次遵循。

但 Claude Code 对没有被明确要求使用的 Skill，并不会自动打开。

这说明：

Agent 的执行能力，不只取决于模型知道什么，还取决于 Harness 如何把正确的指令送到正确的推理步骤。

3. 减少上下文，也不一定意味着优化成功。

在简单任务中，删掉部分记忆和 Skills 文本，可以降低约 19% 的执行成本，而且没有测出明显的成功率变化。

但在更复杂的任务中，同时删除记忆文本和工具描述建议，成功率却从 60.4% 降到了 0%。

所以 Context Engineering 不是一味压缩 Token，而是要判断哪些上下文真正影响决策。

我觉得 g-harness-evals 最值得拿来做的，其实是 Harness 的消融实验（Ablation Study）。

假设你自己写了一套 Agent Harness。

可以在尽量一致的模型、任务和运行环境下，逐项测试：

加入 Memory Retrieval，成功率是否真的提高？

引入 Context Compression，节省了多少 Token？有没有损失能力？
优化 Tool Routing，是否减少了无效工具调用？
把规则从 Skill 改成 Hook，执行可靠性是否改善？
更换整个 Harness，Cost per Solved Task 到底相差多少？
这样一来，Harness 的优化就不再是「我觉得这个 Prompt 更好」，而是可以通过数据验证。

当然，目前项目只有 20 个公开任务，评测还处于开发阶段，不能直接拿来断言哪个 Harness 最强。

但我觉得这个方向非常重要。

以前我们习惯给模型跑 Benchmark，接下来可能需要给 Harness 也建立一套严肃的 Benchmark。

因为一个 Agent 最终好不好用，已经不只是模型推理能力的问题。

System Prompt、工具设计、Memory、Hooks、执行循环、上下文缓存，每一层都可能影响性能。

同样的模型能力，谁能用更少的 Token、更短的时间、更稳定地把任务完成，谁的 Harness 才更有竞争力。

项目地址：https://github.com/garrytan/g-harness-evals

07｜LearnHarness 用知识图谱续学

来源（X） · @Xudong07452910 · 2026-11-09 09:19

推荐一个挺有意思的开源项目 LearnHarness，感觉可以拿来啃各种难懂的知识。

它会先通过提问摸清你的知识基础，找到理解上的盲区，再用 Agent 规划学习路径，边讲边练，根据你的回答不断调整教学内容。

它的 Memory 设计也很有意思，会把学过的概念和推理关系保存成知识图谱，下次可以接着之前的进度继续学。

用途也挺广，数学、机器学习、编程、物理、经济学、哲学，甚至备考、读复杂的科研论文，都可以拿来试试。

感觉很适合想系统学习一个新领域，又不知道从哪里入手的人，值得收藏研究一下！
