03｜Context Mode插件反增上下文

来源（X） · @chasen_liao · 2026-11-03 19:09

之前我写过一篇文章，介绍 Context Mode 可以帮 Pi 精简上下文。但今天我把这个插件删了，因为我发现它可能正是 Pi 启动慢的原因之一!!!!!!🤯

这段时间我用 Pi 的时候，经常感觉启动要等很久。后来排查了一圈，发现问题和 Context Mode 有关，其他插件没有出现同样明显的慢启动

更让我意外的是，我顺着这个问题往下查，发现这个号称能精简上下文的插件，本身就会给上下文增加一笔不小的开销

我和 Codex 用 Pi 做了一组隔离对照，模型用的是 GPT-6 Luna，Context Mode 版本是 1.0.169。两边使用同一个提示词，只让它写一个内容为 hello 的文件，同时保留 Pi 的 Code Mode 和 Tool Search

装着插件的时候，发给模型的工具一共有 17 个，第一次请求的输入是 8,021 token。卸载插件后，同样的任务只剩 6 个工具，第一次请求是 2,004 token

也就是说，文件还没开始写，装着 Context Mode 的这次请求就多带了大约 6,000 token

原因也比较直观：它额外注册了 11 个 ctx_ 工具，这些工具的描述加起来有一万多字符，还要带上参数定义。插件也会给模型补充工具使用的路由提示，所以这笔开销不全是工具描述，但工具定义确实占了很大一块

启动时间也测了一下。隔离环境里，从启动到进入 Agent 阶段，装着插件大约是 2.37 秒，卸载后大约是 0.28 秒。我们看了插件代码，它会在处理提示词前等待 MCP bridge 启动并注册工具，这和测试里多出来的等待是对得上的

当然，这只是我的电脑上做的小样本测试，不代表所有人都会慢这么多

至于它到底帮我省了多少上下文，我们还测了日志统计。让模型自己完成任务时，Context Mode 用自己的工具处理日志；没有插件时，模型也会用 shell 先筛选，两个结果都找对了，这个案例里没有看到明显的上下文节省

另外一次要求模型用 read 读取原始日志，两边返回的都是约 4 万字符，Context Mode 也没有自动把这次 read 输出压缩掉。这不代表它在所有大输出场景都没用，但至少我之前把它理解成会自动拦截所有大输出，这个说法需要修正

所以我现在把 Context Mode 删掉了，保留 Pi 内置的 Code Mode 来编排工具。对于日常找文件、搜代码，我更愿意留 pi-fff：用 fffind 定位文件，用 ffgrep 搜内容和按需翻页，找到位置之后再读取相关代码

如果你跟我一样，主要想解决代码搜索把上下文塞满的问题，我会更推荐先试试 pi-fff。Context Mode 则可以按自己的任务需要再考虑，尤其要把它额外带来的工具上下文和启动开销一起算进去

pi-fff 安装命令：pi install npm:@ff-labs/pi-fff

传送门 👉 https://github.com/dmtrKovalenko/fff/tree/main/packages/pi-fff

04｜sheepdog多Agent飞书调度开源

来源（X） · @Matthewohmygosh · 2026-11-04 05:30

看完 DeepSeek 的 Super-agent，我发现它和我自己折腾了一个月的 Sheepdog 几乎一模一样

前几天晚上读完 DeepSeek Harness 团队的《Super-agent 设计探索：迈向更自主的 Agent 系统》和他们开源的 1.5 万行 TS 原型 dsh-superagent-prototype，紧接着这两天又看到数字生命卡兹克写他折腾一年的“朱元璋飞书批奏折” Agent 系统，我越读越想笑：

这不就是我从 10 月初开始在自己电脑上折腾、每天帮我接管飞书消息的那个开源项目 sheepdog（牧羊犬）吗？

无论是顶层那句「单任务的上限取决于模型能力，多任务的上限取决于人的注意力」，还是底层的「常驻轻量 Router 接单分诊 + 独立隔离的 Worker/Session 并行干活 + Thread 话题订阅直通 + 飞书卡片拍板 + Watchdog 异常看门狗 + 单个本地 SQLite 账本」，两套完全独立写出来的系统，核心骨架几乎一模一样。

趁着这波热度，聊聊我在自己飞书号上跑过 16,000+ 条真实消息、调度 70+ 个常驻 Session / Session Group 和 600+ 个临时 Subagent，甚至最后让它自己给自己写补丁热升级的真实感受与来龙去脉：

━━━━━━━━━━━━━━━━━━━━
1️⃣ 起因：Agent 越强，我怎么反而成了全公司最累的「人肉路由器」？
━━━━━━━━━━━━━━━━━━━━

到了今年秋天，单次 Coding Agent 的能力已经很强了。但怪事随之而来：Agent 越能干，我每天反而越累。
我电脑上同时开着十几个 session 窗口，飞书上躺着几十个群和私聊。我每天活成了人肉传声筒：肉眼盯飞书 → 判断归哪个窗口管 → 复制文字截图切去终端粘贴 → 等跑完再复制回飞书。开个会回来就是几十条未读。

正如 DeepSeek 所说，人的注意力同时只能跟进 3～5 个活跃会话。10 月 9 日那天我彻底受不了了，建了 sheepdog 写下第一行提交：我是牧羊人，电脑里开着的 AI session 是羊群，跑在本机上的牧羊犬负责每分钟巡视飞书、分派消息、盯住卡死的羊，只在需要拍板时叫我一声。

━━━━━━━━━━━━━━━━━━━━
2️⃣ 快慢脑模型分工与三级拓扑：tp_bus (Flash) + Session / Session Group (Argon) + Subagent
━━━━━━━━━━━━━━━━━━━━

为什么不能用一个大主会话包办一切？因为主会话一旦热心开始拉代码跑测试，后面的急事就全堵死（队头阻塞），20 个项目的上下文还会串味。我们在 sheepdog 里把模型选型和会话层级彻底切开（见图 1）：

• 总线 tp_bus 用 Gemini 3.8 Flash：手里握着整份羊群名册（roster.toml），严禁干重活，只准花几秒钟分诊转交（sheepdog forward）或按需新开会话（new-session）。Flash 首字极快、成本极低，在 120 个会话的长周期回放评测里拿到跟重模型一模一样的 98.33% 指令保留率，用来守大门做秒级分诊简直绝配。
• 70+ 常驻 Worker Session 全升 Gemini 4 Argon：负责各自领域跨周记忆的常驻会话需要极强的深度推理与排障能力。后来 Gemini 4 Argon 一出，我第一时间把所有 Worker session 全升级到了 Argon。
• 纵向派生 Subagent（羔羊 lamb）：给常驻 session（母羊）立下硬规矩——「单批次业务工具调用 ≤3 步、耗时 ≤45 秒」。一旦遇到查几万行日志或跑长脚本的脏活，母羊必须在头 3 步派用完即焚的临时 subagent 去后台吞掉过程噪音，自己立刻交 waiting 卸锁继续秒回消息。
• 横向升格 Session Group（同羊圈多槽位 #1/#2）：跟高频搭档或核心发版频道对接时，90 秒内的连发消息自动合批进 #1；一旦 #1 忙超 180 秒还没结案，新来的独立急事绝不排队，自动唤醒同组空闲的 #2 并行接单！且唤醒 #2 时自动注入「#1 最近收发摘要 + 在跑 subagent 快照」，既不断片也不撞车。

━━━━━━━━━━━━━━━━━━━━
3️⃣ 一事一串（--key）与飞书“批奏折”快路径直通
━━━━━━━━━━━━━━━━━━━━

把并发拉满后，怎么防止被 70 个 session 的汇报淹没？
• 严格区分汇报（sheepdog report）与拍板（sheepdog ask，必须带明确的 A/B 选项，否则代码直接拦回）。
• 一事一串：每个事项带一把 --key（如 --key ssl-cutover），首张卡片落主屏，后续所有追问和进展自动收拢进这张卡片的飞书子话题（Thread）里。
• 0 总线 Token 快路径直通（见图 2）：一旦卡片发出，--key、飞书子话题和原 session 就锁进本地 SQLite 的 owner_threads 表。接下来我只需要在手机飞书卡片上点一下 [A/B] 按钮、在子话题里回句话、或者开会时随手对原消息点一个 👌 表情，全靠 SQLite 确定性查表毫秒级直通原发问 session 并自动结案，一滴 Token 都不经过总线（这也和 DeepSeek 的 Subscription Fan-out 不谋而合）。

━━━━━━━━━━━━━━━━━━━━
4️⃣ 那些论文里不会写的「四大真机社死与翻车现场」
━━━━━━━━━━━━━━━━━━━━

在真实飞书号上跑 16,000+ 条消息，80% 的功夫都在跟边界摩擦斗智斗勇（见图 3）：

• 现场一（我和自己的 Bot 当众抢话）：早期有次同事私聊问问题，我刚打字回「稍等我看眼监控」，不到两秒后台 session 啪地用我身份发出一张结论相反的大卡片，同事当场打出三个问号。后来我们在 sheepdog reply 发送前最后几毫秒加了只读回查：只要我已亲口发言，或过去 15 分钟内正在打字（owner-busy），当场以 exit code 3 熔断停发，并把我的原话带回给 session 当背景消化。
• 现场二（两只 Bot 在群里无限客套）：同事的 Bot 在群里发同步卡 @ 了我，我的 session 礼貌回「收到，感谢同步！」，对方 Bot 秒回「不客气！」，我方又回「辛苦了！」……逼出了 Loop Breaker：自动识别 🤖 机器人标签最多回一次，10 分钟内来回超 4 次直接拉闸静默 30 分钟。
• 现场三（下午突然失忆忘掉安全红线）：长周期会话跑半天后触发宿主 Context Compaction（上下文自动压缩），有损摘要直接把早上喂的生产安全红线当废话冲掉了。现在 sheepdog 每分钟增量扫 transcript.jsonl，一检出压缩标记，立刻把完整的 rules_after_compaction 重新塞进它嘴里。
• 现场四（静默卡死还嘴硬报正常）：模型口头登记的 work set 只供展示，绝不影响路由。看门狗每分钟按 SQLite 回执 + 真实工具调用时间戳硬算 6 态（15m 无工具调判 stalled、30m 判 lost，自动扣留新消息并告警，恢复后自动补送一次），经 20,000 轮随机差分模糊测试验证。

━━━━━━━━━━━━━━━━━━━━
5️⃣ 从 Watchdog、定时盯自动发版，到「自己给自己修 Bug 热升级」
━━━━━━━━━━━━━━━━━━━━

最近两周，这套系统真正活过来了（见图 4）：
1. 进程外 launchd Watchdog：每 5 分钟跑一次 0-Token 的健康恢复脚本，连守护进程单实例锁、WebSocket 断连和僵尸锁都能自愈。
2. 定时盯着自动发版（prod-release-pilot + Sheepdog Loops）：平时靠 0-Token 的本地 Python 探针静默扫描飞书审批单与云状态，有单子或异步前置条件（如 SSL 证书签发）就绪才唤醒 session 核对 PR Review、触发构建、核验 Cloud Run 切流并办结审批单。
3. 自主修复与原地热升级闭环（规格 7.93）：10 月底我对维护 sheepdog 的主脑说：「下次不用我同意了，你发现问题直接修就行了，大不了保留回滚按钮，并且每次更新通知里告诉我更新了什么、解决了什么问题。」
从那天起，遇到摩擦点它会自己改 sheepdog 源码 → 自动派生独立验证 subagent 跑 T1 变异证伪（故意改坏被测行确认测试必变红，再还原跑通 1,230+ 条回归测试）→ 推 GitHub 并调 os.execv 毫秒级原地热升级 → 给我飞书发一张写明「📋 更新了什么 / 🎯 解决了什么问题」且底部带着 [⏪ 回滚至上一版] 按钮的卡片。目前 91 道真实事故回归棘轮（REG-001 ~ REG-091）一大半都是它自己升上去的。

━━━━━━━━━━━━━━━━━━━━
6️⃣ 1 秒钟在本地领养一只你自己的「牧羊犬」
━━━━━━━━━━━━━━━━━━━━

Chat 只是人机交互的起点。当模型足够聪明之后，用一套极简、确定性的本地调度与账本系统，把人从“盯窗口的监工”解放成“只管边界和拍板的牧羊人”，才是真正在释放生产力。

sheepdog 已在 GitHub 完全开源（Apache-2.0，Python 3.11 纯标准库实现，0 第三方依赖）。哪怕还没配飞书，复制下面 3 行命令，1 秒钟就能在本地跑通完整的羊群看板（sheepdog board）与防撞车调度沙箱：

git clone https://github.com/Matthewoho/sheepdog.git
cd sheepdog
python3 scripts/demo_duty_board.py
