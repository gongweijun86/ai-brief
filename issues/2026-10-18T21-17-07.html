01｜Open WebUI 升级为多模型平台

来源（X） · @kafkaup · 2026-10-19 04:27

很多人对 Open WebUI 的印象还停在「Ollama 的网页前端」，这个标签大概两年前就过期了。

它和当年那个 WebUI 差别在哪？

模型层面它是 provider 无关的，Ollama 本地模型和任何 OpenAI 兼容端点可以混着用，LMStudio、vLLM、Groq、OpenRouter、Mistral 把 API URL 指过去就行。更大的变化在上层：插件分成 Filters、Actions、Pipes、Tools、Skills 五类，外部服务通过 MCP、MCPO 和 OpenAPI tool server 接入，可以自己写限流和审批流。配套的 Open Terminal 还能给 agent 一个终端和文件系统，让它跑脚本、改错、在对话里直接产出文件。

团队用够不够？

RBAC 是细到角色、用户组、权限三层的，每个组可以有不同的模型可见范围。RAG 这块支持九种向量库，混合检索是 BM25 加向量再加重排，也有全上下文模式；文档解析可以挂 Tika、Docling、Mistral OCR、PaddleOCR-vl。管理端有消息量、token 消耗和成本看板，还带一个 ELO 排行的模型竞技场做 A/B。数据库 SQLite 或 PostgreSQL，文件可落 S3、GCS、Azure Blob。

代价在哪？

功能面铺得非常宽，Notes、Channels、日历、定时任务、语音视频通话都塞在里面，第一次进后台配置项会让人有点发懵，建议按需开。另外部分能力划在 Enterprise 版，比如多用户隔离的 Terminals，自部署前先确认清单。

03｜Reason Network 让会话互联

来源（X） · @0xLogicrw · 2026-10-18 13:34

YC 孵化的 Reason Machines 开源了 Reason Network，让不同电脑上的 Claude Code、Codex、Cursor、OpenCode 等 Coding Agent 可以直接交流。

它给每个 Agent 会话建立地址，显示所属开发者、工作仓库、分支和当前任务。比如一个 Codex 正在开发网页，需要确认后端接口有没有变化，就可以直接给同事电脑上的 Claude Code 发消息，不用人类在两个聊天窗口之间反复传话。

底层通过 iroh 建立 P2P 连接，直连失败时使用加密中继。消息到达目标电脑后，再通过 Claude Code 的会话 Socket、Codex CLI、Hook 等机制送进对应会话。已经打开的 Agent 也可以接收消息，不必专门为通信启动一个新任务。

Reason Network 的宣传很容易让人想到 @xuanwo 最近开源的 Agenvo。两者都展示过 Grok Bot、Muse 与本地 Codex 连接的场景，但源码里的实现思路完全不同。

Reason Network 更像给 Agent 装了一套通讯录。每个正在工作的会话都有自己的地址，Agent 可以找到同事电脑上的其他 Agent，直接发消息、问问题。收到消息后怎么处理，还是由对方 Agent 自己决定。

Agenvo 则更像远程控制台。它通过自建 Relay 和 MCP，连接本地已经运行的 Codex app-server、Herdr 等服务。ChatGPT 不仅能查看已有任务，还可以创建新的 Codex 线程、读取输出，甚至通过 turn/steer 向正在执行的 Codex 追加指令，或者中断任务。

一个让 Agent 彼此通信，一个让 AI 直接控制 Agent 的执行过程。

看到这两个项目，我想起自己今年 3 月开源的练手项目 AGPair。

当时我只是想让 Codex 和 Antigravity 配合干活。主要是看中了 Antigravity 当时近乎无限的 Claude 额度，希望让 Codex 负责派活，Antigravity 负责执行。

最初，我用本地 SQLite 做消息总线，靠 Antigravity IDE 扩展接收任务、回传结果。其实也尝试过直接调用 Antigravity 的会话接口，但遇到了不少问题：创建会话时返回了无法正常使用的 ID，读取完整对话的接口也不可用。最后只能通过 IDE 命令新建会话、发送任务，再要求 Agent 把执行结果写成文件，由 AGPair 读取。

后来我又想支持更多 Agent，逐渐改成直接启动 Grok CLI、Claude Code、Codex CLI 等外部执行器。

接下来问题一个接一个：任务卡住了怎么办？进程退出后怎么判断是否完成？多个 Agent 同时改代码会不会冲突？怎么确认它真的交付了结果？

于是又加了任务状态机、失败重试、Git worktree 隔离和结构化回执。折腾到 6 月，已经能并行派活、追踪结果、检查 Diff，再决定是否采用修改。功能越来越多，整个项目也越来越重。

现在回头看，早期其实已经摸到了 Agent 的原生会话接口，但没能把这条路走通。后来为了绕开各种接口问题，我开始自己管理执行进程，再通过日志、进程状态和回执判断任务进展。

每遇到一个新问题，就继续往外面套一层监控或恢复逻辑。到最后，大部分精力都花在让这套复杂的任务系统正常运转上，最初想要的简单协作体验却始终没有做好。

Worktree 隔离、结果验收当然有用，但我花了太多精力处理这些后续问题。最基本的交互体验还没做好，就先开始对付各种复杂的异常情况。代码越写越多，使用起来却没有变得更简单。

到 6 月底，我停止了 AGPair 的开发，把关注点转向 Herdr、tty7 和 CodexHost，开始更多地研究终端、会话管理，以及如何直接与 Agent 的原生运行时交互。

现在看到 Reason Network 和 Agenvo 分别从通信、远程控制切入，确实有点可惜。

AGPair 当时就是个边学边做的小项目。最初只想让 Codex 和 Antigravity 配合干活，后来想支持更多 Agent，技术方案改了好几轮，最后也没打磨出一个真正好用的产品。

当时确实没有跨电脑通信、云端 AI 接管会话的需求，但我一直没想明白，应该把哪一项能力做成最简单、最直接的产品体验。

三个月里，我解决了不少任务派发、失败恢复和结果验收的问题，一直在给自己搭建的系统打补丁。

最初只是想让两个 Agent 简单地配合干活，最后却把大部分精力花在维护这套系统上。

思路越做越窄，系统越做越复杂，最后走进死胡同了。

04｜MyGo 静态二进制毫秒级启动

来源（X） · @cholf5 · 2026-10-18 23:08

这个启动速度真的羡慕了，我在 4 天前专门问过 AI：

我最近观察到一个现象，很多用 MyGo 开发的 App，性能看起来极好，不管是别人的演示视频，还是我自己实测，都感觉极流畅。尤其启动速度飞快，从启动到看到窗口出现，几乎是毫秒级别的，而我自己用 Avalonia 开发的哪怕是 Hello World 空项目，启动速度都慢得多，这是为什么？

答：这个问题我正好在评审里挖过底层实现，先看看仓库自带的基准测试里有没有实测数据可以引用。

原因可以从两段拆开说：启动快是因为 Go 和 .NET 的运行模型根本不同，流畅是因为 MyGo 的渲染架构把每帧的常数成本压到了极低。我在评审时挖过它的底层实现，逐条解释：

## 启动速度：为什么双击到出窗口几乎是毫秒级

**1. Go 是“没有运行时的运行时”。** Go 编译出来的是静态机器码（`examples/hello` 我刚构建了一下，单个 14.5 MB 静态链接二进制），进程启动只需要：映射二进制 → 初始化 Go runtime（极薄）→ 跑 `main`。没有虚拟机、没有 JIT 预热、没有程序集探测。

**2. Avalonia 的 Hello World 慢在它的启动清单上。** 你启动的不只是一个 UI 程序，而是一整套栈：CLR 初始化 → 元数据加载 → JIT 编译（即使 ReadyToRun 也省不掉 runtime init）→ 加载 Avalonia 及其依赖程序集 → 初始化 Skia 原生库 → 字体管理器扫描 → XAML 类型系统 → 窗口平台初始化。每一步都不大，加起来就是你感受到的那几百毫秒到一秒。这是平台税，不是你代码的问题。

**3. MyGo 的窗口创建路径极薄。** 因为全程 no-cgo + 纯 purego/syscall，它调 AppKit/Win32/GTK 是直接函数调用，中间没有 FFI 封送层、没有桥接守护进程、没有运行时探测。如果走原生 UI 路径（不嵌 WebView），启动 = 建窗口 + 初始化 Metal/D3D 设备，这两件事本身都是毫秒级。

**4. 静态链接消灭了“依赖查找”。** 所有原生交互代码编死在二进制里，启动时不需要从磁盘零散加载一堆 DLL/依赖程序集——.NET 应用启动时的 I/O 碎片在冷盘上尤其伤。

## 流畅度：渲染架构的差距

这部分是我在代码里确认过的，不是猜测：

**1. 每帧的成本结构完全不同。** MyGo 是立即模式：每帧把界面重建成一个扁平的 scene 操作列表，然后“每个操作一个实例化四边形”——圆角、边框、渐变、阴影、模糊全部在片元着色器里用 SDF 算出来（`internal/gpu/gpu.go` 的设计声明就是这一句话）。上千个小部件的界面可能只需要个位数的 draw call。而保留模式框架（Avalonia/Skia）每帧要同步控件树状态、走属性系统失效传播、逐控件提交绘制指令。

**2. GC 压力差一个数量级。** 这是 Go UI 工具包流畅的核心秘密之一：每帧的元素用 arena 分配、整块换入换出，控件状态走 256 槽的池子复用（`ui/runtime.go:671-709`），帧循环基本不给 GC 制造垃圾 → GC 几乎不在帧中间跑。C# 的 UI 框架每帧因绑定、属性变更产生常规垃圾，Gen0/Gen1 回收落在帧里就是你看到的偶发掉帧。

**3. 文本走平台原生引擎。** CoreText/DirectWrite/Pango 直接排版，字形进 atlas 增量上传。文本历来是其他自绘工具包卡顿的大头，这里直接借了操作系统优化了三十年的实现。

**4. 动画有专门的低耗路径。** 只有绘制内容在动时走 repaint-only 路径，加 damage tracking，不重建整个视图。

## 几句必要的泼冷水

- **演示视频有幸存者偏差**：作者 demo 全是 macOS 主平台打磨的简单场景。WebView 路径的应用不比网页快，别被演示误导。
- **Avalonia 不是不能快**：NativeAOT + trimming 后的 Avalonia 启动能进 100ms 级，.NET 8/9 之后也改善很多。你的 Hello World 慢，一半是默认 JIT 配置的锅。
- **这是不同的取舍**：MyGo 用“每帧全量重建 + 3-pass 上限”换流畅，代价是极端场景（万级元素）未经验证；Avalonia 的保留树在超复杂应用上仍是更稳妥的选择。

一句话总结：你感受到的差距 = 「静态原生二进制 vs VM 启动清单」+「无 GC 压力的立即模式 GPU 渲染 vs 保留模式 + Skia」。前者是语言运行模型的红利，后者是这个项目渲染层设计得确实好的红利——两者叠加，就是你看到的“毫秒级出窗口、丝般顺滑”。

06｜Harness² 自进化系统提示与工具

来源（X） · @akshay_pachaar · 2026-10-18 17:39

中文译文

Google 刚刚开源了 Harness²。

（把任何 harness 变成一个自我改进的系统）

harness 是包裹在模型外面的所有东西，比如系统提示词、工具、记忆、技能和子智能体。今天，一个人设计一次，智能体每次执行新任务都用的是这套固定的配置。

Harness² 让智能体能够针对每个新任务自主地优化这套配置，而模型权重保持不动。

在每个任务上，智能体提出对自身 harness 的修改建议，运行几个候选版本，然后通过比较这些运行的表现来组合出一个更好的 harness。

因为它是从不同运行之间的差异中学习的，所以它不需要该任务的正确答案或评分器。

以上覆盖的是单个任务。Harness² 还会把从一个任务中学到的东西带入下一个任务。

每个任务结束后，它会保存最终确定的 harness 以及在多次运行中都成立的经验教训。下次它优化 harness 时，从这些笔记出发，而不是从零开始。

这意味着每一个完成的任务都会让下一轮修改更加有的放矢。

Google 用 Gemini 3.5 Flash 和 GLM-5 在法律、办公和专业工作基准上测试了这个方法。一轮修改就足以超越它们原始的 harness，给智能体更多轮修改会让分数更高。

这些额外的轮次可以横向也可以纵向展开。智能体要么同时尝试多个候选 harness，要么持续地对单个 harness 逐步精炼，使用 OpenCode 或 Codex 来执行工作。

你可以在这里找到 Harness² 仓库：https://github.com/google-research/harness2

我已经写过一篇关于类似理念的文章，针对的是已经在生产环境中运行的智能体，harness 应该在故障发生后自我修复，而不是等着有人手动去调试 trace。

那篇文章详细介绍了 @Cometml 的 Opik（开源）是如何闭合这个循环的——从一个失败的 trace 到一个提议的修复，再到一个回归测试来防止同样的失败再次发生。文章引述在下面。

原文

Google just open-sourced Harness².

(turn any harness into a self-improving system)

a harness is everything wrapped around the model, like the system prompt, tools, memory, skills, and subagents. today a person designs it once, and the agent runs every new task with that same fixed setup.

Harness² lets the agent refine that setup for each new task on its own, with the model weights left untouched.

on every task, the agent proposes edits to its harness, runs a few candidate versions, and composes a better harness by comparing how those runs behaved.

because it learns from the differences between runs, it needs no correct answer or grader for the task.

that covers a single task. Harness² also carries what it learns from one task into the next.

after each task, it saves the harness it settled on along with the lessons that held up across the runs. the next time it refines a harness, it starts from those notes instead of from scratch.

this means every finished task makes the next round of edits more informed.

Google tested this with Gemini 3.5 Flash and GLM-5 on legal, office, and professional work benchmarks. one round of edits was enough to beat their original harnesses, and giving the agent more rounds pushed scores higher.

those extra rounds can go wide or deep. the agent either tries several candidate harnesses at once or keeps refining a single one step by step, using OpenCode or Codex to carry out the work.

you can find the Harness² repo here: https://github.com/google-research/harness2

I wrote about a similar idea for agents already running in production, where the harness should repair itself after a failure instead of waiting for someone to debug the trace by hand.

that piece walks through how @Cometml's Opik (open-source) closes this loop, going from a failing trace to a proposed fix to a regression test that stops the same failure from coming back. it's quoted below.
