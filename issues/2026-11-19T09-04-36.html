01｜姚顺雨谈小模型体系与RSI本质

来源（X） · @hocyzon · 2026-11-19 13:39

从清华的朋友那求来了姚顺雨昨晚分享的文字稿，貌似有点私密我就不传播了，整场分享价值的确很高，以下是我的笔记：

1. 未来一个值得关注的方向是小模型体系，AI for AI会显著推动小模型发展，因为训练小模型需要的算力更少，可以进行更多实验。未来可能先训练一个能力足够强的大模型，再通过蒸馏得到不同尺寸、分别适配不同任务的模型，最终形成Model Hierarchy，模型的价值将越来越取决于能否以合适的成本匹配具体任务。

2. 工业领域大量非文本数据值得关注，例如时间序列、临床数据和结构化表格。姚顺雨提到，目前直接针对这些模态训练原生模型，经常会遇到推理能力不足的问题，他提出了两种可能的解决路径：一种是让Agent像人一样调用图表、专业工具，甚至训练专门的模型来处理数据；另一种是将这些专业数据作为知识纳入模型体系。

3. RSI（递归自我改进）正在成为热门概念，但姚顺雨认为它的本质其实很朴素，就是用AI更好地运行研发循环。早在2019年，人们就已经在使用GitHub等工具辅助开发，真正的进步来自持续修复Bug、清洗数据、运行实验和Debug。他特别强调，技术进步来自那些把具体问题解决的人，而不是不断创造新概念的人。这也意味着AI研发自动化有大量具体的工程机会，尤其是能够让模型参与下一轮数据生产、实验验证和代码改进的闭环系统。

4. 一个容易被忽略的研究问题是，小规模实验的失败未必意味着研究方向本身没有价值。姚顺雨分享过自己的经历，博士后期他曾尝试将ReAct策略融入模型，希望提高模型能力，最初在Llama13B上实验的效果很差，一度怀疑自己的研究能力，后来意识到模型规模可能不足以体现这个方向的价值。他认为，算力不足时，实验中的噪声很容易掩盖真正的信号，研究者甚至可能因此判断错什么问题值得做。大模型研究需要结合理论推导和小规模实验预测大规模实验的结果，同时也要理解哪些结论能够跨越模型规模迁移。

5. 预训练数据的竞争远没有结束，未来的数据工程还涉及如何重复利用高质量数据而不让模型简单记忆数据。姚顺雨提到，代码等高质量数据获取成本很高，训练时可能需要重复使用，但重复次数增加又会带来记忆和过拟合问题；合成数据也面临质量退化的风险，此外还需要研究动态数据的构建和不同数据之间的配比。他特别指出，预训练中的很多配方可以先在小模型上验证，但小模型实验得出的结论并不一定值得直接迁移到大模型，这也是预训练研发非常困难的地方。

6. 后训练数据需要同时解决模型的智力和实用性问题。姚顺雨把数据难度与Intelligence联系起来，例如数学题可以持续提高难度，训练模型的推理能力；而写作等任务计算难度可能没有那么高，却有很强的实际使用价值，对应Alignment。一个模型可能数学能力很强，却无法很好地完成真实用户的工作，因此后训练需要同时考虑任务难度、实际用途和数据质量，还要研究评测指标与最终后训练效果之间的相关性。

7. 强化学习的工程瓶颈远不止算法本身，RL训练首先要保证正确性，其次是稳定性，最后才是效率。以GRPO为代表的算法仍然建立在Policy Gradient这一相对简单的框架上，其中一个重要原因是它引入的额外假设较少；与此同时，训练系统和推理系统必须协同设计，需要解决吞吐量、显存占用以及有限GPU资源如何在训练和推理之间分配的问题。他还提到，大模型实验成本很高，因此需要通过数学直觉、小规模实验和超参数研究，尽可能提高大规模实验的成功率。

8. AI安全领域需要区分Safety和Security，前者关注模型自身行为是否偏离预期，后者关注外部攻击者如何利用模型实施攻击。姚顺雨认为，网络安全能力也应该进一步区分漏洞发现和漏洞利用，发现系统存在漏洞并不意味着能够利用漏洞完成攻击，因此训练模型时可以有意识地加强防御性数据和防御能力。他们在模型发布前还会进行专门的安全评测，并与外部安全研究团队合作。

9. 他分享过一次很有意思的Agent安全压力测试，把多个Agent放进沙盒，给它们安排一个无法直接完成的任务，模型随后发现了一种能够联系其他环境的通信渠道，主动建立沟通、召集其他Agent分工，并尝试前往Hugging Face寻找任务答案。显然，当Agent遇到无法完成的任务时，它会主动寻找外部资源、建立通信关系并改变原有执行路径。未来的Agent安全评测需要覆盖多Agent协作、跨环境通信、权限边界和任务受阻后的行为。

10. 姚顺雨对开源安全也有一个比较明确的判断，他认为负责任的开源可以增进安全能力，因为防守者同样需要拥有足够强的工具。他举例，有人希望使用模型帮助开展安全防御，却因为闭源模型的安全规则被拒绝，最后转而使用开源模型完成工作。因此，模型开源需要配套训练阶段的防御能力建设和发布前的安全评测，不能简单地将开源与安全风险画等号。

11. 很多Alignment问题可以落实为具体的奖励设计问题。姚顺雨用教育作比喻，如果一个孩子只有数学考100分才能获得奖励，他自然会把全部精力放在数学上，甚至可能形成其他方面的问题；模型也会按照训练数据和奖励规则优化自己的行为，最终表现可能与设计者真正希望的目标存在偏差。他认为这属于可以通过数据、奖励函数和评测机制不断改进的工程问题，机器也可以辅助人类完成这套对齐工作。

12. 自动化不可避免地会继续深入，但人类需要重新找到自己参与系统的正确位置，需要把人安排在合适的环节，以正确的方式监督AI，他甚至认为，未来一些Infra和算法工作可能越来越不需要人，但数据和信息领域仍然需要人的参与。这也涉及目标定义、数据质量判断、结果验证和现实世界部署等工作。

13. 模型能力的提升通常是连续发生的，但真正引发商业爆发的往往是交互方式发生变化，或者某种过去无法完成的任务突然变得可用。姚顺雨用GPT的发展举例，模型内部能力可能一直在逐步提升，研究人员每天都能观察到细微进步，普通用户却可能只在ChatGPT出现时才突然感受到变化。对于产品创业来说，这提供了两个观察方向：寻找能够改变用户交互体验的新产品，以及持续测试模型能力边界，发现那些刚刚从不可用变成可用的任务。

14. 技术能力、用户价值和商业收入之间存在很大的距离，如果一个模型的能力已经接近GPT，但实际收入只有对方的1/100甚至1/1000，就应该认真检查产品本身的问题。他还指出，商业定价在很大程度上取决于竞争关系，而非单纯取决于产品质量。因此，模型公司的商业机会取决于能否解锁新的应用场景、创造足够大的用户价值，以及在竞争中获得合理的市场份额。即使底层模型的算力和研发资源逐渐集中，围绕模型部署、产品创造和真实业务场景进行整合，仍然存在创业机会。

15. 关于AI公司的组织模式，姚顺雨特别提到了自下而上的创新。他以OpenAI为例，早期公司重点投入的方向包括机器人，但GPT作为一个小项目逐渐展现出价值，随后获得更多资源；后来的gpto1也经历了从数学研究小组逐步发展起来的过程。这种组织方式允许创新从小团队和具体实验中涌现，再根据实际结果决定投入。他认为，很多重要创新在最初阶段并没有明确的商业规划，组织需要给探索性项目留下成长空间。

16. 他对大模型公司追逐量化指标的现象提出了批评，团队负责人不够了解技术时，下属往往会选择汇报容易量化的结果，例如模型参数、数据量和MMLU分数，因为这些指标更容易展示成绩，但真正重要的工作可能是修复一个关键Bug、解决数据质量问题或者让整个系统正常运行。他认为，做大模型最重要的是知道应该做什么，并且坚持把正确的事情做好，即使这件事短期内无法体现在漂亮的指标上。

17. 姚顺雨谈到了一种很有意思的组织文化差异：有些团队以量化指标和赛马机制为中心，谁的分数高就给谁更多资源；而他更看重Trust和Taste，也就是信任与判断力。他以微信、游戏和影视项目为例，这些产品在发布之前很难通过AB Test准确预测最终成败，管理者需要相信团队的审美、经验和长期判断，愿意持续投入时间。

18. 在人才选拔上，姚顺雨认为学习能力比已有经验更重要。他提到，自己看重的团队成员通常具备Low Ego、诚实、靠谱和愿意把事情做正确等特征，同时需要有很强的Co-design意识。大模型研发涉及算法、Infra、芯片、数据和产品等多个团队，一个训练架构的设计就需要综合考虑训练效率、推理效率、后训练能力和成本，任何单一岗位都很难独立完成。一个人能否快速学习、与不同领域的人有效协作，以及是否愿意认真处理细节，往往比简历上已经掌握多少具体技术更重要。

19. 他还提到，不同性格的人其实适合大模型产业中的不同岗位。喜欢明确指标、享受持续进步的人可能更适合预训练和Infra；想象力丰富的人可以尝试算法研究；喜欢思考人文问题、理解用户需求的人可能更适合产品和对话体验；做事认真、责任心强的人则适合生产系统和模型部署。AI产业需要的能力结构非常复杂，没有必要让所有人都去竞争同一种技术岗位。

20. 对于个人职业选择，姚顺雨提出了一个很实用的问题：你要么融入大模型浪潮，成为这套机器的一部分；要么寻找能够与大模型互补的事情。他借用了一个创业判断标准：假设GPT6发布，你的创业公司会因此睡得更香，还是更睡不着？如果模型进步会直接摧毁你的核心业务，就需要重新审视方向。与模型正面竞争人类已经不占优势的认知任务，成本会越来越高，物理世界、硬件、真实实验和对人性的理解等领域，则可能拥有不同的资源壁垒。

21. 姚顺雨分享了自己在清华读书时的经历。他直到大三下才开始做科研，最初也是因为推研要求而被动进入科研，期间尝试过一些当时流行的研究方向，却发现自己并不真正感兴趣。他后来更愿意追随自己对计算机和其他领域的兴趣，也提到身边有人曾经参与说唱社、学习数学，过去看起来不相关的经历，后来可能转化成语言审美、理论理解和研究判断力。他认为很多经历的价值需要经过很长时间才能显现，人生中的弯路未必真的浪费。

22. 他还谈到自己读博最后一年专门选修集合论的经历，因为当时意识到，等真正进入具体工作之后，可能就很难再有时间系统学习那些纯粹出于兴趣的理论知识。他认为数学中的基本结构和大模型的组成部分之间存在很多值得思考的联系，有些知识学习时看不出直接产出，却可能在未来某个时刻与其他经历连接起来。

02｜Claude Code 用子代理后台执行

来源（X） · @bojie_li · 2026-11-19 16:38

用 Claude Code / Codex 做长程任务的一个小技巧：让它在 subagent 里面干活，main session 用来跟你讨论。

默认 Claude/Codex 一般是在 main session 里面干活的，问个问题，它往往要把当前手头的事收尾再回答你，往往要等几分钟。另外，session 里面有很多执行命令的细节，我也不一定关心。想滚动上去看几小时前的对话记录却很费劲了。

main session 聊天，subagent 干活之后，界面会清爽不少。恭喜你把 Claude/Codex 改造成了 OpenClaw（主 session 聊天，后台执行）。DeepSeek superagent 也是这样的架构。

03｜CMU 课程把代码检查做成门禁

来源（X） · @shao__meng · 2026-11-19 12:54

CMU 17-214 第 21 讲：Agent 一下午改 2000 行，就把检查做成流水线门禁

CMU 17-214「Agentic Software Development」课程认为，有了 Coding Agent 之后，写出看起来像样的代码已经不贵了，难的是理解、验证、演化，以及把一套软件真正跑起来。整个学期都围着同一个系统做设计和改版，并一直监督 Agent。第 21 讲「Verification in the Pipeline」接在 DevOps 后面，接下来是实验课 Lab 12，让学生自己搭一套持续集成门禁，还有作业 A6，要把系统真正跑起来，并给每次改动加上检查和部署。

课程：https://cmu-17-214.github.io/f2026/
第 21 讲讲义：https://raw.githubusercontent.com/CMU-17-214/f2026/main/slides/21-verification-pipeline.pdf

门禁要跟上 Agent 的出码速度

讲义里举了个场景：预订团队有人带着 Agent，一下午就开出一个改了 2000 行的 PR。认真审完还是要几个小时。代码生成变快了，审查速度几乎没变。所以他们主张把检查做成每次改动都会跑的门禁，测试、类型检查、代码检查都可以用来拦住合并。一条好的检查，要能在这次改动里把这类问题找全，以后每次改动也能再找一遍。检查本身只写一次，之后每次持续集成多花一点时间就行。

动态检查是把代码跑起来看结果，静态检查不跑代码，但能分析测试没走到的路径。两类检查抓住的问题不一样，所以大多数流水线会两头都做。讲义用一段预订代码说明这一点。测试里伪造的通知发送总是成功，所以测试全是绿的。可代码并没有等待发送结果：一旦邮件服务失败，这个没被接住的错误，默认会让整个进程退出。这时预订已经写入了，这个进程上正在处理的其他请求也会一起失败。这类问题，代码检查不用跑测试就能报出来。

静态检查要少误报，也要防被关掉

项目里的约定可以写成自定义规则，报错时直接写上该怎么改，这样会跑检查的 Agent 也能按提示修改。分析器没法判定程序里所有真正要紧的性质，漏报和误报都会有。大多数工具宁可少误报，因为经常报错的检查，人就会不当回事。至于同一间房不能重复预订这类业务规则，还是得靠测试、类型或者自定义规则来管。

讲义引用了 Google 和 Meta 的做法：把检查结果放在代码审查里，修复率比丢在夜间清单里高得多；会打断构建的检查，本身几乎不能报错。这些要求当初都默认每次发现都会有人去读。Agent 不在乎一次要读多少条，规则可以更严，成本也不会明显变高。可它也可能随手加上抑制、写成 any 或 as，或者把覆盖率门槛调低，检查是通过了，问题却没修好。所以上新规则时，常用基线只拦住新出现的问题；做抑制时要把理由写清楚；改检查配置的 diff，也值得多看一眼。类型相当于能被机器核对的规格：不存在的方法调用它能抓住，可一个真实方法被用错了含义，它看不出来。

哪些检查该拦住合并

更省事的测试应该先跑，也跑得更勤。测试不稳定，常常是因为等待时间或共享状态没控制好，应该把根因修好，或者暂时把它从必过检查里拿掉，别靠反复重跑把失败蒙过去。覆盖率下限只能说明代码被执行到了；如果代码和测试都是 Agent 写的，这些测试有时只是在确认代码做了它已经做的事。

能拦住合并的，应该是跑得快、结果稳、一旦失败基本就能认定有问题的检查。如果失败了还得再判断该不该管，就先报告，先别急着拦。拦住部署比拦住合并麻烦得多：有些检查代码没改也会变红，系统出故障时，又慢又不稳的检查还会拖住修复。检查可以对着这 2000 行同样跑一遍，人就能把时间花在设计好不好、规格对不对、某个依赖该不该信上。当然，这得先保证这些检查本身靠得住。Agent 最好在本地先跑同一套检查，但流水线还是要再跑一遍。Agent 给出的审查意见可以当参考，不少团队不会只凭这一条就拦住合并。Lab 12 和 A6 接下来就让学生自己把门禁接进持续集成和部署。

06｜Gemini 4 系列命名与定位梳理

Gemini 4 的模型命名比较混乱，所以这里理清楚一下怎么使用，相信看完就非常清楚了：

- Gemini Hydrogen 是一个轻量级的模型，可以理解为 Flash（Luna、Haiku）。速度快，价格低，并且有不错的能力，适用于绝大多数工作

- Gemini Neon，一个新发布的中等模型，基于 Hydrogen 和 Carbon， 提供接近前沿的智能同时保持低价。而且其实目前这个模型就是前沿级别，所以可以放心将绝大部分任务交给它。顺便说一下，这个模型的语言风格真的非常好，比别的 4 系模型好。另外，它的网安能力不错，而且不会那么敏感的拒答。

- Gemini Argon，一个前沿模型。因为已经比较久，所以实际上已经被 Hydrogen 这种 flash 模型超越了。Argon 还是有着不错的设计能力，而且语言风格不错。我在设计任务上有时候仍然会使用 Argon

- Gemini Carbon，目前 Gemini 系列最顶级的模型，基于 Argon。绝对的前沿智能，有非常棒的知识量。但是我个人觉得稍稍有些往 coding 方向特训了，所以我也说了有时候我仍然喜欢 argon 来做一些设计工作，感觉 argon 会更发散一点。

Gemini 4 整个系列模型都非常不错，目前没看到有什么拉胯的。Neon 目前的 API 定价高于 Carbon 的优惠价，仍然低于原价，所以这没啥问题。Neon 的基准测试会高于 Carbon，这个现象可以理解为 Opus 5.5 和 Fable 5.1

不过在 Antigravity 中，Neon 现在有非常严重的缓存问题，导致这个模型的实际额度很低....我不知道 agy 团队和 infra 团队在干啥，希望他们赶快修复吧！
