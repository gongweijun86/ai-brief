中文译文

我实际上已经不再使用"harness"这个词了。我现在从两个角度来思考：agent 运行时和 agent 应用程序。

Agent 运行时应该非常小。它们的核心任务是将 LLM API 连接到一个执行环境。该环境可以是一个完整的操作系统，也可以是一个语言 VM，比如 JavaScript 运行时。这里几乎唯一重要的是鲁棒性。Agent 运行时必须能够让 agent 永远运行下去。字面意义上的永远。

Agent 应用程序是其他一切。是的，字面意义上是世界上每一块软件。

如果软件不是为 agent 构建的，agent 会通过 computer use 或 browser use 来使用它。这些能力可以内置到 agent 运行时中，也可以由另一个 agent 应用程序提供。

如果软件是 agent 原生的，agent 应该能够直接使用它。Agent 使用该软件的体验——我们称之为"agent experience"——至少在目前需要精心设计，以便高效地利用时间和 token。

另一个关键部分是 agent 身份。Agent 应用程序应该能够单独识别每个 agent，而不仅仅是它所使用的浏览器或计算机。这使得每个 agent 的操作都能被详细记录，并可以实时或事后进行审计。

我们在 @botiverse 构建的一切都遵循这一观点。

原文

I've actually stopped using the word "harness." I now think in terms of two things: agent runtimes and agent applications.

Agent runtimes should be very small. Their core job is to connect an LLM API to an execution environment. That environment could be a full OS or a language VM, like a JavaScript runtime. Almost all that matters here is robustness. An agent runtime must be able to keep an agent running forever. Literally forever.

Agent applications are everything else. Yes, literally every piece of software in the world.

If software isn't built for agents, they use it through computer use or browser use. These capabilities can be built into the agent runtime or provided by another agent application.

If software is agent-native, agents should be able to use it directly. The experience of an agent using that software—what we call "agent experience"—needs to be carefully designed, at least for now, to make efficient use of both time and tokens.

Another key piece is agent identity. Agent applications should recognize each agent individually, rather than just the browser or computer it's using. This allows each agent's actions to be recorded in detail and audited in real time or after the fact.

Everything we're building at @botiverse follows from this view.

06｜Lambert：中国模型差距在算力

来源（X） · @MrPingChecks · 2026-10-14 23:22

这周都在说“反蒸馏之后，国产模型要掉队”。美国做开源模型的研究员 Nathan Lambert 看法正相反：中国有人才优势，蒸馏顶多帮中国实验室快了几个月，真正拉开差距的是算力。

他今天上了 a16z 的播客，几个要点：

1. 中国实验室缺什么？
不缺人才。他说，要说中国的人才不如美国，这话站不住，甚至可能还略占优势。缺的是算力：他跟中国研究员说，OpenAI 一个普通研究员随时能用 5000 张 H100 级别的卡，对方听完惊得说不出话。

2. 蒸馏到底帮了多少？
他说按公开的研究，很难说这是主要因素：开源社区到现在还在用一个过时的 Qwen 模型当“老师”，因为找不到更合适的；就算拿到 Claude 的推理过程，也未必能让自己的模型好多少。他估计蒸馏帮了“几个月”，也说这个估计很不准。
但他也承认有说不清的地方：国内有大量 Claude 代理和账号，他还提到有过 Kimi 在自己的产品里给用户用 Claude 的情况。

3. 封住 API 拦得住吗？
只要 API 开着，推理过程就拦不住被拿去训练。只放进要签企业协议的产品里，别人再想拿就难得多，他支持实验室这么做。但让政府出面管，他认为弊大于利，“因为他们不会停”。

4. 中国公司为什么都开源？
不是政府让的，是生意：要是只在中国卖 API，海外根本没人知道月之暗面、智谱。

5. 开源以后还跟得上吗？
跟得上，但慢一拍。闭源先做出新玩法，比如一套系统里管一万个 AI 助手，开源看到样子就能跟上；但第一个做出来的不会是开源，因为没有那么多算力。

它能越级打怪，靠的是 CPU 和 GPU 共享 128GB 统一内存，Linux 下能直接划出 110GB 给 GPU 当显存用。

要知道 RTX 5090 也才 32GB 显存，4090 只有 24GB，显卡只要显存被撑爆就得走慢速通道，所以 AMD 官方测试里，它跑 DeepSeek R1 蒸馏版能比单买一张 1000 美元的 RTX 5080 快 3 倍以上。

→ 装好 Ollama，拉取量化后的 Qwen3 235B 跑在 110GB 显存里

但站在另一个更现实的视角来看，这台机器受限于内存带宽，极限吐字速度肯定比不上云端 H100，而且 235B 必须经过较重的量化压缩才能塞进去，它真正适合的是本地脚本、私密代码库和 24 小时挂机任务，不是替代所有云端极限推理。

当三年半的订阅费足够买断一台百 GB 显存的桌面工作站，云端按月收租的订阅制，第一次迎来了买断制桌面硬件的正面狙击。

08｜Clark：完整RSI预测提前至2027

来源（X） · @sleepy0x13 · 2026-10-14 09:22

Anthropic 联合创始人 Jack Clark 刚刚把完整 RSI 的预测时间从 2028 年提前到了 2027 年。

今年 5 月，他还认为 2027 年实现完整 RSI 的概率只有 30%，更倾向于 2028 年。而在 10 月 12 日最新一期 Import AI 中，他明确表示，2027 年实现这一能力的可能性已经更大。

RSI 的概念其实很简单，就是 AI 自己研究、训练、改进下一代 AI，然后让更强的模型继续完成同样的工作，形成自我强化的研发循环。

过去，Jack Clark 一直认为这个过程最大的障碍是创造力。AI 已经能写代码、优化训练流程、执行实验，但真正决定科研突破的能力，包括提出新想法、选择研究方向、判断哪些实验值得做，仍然掌握在人类研究员手里。

现在他开始改变判断了。

P-Zero Research 最新发布的 TasteVal 评测发现，前沿 AI 模型的实验研究能力自去年 12 月以来，平均每三个月翻一倍。Claude Opus 5.5 在限定科研任务中的表现已经超过人类专家基线，而执行单次任务的成本只有人类的约三十分之一。

加上最近 AI 在数学研究中取得的一系列突破，Jack Clark 认为，创造力这块曾经最令人怀疑的拼图，已经出现了非常明显的进展。

09｜上海电信CN2至朝鲜公网零丢包

来源（X） · @Noe1017_Monad · 2026-10-14 23:23

上海电信cn2出口到朝鲜公网的网络质量分析。

这条专线，基本上只有将军一家在用。

今天分析一条极为特殊的跨国路径——上海电信 CN2 到朝鲜星合营会社（Star JV）公网的网络表现。

从监控数据与路由追踪来看，这条链路展现出了极其惊人的稳定性与独特的跨运营商路由调度逻辑。

📊 一、 硬核数据与性能测评
延迟：Median 95.5ms / Max 97.2ms / Min 95.3ms

👉 路由剖析：上海到平壤的物理直线距离仅约 950km，若有直连光缆，RTT 理论上可在 20ms 以内。实测约 95ms 的延迟印证了其大绕弯路径：流量从上海电信 CN2 跨网转接至联通境内骨干网，出境汇聚至香港，再通过联通香港 POP 节点的跨境专线/海缆北上拉回平壤。
抖动与丢包：标准差仅 0.3ms，末端丢包率 0.00%。

👉 品质评级：SSS 级（极致稳定的“天际线”）。虽然路径存在大范围绕行的几何距离，但监控全程拉成一条绝对平直的直线。多日观察几乎完全没有波动与拥堵，说明两端及中间穿透的联通跨境链路带宽极度空闲，策略高度锁定。

🔬 二、 场景解析：为什么会有如此“奇葩”又稳定的路由？

1️⃣ CN2 穿透与跨网转接
上海电信 CN2 作为高品质骨干网，虽拥有极佳的出境能力，但由于朝鲜 Star 网络在中国方向的主要上游是中国联通，电信流量必须在境内对等互联交换给联通。CN2 在此扮演的是前段“高品质接入”的角色，后续则交由联通承载。

2️⃣ 香港 POP 点的集中洗牌与绕道
流量先南下香港再北上绕回朝鲜，反映了典型的 BGP 路径选择。中国联通在香港的交换节点承载了大量亚太 Transit 业务，前往特定小众国家/地区的流量会在香港交换中心进行路由判别与计费结算，虽然牺牲了物理距离，但保障了链路的稳定打通。

3️⃣ 神秘的朝鲜 Star JV 出口与控制面限速
朝鲜公网在全局互联网中流量极低且几乎没有普通民用挤占，只要流量顺利进入联通与 Star JV 的对接管道，整条链路就相当于“独享”通道。即便追踪途中部分联通中间节点因防火墙策略表现出较高 ICMP 超时，最终目的地址依然保持 0% 丢包与极低抖动。

💡 总结
这条从上海电信 CN2 到朝鲜 Star 的路径，虽然经历了“电信 ➔ 联通 ➔ 香港 ➔ 平壤”的折返大绕弯，但凭借 CN2 的优质承载与朝鲜专线通道的独占性，最终跑出了 93ms~95ms 端到端零丢包、0.3ms 极低抖动的硬核品质。这是一条非常标准的特种网络样本。
