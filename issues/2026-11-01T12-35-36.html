01｜AI短片用极简叙事绕开技术短板

来源（X） · @guanmo_ai · 2026-11-01 17:39

用 AI 做短片，很多时候容易陷入“堆砌特效和复杂运镜”的误区，反而忽略了叙事本身的节奏。这支用 30 秒戒烟短片，在创作思路上提供了一种很克制、也很聪明的解法：

1. 戏剧张力与反差：慈祥老太太配荒诞的物理击飞，慢节奏复古爵士乐配干脆利落的动作卡点。借用冷幽默的视听语言，把大众对“二手烟”的潜意识情绪外化，高级且不让人觉得说教。

2. 视觉锚点的高度统一：老太太的酒红风衣、碎花衬衫与黄色手提包贯穿始终，配合韦斯·安德森式的对称构图与复古暖色调，在不同光影场景切换中依然保持了极强的镜头连贯性。

3. 极简的叙事留白：放弃冗长的剧情铺垫，8 个场景只重复同一个核心动作——掏出弹簧拳套枪。用重复建立叙事韵律，既放大了荒诞感，也巧妙绕开了当前 AI 视频在长镜头复杂交互上的技术短板。

在模型能力边界之内做减法，用“1 个鲜明人设 + 1 个核心动作 + 多场景变奏”去构建故事，往往比单纯炫技更能打动人。这支片子的分镜逻辑很值得做视觉和内容的朋友参考

02｜Claude用记忆循环取代提示词

来源（X） · @huxlab · 2026-11-01 15:24

Anthropic 的工程师说：我们内部已经不怎么写 prompt 了，写的是循环。

她在台上花了半小时，展示了 Claude 团队如何创建能够自我提示的循环。

如果这堂课卖 700 刀，今年 Agent 课的榜单大概就是它。但它是免费的。

真正拉开代际差距的，不是谁的 Prompt 写得好，而是Agent系统架构彻底换了：

1. 记忆从一份 CLAUDE.md，进化成 Agent 自己读写的 memory/ 目录

2. 记忆待在对话里会烂掉：注意力被劈开，规律被埋住，旧笔记还在自信地用错

3. 白天各 Agent 把进展写进团队记忆

4. 夜里再跑一轮 dreaming：核对、整理、补全。第二天开工的那个，自动比昨天聪明一点

数据结果也很直观：一次通过的错误少了 97%，验收快了 30%。人回去看产品，不再一直盯着提示词。

提示词是一次性的，而循环能够持续执行。

差的不是你会不会问。

是你的 Agent 睡一觉之后，还记不记得昨天学到的东西。

03｜微软开源4B桌面代理双通道模型

来源（X） · @yibie · 2026-11-01 18:43

桌面代理（CUA，让 AI 自己操作电脑干活）现在有两条技术路线：一条只靠截图加鼠标点击，一条让模型直接写代码改文件。微软把两条路塞进同一个 4B 开源模型 Mage-VL-Cowork，刚放上 Hugging Face。

核心数字：OSWorld-Verified 66.0%，361 道留出题、50 步预算，两次完整跑分平均。对比同表，Qwen3.6-27B 是 63.9%，Muse Glimmer-30B 是 65.9%。不过 ScaleCUA-Qwen3.5-9B 是 68.7%，比它高，所以这不是「小模型全面赢」的故事。

真正的变化在动作选择。这个 4B 策略里没有外部路由器，模型自己判断这一步走哪个通道：视觉布局、画布编辑、应用里的实时状态，走 computer_use，11 个 GUI 原语加归一化坐标；表格、文档这类结构化编辑，以及做完后的确定性校验，走 bash，一个持久 shell 加 Python 环境。背后的直觉很简单：在菜单里点几十下改一个 xlsx，不如直接用 openpyxl 写文件；但改一张图的视觉效果，脚本写不了。

训练配方有三步值得抄作业的人看。

1. 先修教师 harness 再收轨迹。微软发现强模型拿到冗余工具也会养成坏习惯，而且坏习惯会蒸馏给学生。删掉 xdotool 和冗长的无障碍树这类重复通道、预装领域 Python 库后，GPT-5.4 教师升到 92.0%、步骤少 29.2%，学生对应 +12.5 个百分点（37.6% 对 25.1%）。

2. 题库按技能复用。Mage-CUA-Forge 为每一项原子技能写一次生成工作流，而不是每个任务跑一遍开放式 agent 循环。共产出 293,806 个任务、覆盖 6,915 项技能，单任务生成成本从 0.906 美元降到 0.158 美元，降了 82.6%。

3. 五阶段先分练再合并。视觉 grounding、GUI 执行、终端能力分别训练，再用 Hybrid SFT 学通道切换，最后在线 GRPO 用可验证的任务结果做强化学习：45.56% 到 55.84% 再到 66.0%。在线 RL 这一步加了 10.16 个百分点，同时平均模型调用从 21.57 次压到 18.77 次，输出 token 从 7,374 降到 5,499。

上下文管理上它用非对称滑动窗口：最近 3 张截图和 4 条完整回复保留，更早的历史压成一行 Action 摘要，活动窗口 32K token。4B 权重 bf16 约 9.48 GB，Apache-2.0 许可。

我的判断：这条路线对做企业桌面助手的团队压力最直接。如果你们的代理默认每个操作都模拟人类点界面，现在有一个可下载、可复现的对照组，评测维度也变了，不能只看任务成功率，还要看它选的路径是否合理、成品文件是否真的对。但别把它当成成品助手：66.0% 是厂商自报，同表就有更高的 9B 模型；调用次数和 token 下降也不等于用户等待时间下降，脚本可以很短但应用启动很慢；训练侧五阶段标称 7.79 ZFLOPs、32 张 B200，小模型省的是推理时的钱，上游投入一点不轻。模型和配方都开源了，能不能站住，要看外部在相同条件下重跑的结果。

04｜苹果前审核负责人谈拒审风险

来源（X） · @83dwn · 2026-11-01 04:08

曾经掌管苹果 App Store 审核的负责人，最近写了一篇文章，我觉得所有 iOS 独立开发者都值得看看。

作者是 Phillip Shoemaker @pbsIdentity

2009 年至 2016 年，他负责领导 Apple 的 App Store Review 团队，经历了 Steve Jobs 和 Tim Cook 两个时代，也是苹果早期 App Store 审核规则和流程的主要建设者之一。

换句话说，他曾经就是制定和执行这些规则的人。

最近，他发表了一篇文章：

Apple Approved the Fix. Then It Called the Developer a Liar.

苹果批准了开发者的修复，随后却指责开发者撒谎。

这个标题让我很有感触。

最近在 X、Reddit 和各种 iOS 开发者社区，经常能看到类似的经历：

1. 新 App 提交后，Waiting for Review 一等就是几周。
2. 好不容易进入审核，却因为 Guideline 4.3（Spam）被拒。
3. 明明是自己独立开发的产品，却被认定为重复或低质量应用。
4. 反复修改、申诉，依然得不到明确的解释。
5. 更严重的，甚至收到开发者账号终止警告，或者直接被封号。

我自己最近也经历了类似的事情。

一个新 App 提交审核，等了将近一个月，最后等来的不是批准，而是拒审和补充材料的要求。

尤其是 AI 正在大幅降低 App 开发门槛，大量新应用涌入 App Store，苹果对低质量和同质化产品的审核也越来越严格。

但问题是：什么算重复？什么算缺乏创新？什么又算一个已经饱和、不再需要新 App 的品类？

这些标准并没有非常清晰的边界。

Shoemaker 在此前的文章中也谈过，App Review 并不是简单地按照规则手册进行合规检查。审核人员有自己的判断空间，同一个 Build，今天被拒，过几天也可能获得批准。

更重要的是，对审核人员而言，错误批准一个存在风险的 App，与错误拒绝一个正常 App，承担的后果并不对等。

这也解释了为什么审核可能越来越保守。

结合他的分析，我觉得有几个经验值得独立开发者记下来。

第一，不要因为自己的 App 曾经通过审核，就认为后续版本一定安全。

审核通过并不意味着苹果对你的产品、业务模式和所有实现方式作出了永久认可。

后续版本仍然可能因为之前没有被发现的问题而遭到拒绝。

第二，4.3 不能只从代码是否原创来理解。

即使代码完全是自己开发的，也不代表一定能够避开 Spam 条款。

苹果还会考虑应用是否与大量现有产品过于相似，以及它是否提供了足够独特、高质量的用户体验。

所以，在开始开发之前，除了验证市场需求，也应该评估这个产品在 App Store 审核体系中的风险。

第三，提交审核时，尽可能降低审核人员理解产品的成本。

特别是那些功能比较复杂、需要登录、依赖服务器、涉及订阅或者动态内容的应用。

Review Notes 不应该只是简单写一句“Please review my app”。

应该主动解释核心功能、特殊交互、测试方式，以及可能让审核人员产生疑惑的地方。

第四，遭到拒审时，不要只想着证明苹果错了。

有效的申诉应该让审核人员更容易理解问题、核实事实，并确认相关风险已经得到解决。

如果确实违反了规则，就说明原因、修复方式以及如何防止再次发生。

如果是审核人员误解了产品，就提供清晰的操作步骤和证据。

情绪化的争论通常解决不了问题。

第五，也是我认为最重要的一点：开发者账号本身，已经成为一种需要认真管理的商业资产。

对于独立开发者来说，账号一旦被终止，损失可能远远超过某一个 App。

因此，不能为了加快上线而刻意隐藏功能、规避审核，或者在被拒之后不断尝试各种投机性的提交方式。

今天节省的一点时间，可能给未来所有产品带来风险。

我并不反对苹果清理 App Store 里的低质量应用。

事实上，作为开发者，我也不希望这个市场被大量换皮 App、粗制滥造的 AI 应用和各种欺诈产品淹没。

但一个健康的平台，除了需要严格的审核，也应该有足够透明、稳定、可预期的规则。

开发者可以接受产品不符合标准。

最难接受的，是投入了大量时间和资金，却依然不知道标准究竟是什么。

AI 正在让软件开发变得越来越容易，但把软件真正交付到用户手里，似乎又在变得越来越困难。

对于依赖 App Store 生存的独立开发者，这可能是未来几年必须面对的现实。

推荐大家关注 Phillip Shoemaker。他的文章不一定代表今天苹果的官方立场，但作为曾经负责审核体系的人，他提供了一个很少有人能够接触到的视角。
