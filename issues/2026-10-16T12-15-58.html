03｜Skill、Tool与MCP按规模选型

来源（X） · @kafkaup · 2026-10-16 19:57

讲一下 tool、skill 和 MCP 的区别以及选型的问题。

我们都知道：
• Skill 偏的是“怎么做”，它沉淀的是一套方法、流程、判断经验。
• Tool 是 agent 实际调用去完成具体动作的工具。
• MCP 更往外一层，解决的是这一套能力怎么通过一套相对标准的协议，被 agent 发现、理解和调用。

这三个东西不是互斥的。一个 agent 完全可以先通过 skill 确定当前任务该怎么做，然后在执行过程中调用 tool；其中一部分工具在内部系统里，另一部分则通过 MCP 来调用。

如果只从功能角度看，其实很好理解，但在做产品的时候，只从功能角度区分是远远不够的，它还涉及到团队协作、版本管理、后续的迭代和维护成本。

一个 skill 或一个 prompt / tool 最开始被一个人、一个产品使用时，怎么写都比较自由。但当它从个人开发产物变成团队资产，就会涉及到复用，进而对更多产品产生影响。这个时候，版本管理、迭代、权限以及责任边界等问题都会随之产生。比如一个 skill 最开始可能只是某个人写的 SOP，但当它被多个产品或业务线调用时，就不再只是一段可以随便修改的 prompt，它需要有版本、有 owner、有适用范围，也需要明确改动之后哪些任务要重新跑 eval。

Tool 作为一种能力资产，真正需要的是稳定的调用边界：底层可以随意改变，但上层最好不要每次都跟着重写。如果所有能力都在一个工程、一个团队里，普通的 tool calling 就已经很好用了，甚至比 MCP 更简单。但当这些能力分散到不同系统、不同团队甚至外部服务后，膨胀的不只是代码和服务数量，更是围绕工具建立的一整套维护与接入成本。每个团队都有自己的接口格式、参数定义和接入逻辑，不同的 agent 都要分别适配，此时统一协议的意义才显现出来。

MCP 的价值在于让底层与上层解耦：底层可以继续迭代，上层也可以独立开发，只要双方遵循一套相对稳定的协议协作，就不需要底层稍作修改、上层就得全部重写。

这又进一步涉及到生命周期管理。一个能力只要长期存在，就必然经历升级、兼容和废弃。如果前期的接口和资产没有规范统一，后续管理会非常痛苦。当 tool 的数量和团队规模扩大后，统一的协议能让这些能力作为资产得到更好的治理，在版本控制、权限分配、审计与依赖管理等方向上，也更容易走向平台化。

此外，这些架构设计还会反过来影响模型表现。如果几十个工具各写各的，模型的 tool selection 就会越来越困难；MCP 至少能让工具描述、schema 和调用方式保持统一，模型侧的不稳定性也会更容易控制。

在做技术选型时，一个非常重要的考量维度就是规模：
• 规模小的时候，重复开发可能比治理更便宜。
• 规模起来之后，治理一定比重复开发更便宜。

所以，skill、tool 和 MCP 不仅有功能定位上的差异，更对应了 agent 工程中不同的资产类型。选型时不需要纠结哪种概念更先进，而是要结合你的 agent 业务当前所处的阶段来判断：眼下究竟是要优先提高今天的开发效率，还是要提前降低未来的维护与治理成本。

04｜PenguinHarness统一RSI框架

分享一个 LlamaFactory 作者参与开源的项目：PenguinHarness 🐧

一款主打极简设计与多 Agent 协作的自进化 Harness 框架。它的核心思路是：固定模型，通过 Agent 之间的迭代评估与优化，持续改进提示词、Skills、工具和工作流，让 Agent 用得越好。

对多 Agent 协作、Agent 自进化感兴趣的朋友可以关注一下。

Yaowei Zheng | LlamaFactory @code_hiyouga

大家好！很高兴分享我们团队的开源新作 PenguinHarness～

在 Github 获得了 7 万 Star 以后，我们正在打造自进化（RSI）领域的 LlamaFactory，志在成为统一、高效、稳定、灵活的 Agent 自进化框架。

一句话介绍：
🐧 我们开源了 Multi-Agent 自进化框架：PenguinHarness，将所有 RSI 算法集成到一个统一框架中，现已获得了 2600 Github Stars。

📖 为了更全面地了解现有 RSI 工作，我们详细调研了 140 篇论文，将它们归纳整理分类，形成了 awesome-rsi 仓库，并发表了综述 paper。

📊 为了公平对比不同算法的自进化效率，我们构建了自进化 Benchmark：GDPevo。涵盖 6 大企业场景、240 个 Task，对 6 种主流 Agent 进行了评测。

以下为详细介绍：

和 LlamaFactory 的思路一样，我们想把所有和 RSI 有关的数据、模型、算法和评估都集成到一个开源 Harness 框架里面，方便大家实验和调试。现在已经集成了 5 种 RSI 算法和 7 个 Benchmark，未来我们的目标是扩充到 100 多个。同时，我们借鉴 DSH 的 Everything is Plugin 思路，把所有的算法和 Benchmark 都做成插件，相互解耦，让用户可以灵活调用任意 RSI 算法进化不同的 Agent。我们也做了精美的客户端，任何操作系统都可以一键安装，本地运行，可以到官网下载最新版体验。

开源仓库：https://github.com/Prism-Shadow/GDPevo

07｜Magnetar推出后量子安全zkVM

来源（X） · @alacheng · 2026-10-16 19:55

好久没怎么看zkvm的变化，微软新推出了个“后量子安全的ZKVM”（估计后续基于后量子安全叙事的项目会出现，可以多关注）

Magnetar 是微软研究院（Microsoft Research）由 Srinath @srinathtv 主导推出的一款 新的zkVM（零知识虚拟机），于10 月正式发布。它是首个同时满足以下三个核心属性的 zkVM：

-通用性（General-purpose）：支持 RISC-V 64 位整数指令集。开发者可以用 Rust、Go、C 等主流语言正常编写程序并编译到 RISC-V，Magnetar 直接证明其执行正确性，无需手动改写成电路。

-纯标准哈希的后量子安全（Post-quantum from standard hashes alone）：安全性完全基于标准哈希函数（如 SHA-256 或 SHA-3），不依赖椭圆曲线、格（lattice）、Poseidon 等电路友好哈希、可信设置（trusted setup），也不依赖未证明的 proximity gap 猜想。达到 120 位可证明安全性，透明（transparent）且后量子安全。

-为递归设计（Built for recursion）：验证过程主要是评估标准哈希和二元域算术，而这些正是 Magnetar 自身证明效率很高的工作负载。。

性能亮点在 15 个工作负载上比现有 zkVM 快 10–39 倍，
证明大小约 600 KiB，验证时间约 11–13 ms。

作者 Srinath Setty，也是zk领域的老手了，之前有很多贡献，Spartan（CRYPTO 2020）：无需可信设置的高效通用 zkSNARK，用于 R1CS，是后续许多系统的基础。

Nova（CRYPTO 2022）：引入基于折叠方案（folding schemes）的递归零知识论证，实现增量可验证计算（IVC），对后来的递归证明影响巨大。

HyperNova（CRYPTO 2024）：支持可定制约束系统（CCS）的递归论证，进一步优化折叠。

项目介绍：https://www.microsoft.com/en-us/research/blog/proof-based-general-purpose-computing-with-magnetar/

项目论文：https://www.microsoft.com/en-us/research/wp-content/uploads/2026/10/magnetar-1.pdf

08｜多Agent交叉审查自动化PR流程

来源（X） · @vikingmute · 2026-10-16 15:56

最近开发项目的经验发现，PR 完全没用了，原来是人类 review 的关卡，现在开之前 AI 都 review 完了，变成了一种仪式感的东西，就是看看 CI 变绿就无脑点通过了。

现在我的开发方式变成了，同一项目多个 feature，采用基于 worktree 的多 branch 并行开发，开发完了，大 feature，双甚至三 Agent 用不同模型从头开始交叉 review ，改 P0 - P1 的共性问题，别的不管了，小修改，直接一个模型 review 一次。

Review 通过以后，跑一次全量 E2E，跑 pre-commit 检查，没问题就直接 merge main 提交了，整个流程可以完全自动化，不用任何人工确认了。
