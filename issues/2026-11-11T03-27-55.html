01｜LangChain提出Eval驱动开发

来源（X） · @Xudong07452910 · 2026-11-11 08:30

之前推荐过几篇 Agent Eval 相关的文章，今天再推荐一篇 LangChain 最新的《What Is Eval-Driven Development》，这篇讲得挺实用，很适合正在做 Agent 和 Harness 的朋友。

文章主要介绍 Eval-Driven Development（EDD），核心思路是把 Eval 融入 Agent 的日常开发。

先定义什么算成功，写好 Eval、跑 Baseline，再修改 Prompt、Tool 或 Harness，通过相同的任务对比效果。

文中有个挺有意思的例子。

给知识库 Agent 新增 create_ticket 工具后，整体 Eval 分数提高了，结果它连「VPN 怎么连接」这种普通咨询都开始创建故障工单。

通过 Trace 排查才发现，工具描述太宽泛，导致 Agent 错误调用了工具。

这也说明不能只看 Eval 平均分。一次改动可能让新任务表现更好，却破坏原本正常的功能。除了最终结果，还需要检查执行轨迹，并保留独立测试集，避免反复优化导致过拟合。

这套思路很值得借鉴，尤其是现在大家都在不断调整 Skill、Prompt 和 Harness。

新增一个 Skill、修改一段 Workflow，甚至删掉旧 Harness，都应该通过 Eval 判断是否真的有效。

感觉 Eval-Driven Development 很值得成为 Agent 开发中的常规习惯，每次迭代都能有据可依。

原文：https://www.langchain.com/blog/what-is-eval-driven-development

06｜向AI描述问题而非解决方案

来源（X） · @ErwinWu000 · 2026-11-10 14:27

最近和清华、微软的同伴们在做一个项目，我们的思考是：

1. 现在大家用AI最核心的一点，是要善于从第一性原理出发，思考最关键的问题。
2. 可以描述你的喜好和当前面临的困境，但最好不要把你要的解决方法直接说给AI，因为你要解决的可能只是其中一个环节，而不是最本源的问题。

最直观的一个例子：
如果因为面试投递特别多，人工无法按时跟进导致会错过面试。

这时候如果只把苦恼定义为容易错过面试，那最后得到的只是一个日程安排提醒。
如果把问题定义为人工无法去跟进如此多的面试投递，最后得到的是AI全自动帮你做面试跟进的工作流。
这两件事的自动化程度不可同一而语。

一个改进你的追问（grilling）的技巧

不要谈论"是什么"，试着多解释"为什么"。

糟糕："我想为管理员构建一个带有图表和筛选器的数据分析面板"

好的："管理员目前无法看到应用中重要数据的总览"

如果你一开始就在描述你提出的解决方案，agent 就会固守它。它会假设所有重要部分都已确定，只会在实现层面追问你。

但如果你描述的是问题，你就会给 agent 更多发挥创造力的空间。

你将获得一次更深入、更优质的对话。

原文

One tip to improve your grilling

Instead of talking about the 'what', try explaining more of the 'why'.

BAD: "I want to build an analytics panel for admins with graphs and filters"

GOOD: "Admins can't currently see an overview of the important data in the app"

If you start by explaining your proposed solution, the agent will stick to it. It'll assume all the important stuff is settled, and just grill you on implementation.

But if you describe the problem, you'll give the agent license to be more creative.

You'll end up with a much deeper, better conversation.
