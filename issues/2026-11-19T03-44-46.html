01｜SSEngine将预填充提速至3倍

来源（X） · @OLDPANN · 2026-11-19 10:41

华盛顿大学 ServingStudio 开源了 SSEngine-GLM5.3-Flash，给 GLM-5.3-Flash 做预填充。流水线并行，前缀缓存跨 HBM、DRAM 和 SSD，调度按剩余预填充最短的请求优先。

没有解码路径，每个请求只返回 1 个 token，解码要放在别处。

04｜核化注意力在多数场景仍落后

来源（X） · @qingke_ai · 2026-11-19 10:30

五年了，核化注意力还是没打赢 FlashAttention。而且很多论文报的加速，在今天的基线上一复现就没了。

这篇做了一个该有人早点做的系统评估。效率方面：训练时和视觉 Transformer 里，FlashAttention 的显存和墙钟时间在多数序列长度下都优于 SOTA 核化方法，唯一明确的例外是因果语言模型推理时的显存。也就是说「用 O(N) 核化注意力替换 softmax」这个核心前提，在多数场景下站不住。他们还发现，很多报告的加速无法在现代基线上复现。

质量方面：在一个统一的蒸馏协议下，现有核化方法相对 softmax 还有 2 到 10 分的差距，而且模型规模变大并不能自动填上这个差距。

不过这个差距不是核化本身的宿命。他们给了 LARA++，在 LARA 的基础上用重要性采样近似 softmax，把差距收了回来（论文的结论是质量可以接近 softmax）。

判断：这篇的价值在方法之外——它给了这个领域一把统一的尺子。谁再声称「O(N) 注意力又快又好」，得先过这套蒸馏协议和现代基线。

边界：评估主要覆盖训练与 ViT 场景；因果推理场景只有显存一项例外被点出；LARA++ 的收益依赖实现质量。

https://arxiv.org/abs/2611.22947

05｜Mirobody本地解析体检报告实测

来源（X） · @cxjwin · 2026-11-19 11:27

上个月的体检报告，我交给了开源项目 Mirobody，在自己 Mac 上从读报告到回答问题全跑通了，没填一个 API key。58 行化验数值逐项对过原件，全对。可第一次上传时，化验单那几页它一条都没读进来。

装法：Homebrew 装 llama.cpp 跑模型，colima 起 Docker 跑应用，设置页选「100% 在本机运行」，用默认的小模型 minicpm5-2b，读图交给 glm-ocr。模型下载加载 6 分钟。机器是 M4 Pro、48GB，模型走 Mac 的 GPU。

第一次传整份 14 页的 PDF，1 分钟处理完，进来 33 条，全是前几页的查体和结论，化验单 3 页一条没有。翻日志，读图的模型一次都没被调用。这 3 页是嵌在 PDF 里的扫描图，页眉页脚却是文字，按文档写的规则，有文字层的页不走 OCR。

我把这 3 页截成图片单独传，一分半处理完，58 行化验结果全进来了，数值和原件逐项对得上。错了 3 处小地方：红细胞的参考范围多读出一个「1」，一个项目名丢了个字，甘油三酯旁边印的上箭头没记下来。

Mirobody 主要干的事，是把每条读数对到标准编码 LOINC，不同医院、不同写法的同一项才能连成一条线。这 58 行对上了 20 行。生化、甲功、糖化基本都对上了，单位不同还会选不同的编码；血常规 22 项、尿常规 14 项一项没对上，卡在「白细胞WBC」这种中文直接连着缩写的写法上。

最有意思的是肌酐。报告上写的是「肌酐(Cre)」，而 Cre 在 LOINC 里查到的是一种耐药菌的培养检查。它判断这个名字有歧义，就留空，没有瞎猜。

然后我问它：「我这次体检有哪些指标超出了参考范围？」2B 小模型想了 84 秒，走了 11 步。报告上标了箭头的 5 项全找到了，但把一项在范围内的血糖也算成了超标。它查表没拿到数值，转头去翻了原文件，回答里的数字也没带来源链接。我的血脂和肝功能确实有几项偏高，具体数值就不放了。

接 Claude Code 这一步，我换成了项目自带的演示账号。MCP 接上以后，Claude Code 查到的读数会发到 Claude 的服务器，所以这一步没用我自己的数据。问它「胆固醇这几年怎么变的」，只有一条记录的时候，它直说看不出变化，没编趋势；我再传两份合成报告（一份 PDF、一份 CSV，写法不完全一样），三次读数被认成同一项，按日期排好，每个数字都标了出自哪个文件。

ChatGPT Health、阿福是厂商的云服务，注册就能用。Mirobody 是 Theta Health 开源的（Apache-2.0），国内的网页版和微信小程序也基于它。开源版能把记录和模型都留在自己电脑上，代价是得自己折腾，小模型也慢。它不做诊断，那次回答最后一句也是让我拿报告去问医生。

认不出的写法可以去提 issue，它的词表就是这么一行一行补起来的。
https://github.com/thetahealth/mirobody

在 Claude Code 中输入：

/plugin marketplace add patch-gg/pixelfx
/plugin install pixelfx@pixelfx
不用自己从零绘制游戏特效，也不用到处找素材。
MIT 开源协议，支持商用。
全部特效在线预览：https://patch-gg.github.io/pixelfx/

11｜GPT-6.2修难题能力全面回落

来源（X） · @agentzh · 2026-11-19 10:59

中文译文

我们对 OpenAI 全新 GPT-6.2 系列的最新基准测试结果出炉了！从零编写代码的结果喜忧参半，而修复困难 bug 的结果则出现了意想不到的转折… 🧪👇

我们对新款 GPT-6.2 Sol 与 Astra 进行了测试，对比上一代的 GPT-6.1 Sol 与 GPT-6 Astra，覆盖全部三个推理力度档位（xhigh、max、ultra），使用了我们两个私有内部基准测试：
• OpenResty 编码评估：为真实生产环境中的挑战设计算法并编写新代码。
• Bug 猎手评估：在复杂的专有代码库中定位并修复困难 bug，同时不引入回归问题。

以下是全部 12 种配置的详细分解（基于下面 4 张图表；所有时间为每任务平均耗时）：

1) GPT-6.2 Sol（编码）：xhigh 略有提升，max 和 ultra 出现倒退。
• xhigh：86.1% → 86.4%（+0.3 个百分点），平均耗时从 14.2 分钟缓慢上升到 15.8 分钟。
• max：从 86.8% 下降到 82.6%，耗时增加约 26%（16.4 分钟 → 20.6 分钟）。
• ultra：从 83.8% 下降到 80.7%。速度稍快（11.1 分钟 → 10.3 分钟），但以牺牲准确率为代价。

2) GPT-6.2 Astra（编码）：max 档位有明显提升，但代价是耗时大幅增加。
• max：从 81.9% 跳升到 86.6%（+4.7 个百分点），但平均运行时间几乎翻倍（约 1.9 倍，从 12.2 分钟 → 23.1 分钟）。
• ultra：从 83.9% 微升到 84.6%。
• xhigh：从 83.9% 下降到 83.2%，且耗时更长（8.9 分钟 → 12.9 分钟）。

3) 困难 Bug 猎手评估：全部 6 种 GPT-6.2 配置相比其前代都有下降。
得分全面下降，幅度为 1.3 到 8.1 个百分点：
• Sol max：88.3% → 81.9%（耗时：22.0 分钟 → 23.6 分钟）。
• Astra max：87.4% → 79.3%（该组中最低）。
• Astra xhigh：86.8% → 81.0%，且耗时几乎翻倍（9.8 分钟 → 19.0 分钟）。

结论：
至少在我们的工作负载上，GPT-6.2 并非全面升级。讽刺的是，新款 6.2 Sol xhigh 在两项评估中都击败了自己的 max 和 ultra 档位——而上一代的 GPT-6.1 Sol max 在该组中仍然保持着编码（86.8%）和 Bug 猎手（88.3%）两项评估的最高纪录。
更新的模型和更高的推理档位并不自动意味着更好的结果——你仍然需要在自己的真实任务上对它们进行验证！

Our latest benchmarks for OpenAI’s brand-new GPT-6.2 lineup are in! Writing greenfield code is a mixed bag, and the results on fixing hard bugs took an unexpected turn… 🧵👇

We tested the new GPT-6.2 Sol & Astra against the previous-gen GPT-6.1 Sol & GPT-6 Astra across all three reasoning effort tiers (xhigh, max, ultra), using two of our private, in-house benchmarks:
• OpenResty Coding Evals: Designing algorithms and writing new code for real-world production challenges.
• Bug-Hunting Evals: Locating and fixing tough bugs in complex, proprietary codebases without introducing regressions.

Here’s the breakdown across all 12 configs (based on the 4 charts below; all times are avg per task):

1) GPT-6.2 Sol (Coding): Slight uptick on xhigh, regressions on max and ultra.

• max: Dropped from 86.8% → 82.6%, while taking ~26% longer (16.4m → 20.6m).

Newer models and higher reasoning tiers don't automatically mean better results—you still have to validate them against your own real-world tasks!
