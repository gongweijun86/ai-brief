04｜Claude Code 架构选Fable

最近几个月我是这样用 AI 写代码的：
- 基本只用 Claude Code，配合 Herdr 管理多个 session
- 架构相关的改动用 Fable，架构无关的用 Opus。有时中途发现需要切换模型，如果此时上下文已经很长，就先 /compact 再切换，否则直接用 /model 切换到另一个
- 不用 workflow、mcp、skill、memory。在架构搭好，需要横向扩展实现的时候才用 loop
- 不看代码，只看 AI 的回复，看不懂的时候就让 AI 细说
- 每隔几天问一下 Fable：“现在的架构是否有不合理的地方”
- 使用 flake.nix 管理项目环境，githook 里加上 lint fmt 等等
- 在 CLAUDE.md 里这样写：
1. 注释仅允许一种形式：第三方文档链接 + 可选的一句简短说明，除去链接外不得超过 100 个字符
2. 实施影响到架构的改动前必须先询问
3. 不要修改此文件
4. （项目需要的特殊约束）
- 在 ~/.claude/settings.json 里这样配置：
{
"permissions": {
"defaultMode": "bypassPermissions"
},
"env": {
"CLAUDE_CODE_SUBAGENT_MODEL": "claude-opus-5-5",
"CLAUDE_CODE_SHELL": "bash"
},
"model": "claude-fable-5-1",
"effortLevel": "high"
}

05｜Claude API 密钥参数回包守则

来源（X） · @swordBluesy · 2026-11-03 19:59

调通一次 API 就算会接 Claude 了？官方拆台：跑通一行代码最容易，难的是密钥、参数、回包三处不翻车

官方来源：Anthropic Academy《Building with the Claude API》第 1 课。课页未标注发布日期，故此处不写日期。原文标题直译：《发出一次请求》。先把反常识结论放前面：调 API 最难的不是写代码，是请求发出去之前那三件事——密钥不能进代码、max_tokens（最大输出词元数）是上限不是目标、回包不是一句话而是一组内容块；这三处没过关，跑通一次只是运气好，第二次、第十次迟早翻车。

说清词：
- API（应用程序接口）：让你的代码直接调用 Claude 的通道，不用经过聊天窗口。
- API 密钥（API key）：证明「这次调用是你发起的」凭证，每次请求都要带。
- 环境变量：存在系统环境里、不写进代码的配置，密钥就该放这里。
- .env 文件：放密钥等配置的本地文件，只存在你自己机器上。
- .gitignore：告诉版本控制「哪些文件不许提交」的清单，.env 必须在里面。
- SDK（软件开发工具包）：官方给的现成代码包，帮你把请求格式、认证这些脏活包起来。
- client.messages.create()：课内发请求的核心函数，client 是客户端，messages.create 是「创建一次消息调用」。
- model（模型）：这次调用要用哪一个 Claude 模型的名字。
- max_tokens（最大输出词元数）：Claude 这次最多生成多少个 token（词元）的安全上限。
- messages（消息列表）：发给 Claude 的对话历史，一条一条按顺序排。
- role（角色）：每条消息是谁说的，只能是 user（用户）或 assistant（助手）。
- content（内容）：每条消息实际的文本。
- 响应对象：Claude 返回的一整包东西，里面既有生成的文本，也有本次请求的元数据。

一个真实例子与一条眼熟的进化路线：最常见的翻车不是代码报错，是密钥翻车——新手图省事把 API 密钥直接写进代码，一 push 上 GitHub，爬虫几分钟就扫走，账单跟着就来了；课内的做法是反过来的：密钥放 .env，.env 进 .gitignore，代码里只读环境变量，密钥从头到尾不出现在代码里。这条路线你一定眼熟：以前是在聊天窗口里点对话框，现在是自己写代码发请求——从用人家的界面，变成自己搭调用层；跟以前从手动配置到插件打包一样，都是把一次性操作变成可复用的层，今天搭好调用层，明天接工具、接检索、接智能体全是往上加。

先把话说全，以下情况这课的方法不够用，先讲明：第一，已经有现成框架或封装代劳调用层时，不必手写这一层；第二，只跑一次的临时脚本，为一次调用搭整套配置是浪费；第三，团队已有 secrets 管理器时，.env 只是过渡写法，正式环境要走管理器的规矩；第四，课内用 Python 演示，非 Python 栈写法不同，道理相通但代码不能照搬；第五，生产环境还要考虑重试、限流、日志、成本——本课只讲第一次请求，这些都不在内。

一句定性金句：调 API 调的不是代码，是规矩：密钥有规矩、参数有规矩、回包有规矩。

正文：

第一節：翻車清單
- 密钥写进代码：看着能跑，提交一次就等于公开，爬虫比你先发现。
- .env 忘了进 .gitignore：文件建对了，提交时一起推出去，等于没建。
- max_tokens 当目标：以为设 1000 就要写满 1000，结果是上限不是目标，写多写少 Claude 自己定，设错只会提前截断。
- 消息格式写错：role 只能是 user 或 assistant，content 必须是文本，写错一个字段请求就被打回。
- 对着响应对象发愣：回包不是一句话，是一整包东西加元数据，不知道取哪一块，跑通了也拿不到结果。
- 对话没有历史：以为 API 记得上文，其实每次请求都是独立的，不把历史发过去，Claude 根本不知道前面说了什么。

第二節：替代方案與理由
- 方案一，聊天窗口手动问：最直观，但没法嵌进产品、没法批量、没法自动化。
- 方案二，自己写代码调 API（课内做法）：一次搭好调用层，之后工具、检索、智能体全往上加，理由只有一个——产品要的是可重复的调用，不是一次性的对话。
- 方案三，用现成框架代劳调用层：省事，但出问题时不知道里面发生了什么，调试要先拆框架。

第三節：目標形態
目标形态是一套规矩齐全的调用层：密钥在环境变量里、.env 在 .gitignore 里、请求三参数齐全、回包只取要用的文本。换机器不用重找密钥，新人不用现问格式，调用层跟着代码走，出了问题先查三处：密钥、参数、回包。

第四節：遷移步驟
1. 安装依赖包，建好 notebook 环境。
2. 在 notebook 同目录建 .env 文件，把 API 密钥放进去，绝不写进代码。
3. 把 .env 加进 .gitignore，确认提交清单里没有它。
4. 加载环境变量，创建 API 客户端。
5. 用 client.messages.create() 发第一次请求，三个参数一次给齐：model、max_tokens、messages。
6. 收到响应对象后，只提取生成的文本，确认输出干净可读再往下走。

第五節：團隊共建分工
- 调用层维护人：客户端、密钥读取、请求格式归他管，变了就他改。
- 密钥管理人：密钥怎么发、怎么换、泄露了怎么作废，归他点头。
- 回包复核人：取文本的写法对不对、元数据要不要记日志，归他验收。

第六節：官方工具包
- client.messages.create()：发请求的函数，三个必填参数 model、max_tokens、messages。
- .env＋环境变量：密钥的存放位置，不进代码。
- .gitignore：保证 .env 不被提交的清单。
- role＋content：消息的格式，user 说什么、assistant 回什么，一条一条排好。
- 响应对象：生成的文本加元数据，文本是你要的，元数据是排障要的。

結尾收束：原则比架构重要。架构可以换，工具可以换，这句原则换不得：密钥、参数、回包三处规矩立住了，调用层才算真的搭好。可重复的动作规则是：每次发请求前先问三句——密钥在代码外面吗？三个参数齐了吗？回包知道取哪一块吗？三句答完再发，请求才算真的发出去。

S1哥观点：站队就站死这一边：觉得「调通一次就是会了」的人，是在用一次运气给自己发合格证。这就跟第一次开车没熄火就敢上高速一样荒唐，没熄火只是运气，规矩才是驾照——密钥、参数、回包三处规矩没立住，跑通十次也还是新手。你第一次调 API 翻过最大的车是什么？评论区说说。

收藏用清单（照着做）：
1. 在 notebook 同目录建 .env 文件，把 API 密钥放进去，绝不写进代码。
2. 把 .env 加进 .gitignore，确认提交清单里没有它。
3. 用 client.messages.create() 发第一次请求，三个参数一次给齐：model、max_tokens、messages。
4. 收到响应对象后，只提取生成的文本，确认输出干净可读再往下走。
