01｜温度0不保证贪心解码可复现

来源（X） · @Chonghan_Liu · 2026-10-13 05:22

你说的 Temperature 设置成 0，那是最最最最基础的回答，三年前的回答，但这并不能保证你是用贪心算法的方式去把问题回答出来的。

首先你要看它是官方的 API 接口还是本地部署：

1. 官方的 API 接口：就算设置了 Temperature 为 0，你就算走了 Greedy 的贪心算法，但在不同的 Batch 里面，它的 Logprobs 还是会有不同的影响。
2. 本地部署：这会牵扯到更多的问题。你要保持相同的 Kernel，Batch Size 要为 1，Seed 数要相同，关掉 prefix caching，还有 GPU 的型号，以及各种所有的 Setting 都要完全一致

05｜多智能体持久记忆增益微弱

来源（X） · @omarsar0 · 2026-10-12 21:54

中文译文

必读论文，关于多智能体系统与持久记忆的有效性。

我们最近看到了许多通过持久记忆扩展多智能体系统的爆火案例。

这项工作对此进行了更深入的研究。

他们测试了一个三层链式智能体系统。

将长上下文工作分配到多个智能体上，可将每个查询的峰值 KV 缓存削减至 14.3 MiB，而单遍和 RAG 基线大约需要 35 MiB。

持久化的轨迹召回层增加了 0.368 MiB 的峰值缓存，准确率变化为 +0.015，其置信区间跨越零。

作者解释了原因。

单问题基准测试为每个条目提供各自的证据并独立评分，因此存储的轨迹没有什么有用的内容可供召回。

论文：https://arxiv.org/abs/2610.07782

与论文对话：https://academy.dair.ai/papers/persistent-memory-in-multi-agent-llm-inference-what-it-costs-what-it-buys-and-wh-2610.07782

原文

Must-read paper on the effectiveness of multi-agent systems and persistent memory.

We have recently seen many viral examples of multi-agent systems scaled via persistent memory.

This work takes a closer look.

They test one three-tier chain-of-agents system.

Splitting long-context work across agents cuts peak KV cache to 14.3 MiB per query, against about 35 MiB for single-pass and RAG baselines.

The persistent trace-recall tier adds 0.368 MiB of peak cache and changes accuracy by +0.015, with a confidence interval that crosses zero.

The authors explain why.

Single-question benchmarks give each item its own evidence and score it independently, so stored traces have nothing useful to recall.

07｜AI Evals 评估方法口袋指南

来源（X） · @shao__meng · 2026-10-12 08:47

Pocket Guide to AI Evals

@HamelHusain 把自己「Applied AI Evals」课程重要概念浓缩成了 13 张信息卡，做成了口袋指南，这个好，方便随时查看！

信息卡：https://hamel.dev/notes/llm/evals/flashcards/

1. 误差分析：流程为收集 100+ 条多样 trace → 开放式编码写非结构化笔记 → 聚类归类 → 按频次排优先级，循环直到"理论饱和"（新数据不再带来新失败模式）。与邮件版相比，这张卡补充了一个实操细节：trace 需标注 pass/fail 和 失败模式。

2. 何时写评估：这是最容易被跳过的决策卡。先问"误差分析中是否观察到该失败"，没观察到就别写。观察到后看修复需要多少迭代：需要大量迭代的才值得投入昂贵评估（如 LLM 裁判）；小问题考虑用代码断言，或者干脆修掉就继续前进。评估是有成本的，ROI 为正才写。

3. 拒绝通用指标：ROUGE、BLEU、"有用性/忠实度/语气"分数这类通用指标应替换为应用专属指标，如"日历排期失败""邮件收件人错误""未升级转人工"。好指标的五条标准：对应观察到的错误、涉及值得迭代的非平凡问题、范围聚焦于具体失败、结果是二元的（pass/fail 而非 1-5 分）、可验证（LLM 裁判需有人类标签对照）。

4. 常见错误：三条，迷信"自动评估魔法"而不先看数据（off-the-shelf 指标因此失效）；用 LLM 裁判却不对照人类标签测量裁判本身，得到不可信的错位指标；全绿（100% 通过）不是好消息，往往说明评估已饱和或太简单，应持续补充困难用例。

5. 自动化评估的三种类型：代码断言（关键词匹配、确认工具执行等，快、便宜、确定性、可解释，能用则用）；LLM 裁判（处理代码无法覆盖的主观/细微标准，慢、贵、需验证校准，留给重要失败）；护栏 Guardrails（运行在请求/响应通路上，在失败触达用户前拦截，要求低误报率以免拦截正常响应，通常是小分类器或代码检查）。

6. 拒绝 Likert 量表：LLM 裁判用二元 pass/fail 优于 1-5 打分。理由：量表与领域专家对齐的成本高；标注者倾向选中间值逃避艰难判断；还容易诱发"总体质量"这种大而不当的范围。二元评分强迫做出明确决定，这恰好对应现实中的发布决策（够好/不够好），且在误差分析中更易应用。示例中把"is_polite / scheduling / human_handoff"拆成三个独立的 pass/fail 判定。

7. 如何信任 LLM 裁判：唯一办法是对照人类标签测量裁判。人类标注数据切三份：Train（~20%，从中挑选 few-shot 示例进提示词）、Dev（~40%，优化裁判）、Test（~40%，防过拟合的最终检查）。切分比例与 ML 不同，因为"训练"的只是提示词。报告指标时不要用 accuracy，在不均衡数据上有误导性，应分别报告 TPR 和 TNR，目标都在 90% 以上。

8. trace 采样策略：两个维度。探索方向，随机采样（永远与其他策略并行，用于发现未知问题）、聚类（按语义相似度分组，看是否暴露新错误）、数据分析（对延迟、轮次、工具调用数、token 数等做统计找离群点）、分类筛选（用现有评估或 LLM 预测性筛选问题 trace，需谨慎）。利用信号方向，用用户的显式反馈过滤 trace。

9. 合成数据：关键是结构化生成而非零样本生成。"生成 50 个测试用例"这种提示词只会产出雷同、泛化的输入。正确做法：定义关键维度（功能、用户画像、场景）作为提示词变量保证多样性；尽量用真实日志做种子，让模型显式注入变化（新约束、修改变量）制造贴近现实的边界情况；定义输出 schema 并大量生成后过滤；从简单查询起步，迭代增加约束和格式复杂度。

10. 用 trace 构造测试用例：阅读 trace 时在第一个（最上游的）错误处停下，上游失败通常更重要，这样才可控。针对主要失败收集 trace，做最小化复现（尽量少的轮次和复杂度）。核心技巧是 N-1 切分：收集最小化复现的错误 trace 数据集，用错误发生前 N-1 轮作为测试用例（前提是系统没有剧烈变动）。进阶：用 LLM 对用例做有效变形（改写用户提问）扩大覆盖；或用另一个 LLM 模拟用户（做好很难）。

11. 转移矩阵定位 agent 失败：多步 agent（Plan → Search → Code → Finalize）难以判断哪一步最常出错。做法：列出所有状态；以"From 状态"为行、"To 状态"为列建网格；每次失败归因于错误前最后一次成功转移，计入对应格子。网格会直观呈现失败热点（示例中 GenSQL→ExecSQL 转移积了 12 次失败，一眼可见）。源自 Bryan Bischof 的演讲。

12. 部署评估：按目标分三档。CI/CD（pre-merge，用精选测试用例 + 单元测试/LLM 裁判，失败则阻止合并）防止回归；在线监控（post-response 异步，对采样生产流量跑评估，失败触发告警）发现新失败、跟踪表现；护栏（pre-response 同步，覆盖 100% 实时流量，用单元测试/小分类器，失败则拦截响应、重试或降级）保障安全、拦截高影响错误。

08｜Karpathy 拆解 AI 认知四层

来源（X） · @shao__meng · 2026-10-12 09:40

Andrej Karpathy 认为：人们对 AI 能力的认知，正在分裂成四个层级；越往里的人，看到的越不可思议

第一层：~60 亿人（约 75%），几乎没有接触过 LLM
第二层：~10–20 亿人（约 20%），偶尔用免费版 ChatGPT，视之为“更好的谷歌搜索”或写作助手「许多非技术背景的高管也停在这一层」
第三层：~2000 万人（0.2%），在数学与代码领域专业使用前沿模型，亲眼见到原本需数周甚至数月的大项目，现在一次提示就能由 agent 完成
第四层：~5000 人（约 0.00006%），能在内部接触最前沿系统：数千个 agent 协作数周，执行软件巨型项目、零日漏洞挖掘、网络攻防、发现新科学、推进数学前沿「人类的审阅速度已经跟不上产出」

漏斗为何形成？三个结构性原因
1. 影响力随问题规模扩展：你让 AI 做的事情越大、越有野心，感受到的能力差距就越大。用 AI 查菜谱和用 AI 建造复杂系统，看到的是两个完全不同的东西。
2. 能力的“锯齿状”：LLM 的能力分布极不均匀：在数字化、可验证、有明确经济价值的领域（代码、数学）最强，在模糊、主观、缺乏反馈信号的领域则弱得多。处于不同工作场景的人，摸到的是这把锯子的不同锯齿。
3. 访问权限分层：免费版 / 付费版 / 内部前沿系统，物理上就是不同的产品。绝大多数人终其接触到的，只是能力光谱的最底端。

Andrej Karpathy @karpathy

中文译文

翻出这条四月份的推文，因为这种对 LLM 能力共识的差距正在*扩大*。它现在不再是"两群人各说各话"，而更像是一个尖锐的漏斗。

- 粗略估算大约有 60 亿人（约占人口的 75%）几乎完全没有接触过 LLM。
- 大约 10-20 亿人（约 20%）是免费版类 ChatGPT 产品的偶尔、非频繁使用者。这群人看到的是笨笨的聊天机器人，把它当作更好的 Google 搜索、写作辅助工具之类的。也许某个智能体会尝试帮你订机票。我有一些非技术朋友（我认为很合理地）说他们根本不太需要它。甚至许多数学与编程之外的专业人士也处于这个层次。例如，高管和许多其他职能的人大部分时间都在和别人交谈，所以虽然他们在理智上理解发生了什么，但仍然是二手的、有些抽象的。

- 现在我们进入数学与编程领域对前沿级 LLM 的专业使用。大约有 2000 万人（0.2%）亲眼看到，曾经需要他们花数周/数月完成的大型复杂项目，现在可以通过一个提示词由智能体完成。构建应用、复制应用、翻译应用、从二进制文件反编译应用……这一切都发生得非常快，就在最近——不到一年前，我还在手动写代码，把记住的计算机代码命令一个字符一个字符地敲进代码编辑器，偶尔按 Tab 来自动补全一小段代码。

- 最后我们来到大约 5,000 人（约 0.00006%），他们在内部可以接触到前沿级系统。外部世界已经看到了预览。看起来就像是成千上万个智能体在数周内协作进行软件超大型项目：铸造零日漏洞、以机器速度进行网络攻防、发现新的科学成果、推进数学的前沿。这些是行业中顶尖专业人士需要数年工作才能完成的事情。与此同时，人工审查和理解开始跟不上。例如，人们仍在对几个月前的 OpenAI-HF 事件进行"考古"。数学家们可能会花一段时间来仔细研究前沿数学领域的 722 篇手稿。

这个漏斗是由多种因素共同驱动的：

09｜Agent 代码质量来自验证闭环

来源（X） · @shao__meng · 2026-10-12 09:54

99% 的开发者写不出好代码 -- Addy Osmani 与 lauren 分享：代码质量从来不是写出来的，是验证出来的

两位分别来自 Anthropic 和 SpaceXSI 的知名开发者，一致认为：当 AI 让验证变得廉价，工程师的核心工作就从逐行写好代码、逐行审查代码，转变为设计验证闭环、并把个人品味沉淀为可复用的规则。

# lauren 认为：「所有代码都是 slop」

Lauren 拆解了工程师对 AI 代码的普遍焦虑（"slop 会污染我们漂亮的代码库"），论证链条大致是：

1. Slop（劣质代码）从来都存在。人类写了几十年的代码库同样充满瑕疵，我们一直接受它；因为在嵌入式等任务关键领域之外，代码很少需要完美。
2. 大部分人对 slop 的真实定义其实是「不是我写的代码」。她坦承，包括她自己在内 99% 的开发者其实写不出、也说不清什么是「好代码」。
3. 她给好代码下了定义：正确、无 bug、运行快速且成本高效。好代码贵，是因为这三条性质过去无法被廉价地、形式化地保证。
4. 软件工程本来就一直在做交易：用 bug 换速度，靠测试和可观测性兜底，增量演进；她认为这是好事，因为软件天生是持续演化的有机体。
5. 结论：AI agent 无法写出「好代码」（那依然昂贵），但在规模上「平均而言好得多」，她用 "much better on average at scale" 精确地避开了「完美」的陷阱。最后补刀一句妙语："tldr 所有代码都是 slop；当然，我写的除外。"

# Addy 的回应：为什么「规模上的平均更好」成立

Addy 接过这句话并给出了解释机制——"at scale" 的规模来自验证，而 agent 让验证变得廉价：

· 过去让好代码昂贵的那些东西（测试、基准、规格说明、端到端运行）现在让 agent 顺手生成即可，边际成本趋近于零。
· 因此工程师的工作从「审查每一行 diff」转为「构建 agent 能自己跑的验证闭环」。他的原话："That loop is where quality comes from."（质量来自那个闭环。）
· 让品味复利：当 agent 犯错，就把这个错误写下来（落成配置、hook 或测试）让它不再重犯。这是把隐性经验固化为制度性护栏。
· 人仍然对发布负责，但审查的对象变了：看证据（测试结果、基准数据），而不只是看 diff。

10｜Grok Bot 用单工具协议省上下文

来源（X） · @shao__meng · 2026-10-12 11:55

反复学习 Lee Robinson 斯坦福 CS146S 讲座

这回主要看 Grok Bot 的 Harness 和上下文工程是怎么构建的。前段时间 Claude Code 源码泄露、CodeX 开源等等，让我们了解到了 Coding Agent 的架构和工作模式，那 Grok Bot 和 Muse 这种 Personal Agent 有什么不同呢？

# The Harness

① 单工具协议：客户端与服务器之间只有 "send to user"
这是 GrokBot harness 与同类产品最大的架构差异。所有重工具「shell 命令、文件读写、云端 agent、录屏、demo 制作」全部驻留服务器；客户端唯一的通信原语就是“发给用户”。收益是双重的：服务端上，无论客户端是手机 App、桌面端、邮件还是 Slack，都复用同一套工具层；客户端上，收到这个工具的返回后可自行决定渲染方式，登录表单（接 1Password）、支付（Stripe Link / XMoney）、不可逆操作（发邮件）前的草稿审批、甚至只用一个 emoji 回应。“逻辑在服务端、表现力在客户端”，一个工具同时换来了架构简洁与交互丰富。

② 动态工具发现（"tool search tool"）
把 Gmail、Drive、YouTube 等所有 MCP 连接器的完整工具 schema 塞进上下文，工作记忆就所剩无几。解法是上下文里只放工具名，模型决定使用时再从文件读取完整定义；又是“一切皆文件”的延伸。省下的上下文直接转化为更低成本与更大工作空间。

③ 逐级升高的求助阶梯
原则：永远先试最便宜、最可靠的选项。会话历史 → 插件/MCP/API（如 Plaid 查银行）→ 网页搜索 → 浏览器操作 → 整台 Linux 桌面跑脚本 → 全部失败才去打扰用户。电脑端读取信息同样分层：截图 → HTML → 无障碍树（大幅省 token，且直接定位可点击元素）→ 像素级点击（对付弹窗）→ 退回用户（验证码、双重认证）。这套阶梯的设计目标很明确：让 agent 像一个不烦人的同事。

④ 编排者 + 子智能体
主 agent 只做 orchestrator，上下文保持稀疏；重活交给拥有全新工作记忆的 helper（子 agent），只回收最终结果；这就是“无限上下文”体验的来源。每个 helper 是独立的持久化工作流（Temporal），崩溃重启不丢进度。主 agent 像管理待办清单的同事：可查看、可留言、可叫停。整体照着“理想工程团队如何扩张”来建模。

⑤ 四条实战经验与安全底线
· 不要在 turn 中途增删工具（保缓存）；工具 schema 冗长是成本，要修剪；
· “单工具”理论上可建模一切，但若模型 90% 时间在跑 shell，就值得做专用工具；更高效，也对审查系统的人更可读；
· 写给人类看的描述性错误信息，对 agent 同样有效；错误信息即提示词；
· 安全上：模型逐条审查 shell 命令；不可信输入（钓鱼邮件、webhook）绝不能当作用户指令进入模型（提示注入防线）；不可逆操作须用户审批；密码经产品层工作流保持在会话之外。

# Context engineering

① Prompt caching 是成本关键
agent 每轮都要重发全部对话历史，理想状态下大部分 token 应是缓存命中（折扣巨大），只有最新消息是未缓存增量。推论严格：工具定义与系统提示必须跨调用保持静态；prompt 分段固定顺序、近乎做哈希，做 A/B 测试插入新段落时不能打乱其他所有用户的缓存。缓存未命中按 bug 对待。他给出史实佐证：今年 1 月 OpenClaw 在订阅套餐中爆火，这种常驻运行的新用法导致大量缓存未命中，各模型厂商被迫紧急加固。最精巧的一招：用户刚打开聊天框开始打字时，服务器就提前构建 prompt 预热缓存，如同网页在 hover 链接时预取下一页。

② 压缩的时机选择
长程运行的必然终点是压缩，而所有压缩都有损（“这一个问题够写好几个博士论文”）。实操技巧极具体：对话超 10 万 token、用户离开后，要在缓存温热窗口（约 10–60 分钟）内立刻完成压缩；用户半小时后回来时从摘要续聊，成本远低于从全量历史续聊。压缩不是等来了再做，而是抢在缓存过期前做。

③ 记忆的四层结构
· 核心事实：每条消息必带（如“该用户永远小写”），并做“垃圾回收”；大脑此刻不会想着足球赛，事实层也只保留当下相关的；
· 带日期的日志：过往会话的存档；
· 便签（scratchpad）：设计上就短暂，只为接下来半小时到一小时服务；
· 其余一切靠文件：模型随时 grep 检索，“这就是文件的魔法”。

配合三条纪律：长输出写文件而非塞进上下文、昂贵操作（截图等）一律交给子 agent、持续“园艺式”修剪对话；既为成本，也为召回质量。

来源（X） · @shao__meng · 2026-10-12 13:09

斯坦福大学课程 CS329A: Self-Improving AI Agents

学习笔记之「Course Overview」@achowdhery @Azaliamirh 两位老师主讲的自进化智能体课程第一讲，把大模型演进的逻辑链：「规模扩展 → 后训练对齐 → 推理时计算 → 智能体与自我改进闭环」讲述的非常清晰，这也是整个课程的骨架脉络。

第一讲「Course Overview」视频：
https://www.youtube.com/watch?v=6YnLB0XbTnI&list=PLangBM27OtEA&index=1&t=3584s

1. 预训练扩展定律（2018–2024）
自 GPT-3 以来，最令人震撼的经验事实是：计算量、数据量、参数量三个轴上，测试损失都可预测地下降。模型规模从 BERT（3.4 亿）→ GPT-2（15 亿）→ GPT-3（1750 亿）→ PaLM（5400 亿）→ GPT-4（估计万亿级）指数级增长。这带来三件事：基准性能持续提升、少样本/零样本上下文学习（无需微调即可通过示例引导模型）、以及涌现能力。其中最重要的涌现是思维链（CoT）：Azalia 强调，小模型（如 8B 的 LaMDA、7B 级 GPT）给了推理链也无济于事，而 PaLM 级别的大模型能真正利用它，这个性质“直到今天仍然成立”，是后来所有思考模型的根基。

2. ChatGPT 的配方 = Scaling + 指令微调 + RLHF
ChatGPT（2022 年 11 月，5 天破百万用户）超越 GPT-3 的关键不是更大，而是后训练流水线：预训练（下一词预测）→ 高质量数据微调（公司花数亿美元购买的书籍、精作文本）→ 指令微调（指令-问答对，含 CoT 微调，人工+合成数据）→ RLHF（人类对模型输出做偏好排序，训练奖励模型，再用 RL 将模型参数导向高奖励生成；奖励可按正确性、有用性、无害性等加权）。

3. 推理时扩展：约一年半前开启的新前沿
这是全课技术上最重的部分。Azalia 介绍了她实验室的工作 Large Language Monkeys（名字取自“无限猴子定理”）：让模型对同一问题并行采样最多 1 万次，再用验证器（如单元测试）挑出正确答案。核心发现：
· 覆盖率（至少一个样本解出问题的比例）随样本数呈对数线性增长；
· Llama 3 8B/70B 单样本不如 GPT-4o，但采样足够多次后反超；模型“知道”的远多于一次提问所暴露的；
· 有些难题 1 万个解里只有三四个正确，说明扩展推理计算是触及模型真实能力上限的必要手段。

随后的问答质量很高：重复采样提升的是 pass@k（覆盖），而 o1 这类推理模型提升的是 pass@1；本质是模型通过 RL 学会了“判断哪条推理链是对的”；两者是同一枚硬币的两面。o1 在 AIME 上展示了 pass@1 随测试时计算的对数线性提升，DeepSeek（2024 年 12 月）则把两件事合流：用测试时扩展批量生成可验证的合成数据，回流到训练集再微调模型。这个“生成—验证—回灌”的闭环正是课程标题“自我改进”的技术含义。

4. 从 LLM 到 Agent
Aakanksha 的判断很明确：聊天模型和推理模型本质仍是单轮对话，而 2025 年真正意外发生的是 Claude Code、Codex、Deep Research 这类智能体开始端到端完成真实工作流。她给出的 Agent 定义是教科书式的：给定目标 → 规划步骤 → 与环境交互（含工具调用）→ 依据反馈修正 → 判断何时停止或承认失败，并可能需要记忆维持任务状态。

但她同样诚实地指出现状：多数落地系统仍是人工编排的静态工作流图，LLM 调用、LLM-as-judge、工具调用（搜索等），组织成提示链、按复杂度路由、并行扇出再聚合（Deep Research 的做法）、或“LLM 管理者”式规划-执行（Claude Code 的做法）。真正开放式自主循环目前只在编码和深度研究两个领域“出现生命迹象”。编码智能体可靠化的原因被归纳为：更强的模型 + 可验证奖励的 RL（RLVR）+ 训练时扩展，外加自我改进闭环启动，可以自动生成单元测试来验证生成的代码（即 Code Monkeys 一线的思路）。

贯穿全课的一个关键瓶颈：验证
两位老师反复回到 generator-verifier gap：模型生成大量貌似合理的内容很容易，但判断对错需要反馈回路。在数学、代码这类可验证领域，单元测试/标准答案提供了廉价可靠的信号，改进可以持续滚动；而在创意写作等领域，人类反馈成为瓶颈。这个瓶颈直接对应课程第 3 讲「Robust Verification」，也是 Azalia 实验室有论文（如何组合多个验证器）的方向。这是理解当前智能体能力边界的最重要单一变量。

几个值得注意的问答观点
· 推理能力是“训练出来的广义思考者”：数据让模型把分解、回溯、分析等技能泛化成通用能力，而非硬编码的流程模板；模型学到的东西已远超训练数据本身。
· 模型偏爱自己生成的推理轨迹，即使轨迹来自更强的模型，它们也更喜欢自己的。这关系到 STaR 式自我蒸馏为何有效（对应第 5 讲多步推理）。
· 思维链是被“发现”的涌现，不是被设计的：从 GSM8K 首现迹象，到 PaLM 能解释笑话，再到专门训练的推理模型；先是涌现，后是强化。
· 未来值得期待的“涌现”：规划、多步推理、自我纠错，恰好是课程要逐讲展开的能力清单。

应用部分给出四个层次

12｜Google 白皮书：Agent 双验证

来源（X） · @shao__meng · 2026-10-12 17:45

Google 官方「5天 AI Agents 课程」

5份白皮书 (1/5)：The New SDLC With Vibe Coding
https://www.kaggle.com/whitepaper-the-new-SDLC-with-vibe-coding

5天 AI Agents 课程的第一份白皮书，带我们思考：当“写代码”被 AI 自动化之后，软件开发的组织方式要怎么变？白皮书给出了一套可以长期使用的思维模型，其中两个关键概念先记住：Tests & Evals

核心论点：范式已变，但要区分两种用法
软件工程正经历自高级语言以来最大的转变，开发者与机器的接口从语法变成意图。2026 年 85% 的职业开发者日常使用 AI Coding Agents，41% 的新代码由 AI 生成。

"Vibe coding" 源自 Karpathy 2025 年 2 月的帖子，因被滥用而失去意义。到 2026 年，Karpathy 本人修正了表述，引入 Agentic Engineering。

区分二者的关键区别是「Tests + Evals 双验证」，测试管确定性部分（输入产出），评估（evals）管非确定性部分。"没有这两样，无论 prompt 多精巧，你做的都是 vibe coding。"

# 四个关键思维模型

1. Context Engineering（上下文工程）“真正的技能”。 论文断言：AI 生成代码的质量取决于上下文质量，而非 prompt 巧妙程度。六类上下文（指令、知识、记忆、示例、工具定义、护栏）要区分静态（常驻加载，如 AGENTS.md，每个 token 每次交互都要付费）与动态（按需加载，如 Skills、RAG 检索）。核心洞察是一个类比：“模型需要的不是被话术忽悠，而是和一个新团队成员做好工作所需要的同等信息。”静态/动态的边界应作为一等架构决策来评审和版本化。

2. 工厂模型（The Factory Model）。 开发者的主要产出不再是代码，而是生产代码的系统：规格与上下文（定义要造什么）、agents（把规格翻译成实现）、测试与质量门禁、失败回传的反馈回路、约束行为的护栏。“工厂经理不亲手组装每个零件，他设计流水线并把控质检。”

3. Harness 工程 核心公式：Agent = Model + Harness。裸模型不是 agent；行为表现由包裹模型的脚手架主导，指令与规则文件、工具、沙箱、编排逻辑、hooks 护栏、可观测性。这些是团队的地盘，不是模型厂商的。 论文给出可量化的证据：Terminal Bench 2.0 上有团队不换模型、只改 harness，就从 30 名外冲进前 5；LangChain 仅调 prompt/工具/中间件就提升 13.7 分。由此得出一条实用诊断法则：“agent 出错时，直觉怪模型；但诚实地查，大多数失败是配置失败，缺工具、规则含糊、没护栏、上下文塞满噪音。” 这也重新定义了光谱的本质：vibe coding 和 agentic engineering 可以用同一个 agent，差别只在于你多刻意地配置 harness。

4. Conductor 与 Orchestrator 开发者的两种工作模式。 Conductor 在 IDE 里实时盯代码生成、逐段纠偏，适合复杂逻辑和陌生代码库，但人本身会成为吞吐量瓶颈；编排者（orchestrator）异步给多个 agent 派目标、验收结果，需要四种新技能：精确规格化、任务分解、快速评估、约束系统设计。配套的是编码 agent 的三栖格局：编辑器内（Copilot/Cursor）、终端里（Claude Code/Antigravity CLI）、后台云端（Jules/后台 agent），同一个开发者一天三类混用。

# 需要面对的两个问题

80% 问题：AI 能快速生成一个功能 80% 的代码，剩下 20%（边界情况、错误处理、集成点）恰恰需要最深的上下文知识。而且 AI 的错误已从语法错误进化为概念性失败，代码“看起来对”、甚至能过基础测试，这才是最危险的。高手的姿态不是照单全收，而是把注意力押在 AI 搞不定的那 20% 上。

METR 研究的反直觉数据：有测量显示资深开发者用 AI 助手在某些任务上反而慢了 19%，时间耗在验证和纠正 AI 输出上。AI 没有消灭实现工作，而是把它从“写”变成了“评审、引导、验证”。

# 经济学视角：不止步于“开发速度”，引入 CapEx/OpEx 框架

Vibe coding = 低 CapEx、高 OpEx：前期零投入，但隐藏三笔复利债务，token 烧钱率（反复让模型修自己未经核实的错误）、维护税（半年后逆向工程 AI 意大利面代码）、安全修复成本（生产期修漏洞比设计期贵指数倍）；

Agentic engineering = 高 CapEx、低 OpEx：前期投资规格、测试套件、上下文结构，换来边际成本骤降。

在 token 经济下，context engineering 是财务杠杆：与其每次塞进十万 token 的整个仓库，不如给一份高信号密度的 AGENTS.md 提高首过成功率；智能模型路由则是另一杠杆：架构设计用大模型，生成测试、CI 监控路由给小而便宜的模型。

14｜Google 梳理 Agent 协议栈

来源（X） · @shao__meng · 2026-10-12 20:16

Google 官方「5天 AI Agents 课程」

5份白皮书 (2/5)：Agent Tools & Interoperability

这份白皮书紧接 Day1，继续分享 Agent 系统里的零件靠什么标准连接 ？它系统性梳理了 Agent 生态的完整协议栈：MCP、A2A、A2UI、AP2/UCP 等等

Agent 连工具（MCP）→ Agent 连 Agent（A2A）→ Agent 连用户界面（A2UI）→ Agent 连商业交易（AP2/UCP）。

白皮书地址：
https://www.kaggle.com/whitepaper-agent-tools-and-interoperability

MCP：Agent 连工具（USB-C）
· 核心价值：把 N 个模型 × M 个工具的集成复杂度从 O(N×M) 降到 O(N+M)，各自只需对接一次协议。
· 正确姿势：重消费、轻建造。从公共注册表、官方托管服务（已审核）、企业内部注册表三类来源取现成 server，三步接入：发现 → 配置（凭证走环境变量、限定读写权限）→ 连接。
· 实践铁律：公共未审核 MCP 绝不上生产；凭证不硬编码；调试时用 MCP Inspector 查原始数据包，别瞎改 prompt；幻觉参数多半是管道问题；能用只读就连只读；工具用完即卸载，防注意力稀释。

A2A：Agent 连 Agent（HTTP）
· 演进逻辑：复刻“单体 → 微服务”，单 Agent 巨石撞上三堵墙：工具越多决策越差、上下文过载、单点故障。出路是专业化分工。
· 关键辨析：专家 agent 不能当工具调。工具是 fire-and-forget 的被动仪器；专家是协作伙伴，需要暂停、协商、续作。硬塞进工具包装等于引入 GOTO 语句。判断口诀：“你要的是结果，还是分担责任的参与者？”
· 市场机制：Agent Card 是机器可读的“简历”，注册表是“劳动力市场”；agent 可被发现、被雇佣、被计费（含 x402 微支付：HTTP 402 + 加密支付证明，无账户按次付费）。

A2UI：Agent 连界面
· 问题：人类传递洞察靠图表交互，agent 只会吐 JSON。
· 解法：agent 输出的是“乐谱”（声明式组件描述），不是“录音”（可执行代码）或“唱片”（预渲染像素）。任何渲染器用自己的组件库原生演绎。
· 安全模型：只从可信目录请求组件，杜绝代码注入。
· 两种生成模式，按布局决策权划分：意图驱动归 LLM（界面随问题变化）；结构固定归工具模板（零 token 花在 UI 上）。

AP2 / UCP：Agent 连交易
· UCP = 大脑：统一商品目录语言，agent 标准化地查、选、下单。
· AP2 = 钱包：事先授权额度（“最多花 $25”）→ 交易时出示签名“本票”而非卡号 → 超规自动拦截。
· 保障四件事：授权可审计、意图真实、容错幻觉、问责有主。
