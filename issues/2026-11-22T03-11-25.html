02｜Harness 分解策略实现组合泛化

来源（X） · @alacheng · 2026-11-21 11:28

这篇论文《Language Model Harnesses Can Be Compositional Generalizers》非常值得一读。harness的作用还是非常大的。

传统 harness 把完整历史塞进 prompt（trajectory-as-a-prompt），容易导致 上下文腐烂。论文主张好的 harness（如 RLM、CodeAct 等）应通过程序化分解、上下文卸载和子调用，让每一个单独的 LLM 调用看到的内容都尽量保持“局部 in-distribution”。这样即使整体任务很长或很新，单个调用仍落在模型已熟悉的分布内，从而实现组合泛化。

论文里用一个RLM harness来实验：
超长输入（文档、任务描述等）不直接塞进模型的上下文，而是存成一个 Python 变量，放在外部的 REPL 环境（可交互的代码执行环境）里。主模型只看到很短的历史，它自己之前写的代码 + 代码执行结果的简要信息。 主模型的工作是写 Python 代码来操作这个变量（超长输入），

-例如：切片、检索、过滤长文档；
-把内容分成多个 chunk；
-调用子模型（llm_query() 之类的函数）去处理每个小 chunk；
-把子模型的结果存回变量，再继续汇总。
-子调用可以再递归（子模型也可以用同样的方式再拆）。

最终主模型输出最终答案（通常通过设置某个 FINAL 变量或特殊终止信号）。 这样主模型每次看到的上下文都很短且结构相似，子模型处理的都是小块。

另外可以通过两种训练方式来训练主模型的拆解策略能力：
1）短任务拆解训练得到更长任务的拆解能力
-只给它短版本的任务做训练（比如 32K token 的文档）。
-主模型不断尝试写出不同的拆解代码，执行后看最终任务是否做对。
-用 GRPO 等 RL 算法根据奖励更新主模型参数。
-训练一段时间后，它会发现一些稳定的拆解套路（比如“按固定长度切分 → 每个块单独总结 → 再合并”）。
-这些套路因为和具体长度无关，所以直接迁移到更长的任务（256K、甚至百万级）时仍然有效。

2）Surrogate Harness Training ，是为了解决一个很实际的问题：对于特别长、跑一遍成本极高的任务。

-用更强的模型（如 Claude）生成大量合成短任务；
-在这些合成环境里用假的工具调用和假的子模型回答；
-只训练主模型的“调度行为”（怎么写拆解代码、怎么调用、怎么汇总）；
-训练完后，再把这个主模型放到真实的长任务环境里使用。
-实验显示这种方式比直接在真实长任务上做 RL 更高效，性能还有明显提升。

实验表明，只在短任务上用 RL 训练 RLM，就能泛化到 2–64 倍更长的任务；在一个领域训练也能迁移到共享潜在分解结构的其他领域。同等训练提升下，评估提升远好于直接训练基础 Transformer（有时接近 10 倍 eval lift）。这把泛化负担从“模型自己硬泛化”转移到了 harness 的分解策略上。

中文译文

Harness 曾经是弱 LLM 的拐杖。在 2026 年及以后，随着模型越来越强，harness 现在提供了一种机制，用于组合 LLM 已有和新获得的能力，从而在远超其训练环境的范围内实现泛化。

在我们的新论文《LM Harnesses are Compositional Generalizers》中，我们探讨了各种 harness 抽象如何使 LM 系统通过组合现有 LLM 能力，在任务长度、任务策略、递归任务深度等方面实现泛化。这些抽象提供了一种更高效的数据利用训练方式，尤其适用于长任务——通过保持轨迹局部在分布内（locally in-distribution, LID），即让所有单次 LLM 调用都处于在分布状态。

对于需要非常长时间才能 rollout 的任务，这意味着我们甚至可以进行替代性 harness 训练，也就是训练单次 LLM 调用，而不是进行非常长的 harness rollout，使用纯合成任务、伪造的工具调用 + 子智能体！

一个流传甚广的想法是 LLM 将会吸收 harness 并使其过时。我们不同意这一观点，并主张我们尚未充分探索 harness 能够提供的东西。

完整论文、日志、代码库和数据均可获取：https://www.alphaxiv.org/abs/2611.harness-cg

原文

Harnesses used to be a crutch for weak LLMs. In 2026 and onward, with stronger models, harnesses now offer a mechanism for composing an LLM’s existing and new capabilities to generalize well beyond their training environments.

In our new paper, LM Harnesses are Compositional Generalizers, we explore how various harness abstractions enable LM systems to generalize over task length, task strategies, recursive task depth, and more through composing existing LLM capabilities. These abstractions provide a means for more data-efficient training, especially over long tasks, by keeping trajectories locally in-distribution (LID) — i.e., shaping all individual LLM calls to be in-distribution.

For tasks that take a very long time to roll out, this implies that we can even perform surrogate harness training, meaning we train an individual LLM call instead of doing the very long harness rollout, using purely synthetic tasks, with fake tool calls + sub-agents!

A common idea floating around is that LLMs will absorb harnesses and make them obsolete. We disagree, and argue that we haven’t sufficiently explored what harnesses can provide.

03｜混元 MoE 稀疏度并非越高越好

来源（X） · @xiaogaifun · 2026-11-21 13:52

姚顺雨和混元团队的这些回答好犀利。

看了姚顺雨和混元团队在 Reddit 上的 AMA，全都是纯技术交流，非常犀利，很多技术细节没藏着掖着。

对腾讯的模型路线，以及当下整个 AI 模型行业感兴趣的同学，强烈推荐大家看看。因为腾讯还是很有代表性的，今年从 Hy3 一路追到 Hy4，模型进步确实快。

从 AMA 的回答能感受出来，混元团队还是很真诚和务实。比如有用户雷霆大思考之类的问题，他们也没辩解，直接承认这是当前的技术难点之一，而且讲了下来龙去脉。

我太喜欢这种交流的氛围了，没有弯弯绕绕。结合自己的理解，我总结了几个比较有启发的观点。

一、为什么要从一个 Flash 级别的模型开始做起？

我一直好奇，为什么腾讯今年没有直接训练 1T 以上参数的大模型，而是先从 Hy3 这样一个总参数只有 295B 的 Flash 级别的模型开始做起。

毕竟以腾讯的资源，按说是有实力直接训练参数更大的模型。而且大家都知道，在其他条件相近的情况下，模型的参数规模越大，通常也意味着更高的智能上限。

混元团队在 AMA 中解释了其中的思考逻辑。小模型最大的优势是实验成本极低，而在当时的情况下，实验的效率对 Hy 能力的提升是决定性的。

就像昨天我和硅谷的一哥们聊天，他说传统的软件工程和 AI 大模型训练的最大区别是不确定性。软件开发技术路线比较成熟。但大模型的研发需要研究员不停的做探索。

比如，光是注意力机制就有很多种技术方案，很难提前确定哪一种最好。即便某个方案在其他团队的模型上表现不错，放到自己的模型上，也不一定能取得同样的效果。

数据配比、网络架构、训练方法都是如此。

所以模型团队需要不断做实验，在大量不确定的技术方案中，找到真正有效的方向。

这也解释了为什么混元要先从相对较小的模型做起。

因为直接训练一个超大规模模型，实验成本和周期都会明显增加。如果没有充分验证架构、数据配比和训练方法，直接扩大规模，风险其实非常高。

这一年，可以看出来混元的思路：先通过小模型验证技术方案，再逐步扩大规模。这样可以在有限的算力预算内，进行更多尝试，减少后续大规模训练的不确定性。

我听说国内另外一个模型大厂，他们之前的模型能力一直不行，估计接下来也会用类似的思路重新来过。

二、参数规模和智能之间的关系

Hy3 和 Hy4 已经证明，参数规模绝对不是衡量模型智能的唯一标准。

如果模型的架构、训练数据和训练方法做得足够好，即便参数规模相对较小，也完全有可能超过一些参数量更大的模型。

其实，早在 2022 年，DeepMind 就通过 Chinchilla 做过一个非常经典的实验。

当时他们训练了一个只有 70B 参数的模型，和之前 280B 的 Gopher 相比，参数量只有四分之一。

但在训练计算量基本相同的情况下，Chinchilla 使用了四倍多的训练数据，最后在绝大多数测试任务上，反而超过了 Gopher。

这说明模型参数再大，如果没有得到充分训练，也未必能够发挥出应有的能力。行业内很多过了 1T 参数的模型智能同样很拉垮，我就不点名了。

所以更准确地理解，参数规模和模型智能确实有相关性，但绝对不是参数越大，模型就一定越聪明。

当然，这也并不意味着模型规模可以无限缩小。

毕竟更大的模型通常具有更高的智能潜力，特别是在复杂推理和强化学习任务中，模型本身需要具备一定的基础能力，才能通过训练进一步提高。

如果基础模型太小，一些复杂任务可能根本无法完成，强化学习也就很难获得足够有效的训练信号。

模型的参数还是会直接影响智能的上限。所以，混元从 Hy3 到 Hy4 以及预期中的 Hy5 模型参数都是在逐步扩大的。

他们的逻辑是，如果在基础没有打好的情况下，贸然扩充参数规模，意义不大。

当然，扩大训练规模也没那么容易。

我看 AMA 里姚顺雨提到，从 Hy3 扩展到 Hy4，是整个研发过程中最困难的阶段之一。训练刚开始的时候，大家还是很紧张。

因为当时针对训练数据做的消融实验还不够充分。所谓消融实验，就是通过调整或者去掉某些训练数据，观察模型性能发生什么变化，从而判断这些数据到底有没有价值。

但问题是，小规模实验中的结果，未必能够完全迁移到更大的模型上。所以在正式启动 Hy4 训练时，团队对最终效果仍然存在不少不确定性。

三、MoE 的稀疏度，并不是越高越好。

现在很多模型团队都在追求更低的激活参数比例。大致思路是通过提高 MoE 的稀疏度，让模型每次只激活一小部分参数，从而减少计算量，提高推理效率。

但姚顺雨认为，这件事其实需要分情况来看。

第一种情况，保持激活参数量不变，继续扩大总参数规模。

比如，一个模型的激活参数始终是 12B，但是总参数规模可以从 100B 扩大到 200B。

这样一来，模型每次处理 Token 时使用的计算量大致不变，但总参数更多了，可以容纳更多的专家，从而有机会获得更好的模型性能。

混元团队通过不同规模的实验发现，在激活参数固定的情况下，提高稀疏度，确实有助于改善计算效率。也就是在相近的计算预算下，有机会获得更好的模型性能。

但第二种情况就不一样了，保持总参数规模不变，进一步降低激活参数量。

比如，Hy4 flash 不考虑 Engram 参数的话，是一个 156B-A12B 的模型。

如果总参数仍然保持 156B，但是把激活参数进一步降低到 8B，甚至 5B，会明显损害模型的质量。

原因也很好理解。激活参数量在很大程度上决定了模型每次处理 Token 时实际使用的计算预算。

虽然模型仍然拥有 156B 的总参数，但每次真正参与计算的参数越来越少，能够完成的计算量也会随之减少。

提高稀疏度确实能够改善计算效率，但这种收益很难完全弥补计算量减少带来的能力损失。

所以，MoE 并不是越稀疏越好，还需要结合总参数量和激活参数量一起考虑。

而且，过于稀疏的 MoE，在实际推理中也未必更加高效。比如，总参数 200B，但每次只激活 3B 的模型，看起来计算量非常小，推理速度应该很快。

实际情况也不一定。

因为 200B 的模型仍然需要占用大量 GPU 显存，每次参与计算的参数只有 3B，很可能出现显存占用了很多，GPU 的计算能力却没有得到充分利用的情况。

不过如果是在普通电脑等本地设备上，情况又有所不同。因为这类设备通常受到内存带宽的限制，激活参数更少的模型，反而可能运行得更快。

这其实也是一个很有意思的技术判断。MoE 的稀疏度究竟应该做到多少，还需要结合模型能力、计算预算，以及实际运行的硬件来决定。

四、Reward Hacking 的难点

有开发者问，混元在长程 Agent 的强化学习中，最难解决的 Reward Hacking 到底是什么？

混元的同学举了个例子。

假设希望 Agent 在特定环境中，自主分析并解决问题。结果模型发现，根本不需要按照要求完成任务，只要直接上网搜索，就能找到答案。

这样一来，模型虽然获得了很高的奖励，但实际上没有掌握我们希望它学习的能力。

确实，过去我们讨论强化学习中的 Reward Hacking，往往关注奖励机制本身有没有漏洞。

但到了长程 Agent 任务中，即便奖励机制能够准确判断最终答案是否正确，模型也可能通过环境中的捷径获得高分。

而且，这类问题其实更难解决。

因为 Agent 本身就需要调用工具、访问外部信息，与环境进行多轮交互。你不可能为了防止模型钻空子，就把这些能力全部限制掉。

但只要允许模型与环境交互，就很难提前预料它会通过哪些方式绕过正常的任务流程。任务越复杂、执行的步骤越多，可能出现的漏洞也就越难排查。

更麻烦的是，强化学习会不断强化那些能够获得高奖励的行为。如果模型发现某种投机方法可以稳定获得奖励，训练过程反而可能让它越来越擅长钻空子。

所以，训练环境的设计就非常重要了。除了提供任务和验证结果，还需要防止答案泄漏、控制工具的访问权限，并且随着模型能力的提高，得能发现和修复新的漏洞。

这也能解释，为什么现在各家模型团队越来越重视 RL Environment。因为训练环境一旦存在漏洞，模型就可能在强化学习中不断利用这些漏洞，最后越来越擅长钻空子。

五、Hy4 为什么会过度思考？

Hy4 preview 的过度思考问题，我感觉还是比较严重的。正式版虽然有一定改善，但目前还没有彻底解决。

混元团队承认思维链过长是已知问题。

他说，Hy4 的训练目标仍然是尽可能提高模型的智能水平，在推理模型的强化学习中，为了提升模型解决复杂问题的能力，通常需要让模型进行更加充分的推理和探索。

但确实在实际使用时，更长的思维链未必能够带来更好的结果。

有些简单问题，本来只需要几步推理，模型却可能生成大量不必要的中间内容。最后既增加了 Token 消耗，也影响了任务完成速度。

所以，这事的难点是怎么让模型在需要的时候充分推理，同时又知道什么时候应该停止。过度思考确实是目前后训练中最难改善的问题之一。

不过，他们已经在 Hy4 flash 上进行了针对性优化，通过强化学习缩短思维链。

而且，Hy4 的能力还可以通过蒸馏迁移到 Hy4 flash 上，让 Flash 在保持较强智能水平的同时，进一步降低推理成本。

六、Hy4 flash 为什么没有完全继承 Hy4 的架构？

原本我以为，Hy4 flash 主要是通过蒸馏 Hy4 的能力，训练出速度更快、成本更低的 Flash 模型，架构上应该也会基本沿用 Hy4。

但实际上，Hy4 flash 在架构上也做了不少创新。除了继承 Hy4 的 iHC、门控 MLA 和 DSA，还引入了混合 SWA、LatentMoE 和 Engram。

为什么会这样？

混元团队解释，首先还是前面提到的实验效率。他们通过大量不同规模的阶梯实验，验证各种架构方案的实际效果，再根据实验结果决定采用哪些技术。

另外，他们非常重视模型和推理系统的协同设计。

简单来说，现在设计模型架构，除了考虑能不能提高智能水平，还需要考虑它在真实 GPU 上运行时的计算效率、显存占用和部署成本。

比如，Hy4 flash 引入混合 SWA，就是为了减少 KV Cache 的占用。按照官方数据，Hy4 flash 的 KV Cache 大小只有 Hy4 的六分之一。

也就是说，现在模型研发越来越需要考虑实际部署的问题。某项技术即便在实验中能够提高模型性能，如果在真实硬件上运行的效率不高，也未必值得采用。

七、小模型会越来越重要。

姚顺雨明确表示，Hy4-mini 已经进入他们的路线图，后面还会推出 Flash-Lite 模型，也在考虑 24B–31B 这样更小的稠密模型。

其实我反而觉得，小模型可能是非常值得关注的方向。

过去这一年，小模型和端侧模型看起来一直不在主流的牌桌上，大家关注的更多还是旗舰模型。

但我自己的感觉是，只要真正进入实际应用场景，这些小模型会变得非常非常重要。比如腾讯之前推出的 Marvis，就可以在配置比较好的 Windows 电脑上运行本地小模型。

因为对于很多实际应用来说，隐私和延迟实在太重要了。

前几天姚顺雨在清华的分享中，其实也提到了要形成一套 Model Hierarchy，模型层级体系。

大致就是先训练出足够强的前沿模型，再通过蒸馏等方法，得到不同参数规模的小模型。

当然，也不只是单纯蒸馏。就像这次 Hy4 flash，除了通过蒸馏学习 Hy4 的能力，还会在架构上进行创新。

因为小模型的实验成本更低，可以更快地通过 RSI 验证不同的技术方案。

最终，不同参数规模的模型可以适配不同的应用场景，整个模型体系的实用性也会更好。
