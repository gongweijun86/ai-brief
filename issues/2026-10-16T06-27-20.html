02｜RSIGym 把训练基建做成五类服务

来源（X） · @bojie_li · 2026-10-16 00:21

刚看到前 Kimi RL infra，现 @Evolvent_AI co-founder @FanqingMengAI 搞的 RSIGym，一个 RSI 环境。RSI 并不是一个模型问题，而是一个系统工程。从这个角度出发，一个关键问题是：给 RSI agent 提供的环境，是否对 agent 友好，也贴近真实生产中的研发流程。

为啥不让 agent 自己搭环境呢？因为它自己搭环境又费时间，又一定会踩坑。比如我自己让 agent 搭模型训练的环境，经常在 CUDA / torch 上浪费很多时间，也很难在多个任务间协调好 GPU 卡。让 agent 自己搭芯片仿真和物理设计的环境，经常无法管理好内存和磁盘资源，导致内存或者磁盘满了，连 SSH 都进不去了。

模型训练的 infra 已经很成熟，没必要让每个 agent 都重新搭一遍。RSIGym 把这些能力部署成远程服务，通过 API 和 skill 文档提供给 agent。这样方便并行开展实验，研究工作区与计算服务的隔离也有助于减少 hacking 的机会。

RSIGym 的这个设计称为 Everything as a Service，包含训练、推理、蒸馏、评估、沙盒五类服务。

RSIGym 还提出了 RSI-Index，综合多个 agentic benchmark，衡量前沿 agent 联合改进一个较小模型（Qwen3.5 35B A3B）的 weights 和 harness 的能力。六个前沿模型组成的研究 agent 在五个 benchmark 上都取得了显著提升。Opus 5 的 RSI-Index 最高，达到 0.4809，也就是平均弥补了 48.09% 的剩余可提升空间。

有趣的是这些 agent 不仅迭代模型权重，还会自动迭代 harness，解决共性问题，例如 terminal bench 中的 shell 状态保持、长输出的截断与恢复、工具调用死循环检测等。去年我们都是一个一个 bad case 修的，今天 agent 自己就能解决了。

RSIGym 也支持一些有意思的实验，比如单独迭代已有的 DSH harness、让模型自己训练自己，以及断开公网后的研究实验。欢迎大家用它试试自己的想法！

Anthropic Engineering 知识体系提炼（3级目录）
以下按技术书知识体系，对 https://www.anthropic.com/engineering/ 中工程文章进行结构化整理。一级为知识领域，二级为子主题，三级为具体实践点 + 1-2句实战案例说明。
1. Agent 设计与架构模式
1.1 基础构建块与工作流模式
•增强型 LLM 与简单组合模式 从单次 LLM 调用 + 检索/工具开始，仅在验证有明确收益后再引入多步流程。实战案例：客户支持 Agent 通过工具查询客户数据与知识库、执行退款操作，以“成功解决工单”作为可量化指标，避免一上来就上复杂框架。
•Prompt Chaining / Routing / Parallelization 将任务拆成顺序步骤、按输入路由到不同提示、或并行执行子任务。实战案例：文学翻译使用 evaluator-optimizer 循环，一个模型翻译、另一个模型提供反馈迭代优化，显著提升风格与准确性。
1.2 自主 Agent 与长期运行
•自主循环与停止条件 LLM 动态规划、调用工具、根据环境反馈调整。实战案例：SWE-bench 风格编码 Agent 根据 PR 描述迭代修改多文件并运行测试，直到通过或达到明确停止条件。
•长运行 Agent 的 Harness 设计 为跨上下文窗口的任务设计初始化 Agent + 执行 Agent 的双阶段结构，并维护进度追踪。实战案例：通过结构化笔记（如 NOTES.md 或 to-do 列表）在上下文重置后恢复状态，使 Agent 能持续完成多小时任务。
1.3 托管 Agent 与脑手解耦
•Scaling Managed Agents 将“大脑”（规划与推理）与“手”（执行环境/沙盒）解耦，通过 session/harness/sandbox 分层接口提升可扩展性。实战案例：TTFT p50 降低约 60%，并支持更安全的自托管沙盒与 MCP 隧道。
2. 工具使用与 Agent Skills
2.1 工具设计原则
•Writing Effective Tools for Agents 工具应自包含、无重叠、参数明确、token 高效。实战案例：通过“原型 → 评估 → 优化”三阶段流程，用 Agent 自身迭代工具描述，减少模糊调用导致的错误。
•Advanced Tool Use 与 Programmatic Calling 支持 Tool Search、代码调用 MCP、工具使用示例等能力。实战案例：Agent 编写代码调用 MCP 工具而非直接自然语言调用，token 消耗可降低约 98.7%。
2.2 Agent Skills 与 Think Tool
•Equipping Agents with Skills Skills 是可发现的文件夹（含 SKILL.md），预加载 name + description，按需动态加载完整内容。实战案例：为 PDF 处理等场景封装 Skill，将通用 Agent 快速特化为专业能力，类似给新员工提供入职手册。
•The “Think” Tool 在复杂工具调用场景中强制 Agent 暂停并输出思考步骤。实战案例：在 tau-bench 等基准上提升约 54%，与 Extended Thinking 形成互补。
3. 上下文工程与检索
3.1 上下文工程核心原则
•Context Engineering vs Prompt Engineering 上下文是有限资源，存在“context rot”和注意力预算限制，需持续 curated 高信号 token。实战案例：Claude Code 采用 just-in-time 检索（glob/grep/Bash），结合 CLAUDE.md 提供初始上下文，避免一次性加载全部代码库。
•Compaction 与结构化记忆 接近窗口上限时摘要历史、清除工具输出，并持久化关键笔记。实战案例：Pokémon 游戏 Agent 用结构化笔记记录等级、策略与进度，跨数千步与上下文重置仍保持连贯。
3.2 检索增强
•Contextual Retrieval 结合上下文嵌入 + BM25 + 重排序，显著降低检索失败。实战案例：相对传统 RAG，检索失败率降低约 67%，提升长文档问答准确性。

04｜机械可解释性九成神经元清晰可读

来源（X） · @MaxForAI · 2026-10-16 10:41

有点震撼。。。我们可能真的快要搞清楚大模型内部到底是怎么运作的了。

OpenAI早期机械可解释性研究的参与者，昨天突然提出了一个很大胆的结论：

我们可能一直误解了神经网络。

昨天， @nickcammarata 发了一篇很有意思的文章，叫《Neural Networks Are Already Clean》。

这哥们早年就在OpenAI做机械可解释性研究，2023 年还牵头启动了@OpenAI 第一个大规模自动化神经元解释项目。

当时他们发现，现有工具只能解释大约 2% 的神经元。

Nick因此得出了一个很悲观的判断：神经网络内部存在大量纠缠，想搞清楚它们到底在干什么，可能非常困难。

结果三年后，他带着更先进的工具和Agent重新研究，发现情况完全不同。

在他们测试的现代视觉模型中，最后一层 99%～100% 的神经元都能找到相当清晰的解释。

甚至在Qwen3-32B这样的语言模型中，初步研究也发现，约90%的神经元都有一个可以识别的主要功能。

最有意思的是，他还重新研究了过去的一些经典案例。

比如曾经有一个神经元，既会对猫脸产生反应，也会对汽车前脸产生反应。

以前大家觉得，这是典型的Superposition，多个不相关的概念纠缠在了同一个神经元里。

结果重新研究后发现，这个神经元可能只是在识别一种共同的V形视觉结构。

猫脸和汽车前脸恰好都有这种特征。

全世界的家人们折腾了这么多年，可能连最基础的观察方式都有问题。

而且我觉得这篇文章最值得关注的，其实是他们使用 Agent的方式。

他们让Agent自动观察神经元、提出功能假设、设计实验、分析电路，再通过新的输入验证假设，甚至自动审查了10 万张神经元归因图。

这其实也是我最近一直关注的一个方向：让 AI 自己去做科学研究，把大量观察、假设、验证的工作自动化。

过去需要研究员花大量时间逐个分析的神经元，现在已经可以让Agent成规模地开展研究了。

当然，目前这些结果还处于早期阶段，距离完整解释大模型的内部机制，还有很多工作要做。

但我觉得Nick提出的这个观点非常有意思：

神经网络内部可能一直都很有规律，只是过去我们的工具太原始，根本看不清楚。

如果这个方向最终被验证，机械可解释性领域过去很多基础假设，恐怕都需要重新审视了。

05｜Vibe Coding 沉淀个人开发工作流

来源（X） · @xulijian1994 · 2026-10-15 14:14

Vibe Coding 玩久了，发现真正影响开发效率的，可能不是模型有多强，而是自己的使用习惯。

分享几个我觉得很值得养成的习惯：

1. 不要重复造轮子

开发之前先让 AI 去 GitHub 搜一圈，看看有没有成熟的开源方案。能复用就复用，没必要什么都从零开始。

2. 定期更换对话窗口

别一个对话用到天荒地老。上下文反复压缩，容易让模型遗忘任务、偏离目标，Token 消耗也可能越来越高。

建议完成 2～3 个独立功能，或者经历几次上下文压缩后，找个合适的节点换窗口。

前提是做好项目文档和持久化记忆，让新对话能够快速接手。

3. 不要让 AI 无脑通读文件

很多时候只需要几行代码，AI 却把整个项目文档读了一遍。

正确做法是先检索关键词、目录和索引，再按需读取相关内容。既节省 Token，也能减少无关信息对上下文的污染。

4. 定期给自己的开发记录做一次「蒸馏」

这点我觉得最有价值。

让 AI 定期分析历史对话，把高频任务整理成 Skills，把模型经常犯的错误写进 AGENTS.md，把有效的开发经验沉淀成项目规范。

可以先用便宜的模型整理历史记录，再让能力更强的模型分析总结，最后人工审核，形成自己的工作流。

说到底，Vibe Coding 不是把需求扔给 AI，然后坐等结果。

真正值得积累的，不只是 AI 帮你写出来的代码，还有你在整个过程中沉淀下来的经验。

模型大家都能用，但每个人积累出来的工作流，差距可能会越来越大。

08｜Agent 评测从真实失败案例起步

来源（X） · @Xudong07452910 · 2026-10-16 10:00

这篇 LangChain 关于 Agent Eval 的文章很实用，尤其适合已经开始把 Agent 放进真实工作流的人。

它给出的起点其实很简单。先从真实 trace 里挑 10～20 个你最在意的失败案例，做一套小 Eval，然后不断把线上新失败加回去。 不用一上来就造一个巨大的 Benchmark。

而且 Agent 不能只看最终答案。

结果可能是对的，但中间多调了工具、走错了路径，甚至做了没有权限的操作。所以 Eval 还要看 trajectory、tool call 和最终环境状态。能用代码检查的就用代码，主观问题再交给 LLM Judge，并用人工评分去校准。

所以 Agent 真正进入生产以后，Eval 会逐渐变成开发流程本身的一部分。

每发现一个失败 case，就把它留下来。Agent 每犯一次错，测试集就应该变强一点。

09｜Pi 源码拆解 Agent 会话持久化分层

来源（X） · @fttt007 · 2026-10-16 11:26

读 Pi 源码，终于理清了这几层：

• `existingSession.messages`：恢复出的历史消息数据
• `Agent`：维护内存状态，调用模型、执行工具，本身不负责持久化
• `SessionManager`：管理会话历史与持久化
• `AgentSession`：把执行、工具配置和历史保存串起来

关键区别：Agent 初始工具列表为空 ≠ Agent 不会调用工具。

一个是执行引擎，一个是历史管理，一个是把它们接起来的会话层。
