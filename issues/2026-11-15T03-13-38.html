01｜Anthropic常驻Agent架构

来源（X） · @Xudong07452910 · 2026-11-15 09:20

Anthropic 新发布的《Building always-on agents》非常值得关注，刚好能和之前 DeepSeek 的 Super-agent、LangChain 的 Async Subagents 放在一起理解。

DeepSeek 则通过 Router 接收 GitHub、飞书等事件，在授权规则内判断是否启动任务，再交给独立 Worker 执行。

LangChain 让主 Agent 保持响应，长任务交给后台 Subagent 独立运行，还能随时查看进度、修改指令。

Anthropic 这次把背后的架构拆得非常细。

Agent 平时休眠，收到消息、Webhook 或定时触发才唤醒，执行一轮任务，保存状态后继续休眠。

整个系统围绕 5 个核心组件设计：

Inbox 接收事件，负责去重和失败重试。
Timer 定时唤醒 Agent，主动跟进任务。
Memory 保存跨 Session 的记忆和任务进度。
Permissions 管理权限、凭据和人工审批。
Outbox 控制何时向用户发送消息。

我个人比较喜欢 Deferred Tool Call 这个设计。需要人审批时，先保存 Session，释放 Worker，等用户回复后再恢复执行，不会一直卡在那里。

这几篇文章放在一起看，感觉大家越来越关注 Agent 如何持续工作，以及怎么减少人的管理负担。

想自己搭 Always-on Agent 的朋友，真可以系统性的学习这篇，很多设计都能直接参考。

原文：https://claude.com/resources/articles/building-always-on-agents

02｜7组Agent工具替代方案清单

来源（X） · @meow2149 · 2026-11-15 07:35

整理了7组agent工具替代方案，从模型管理到桌面自动化，按使用场景直接找。

一、模型管理：CC Switch → Magpie

▪︎ CC Switch：管理和切换不同agent的供应商配置，也支持本地路由。

▪︎ Magpie：通过统一网关，集中管理多个agent的模型、账号、协议转换和请求路由。

二、终端工作区：iTerm2 → cmux、Herdr

▪︎ iTerm2：macOS终端，支持标签页和分屏，用来运行命令、管理终端窗口。

▪︎ cmux：围绕agent组织工作区，整合分屏和任务通知，方便查看哪些任务需要处理。

▪︎ Herdr：管理终端会话和运行状态，窗口关闭后，后台任务仍可继续运行。

三、终端编程：Aider → Pi、OMP、OpenCode

▪︎ Aider：终端里的AI结对编程工具，通过模型协助阅读和修改代码。

▪︎ Pi：精简、可扩展的编程agent，支持自定义工具、命令和工作流。

▪︎ OMP：Pi的增强分支，加入Hashline编辑、语言服务和调试能力。

▪︎ OpenCode：支持多家模型供应商，提供终端、Web等交互入口。

四、并行开发：Conductor → Paradev、Emdash、Parallel Code

▪︎ Conductor：在Mac上通过独立工作区并行运行coding agent，集中审查代码改动。

▪︎ Paradev：原名Superset，定位为Conductor的开源替代，整合终端、代码审查和浏览器预览。

▪︎ Emdash：接入不同coding agent，在独立工作区中并行处理任务。

▪︎ Parallel Code：为任务创建独立分支和Git Worktree，集中管理多个agent及其代码改动。

五、远程访问：Happy → Paseo、Cindy

▪︎ Happy：通过手机或浏览器，远程查看和控制电脑上的coding agent会话。

▪︎ Paseo：跨设备访问开发工作区，查看会话、发送指令、审查代码。

▪︎ Cindy：统一接入Claude Code、Codex和Pi，支持跨设备继续处理任务。

六、个人助手：OpenClaw → Hermes Agent

▪︎ OpenClaw：可自部署的个人agent，通过消息平台接收指令、调用工具并执行任务。

▪︎ Hermes Agent：支持记忆、Skill和定时任务，也提供从OpenClaw导入部分配置、记忆和技能的迁移路径。

七、桌面自动化：PyAutoGUI → agent-desktop

▪︎ PyAutoGUI：用Python脚本控制鼠标键盘，通过坐标和截图定位界面。

▪︎ agent-desktop：通过系统无障碍接口读取界面元素，适合支持该接口的桌面软件测试、表单填写和菜单操作。

10｜CEL让机器人集群成功率升至98%

来源（X） · @jiqizhixin · 2026-11-15 09:12

中文译文

如果一台机器人的失败可以引导整个机器人集群从另一台机器人的成功经验中学习，会怎样？

清华大学、AgiBot 和 Infinitence AI 提出了集体经验学习（Collective Experience Learning，CEL），这是一篇 arXiv 技术报告，通过最多 96 台机器人的训练集群进行了验证。

瓶颈在于：增加机器人虽然可以增加可用经验，但专家操作员未必能在同等规模上提供纠正动作。

机制：失败引导的经验检索微调（Failure-guided Experience Retrieval Fine-Tuning）会在共享池中搜索与近期失败相似的成功轨迹片段，然后优先将这些片段用于策略更新。一个异步、容错的系统能够在本地中断的情况下持续进行经验收集和训练。

成效：在手机包装任务上，在训练收集集群之外的两台同型号机器人上，每个策略经过 120 次试验，成功率从 79.2% 提升到 98.3%。在保持每台机器人收集时间不变的情况下，从 16 台扩展到 96 台机器人，成功率从 86.7% 提升到 98.3%。专家监督的初始化仍然是必需的，在这些实验中，人类提供了结果标签和环境重置。

《从集群经验中学习：机器人的集体学习范式》

论文：https://arxiv.org/abs/2610.25736
项目：https://cel-robot-learning.github.io/
我们的报告：https://www.jiqizhixin.com/articles/2026-10-30-9

📬 #PapersAccepted by 机器之心

原文

What if one robot's failure could point the whole fleet toward another robot's successful experience?

Tsinghua University, AgiBot and Infinigence AI introduce Collective Experience Learning (CEL), an arXiv technical report demonstrated with a training fleet of up to 96 robots.

The bottleneck: Adding robots increases available experience, but expert operators cannot necessarily provide corrective actions at the same scale.

The mechanism: Failure-guided Experience Retrieval Fine-Tuning searches a shared pool of successful trajectories for segments resembling recent failures, then prioritizes those segments for policy updates. An asynchronous, fault-tolerant system keeps experience collection and training running through local interruptions.

The payoff: On phone packaging, success rises from 79.2% to 98.3% over 120 trials per policy on two same-model robots outside the training collection fleet. Holding collection time per robot fixed, expanding from 16 to 96 robots raises success from 86.7% to 98.3%. Expert-supervised initialization is still needed, and humans supply outcome labels and environment resets in these experiments.

Learning from Fleet Experience: A Collective Learning Paradigm for Robots
