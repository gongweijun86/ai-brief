03｜LangGraph 恢复状态不等于幂等

来源（X） · @UPing123zzz · 2026-11-14 13:56

最近在研究 LangChain 和 LangGraph，发现很多人对这两个东西的理解其实有点混乱。

有人觉得 LangChain 是旧框架，LangGraph 是新框架；也有人认为 LangChain 适合简单 Agent，LangGraph 才能做复杂项目。

但其实，这两个东西根本不是简单的替代关系。

它们解决的是不同层级的问题。

先说 LangChain。你可以把它理解成一个高层 AI Agent 开发框架。

它主要帮你把大模型、Prompt、Tools、上下文以及 Agent 执行循环组织起来。

比如你想做一个招聘 Agent，让模型根据用户的问题，自动查询岗位 JD、读取相关信息、调用工具，最后生成分析结果。

如果直接使用模型 API，你可能需要自己处理模型请求、工具调用、结果回传和下一轮推理。

而 LangChain 已经封装了不少相关能力，可以让你更方便地把这些组件连接起来。

它更关注的是，怎么快速构建一个具备模型推理和工具使用能力的 Agent。

但问题来了。如果你的业务不是简单地调用工具、返回结果，而是需要多个明确的执行步骤呢？

比如招聘系统需要先解析简历，再匹配岗位，生成评分报告，然后根据业务规则进入不同处理流程，最后等待 HR 审批。

而且任务执行到一半突然中断了，你还希望它能够从之前的状态继续执行，而不是所有步骤重新跑一遍。

这时候就轮到 LangGraph 了。

LangGraph 更接近一个有状态的工作流编排框架。

它最核心的三个概念就是 State、Node、Edge。

State 负责保存执行状态，Node 负责执行具体任务，Edge 负责决定任务下一步流向哪里。

你可以明确规定哪些步骤必须执行，哪些地方允许模型自主决策，什么时候进入条件分支，什么时候暂停等待人工审批。

它还提供 Checkpoint、Interrupt 等机制，让开发者能够设计状态持久化、暂停与恢复流程。

但这里有个特别重要的区别。

LangGraph 能帮你恢复工作流状态，不代表它自动解决了业务幂等问题。

比如 Agent 调用一个付费 API，实际上已经执行成功，但程序还没保存结果就崩溃了。

如果恢复后直接重新调用，依然可能产生重复扣费。

所以真正的生产系统，还需要自己处理外部任务 ID、幂等键、业务状态和错误恢复。

说到这里，其实就很容易理解这两个框架的关系了。

LangChain 更关注模型和工具怎么组织起来，让 Agent 具备执行任务的能力。

LangGraph 更关注任务执行过程怎么被组织、控制和管理。

而且现在 LangChain 的 create_agent 本身就是建立在 LangGraph 之上的。

两者完全可以配合使用。

比如用 LangChain 创建一个能够调用招聘工具的 Agent，再把它放进 LangGraph 的某个节点，由 LangGraph 管理整个招聘业务流程。

当然，这也不代表所有 AI 项目都必须使用这两个框架。

如果你的需求只是调用一次模型，提取几个字段，返回一份 JSON，直接使用模型 SDK 可能更加简单。

如果业务流程完全固定，普通的后端代码和状态机也可能足够。

我觉得现在很多人学 AI 开发，最容易犯的错误，就是还没想清楚业务到底需要什么，就急着引入各种 Agent 框架。

最后框架装了一大堆，工作流画得特别复杂，真正出了问题反而不知道从哪里排查。

说到底，LangChain 和 LangGraph 真正值得学习的，不只是它们的 API 怎么调用。

而是它们背后的模型工具调用、任务状态、条件路由、执行恢复和工作流设计思想。

你得知道什么时候应该让模型自主选择工具，什么时候应该使用确定性流程，哪些状态必须保存，哪些操作需要人工审批，以及任务失败以后应该怎么安全恢复。

这些东西即使以后换了框架，依然是非常重要的工程能力。

所以我的理解是：

LangChain 让你更方便地构建 Agent。

LangGraph 让你更精细地控制 Agent 的执行流程。

但真正决定一个 Agent 能不能交付的，不是你选择了哪个框架，而是你有没有把业务流程、状态、权限和异常处理设计清楚。

学框架当然重要，但更重要的是搞明白框架到底帮你解决了什么问题。

不然最后 LangChain、LangGraph 都会用了，却连为什么需要一个 Checkpoint、为什么工具调用不能无脑重试都解释不清楚，那其实还是停留在工具使用层面。

这也是我觉得做 Agent、FDE、企业 AI 落地，最值得长期积累的工程能力。

04｜Agent 并发需限流与指数退避

来源（X） · @bencongyyds · 2026-11-14 21:27

做 Agent 别只顾着把并发拉满，上游限流保护与指数退避才是多任务稳定运行的护城河。几十个子任务同时打向外部接口，没有信号量控制和 jitter 重试，瞬间就会触发 429 雪崩。学会优雅降速与排队削峰，系统才能在高并发下稳稳交付。

07｜TurboFieldfare跑26B模型

来源（X） · @GitHub_Daily · 2026-11-14 13:30

手上只有一台 8 GB 内存的 MacBook Air，想跑个本地大模型，结果模型文件就有 14 GB 多，内存根本塞不下。

TurboFieldfare 能让 Gemma 4 26B-A4B 在苹果芯片 Mac 上跑起来，模型权重和缓存只占大约 2 GB 内存，还带一个原生的 Mac 聊天应用。

它只把 1.35 GB 的共享部分和缓存留在内存里，每生成一个词，再从 SSD 临时读出用得上的那几个专家。

GitHub：https://github.com/drumih/turbo-fieldfare

作者在 8 GB 的 M2 MacBook Air 上实测，每秒能出 5.1 到 6.3 个 token，换成 24 GB 的 M5 Pro 能到每秒 31 到 35 个。

运行时是用 Swift 和 Metal 专门为这个模型写的，没用 MLX 或 llama.cpp，作者还整理了 103 组实验记录。8 GB 的 Mac 能跑 26B，我是没想到。

聊天记录存在本地，装上图像扩展包还能看图，另外有命令行和兼容 OpenAI 接口的本地服务。第一次下载模型大约 15 GB。

10｜Claude Code数据库设计Agent

来源（X） · @TiagerBao · 2026-11-14 13:52

AI 写代码最容易埋的坑之一，就是数据库表设计错了，等上线后才发现改不动。

发现一个 Claude Code 专用 Agent：Database Architect。

它不只是帮你生成 SQL，而是提前参与数据库架构设计。

主要能做这些事：
数据建模：表结构、主外键、索引、约束
技术选型：PostgreSQL、MySQL、MongoDB、向量数据库
多租户设计：RLS、Schema 隔离、独立数据库
性能规划：读写模式、分库分片、扩展方案
数据迁移：生成迁移脚本和回滚方案

安装命令：
npx claude-code-templates@latest --agent database/database-architect

我觉得最实用的是让 Agent 先分析业务访问模式，再设计表结构，而不是代码写完才补数据库。

不过生成的 DDL 和迁移脚本仍需要人工审核，尤其是生产环境的数据变更。
你现在用 AI 开发项目，会让它直接设计数据库，还是自己先把表结构定好？

项目：https://www.aitmpl.com/component/agents/database/database-architect
