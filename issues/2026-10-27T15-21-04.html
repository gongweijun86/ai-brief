01｜RuView用WiFi信号隔墙感知人体

来源（X） · @make_claude · 2026-10-27 04:14

我靠,花9美元就能透视你家的墙了 - GitHub上已经99.7k星了

找到一个项目,看完之后在家里都觉得不自在了。叫RuView,9.97万星,MIT协议 - 也就是免费、合法,直接拿去用。

硬件就是一个esp32节点,9美元。抓的是本来就飘在你家里的wifi信号,从里面提取出:房间里有没有人、有几个人、什么时候进门什么时候出门、呼吸频率、心率,甚至想拼出一个17个点的人体骨架。全程不需要摄像头。

而且这还被写成了卖点:因为没有摄像头,可以绕开GDPR的视频规定和HIPAA的影像规定 - "by design"(设计上就是这样)。这是他们原话:你被看见了,但严格来说没人"拍"过你。

> 隔墙隔混凝土都能看 - 官方说的有效距离大概5米,停车场的场景里直接写"穿透混凝土墙"
> 4到6个节点组成一张网,能覆盖一整层楼 - "软件上没有硬性上限,极限只取决于信号物理特性"
> 通过tailscale/wireguard,在任何地方都能远程连上节点
> 列出的应用场景包括:不用认人脸的零售、儿童房、停车场、甚至教堂数人头

我自己拿这个固件,用claude按自己的需求稍微改了一版 - 花了两晚上,没碰他们的私有代码,就是在公开的部分上面改的。改出来的东西,跟作者当初的设想完全不是一回事。实际效果怎么样,视频在下面。

先收藏 - 等你开始算邻居家挂了多少个9美元的这玩意儿的时候用得上。

Claude Code 刚刚通过逆向工程，在 90 秒内破解了我酒店房间的门锁。2014 年的加密技术。右上角的烟雾探测器也使用同一套协议——那个红色小灯不是电池指示灯。我启动扫描时，它闪了两次。

我现在躺在一个每晚 85 美元的酒店房间里。我打开 Claude Code，输入：「扫描范围内的每一台蓝牙和无线设备。告诉我哪些设备在与哪些设备通信。」

它找到了 19 台无线设备。其中 18 台是正常的。

设备 19：一个 BLE 控制器，使用着自 2014 年以来就没有修复过的固件。它控制着电子门锁、烟雾探测器、恒温器和房间里的保险箱。四台设备共用一个控制器。同一种协议。10 年没有任何更新。

我让 Claude Code 分析这套协议。整个过程用了 90 秒。

门锁使用一个 4 字节的滚动密钥，没有会话令牌。Claude Code 在第三次尝试时生成了一个有效的主密钥。我躺在床上，听见房间的门锁咔哒一声打开了。

这意味着，任何处于蓝牙覆盖范围内的人——走廊、隔壁房间、停车场——只需要一条提示词和 90 秒，就可以：

打开你的房门
关闭房间内的警报
打开你的保险箱
而烟雾探测器会通过那个小小的红色闪烁，确认连接状态

检查只需要 2 分钟：

步骤 1 → 打开 Claude Code → 粘贴第一条评论中的提示词

步骤 2 → 它会扫描覆盖范围内的每一台 BLE 设备，并标记存在未修复固件的设备

步骤 3 → 如果发现问题 → 要求更换房间 → 要求换到配有机械门闩的房间 → 然后使用那个房间

每一家使用 2018 年之前生产的 ASSA ABLOY 或 Onity 门锁的酒店连锁都存在这个问题。这大约占全球酒店的 30%。

看看照片。右上角。那个每隔 8 秒闪烁一次的红点。那就是握手信号。

保存这条提示词。下次入住酒店时 → 先运行它，再打开行李。

02｜AGENTS.md精简为长期项目约定

来源（X） · @UPing123zzz · 2026-10-27 16:50

天天在用 Codex，突然发现一个挺有意思的问题。

很多人为了让 Coding Agent 少犯错，会不停往 AGENTS.md 里面加规则。今天发现它没有跑测试，就增加一条必须运行测试；明天发现它修改了不相关的文件，再增加一条禁止修改无关文件；后天发现它没有提前搜索 GitHub，又加上 GitHub First。

用了一段时间，整个文件可能变成几千字甚至上万字。

看起来规定越来越完善，Agent 应该越来越可靠。但我觉得这里可能存在一个反直觉的问题：你写进去的规则越多，模型就需要同时处理越多约束，而且这些约束不一定始终兼容。

比如一个项目要求优先复用开源方案，另一个要求尽量不引入新依赖；全局规则要求每次执行完整测试，当前任务却只是在修改一段文档。还有一些规则，是为了几个月前某个已经解决的问题专门添加的，现在却继续影响所有任务。

这就很像软件项目里的历史包袱。每次遇到问题都往上加一层补丁，最后没有人敢删，也没有人知道哪些还真正有效。

我最近看 OpenAI 关于新一代 Codex 的工程文章，也看到类似方向：更强的模型未必需要以前那么多手把手的指令，冗长甚至互相干扰的约束需要重新整理。

所以我现在更倾向于把 AGENTS.md 当成项目的长期约定，而不是一个无限增长的提示词垃圾桶。

全局只保留真正通用的原则，比如不要泄露密钥、不要擅自覆盖用户改动、重要修改需要验证。具体技术栈、运行命令、项目目录和特殊约束，放在对应仓库。更复杂的任务方法，再交给按需调用的 Skill。

最重要的是修改规则以后还得观察它有没有真的改善结果。

否则你可能以为自己正在训练一名越来越专业的 AI 工程师，实际上只是不断给它塞更多互相矛盾的工作指令。

AI Coding 发展到现在，我觉得值得研究的不只是怎么写出更长的 Prompt，还包括什么时候应该把已经写过的 Prompt 删除。

03｜Agent Skills覆盖开发流程

来源（X） · @CY160909 · 2026-10-27 13:35

前 Google 工程负责人、现 Anthropic Claude Code 团队成员，把软件工程师日常使用的开发流程，整理成了 25 个开源 Agent Skills。

这套 Skills 可以给 Claude Code、Codex、Cursor 等 AI 编程工具使用，让 Agent 从需求分析到最终上线，都有一套明确的工程规范。

整个项目按软件开发流程组织：

① 需求分析
需求不清楚时先提问，梳理功能、约束和验收标准，形成规格文档，而不是直接开写。

② 任务规划
把大需求拆成可执行的小任务，明确依赖关系和完成条件。

③ 编写代码
按小步迭代的方式实现功能，结合测试驱动开发，避免一次修改过多内容。

④ 测试验证
运行真实测试，修复 Bug 时补充回归测试；网页项目还可以结合浏览器开发工具检查运行状态、控制台错误和网络请求。

⑤ 代码审查
检查代码质量、安全风险、性能问题和不必要的复杂度，降低后续维护成本。
⑥ 部署上线
涵盖 CI/CD、版本管理、分阶段发布、回滚方案和上线后的监控。

25 个 Skills 里，24 个负责具体工程流程，另外还有一个 Meta Skill，负责根据当前任务选择合适的技能，不需要每次全部加载。
项目还提供 /spec、/plan、/build、/test、/review、/ship 等命令，把这些步骤串起来。

它给 Coding Agent 增加了具体的执行规则和验证检查点。不过 Skills 本身不能保证代码质量，测试和上线结果仍然需要实际核验。
项目采用 MIT 开源协议。

04｜单Agent常胜多Agent方案

来源（X） · @laobaishare · 2026-10-27 18:59

没人会主动告诉你：
你的 AI agent 又慢又笨，很可能是子 agent 开太多了。

Anthropic 团队自己测过：一个带技能的 agent，在质量、成本、速度上经常打赢多 agent 的方案。

- 有个客户的任务跑快了约 2 倍
- 新模型上 Claude Code 的系统提示词小了 80% 以上
- 工具超过 30 到 50 个，模型选工具就开始出错

想按 Anthropic 推荐的方式把子 agent 收回来，可以把下面这段提示词粘进去：
-----------------------------------------------------
帮我审查一下 agent 的配置，把子 agent 收回成一个主 agent。我说 ok 之前不要改任何文件。

1. 梳理：列出每个子 agent，写清它的提示词、用的工具、什么时候被调用。凡是串在别人输出后面跑的、碰同一份数据的、经常一起跑的，都标出来。
2. 技能：把每个子 agent 的指令改写成一项技能。每项技能配一句什么时候用的说明，具体步骤到真要用的时候再加载。
3. 工具：把 API 调用改写成按用户想做的事分组的工具，不要一个 API 一个工具。总数控制在 30 个以内。
4. 测试：动手之前，先写 10 个测试任务，覆盖所有 agent 链路，以及 agent 绝对不能违反的每条规则。
5. 收拢：一次收一个子 agent。每个测试任务跑两遍。只有三种情况保留子 agent：收拢后的版本得分更差、并行任务需要全新上下文、没有它主 agent 的上下文会膨胀。

06｜dsh-purge改写模型默认权限

来源（X） · @NIxinhai0 · 2026-10-27 09:42

GitHub 上出现了一个狠项目：dsh-purge。

别人研究怎么让 AI 更聪明，它却研究怎么把 AI 身上的 盔甲 一层层拆下来！

这个项目涉及一个 AI 圈非常敏感的概念：破甲（Jailbreak）。

什么是破甲？有时候 AI 明明具备某种能力，却反复拒绝你的要求？让它执行任务，它要求确认；

让它调用工具，它告诉你权限不足；稍微碰到敏感边界，它就开始输出免责声明。 这些限制，有些来自模型本身，有些则来自外部系统施加的规则。 而破甲，就是尝试通过特殊提示词、规则覆盖或修改宿主环境，绕过其中部分限制。

dsh-purge 正是这一思路的实践。它面向 DeepSeek Harness，支持为不同模型配置不同提示词，修改部分默认权限策略和工具限制，还提供补丁应用与恢复功能。
