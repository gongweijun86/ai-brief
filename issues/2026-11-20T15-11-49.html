02｜Postgres凭插件生态成为事实标准

来源（X） · @fishjar · 2026-11-20 20:27

二十年前 LAMP 架构横扫互联网时，MySQL 是所有创业公司的默认选项，Postgres 只是学院派眼里的“另一个数据库”。今天局势彻底倒转，Postgres 成了新项目的事实标准。

胜负在二十年前写下第一行架构代码时就埋下了：
- MySQL 早期为了榨干简单查询的吞吐量，搞了“可插拔存储引擎”，把事务、MVCC 和行锁全外包给 InnoDB。这种上下割裂的基因，让它在面对复杂窗口函数和自定义类型时背满了历史包袱。
- Postgres 从第一天起就死磕对象关系型标准，MVCC 原生嵌在堆表与 WAL 日志里，更狠的是开放的插件与类型系统。

结果就是：NoSQL 兴起时，Postgres 靠 `JSONB + GIN` 倒排索引直接吞下了文档数据库的需求；AI 爆发时，一个 `pgvector` 插件就能在原有事务库里跑向量检索，不用再额外运维一套向量库。

不为短期跑分牺牲底层类型抽象，才换来了跨越二十年的自我进化能力。

05｜海光从Zen 1授权走向自研架构

来源（X） · @injoylin · 2026-11-20 18:32

老黄被搞后，外侄女AMD 苏妈也被搞了

因为苏姿丰培养了一个中国芯片怪物-海光，科创板的千亿市值芯片巨头，把原本属于 Intel 和 AMD 的中国政企服务器市场切走了一大块

2016 年，AMD 处境极其艰难，市值一度跌破 20 亿美元，急需资金推进 Zen 架构研发。

在此背景下，AMD 与中国企业（中科曙光旗下的天津海光）达成了总额约 2.93 亿美元的许可协议：

授权内容： 仅限第一代 Zen 1 架构的服务器处理器设计授权（即后来的海光“禅定”/Dhyana 系列）。

核心限制（关键点）： 这不是源码买断，也不是永久授权。协议规定合资公司只能生产专供中国境内销售的服务器芯片，且不包含后续 Zen 2、Zen 3、Zen 4/5 等任何迭代架构。海光在底层核心微架构上没有修改权，只能在有限的外围模块（如国产加密算法模块）上做定制。

但实际上海光，不仅出了新品，而且在2019年断供之后，海光恰恰是靠着当年拿到的 Zen 1 底层授权作为“跳板”，硬生生消化吸收并走出了一条独立迭代的路线。

1. 产品的代际演进（从“换壳”到“自研微架构”） 海光的 CPU 产品线（主要对应服务器市场的 7000/5000/3000 系列）大致经历了三个阶段：海光一号（C86-1G / 2G）： 2018年前后推出，基本就是基于 AMD Zen 1 架构的“本地化定制版”，集成了中国国家密码管理局认可的加密算法模块（如 SM2/SM3/SM4），直接替代当时的至强（Xeon）中高端处理器。海光二号、三号（C86-3G）：

2019年被列入实体清单、失去 AMD 后续技术支持后，海光开始在 Zen 1 源码基础上自行改写微架构（如优化分支预测、扩充缓存、改进内存控制器等）。海光三号的单核与多核性能已经大幅超越原版 Zen 1，综合表现普遍被认为接近 AMD Zen 2 到 Zen 3 之间的水平。海光四号、五号（C86-4G / 5G）： 从 C86-4G 开始，海光官方正式宣布采用“全新自研微架构”。

近两年曝光和推进的 C86-5G 规格已经相当庞大，单颗最高达到 128 核 512 线程（支持四路并发线程技术），并且海光近期公开透露，集成 CPU+GPU+NPU 的新一代端侧及数据中心处理器预计将在 2027 年实现量产。

2. 不仅做了 CPU，还顺藤摸瓜做出了 AI 芯片（DCU） 除了 CPU，海光另一条核心产品线是 DCU（深度计算单元，即“深算”系列 GPGPU）。这条线同样源自早期与 AMD 生态的技术渊源（兼容类 CUDA 生态的 ROCm/HIP 架构），用于大模型训练和 AI 推理。截至目前（2026年），在英伟达高端芯片受限的背景下，“海光 CPU + 深算 DCU” 已经成为国内金融、电信、能源以及各大智算中心（AI 一体机）出货量最大、生态最成熟的国产替代方案之一。

07｜企业级Agent交付的六项工程要求

来源（X） · @Stanleysobest · 2026-11-20 14:27

最近跑了几家企业做 FDE 驻场交付，我越来越确定一件事：

现在市面上至少80%的 AI Agent 项目，还停留在玩具阶段。

接个大模型，配置几个 MCP，写几段 Prompt，让 AI 自动调用工具，跑通一个流程，就敢跟老板说：我们实现了 AI Agent 自动化。

真进工厂交付，你就知道有多离谱。

举个例子。

一家制造业企业想用 AI Agent 处理客户订单。

客户发来采购需求，AI 自动识别产品型号、查询库存、生成报价单，再同步给销售。

Demo 演示非常漂亮，老板看完很兴奋。

结果正式上线，问题一个接一个。

客户修改了三次订单，Agent 却拿第一次的数量报价。

库存接口超时，Agent 重试了两遍，系统里多出了三张重复订单。

销售经理还没审批，Agent 已经把折扣报价发给客户。

最要命的是，出了问题没人知道错在哪一步，只能翻聊天记录。

这就是为什么我一直强调：会做 Agent，跟能做企业级 Agent 交付，完全是两码事。

真正做 FDE，你至少要解决六件事：

流程编排： 哪些步骤交给 AI 判断，哪些必须按固定规则执行，不能什么都让模型自由发挥。
权限控制： AI 可以查库存，但不能随便改库存；可以生成报价，但大额折扣必须经过人工审批。
任务记忆： 客户修改订单、员工中途接手、系统突然断线，Agent 必须知道之前做到哪一步。
异常恢复： API 超时、任务失败、服务重启，不能每次都从头再来，更不能重复扣费、重复下单。
过程监控： 每次调用花了多少钱、哪个环节出错、为什么出错，都得查得清清楚楚。
统一管理： 当企业同时部署销售、客服、采购、财务 Agent，必须统一管理权限、数据和执行记录。

还有一个很大的误区：

很多技术团队特别喜欢搞多 Agent 协作。

明明一套固定工作流就能解决的问题，非要安排五六个 Agent 开会、讨论、互相调用。

最后 Token 消耗翻倍，响应速度变慢，故障点还增加了。

老板根本不关心你用了几个 Agent。

他只关心三件事：

以前10个人干的活，现在能不能5个人完成？

以前处理一张订单要30分钟，现在能不能压到3分钟？

系统连续运行一个月，会不会突然给我捅个几十万的窟窿？

这段时间我做企业 FDE 交付，最大的感受就是：

AI 技术演示越来越容易，真正把 AI 塞进企业现有业务流程，反而越来越考验工程能力。

未来企业愿意花几十万、上百万买单的，绝不是几个炫酷的 Agent Demo。

而是你能不能深入业务现场，把流程、权限、数据、异常处理和员工操作全部打通。

会调 API 的人越来越多，能在工厂里蹲一个月，把 AI 系统真正跑起来的人，依然稀缺。

这才是我认为未来 FDE 最值钱的地方。
