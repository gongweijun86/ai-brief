01｜billion-context压缩长会话

来源（X） · @lxfater · 2026-11-08 14:55

最近看到一个叫 billion-context 的开源项目，专门解决 AI 编程长会话爆窗口的问题

它架在编程 Agent（比如 Claude Code、Codex、OpenCode、Kimi 等）和模型 API 之间，做一个上下文压缩代理

和客户端自带的一刀切摘要不同，它的核心思路是“让模型自己管上下文”

代理会往对话里注入四个工具：compress（折叠成摘要）、decompress（按需恢复细节）、search_context（关键词检索）和 acp_status（查看用量与可压缩区间）

什么时候压缩、压哪一部分，都由模型自己调用工具决定

因为是局部增量折叠，需要细节时还能解压回来，所以既能省下不少 token，又尽量不破坏前缀缓存

那实际用起来效果怎么样？

我有个朋友说：让模型自主选择压缩的想法确实挺好，但在实际长会话里还不太稳定

跑到后面经过多轮反复压缩，上下文有时候会被带偏，开始出现一些模型自创的缩写或黑话，可读性和连贯性会往下掉；
如果接的是低量化模型，这种走样的情况会更明显，偶尔还会遇到一些小 bug

如果你平时跑超长编程会话经常被 token 账单或爆窗困扰，可以去试试看，这些工具都要自己尝试

https://github.com/ranxianglei/billion-context

03｜Elephant-Goldfish对抗验证

来源（X） · @servasyy_ai · 2026-11-08 17:29

日常让 Agent 堆业务代码，很多人踩过的最大一个坑：

上下文塞得太满，Agent 开始“脑补默契”。

写到第十轮，模型以为自己什么都懂，架构漏洞全被历史对话掩盖过去；
一换新会话或者真正跑测试，全线崩盘。

Google 开源的这个 Elephant-Goldfish Model 插件，思路非常接地气，直戳多 Agent 协作的痛点。

它把这个过程暴力拆成了两个极端角色：

大象（Elephant）：长记忆。吃下你所有的业务背景、历史需求和全局代码，专门负责输出一份详尽的技术规格（Spec）。

金鱼（Goldfish）：零上下文。完全不带任何历史包袱，拿到的只有刚才那份 Spec，直接以“白盒新手”的视角去硬碰硬压测这份规格。

很多时候不是模型写不出代码，而是 Spec 根本没闭环：
- 是不是默认漏了环境变量？
- 接口边界有没有漏写兜底类型？
- 离开当前这个 prompt 堆出来的语境，这份 Spec 到底能不能独立跑通？

在金鱼子 Agent 面前，没有任何“历史会话假象”。
只要规格写得含糊，它一眼就能挑出断层。

在这个流派里，工作流节奏完全变了：

1. 大象 Agent 负责铺全局、起草规格；
2. 金鱼 Agent 无情挑刺，把模糊地带全逼出来；
3. 你作为人类工程师，在最关键的架构节点拍板、批准 Spec；
4. 规格锁死之后，再放给模型去刷代码。

不用等到代码写了三千行才发现地基打歪了。

官方说明里这套插件可以直接接入 Antigravity、Claude Code、Codex 和 ChatGPT 等主流环境。

对经常做多 Agent 流水线的人来说，这种“故意制造信息差”做对抗验证的思路，比单纯堆长上下文管用得多。

项目地址：
https://github.com/google/elephant-goldfish-model

引用内容

Xudong Han @Xudong07452910

我们都知道模型变强之后，以前精心设计的 Agent Skill 可能成了负担，但是怎么去除不必要的 skills 很多人却不知道。

Garry Tan @garrytan 的做法很值得借鉴。他用 Eval 对比了 Opus 5.5 开启和关闭 /investigate 的表现，发现修复率没有明显差异，但每修好一个 Bug 的成本反而高了 43%，于是决定砍掉它。

我觉得这个思路应该成为 Harness Engineering 的常规操作。

比如以前为了提高 Coding Agent 的可靠性，我们设计了「先生成详细计划，再逐步排查问题」的 Workflow。

模型升级后，就可以用同一批真实任务做 A/B Eval，一组保留旧流程，一组直接让模型执行，多次测试，对比成功率、Token 消耗和执行时间。

如果旧流程已经带不来稳定的提升，甚至增加了成本，那就该考虑简化或移除。

Agent 的 Skill 和 Harness 也需要定期做减法。模型在进化，我们为旧模型设计的工作方式也应该重新验证。

05｜Coding Agent自验证交付

来源（X） · @shao__meng · 2026-11-08 17:09

Addy Osmani：Coding Agent 让你成了管理者，但不该让你更忙

当你开始挑任务、交代背景、委派工作、验收结果，你已经在 “管理” Agents。多开几个会话本身意义不大，重要的是建立让 Agents 能自行验证、带着证据交付的工作方式。

# 先让 Agent 能检查自己，而不是让人充当测试系统

Addy 把自验证放在首位：每项任务都应提供可执行的检查，例如测试、构建、类型检查，界面改动还可以用截图验证。

Agent 应先执行、检查、修正失败，再提交结果与证据，而不是说一句“完成了”，把所有验证留给人。必要时，再让没有参与原对话的新 Agent 独立审查，减少沿着同一思路自我认可。

# 最该补充的是仓库里看不到的信息

任务说明不必重复代码已有的内容，更重要的是：为什么做、业务约束是什么、哪些事情不要做，以及怎样才算成功。

重复出现的纠错可以沉淀为共享规则或技能，但规则不是越多越好。随着模型升级，旧约束也要清理；普通偏好可以写成指导，必须遵守的安全要求则需要强制执行机制。

# 并行的上限，往往是人的注意力

无人值守任务开始前，要明确完成条件、验证方式、权限、运行上限、交付产物和审批人。新流程先小范围试跑，再扩大规模。

即使测试全绿，功能也未必值得做。产品取舍、安全边界与发布判断仍由人负责；成效应看交付周期、返工和回退，而不是 Agent 写了多少代码。

08｜OpenAI模型提出局部平滑证明

来源（X） · @jiqizhixin · 2026-11-08 15:12

中文译文

将波在时间上取平均，为何能揭示单帧快照无法显示的规律性？

一份 OpenAI AI 生成的手稿提出了欧拉波方程在每个至少为二维的空间维度中的局部平滑性（local smoothing）的证明。这是一项正在接受独立数学检验的公开研究主张。

瓶颈在于：精确估计必须控制波在传播过程中的集中方式。这些集中现象将这一分析问题与包含各方向线段的集合的几何联系起来。

机制：该手稿引入了辅助流和相应的能量估计，以建立所需的平滑不等式。它还从这些估计中推导出欧几里得空间中 Kakeya 集的完整 Hausdorff 维数结论。

回报：如果这一论证经受住独立审查，它将解决调和分析中的重大猜想。一份 Lean 形式化版本可供查阅，但验证其数学对应关系和审查证明仍然是实质性任务。公开发布和形式化不应与已完成的社区验证混淆。

How can averaging a wave over time reveal regularity that a single snapshot cannot show?

An OpenAI AI-generated manuscript proposes a proof of local smoothing for the Euclidean wave equation in every spatial dimension of at least two. It is a public research claim undergoing independent mathematical examination.

The bottleneck: Sharp estimates must control how waves concentrate while propagating. Those concentrations connect this analysis problem to the geometry of sets containing line segments in every direction.

The mechanism: The manuscript introduces auxiliary flows and associated energy estimates to establish the required smoothing inequalities. It also derives a full Hausdorff dimension conclusion for Kakeya sets in Euclidean space from these estimates.

The payoff: If the argument withstands independent scrutiny, it would settle major conjectures in harmonic analysis. A Lean formalization is available for inspection, but checking its mathematical correspondence and auditing the proof remain substantive tasks.
