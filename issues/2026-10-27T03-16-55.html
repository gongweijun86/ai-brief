02｜Manus用Agent改造内部组织

来源（X） · @Xudong07452910 · 2026-10-27 09:11

昨天看到 Manus 联合创始人张涛写的《用 Manus 改造 Manus》，里面分享了不少他们如何用 Agent 改造内部组织的真实实践，非常值得研究。

他们研发团队通过 Manus-mono 统一入口，一个人可以并行推进十几个需求，移动端大约 7 个人支撑着 4 个 App。

产品经理开始用视频 PRD、测试账号和录屏把需求交给 Agent，自己推进开发和上线。

市场团队也在搭建「数字同事」，把内容合作等日常工作交给 Agent 处理。

最值得关注的是 Manus 已经开始重新划分人的工作边界。很多以前需要跨团队反复沟通、交接的事情，现在可以让一个人带着 Agent 往前推进。

但这也让我想到一个问题。

当开发速度和并行任务数量大幅提升，测试、Review、权限和交付流程能不能跟上？这些可能才是 AI Native 组织真正难改造的地方。

很推荐做 Agent 工程、AI 产品和团队管理的朋友读读，里面的实践比很多泛泛而谈的 AI 组织转型更有参考价值。

06｜微软向6万人提供自愿离职补偿

来源（X） · @berryxia · 2026-10-27 08:46

微软让六万人自坎一刀直接离职，占据了1/4 啊！

真的是有点离谱，这不得闹闹游行示威一把么😛

引用内容

宝玉 @dotey

微软向约 6 万名员工提供自愿离职补偿，约占全员四分之一，12 月初前决定

微软 10 月 26 日（周一）给美国、加拿大、英国和印度部分团队的员工发了一份“自愿离职邀约”：愿意走的人，可以拿一笔相当于标准遣散费的补偿离开。符合条件的大约 6 万人。

消息由 Bloomberg 先报出，微软随后在官方博客公布了首席人力官 Amy Coleman 的内部信，并向 GeekWire 确认了 6 万这个数字。

6 万人占多少？微软年报显示，截至今年 6 月 30 日，全职员工 22.3 万人。6 万除以 22.3 万约等于 27%，和流传的“约 27%”对得上。不过 22.3 万是 7 月裁员之前的数字，按现在的人数算，比例会再高一点（这是我按公开数字推算的）。

【谁能拿到】

要同时满足三个条件。所在国家是美国、加拿大、英国或印度；所在团队参加了这个计划，内部信说参不参加要看各业务的优先级、对客户的承诺和人手需求；职级在微软内部 70 级及以下。

70 级包括总经理和部分挂“副总裁”头衔的人，但不包括“企业副总裁”（CVP，微软更高一级的高管）。所以“副总裁及以下都能拿”的说法不够准确，准确说法是部分副总裁也在范围内。

不看年龄，不看工龄，也不看绩效。

哪些团队在名单上，微软没有公开。The Verge 引述知情人士说，Copilot、CoreAI、Windows 与设备、Xbox、财务和人力资源团队的员工都能申请；Cloud + AI、Microsoft AI 等部门部分参加；销售、市场、安全、量子计算等部门不参加。

【能拿到什么】

补偿和标准遣散费相当：按工龄和职级给一笔工资，股票继续按原计划到账，保留一段时间的医疗保险，再加职业转型服务。符合条件的员工会收到邮件，12 月第一周前做决定。据 Business Insider 看到的备忘录，接受的人在年底离开。

【这算裁员吗】

走不走由员工自己选，所以不算裁员。但微软也说，这个计划不能替代裁员，之后还裁不裁，要看业务情况。微软发言人表示，这不代表公司需要更少的人；据 http://Investing.com 转述，即使员工接受了邀约，公司仍可能设法留住顶尖人才。

微软没有预测会有多少人接受，只说比例会比春季那次低得多。今年春天，微软第一次推出自愿退休计划，只面向美国、年龄加工龄达到门槛的员工，约 8750 人符合条件，约 30% 接受了，微软为此计入 9 亿美元费用。那次还多给了延长的医疗保险，这次没有。

【为什么是现在】

Bloomberg 把这次邀约称为微软最新一轮降本措施。微软正在 AI 数据中心上大量投钱，同时持续压缩人员开支：今年 7 月裁了 4800 人，其中 Xbox 约 3200 人；9 月又裁了几百人；2025 年全年裁员超过 1.5 万人。

Amy Coleman 在内部信里说，这个计划让参加的部门“多了一种方式，让团队人员适应不断变化的需求”。微软周三发布季度财报，可能会披露这次计划的预计成本。

11｜LangChain分享Agent权限设计

来源（X） · @Xudong07452910 · 2026-10-27 08:29

最近 LangChain 分享了内部销售、研发和内容团队的 Agent Harness 架构，里面有不少值得借鉴的工程细节。

他们发现，最棘手的问题之一是「Agent 到底以谁的身份干活」。

比如销售 Agent 查询 Salesforce 可以用公司统一账号，但发邮件必须使用用户自己的授权，而且只能在私聊中操作。

Coding Agent 也一样。帮你提交 PR 时，用你的 GitHub 身份；在后台自动审查代码时，则切换成独立的 GitHub App。

内容 Agent 发公司 Twitter，用的是公司账号，但只有白名单用户能真正发帖。

除此之外，还有几项关键设计：

1. Agent 直接接入 Slack，不用员工换平台；需要时还能从工讨论里「拆」出独立线程
2. Memory 分全局和个人两层，由 Agent 自己决定一条事实记到哪一层
3. 代码在沙箱里执行，经安全代理访问外部服务
4. 大量任务是定时或事件触发的，不一定等人开口。比如新 PR 自动 Review，或者你跟它说一声，它自己挂上每天销售简报

Demo 阶段跑得通的 Agent，一进公司就会撞上身份和权限边界。这些细节平时讨论不多，但真落地一个都绕不过去。

这些细节平时讨论得不算多，但真到落地时，一个都绕不过去。推荐做企业 Agent 的朋友读读。
