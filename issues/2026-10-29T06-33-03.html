02｜EvoRouter 自进化路由降本51%

来源（X） · @snwiki238337 · 2026-10-28 14:33

多 agent 系统正式落地到生产环境中的一个问题就是成本与性能的组合问题，很难进行兼容并蓄，要同时兼顾性能、成本、体验多个因素。
这篇论文 EvoRouter: Cost-Efficient Multi-Agent Routing via Insight-Guided On-Policy Distillation 讲的就是这个工程问题，提出了一套自进化的多智能体动态路由框架。
简单来说的话，过去的 Agent 路由或者编排策略训练，主要的问题是协作模式等的与技能工具的组合是离散且高度相互耦合的。
但是常规强化学习只拿最终任务成败和整体 Token 消耗做标量奖励，无法精细化究竟是哪一步决策错了。

为了破解这种高维决策与粗粒度反馈的错配，EvoRouter 提出了一套自进化闭环。
他们在训练阶段引入专门的专家 Agent，定期分析历史探索轨迹的性能-成本，自动提炼出带有明确触发条件的路由。
同时特权 agent 将这些不断演化的洞察规则与实际执行反馈相结合，通过在线策略蒸馏，在路由模型自身的规划轨迹上注入密集的 Token 级别细粒度监督信号。

引入对数缩放的惩罚项。更新后的路由策略生成更优质的轨迹，进一步喂给专家 agent 提取更准的洞察，形成正向自进化飞轮。
从实际评测来看，EvoRouter 4B 参数量级的域内平均准确率达到 68.69%，相比目前最强的多智能体路由 baseline提升了 7.23 个百分点。

在准确率反超的同时，将整体推理算力成本降低了 50.95%。在未见过的域外任务上泛化准确率达 74.67%。
GitHub：https://github.com/CenYangtze/EvoRouter

arxiv：https://arxiv.org/abs/2610.35690

06｜AI工程评估十五个关键实践方法

来源（X） · @divaagurlxw · 2026-10-28 20:18

中文译文

评估（Evals）是AI工程中最被低估的技能。

1. 从错误分析开始，而不是从指标开始
抽样100多条生产链路追踪。用自由文本标注每个失败（开放式编码），然后将它们聚类为失败类别（轴心编码）。统计每个类别的频率。排名前3的类别就是你的第一批指标。

2. 构建一个版本化的黄金数据集
将输入、期望输出或评分标准，以及元数据（意图、难度、用户群体）存储在版本化的数据集中。对其进行分层处理，使罕见但关键的案例不会被简单案例淹没。将其与你的提示词一起进行版本管理，使每次评分都可复现。

3. 沿显式维度生成合成数据
不要只是让LLM生成"测试题"。定义维度（角色×意图×复杂度×边缘情况），将组合作为元组生成，然后将每个元组转化为一个自然输入。这样你得到的是覆盖性，而不是200个近乎相同的样本。

4. 先用确定性断言
JSON schema验证、正则检查、必填字段、长度限制、代码执行、真正能在测试数据库上运行的SQL。这些成本低、速度快、方差为零。把基于模型的评分留给代码确实无法检查的部分。

5. 分别评估检索与生成
对于RAG，用recall@k、MRR或nDCG来衡量检索效果，对标已标注的相关文档块。用忠实度（faithfulness）来衡量生成效果（每个主张是否都有检索到的上下文支撑？）。如果你只给最终答案打分，你就无法判断是哪一半出了问题。

6. 智能体的轨迹评估
记录每一步：工具名称、参数、结果、token。对标参考路径来评估工具调用的精确率和召回率、参数正确性、步数以及错误恢复能力。一个需要14次调用才能得到正确答案、而3次就足够的智能体，就是一个成本和延迟的bug。

7. pass@k vs pass^k
pass@k = 在k次运行中至少成功一次。pass^k = 在k次运行中每次都成功。在每次运行80%成功率的情况下，pass^5会降到大约33%。生产可靠性取决于pass^k，所以请在你实际使用的temperature下对每个案例运行多次。

8. 用模拟用户做多轮对话评估
给一个LLM一个角色、一个隐藏目标和约束条件，然后让它与你的系统对话，直到目标达成或达到轮次上限。评估目标完成度、达到解决的轮次、以及策略违规。单轮评估会漏掉大多数状态和记忆相关的bug。

9. 像对齐分类器一样对齐你的LLM评审员
人工标注100多个样本为通过/不通过。拆分为训练/开发/测试集。用开发集迭代评审员提示词，然后在测试集上报告TPR和TNR。使用二元输出配合书面评分标准，在给出结论前要求先写一段简短的批评，并固定评审模型的版本。

10. 在两两比较中控制评审员偏差
LLM评审员有位置偏差，且通常更偏好更长的回答。每次A/B比较都要用交换顺序运行两遍，只统计一致的结论。如果冗长导致结果偏斜，则对长度进行归一化或设上限。

11. 尊重统计学
100个样本、80%准确率的情况下，你的95%置信区间大约是±8个百分点。从80%跳到83%很可能是噪声。在宣称胜利之前，先用bootstrap置信区间，或在相同样本上做配对检验。

12. 在CI中设置部署门禁
在每个涉及提示词、模型、工具或检索配置的PR上运行评估套件。为每个类别设置阈值，而不是一个全局总分，这样某一个领域的大幅提升不会掩盖另一个领域的回归。出现回归就让构建失败。

13. 生产环境中的在线评估
抽样一定比例的在线流量，异步运行评审器，并针对每个失败类别的漂移发出告警。使用影子部署（shadow deployment）在真实流量上运行新的提示词或模型，而不向用户展示输出结果。

14. 将成本和延迟作为一级指标
在质量旁边追踪每次请求的token数、每个成功任务的成本（而非每次调用的成本）以及p50/p95延迟。一个保持质量不变、同时将成本削减40%的变更就是真正的胜利，值得发布。

15. 闭环
每个生产失败都变成一个新的标注测试用例。每个新模型版本在任何人讨论切换之前，都要先跑完整套评估。随着时间推移，你的评估集会成为代码库中最有价值的资产。

提示词是用完即弃的。模型每隔几个月就会被替换。

你的评估基础设施才是会不断复利的东西。

原文

Evals are the most underrated skill in AI engineering.

1. Start with error analysis, not metrics
Sample 100+ production traces. Annotate each failure in free text (open coding), then cluster them into failure categories (axial coding). Count frequency per category. Your top 3 categories are your first metrics.

2. Build a versioned golden dataset
Store inputs, expected outputs or rubrics, and metadata (intent, difficulty, user segment) in a versioned dataset. Stratify it so rare but critical cases aren't drowned out by easy ones. Version it alongside your prompts so every score is reproducible.

3. Generate synthetic data along explicit dimensions
Don't just ask an LLM for "test questions." Define dimensions (persona × intent × complexity × edge case), generate combinations as tuples, then turn each tuple into a natural input. You get coverage instead of 200 near-identical examples.

4. Deterministic assertions first
JSON schema validation, regex checks, required fields, length limits, code execution, SQL that actually runs against a test DB. These are cheap, fast, and have zero variance. Reserve model-based grading for what code genuinely can't check.

5. Evaluate retrieval separately from generation
For RAG, measure retrieval with recall@k, MRR, or nDCG against labeled relevant chunks. Measure generation with faithfulness (is every claim supported by retrieved context?). If you only score the final answer, you can't tell which half is broken.

6. Trajectory evals for agents
Log every step: tool name, arguments, result, tokens. Score tool-call precision and recall against a reference path, argument correctness, step count, and error recovery. An agent that reaches the right answer in 14 calls when 3 would do is a cost and latency bug.

7. pass@k vs pass^k
pass@k = succeeded at least once in k runs. pass^k = succeeded in all k runs. At 80% per-run success, pass^5 drops to roughly 33%. Production reliability lives in pass^k, so run each case multiple times at your real temperature.

8. Simulated users for multi-turn
Give an LLM a persona, a hidden goal, and constraints, then let it converse with your system until the goal is met or a turn limit hits. Grade goal completion, turns-to-resolution, and policy violations. Single-turn evals miss most state and memory bugs.

9. Align your LLM judge like a classifier
Hand-label 100+ examples as pass/fail. Split into train/dev/test. Iterate on the judge prompt using dev, then report TPR and TNR on test. Use binary outputs with a written rubric, require a short critique before the verdict, and pin the judge model version.

10. Control judge bias in pairwise comparisons
LLM judges have position bias and often prefer longer answers. Run every A/B comparison twice with swapped order and only count consistent verdicts. Normalize or cap length if verbosity is skewing results.

11. Respect statistics
With 100 examples at 80% accuracy, your 95% confidence interval is about ±8 points. A jump from 80% to 83% is probably noise. Use bootstrapped confidence intervals, or a paired test on the same examples, before declaring a win.

12. Gate deploys in CI
Run the eval suite on every PR that touches prompts, models, tools, or retrieval config. Set per-category thresholds instead of one global score, so a big win in one area can't hide a regression in another. Fail the build on a regression.

13. Online evals in production
Sample a percentage of live traffic, run your judges asynchronously, and alert on drift per failure category. Use shadow deployments to run a new prompt or model on real traffic without showing users the output.

14. Make cost and latency first-class metrics
Track tokens per request, cost per successful task (not per call), and p50/p95 latency next to quality. A change that keeps quality flat while cutting cost 40% is a real win and deserves to ship.

15. Close the loop
Every production failure becomes a new labeled test case. Every new model release gets run against the full suite before anyone debates switching. Over time your eval set becomes the most valuable asset in the codebase.

Prompts are disposable. Models get replaced every few months.

Your eval infrastructure is what compounds.

07｜DeepInfer磁盘KV缓存提速26倍

来源（X） · @_avichawla · 2026-10-28 19:09

中文译文

DeepSeek又做到了！

他们刚刚开源了DeepInfer，这是缓存命中时使首token生成速度提升最多达26倍的推理栈。

当一个请求重复了一个很长的前缀，比如系统提示词或之前的聊天轮次时，服务器可以直接复用已经计算过的KV缓存，而不需要重新运行prefill。

理想情况下，你会期望这个缓存放在GPU内存中，因为磁盘按理说对请求路径上的任何操作都太慢了。

但实际上，DeepSeek把它放在了SSD上。

当DeepSeek推出这个功能时，一个128K token的提示词命中缓存后，首token生成时间从13秒降到了500毫秒。

而去年某一天的生产流量中，56%的所有输入token直接从磁盘提供服务。

所以只要你存储的内容足够小、存储带宽足够宽，磁盘在这里就不是瓶颈。

让我们来理解它是如何工作的。

1) 为什么要复用KV缓存：

在生成任何内容之前，LLM会读取整个提示词，并为每一层中每个token计算一个key和一个value。这就是prefill，在长提示词上这是最慢的部分。

许多请求的开头都是一样的。

例如，聊天应用每次都会重发所有之前的轮次，或者智能体每次调用都重发相同的系统提示词和工具定义。

如果这些KV被保存下来，下一个带有相同前缀的请求就能直接加载它们，只计算新token。

2) 为什么主要使用GPU内存：

每个token在每一层都要存储KV，所以在一个标准模型上，长提示词的KV缓存会占用好几GB。

从磁盘读取这么多数据可能比在GPU上重新计算还要慢。

所以引擎把缓存放在GPU内存中。但GPU内存容量很小，所以旧的前缀很快被逐出，很多重复请求无法命中。

3) DeepSeek让KV缓存变小了：

DeepSeek-V2引入了Multi-head Latent Attention（MLA，多头潜在注意力）。

MLA不是为每个注意力头分别存储独立的KV，而是为每个token在每层存储一个小的压缩向量，然后在注意力计算过程中从这个向量重建key和value。

在V2论文中，与DeepSeek之前的67B模型相比，这将KV缓存减少了93.3%。

而MLA将KV缓存缩小到足以存储在低成本磁盘上的程度。

每个缓存token占用的字节数更少，意味着每次命中需要读取的字节数也更少，这使得从SSD加载比重新计算更快。

4) 3FS从大量SSD上并行读取：

单块SSD仍然太慢，所以缓存存储在3FS上，这是DeepSeek自研的分布式文件系统。

3FS将文件切分成块（chunk），分布到数千块SSD和多个存储节点上。一次读取会从多个磁盘并行拉取块，所以它们的带宽是叠加的。

当一个请求到达时，系统将其前缀与缓存的块进行匹配，从3FS将这些块加载到主机内存中，并在模型已经在运行的同时逐层拷贝到GPU。

而且由于每台prefill机器都能访问所有缓存的前缀，请求不必回到上次服务它的那台机器。

磁盘也很便宜，所以缓存可以保留数天。根据DeepInfer文档，针对智能体流量的缓存前缀保留3天，针对聊天的保留7天。

当KV缓存足够小、存储带宽足够宽时，磁盘缓存就是可行的。DeepSeek从注意力设计中获得了前者，从3FS中获得了后者。

从价格上也可以看出来。在今天的deepseek-flash上，一次缓存命中比未命中的成本低50倍。

如果你使用API，请把提示词中稳定的部分（系统提示词、工具、文档）放在最前面，因为只有从第一个token开始完全匹配才算命中。

原文

DeepSeek did it again!

They just open-sourced DeepInfer, the inference stack behind cache hits that return the first token up to 26x faster.

When a request repeats a long prefix, like a system prompt or earlier chat turns, the server can reuse the KV cache it already computed instead of running prefill again.

Ideally, you'd expect that cache to sit in GPU memory, since disk is supposed to be far too slow for anything on the request path.

In practice, DeepSeek keeps it on SSDs.

When DeepSeek launched this, a 128K-token prompt that hit the cache got its first token in 500ms instead of 13s.

And in one day of production traffic last year, 56% of all input tokens were served straight from disk.

So disk isn't the bottleneck here as long as what you store is small enough, and the storage is wide enough.

Let's understand how this works.

1) Why reuse the KV cache at all:

Before generating anything, an LLM reads the whole prompt and computes a key and a value for every token in every layer. This is prefill, and on long prompts it's the slow part.

Many requests start the same way.

For instance, a chat resends every earlier turn or an agent resends the same system prompt and tool definitions on every call.

If those KV are saved, the next request with the same prefix loads them and only computes the new tokens.

2) Why GPU memory is predominantly used:

Every token stores KV in every layer, so on a standard model a long prompt's KV cache runs into many GBs.

Reading that much from disk can take longer than recomputing it on the GPU.

So engines keep it in GPU memory. But GPU memory is small, so old prefixes get evicted fast and many repeats miss.

3) DeepSeek made the KV cache small:

DeepSeek-V2 introduced Multi-head Latent Attention (MLA).

Instead of storing separate KV for every attention head, MLA stores one small compressed vector per token per layer, and the keys and values are rebuilt from it during attention.

In the V2 paper, this cut the KV cache by 93.3% compared to DeepSeek's earlier 67B model.

And MLA shrank the KV cache enough to store it on low-cost disks.

Fewer bytes per cached token implied fewer bytes to read on every hit, and it made loading from SSD faster than recomputing.

4) 3FS reads it from many SSDs at once:

One SSD would still be too slow, so the cache lives on 3FS, DeepSeek's own distributed file system.

3FS splits files into chunks and spreads them across thousands of SSDs on many storage nodes. A read pulls chunks from many drives in parallel, so their bandwidth adds up.

When a request arrives, the system matches its prefix against cached blocks, fetches those blocks from 3FS into host memory, and copies them to the GPU layer by layer while the model is already running.

And since every prefill machine can reach every cached prefix, a request doesn't have to go back to the machine that served it last.

Disk is also cheap, so the cache can stay for days. As per the DeepInfer docs, cached prefixes are retained for 3 days for agent traffic and 7 days for chat.

Disk caching works when the KV cache is small, and the storage is wide. DeepSeek got the first from its attention design and the second from 3FS.

This is also evident from the price. On deepseek-flash today, a cache hit costs 50x less than a miss.

If you use the API, keep the stable parts of your prompt (system prompt, tools, documents) at the front, since only an exact match from the very first token counts as a hit.
