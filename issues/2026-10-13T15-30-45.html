01｜Opencli 打通国内平台调研数据

来源（X） · @dashiAIxz · 2026-10-13 11:20

再分享一个非常有价值的信息

做自媒体除了剪辑，还有个非常重要的调研环节，找案例、找选题、找资料。但国内的内容平台（抖音、小红书、B 站、知乎、微信等）数据反爬是非常严格的

Agent 很难靠自己轻松的拿到这些信息，我们的做法是通过 @jakevin7 大佬的 Opencli 来调研，基本上你能用上的 99% 国内的平台他都能帮你打通。再配合飞书 CLI，整理成文档

项目地址：https://github.com/jackwener/opencli

另外，让 Agent 写视频脚本很多时候 AI 味严重的一个原因是因为模型本身缺少观点，所以在调研过程中，我会让他抓取视频中的观点、评论区的高赞观点、弹幕中的讨论偏向。这些都是非常重要的信息，让他把这些信息整合起来写视频脚本，就能得到非常好的效果

然后再想想一下，这些东西结合在一起，跑成工作流，想象空间有多大，我就不方便再展开讲了

02｜vLLM 双向 KV 传输复用多轮上下文

来源（X） · @FeitengLi · 2026-10-13 11:39

vLLM 开始支持双向 KV 传输，针对多轮 Agent 在 prefill/decode 分离部署中反复计算历史上下文的问题：上一轮 decode 节点算出的 KV，下一轮可以传回 prefill 节点继续复用。

在 AWS P5en + EFA、一个 prefill 节点配一个 decode 节点的测试中，GLM-5-FP8 在约 20K 输入长度下，首 token 延迟从 2,334 ms 降到 702 ms。但这个对照关闭了 prefill 端的前缀缓存，用来模拟缓存失效或请求换节点。

短上下文里，搬运和协调的开销可能比重算更大。

官方介绍：https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload

04｜田柯宇首度回应字节干扰训练争议

来源（X） · @0xLogicrw · 2026-10-13 15:12

曾因破坏字节跳动模型训练被辞退的田柯宇，在播客《elsewhere 别处发生》中首次详细回应两年前的争议。他称，当时一名新实习生经常超额占用算力，甚至停止其他同事的实验，自己向上级反馈无果后，选择「以暴制暴」。他承认曾用 ChatGPT 编写程序，在约 10 天内手动干扰对方实验 5 次，但否认持续数月攻击训练集群，强调自己并非为了争夺算力，也承认做法不当。

然而，一份题为《实习生 A 视角来了》的反驳材料，给出了完全不同的说法。材料列出多段据称来自字节内部的代码记录，指控田柯宇的破坏行为始于 2024 年 3 月，持续数月，涉及多个项目。他先向 LlamaGen 项目的模型参数混入随机噪声，随后又篡改视频生成项目 Goku 使用的 PyTorch 底层代码，让模型训练结果出错、程序随机中断。这些故障极难复现，甚至出现过 100 台机器运行相同程序，只有一台异常、重启后又恢复正常的情况。中美团队为此长期轮流排查，直到当年 7 月底才发现异常代码。田柯宇在此期间还会根据同事的排查进展调整攻击方式。

更严重的是另一项科研诚信指控。材料称，田柯宇当时负责一个使用上千张 GPU 训练的 VAR 文生图项目，但展示给同事测试的成果，其实来自已经开源的 PixArt 模型。他还在用户输入的 Prompt 前偷偷添加「City」，让同事难以通过相同提示词发现两个模型的关联。此前测试人员就发现，生成图片中经常莫名出现城市建筑，却一直找不到原因。事后团队检查发现，真正的 VAR 模型远未达到展示效果。文末还列出多名相关项目研究人员，称他们愿意为亲历部分作证。

字节跳动早在 2024 年就确认，田柯宇曾通过编写、篡改代码恶意干扰内部研究项目训练，随后将其辞退，并起诉索赔 800 万元及合理支出。田柯宇此次透露，一审法院判赔约 50 万元，其余诉请被驳回，但字节已提起上诉，目前仍在二审。他表示认可赔偿，也为自己的行为道歉，但坚持认为外界严重夸大了他的行为。

06｜pi-durable 工具调用成一等公民

来源（X） · @robotbird01 · 2026-10-13 10:55

🚀 pi-durable v1.2.0 整体内容也跟着 pi主仓库一起升级了

这次 v1.2.0 是迄今最大的一次升级，主题只有一个：把"工具调用"做成一等公民。

1️⃣ 嵌套工具调用 新 API api.executeTool(name, args)：让工具调用工具。嵌套调用是独立的持久化 pi.tool 任务，归调用者所有，完整走一遍参数校验、ToolTask 钩子、输出限界和重放策略；实时进度在 http://pi.live.nestedTools，事件带 parentToolCallId。默认按调用位置记账，replay-safe 的调用者重跑时能重新接上自己的嵌套调用。

2️⃣ 结构化工具输出 工具声明 structuredOutputSchema、返回 structuredOutput，程序化调用工具拿到的是校验过的结构化数据，而不是让模型看的文本。bash 现在返回 { output, truncated, fullOutputPath?, exitCode }——非零退出也不再抛异常，而是带 exit_code 诊断的错误结果。

3️⃣ codemode：用脚本编排工具 新子路径 @earendil-works/pi-durable/codemode：模型写脚本，脚本把对话的工具编排成嵌套调用。脚本能挺过重启——从结果日志确定性重放、重新接上嵌套调用后继续跑。还能调 models.classify() 和 models.generateImages()（也是嵌套调用），并用 Lark 语法约束采样。

4️⃣ 延迟工具 + 工具搜索 工具可标记 deferred：不进模型的声明列表，由 @earendil-works/pi-durable/tool-search 的 tool_search 工具按需 BM25 搜索加载。工具多了以后，声明列表不再爆炸。

5️⃣ 图片支持 read 工具直接返回图片块（PNG/JPEG/GIF/WebP），@earendil-works/pi-durable/images 提供 Photon WASM 处理器：Node 里在 worker 线程准备图片（大图不阻塞事件循环），Cloudflare 有对应加载器。

6️⃣ 性能与内存（这才是本次的隐藏主角） • 文档数组追加：从每次提交全量遍历改为增量规划——3.2 万次单条追加 11.3s → 1.4s • 调度器扇出：500 个拥有的任务链 12s → 50ms；8000 个并行嵌套调用 18.8s → 2.7s • 内存有界化：调度器所有权索引只跟随活跃工作；文档缓存新增 documentRetentionMs（默认 10 分钟）——5000 个对话曾驻留 2.6 万个文档，现在为 0

⚠️ 迁移注意（破坏性变更）： • pi.tool 升级版本 2：ToolTaskInput/Result 改为 tagged union（{ kind: "model" | "nested" }），自动迁移在线任务 • ToolExecutionResult.content 改名 output，旁边新增 structuredOutput • 错误模型收紧：任何 Storage 方法抛错（包括读）现在会让整个 Session 失败（SessionFailed），不再重试；StorageRejected 移除，新增 StorageRequestError 只失败单次调用 • 纯展示写入提交立即落定，不再在收件箱排队——聊天消息发出即显示
