01｜Agent Infra 六步学习路径

来源（X） · @Jerry_fsy · 2026-10-22 19:52

想深入 Agent Infra，别只盯着 Prompt 和框架。

我落地过 2 个生产级 Agent。在这些项目中，我发现最难的不是模型本身，而是重试、状态管理、沙箱隔离和监控这些工程问题。Agent 能不能在生产环境中稳定运行，很大程度上取决于底层 Infra。

我把Agent Infra的学习之路拆成了 6 步，从 Runtime 一直到生产平台。下面是完整的学习路径。

开始前先说清楚 4 件事。
•这是一份公开的学习计划，大约按 6 个月的节奏走。重点是吃透，不比速度。
•Agent Infra 不是 AI Infra。这里不讲 CUDA，也不讲训练和推理。
•已经熟悉 Runtime 的人，可以跳过第 1 步。
•第 2 步最容易被低估。

6 步依次是 Runtime、可靠性、编排、沙箱、可观测与评估、生产平台。

1. 先自己写一个 Agent Runtime
目标：不依赖现成框架，搞懂 Agent 是如何完成一个用户任务的。

学什么：从零写一个 Agent Loop，也就是"思考、调用工具、拿到结果、再思考"这一圈。然后学 Tool Calling、Context Engineering、Streaming、State 和 MCP。可以跟着三元同学的 Super Agent 实战课走一遍，也可以跟着Datawhale的hello-agents做一遍（hello-agents链接：https://github.com/datawhalechina/hello-agents）。我这里只分享整体思路，不贴课程里的代码。
有个捷径是读 Pi 的源码。重点看 Loop、消息结构、消息发出的时机、session、缓存、compact、hook 和 MCP。底层的 LLM 封装可以跳过。

怎么练：搭一个最小的 Loop，跑通一个需要多个工具的任务。再对照 Pi 画一张图，标出消息什么时候发出、session 怎么存、什么时候触发 compact。

验收：你能讲清一次工具调用从头到尾发生了什么。只会调 SDK 可不算过关。

2. 可靠性靠设计，不用先学分布式
目标：进程挂了、网络断了，没跑完的任务还能接着跑。
我的结论是，入门不必先学分布式。可靠性是设计出来的。

学什么：HTTP、SSE 和 WebSocket，进程、线程和协程，还有队列、状态机、超时、重试和幂等。资料先看 System Design 101。MIT 6.1800 和 6.5840 挑需要的部分补。DDIA 先别硬啃。

怎么练：写一个能恢复的小型任务执行系统。杀掉进程再重新启动，做了一半的任务要能接着跑。
我特别看重两点。第一，重新启动一个Agent进程，任务也能接着跑。第二，失败要如实上报，不能当成成功吞掉。

验收：重启以后任务不丢失，重试不会造成重复的业务副作用，任务状态能对得上。

3. 从一个 Loop 升级到编排多个 Agent
目标：从管一个 Loop，升级到管多个子任务和多个 Agent。

学什么：Subagent 的任务分发、结果收集和上下文隔离，异步任务与并发控制，目标拆解与结果对齐，以及更高层的多 Agent 编排工具。

怎么练：把一个任务拆成 3 个子任务，跑通后汇总结果。再故意让其中一个子任务失败，看编排层能不能把整个任务收住。

验收：你能说清哪些工作该交给子 Agent，哪些该留在主 Loop。

4. 危险操作一律放进沙箱
目标：工具可以读写文件、执行命令。出了事，坏掉的是沙箱，不是宿主机。

学什么：入门阶段会用 k8s 调度就够了。入门可以先从 Container + Volume 搭建隔离环境，再逐步了解文件系统隔离、资源限制、网络策略和权限控制。

怎么练：给 Agent 配一个独立的沙箱，故意把里面的目录写坏。确认宿主机没有受影响，任务状态也还能恢复。

验收：危险操作默认在沙箱里执行。权限写在 Tool Definition 里，不靠 Prompt 求模型"小心一点"。

5. 先看得见 Agent 在做什么，再让它变好
目标：看得见 Agent 在做什么，并且能持续改进。

学什么：直接看 Langfuse。可观测（Observability）的核心，把轨迹、工具调用、耗时和失败原因都存下来。评估（Evaluation）是一条"先优化、再验证"的流水线，不是偶尔手动测两个用例。

怎么练：接入 tracing。固定 10 到 20 个用例做回归测试。每次改了 Prompt、工具或编排，都用同一套评估看结果变好还是变差。

验收：出了问题，能定位到是哪一步、哪个工具。每次改动都有改动前后的对比。

6. 把前 5 步拼成能上线的平台
目标：把前面几块拼成一个能上线的平台，而不是一堆 Demo 脚本。

学什么：读 FenixAgent的源码。编排、调度和 Agent 协议对接，都是生产里绕不开的脏活。

怎么练：对照 FenixAgent列一份缺口清单，包括调度、协议、多租户和配额，然后按优先级补。别一上来就把整套系统重写。

验收：别人照着文档，就能把你的服务启动起来并跑通。不能只在你自己的电脑上能跑。

02｜pstack 先验证再编排 Agent

来源（X） · @chenchengpro · 2026-10-22 20:16

读了 @poteto 的 pstack，记一些点。

1. pstack 不是 56 个单独的 skill，而是一套方法论和工作流。先做验证 skill 和 feature map，让 agent 能自己跑起并操作应用。再用 /poteto-mode 按任务类型走固定流程。最后才轮到并行和自动合并。第一步没做好，后面多开 agent 只会更贵，不会更可信。她演讲里的分法是，验证管"对不对"，pstack 管"好不好"。

2. 建验证的方法值得花时间。先把应用做成 CLI，命令能组合，破坏性操作带 --dry-run，输出 JSON，报错时告诉 agent 下一步怎么做。再建 feature map，每个功能写清从哪进、怎么用、CLI 怎么驱动、有哪些坑。她管这个叫"物化的记忆"。我准备先找个 demo 产品试一下，照着她的 Atlas 示例来。

3. 技术栈影响生产力，这点我深有体会。那 agent 友好的技术栈是什么？我目前的答案是轻、快、可调试、可控制。Electron 和 Web 有 CDP，iOS 有模拟器。运行时越难调、越难控，agent 越难用。她说值得为此自建调试工具，甚至换栈。

4. 补上下文的几个 skill 也值得一看。/teach 会调 /how 追运行机制，调 /why 去 git、PR 评论、Linear、Slack、Sentry 里查当初为什么这么写。/recall 从历史会话里捞上下文。还有 /in-your-own-words，让 agent 先用自己的话复述问题，理解偏了能早点发现。

5. 她反对对抽象计划做对抗式评审。原因是 agent 会臆想风险，给不会发生的边界情况加防护。她的做法是先做两三个可切换的原型，用验证 skill 截图测量。然后让几个模型家族各出一版类型签名级的设计，互相评判，挑一个再实现。我之前一直用对抗式评审，确实能想到很多 edge case，但也有不少是多余的。下次试试拿原型换掉一部分评审，看会漏掉多少。

6. 56 个 skill 里有 55 个禁了模型调用，Claude Code 的 Skill 工具会直接拒绝。镜像版建了一张映射表，让 agent 去读对应的 SKILL.md 照着做。能用，但 skill 之间每调一次都多一步，也多吃上下文。这方案比很多产品直接给你塞一堆模型可调用的 skill 好要多了。

7. 她视频里讲的外循环不在 pstack 里。Grok Bot 接了 Slack、Datadog、Sentry，订阅 Slack 线程和 Sentry 告警，自动派云 agent 去复现 bug、开 PR。她一个月 2,500 个 PR，主要靠这一层和验证，pstack 只占一小块。这层得自己搭。

8. 把反复纠正变成结构的四级顺序也值得一看。用架构或数据结构根除 > lint 或测试让 CI 拦 > skill 或规则 > 人工 review。第四级她直接标成 ngmi。她的 Dune 框架就是第一级的例子。每件事只留一种写法，看到坏模式先写 lint 止血，再让 agent 清理，让代码库一直保持"agent 照抄也不会错"。我打算挑一个 agent 老犯的错，用 /correct 试一次。

详细 research 见 https://research.sorrycc.dev/@sorrycc/pstack 。

05｜两层缓存组合降低 LLM 成本

来源（X） · @shao__meng · 2026-10-22 22:17

节约成本的两层缓存：Prompt Caching 复用前缀计算，Semantic Caching 复用整条答案

来自 @samuel_wong_ 在 @bytebytego 发布的内容，主要针对 LLM 应用里的两类缓存：Prompt Caching 复用共享前缀的 KV 计算，Semantic Caching 复用语义相近问题的整条答案。前者减输入成本，后者可能完全跳过模型调用。二者可叠加，但语义缓存的阈值、失效和适用范围要单独设计。
https://blog.bytebytego.com/p/llm-prompt-caching-versus-semantic

为什么要缓存
一次请求的费用来自输入 token 和输出 token。客服类应用里，系统指令、产品手册、历史对话往往远长于用户问题。重复出现在两类地方：同一份长文档被无数次送进模型；大量用户用不同措辞问同一件事。前者对应 Prompt Caching，后者对应 Semantic Caching。

Prompt Caching：复用输入处理
· 匹配规则是输入开头完全一致。模型先做 prefill，再做 decoding；前缀的 KV 状态可跨请求复用。
· 示例：两条请求共享「支持指令 + 产品手册」，只是问题不同。处理完第一条后，第二条可直接复用前缀的 KV。
· 共享内容必须放在前缀。因果模型里，后面的内容会改变前面文本的表示；时间戳、请求 ID 哪怕只放在开头，也会打断整段复用。
· 指令必须字面完全相同，措辞、文档顺序、请求设置都不能变。
· 费用不会归零：缓存写入通常更贵，读取更便宜。文中引用 Anthropic 的标准定价：缓存读约为普通输入的 1/10；5 分钟写为 1.25 倍，1 小时写为 2 倍。例如前缀原价 $1，则一次写 + 一次读 = $1.35，而不是 $2；读得越多越划算，从不复用则亏。
· 它主要省输入处理和首包等待时间，不省生成长答案的工作。

Semantic Caching：复用答案
· 通常做在应用层或独立服务：用嵌入模型把问题变成向量，检索相近的历史问答；命中则直接返回缓存答案，未命中再调 LLM 并可能写入。
· 命中时跳过整次 LLM 调用；未命中则多付一层嵌入与检索成本。
· 难点是相似度阈值：严则命中率低，松则可能答错。相近但不该复用的例子包括：发货前取消 vs 发货后取消；Basic 套餐 vs Pro 套餐；否定词、数字、日期、版本差异。相似度分数不等于正确概率，需要用标注集评估阈值，并同时看命中率和答案合适率。
· 不能只看问题文本。订单状态、指代、语言、权限、产品版本、对话状态都要进元数据过滤，不能指望嵌入模型从问题里自己推断。
· 失效策略：TTL（短但到期前仍可能过期）、版本号（整库失效简单但粗暴，按依赖文档选择性失效更优）、以及指令/格式/模型行为变更时的失效。Prompt cache 的失效不同：前缀一变，旧 KV 从变更点起就不能用；但应用若继续塞旧政策进 prompt，缓存本身不会发现业务规则已变。

如何一起用
推荐顺序：先精确匹配缓存 → 再语义缓存 → 未命中再走 LLM，并尽量吃到前缀缓存。需要校验源数据版本的检查应放在更前面。行动类请求（如「订阅已取消」）绝不能用缓存文案代替真实操作。

方案选型
· Prompt Caching：共享手册、稳定工具定义、长对话历史，但每个问题仍要新鲜答案。
· Semantic Caching：FAQ、稳定说明；不适合强个性化、事实变化快、或需要新鲜创意输出的场景。

06｜MemoryTax 强模型削弱记忆框架

// MemoryTax：Agent 记忆的苦涩教训 //

对 Agent 构建者来说是很好的洞见，建议收藏。

随着模型能力的提升，它们在记忆生成等方面也变得更强。

如今 Agent 记忆框架遍地开花。这项研究测量了当模型本身能够搜索原始历史时，这些框架是否还有帮助。

研究结果表明，强大的模型需要更少的设计化记忆，以及更好的工具来搜索原始记录。

在一个 419 轮的 LoCoMo 对话中，Mem0 仅在使用 GPT-4o-mini 时才胜过朴素的全上下文方案。构建 Mem0 的记忆成本比一整轮全上下文运行还要高。

使用 Claude Opus 5.5，Pi 编码 Agent 搜索原始历史在不到全上下文一半成本的情况下得分为 99%。其唯一一次失误来自于错误的答案参考。

记忆还有一个由写入它的模型所设定的上限。更强的读取者无法恢复更弱的写入者所遗漏的内容。

作者明确界定了范围：一次对话，每个单元格一次运行。在添加记忆层之前，用你自己的 Agent 重复这个实验仍然是一次成本很低的尝试。

// MemoryTax: The Bitter Lesson of Agent Memory //

Great insights for agent builders; bookmark it.

As models increase in capability, they also improve at things like memory generation.

Agent memory frameworks are everywhere right now. This study measured whether they still help once the model can search raw history itself.

The results suggest that a strong model needs less designed memory and
better tools for searching the raw record.

On one 419-turn LoCoMo conversation, Mem0 beats plain full context only with GPT-4o-mini. Building Mem0's memory costs more than an entire full-context rollout.

With Claude Opus 5.5, the Pi coding agent searching the raw history scores 99% for under half the cost of full context. Its one miss comes from a wrong answer key.

Memory also has a ceiling set by the model that wrote it. A stronger reader cannot recover what a weaker writer left out.

The author clearly defines the scope: one conversation and one run per cell. It is still a cheap experiment to repeat on your own agent before adding a memory layer.

07｜freehire 直连 ATS 去重岗位

来源（X） · @kafkaup · 2026-10-22 22:08

招聘聚合站最大的问题从来不是岗位少，而是同一个职位被中介重发四遍，点进去还是个失效链接。

freehire 的思路是绕开中间商：直接爬公司自己的 ATS——Workday、Greenhouse、Lever、Ashby、iCIMS 以及一长串尾部平台，共 124 个 ATS、320 个数据源，每条岗位都链回原始发布页。

▸ 归一化成同一套 schema，按稳定 key 去重，三个 board 上的同一个坑合并成一条
▸ 用 Meilisearch 做分面检索，地区、远程模式、级别、技能、薪资都来自人工维护的词典，不靠模型瞎猜
▸ 存储是 Postgres 加 pgvector，DB 访问用 sqlc 生成，不上 ORM
▸ 爬取、富化、索引、通知全部拆成 run-once worker，跑完就退出，直接丢给 cron
