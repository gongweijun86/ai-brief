02｜Sutton 纠正苦涩教训唯算力误读

来源（X） · @dotey · 2026-11-10 14:24

在 X 上有一点好就是总能看到大神们论道，比如这一段关于“苦涩的教训”的讨论。

今天很多大语言模型信徒们经常拿着《苦涩的教训》当圣经，认为“只要无脑堆算力、堆数据就够了，不需要什么新算法”。而作者 Sutton 本人的这条推文，以及 Prashant Rai 的精辟回复，正是对这种解读的一种纠偏。

《苦涩的教训》讲的是 AI 历史上那些依赖人类专家知识的精巧设计，最终都败给了利用海量算力的通用学习方法。

但这经常被解读为“唯算力论”，认为只要加大数据量、加大模型参数和算力就能实现 AGI。

作者 Sutton 这次发推：
> “光靠暴力计算（Brute force computation）不足以实现真正的智能。我们需要巧妙的新方法（Clever new methods）。在我看来，AI 这门科学还远未终结。”

Prashant Rai（芬兰的自动化博士，做非公路场景的自动驾驶）的转发，也可以看作是一种解读：
> “《苦涩的教训》常常被误解为是在反对‘算法上的精巧创新’，但它真正反对的，其实是把人类自己的小聪明‘硬编码（Hardcoding）’进系统里。”

这句话极其精准地切中了问题的要害，区分了两种截然不同的“聪明”：

一种是错误的聪明，也就是把人类的知识硬编码进去。

比如说人类觉得自己懂国际象棋，于是把棋谱口诀写进代码；人类觉得自己懂语法，于是搞出复杂的句法树规则教 AI 说话；自动驾驶里人类写满几万条 if-else 规则。

这才是《苦涩的教训》批判的对象。这种做法上限极低，一旦算力上来，端到端的神经网络直接把这些人工规则碾得粉碎。

另一种是正确的聪明，是在算法与架构层面的精巧创新。

比如说设计出能够随着算力增长而不断变强（Scale with compute）的通用学习机制。像反向传播算法（Backpropagation）、卷积神经网络（CNN）、Transformer 架构、蒙特卡洛树搜索（MCTS）、时序差分学习（TD Learning）都是属于这种。

这些正是 Sutton 所呼吁的“巧妙的新方法”。没有 Transformer 这个极其精巧的算法/架构创新，给你十万张 H100 显卡，你也训不出 ChatGPT。

03｜Agent 权限设计采用严格 ACL

来源（X） · @zcswl7961 · 2026-11-10 17:07

今天在工位上处理了一个 Agent 权限设计的架构方案，顺手和组内的实习生对了对。

他设计的 Agent 工具调用逻辑（开发Tools的时候），直接用的是系统管理员的全量数据库权限，理由是“这样 Agent 查数据方便，不容易因为报错断掉”。

我跟他说，企业级 Agent 开发里，最难的从来不是怎么给 Agent 喂权限，而是怎么做 Strict ACL（严格访问控制）。

怎么实现基于 Role-Based 的工具动态注入？怎么在 Agent 企图调用写接口时插入 Human-in-the-loop（人工二次审批）？怎么保证 Agent 帮 A 用户办事时，绝不可能调出 B 用户的敏感向量？

把权限体系和审计日志在 Agent 架构里嵌入进去，才算懂 ToB 的规则。

不搞权限隔离的 Agent，在企业安全团队眼里就是一颗随时爆炸的定时炸弹。

05｜Claude 四模型按任务分档选型

来源（X） · @xulijian1994 · 2026-11-10 08:39

Anthropic 发布了 Claude 四大模型的官方最佳实践，15 分钟的文章，给大家整理个省流版。

一、什么任务用什么模型？

1. Fable 5.2：架构设计、大型重构、系统迁移、深度研究、长期运行的 Agent。
2. Opus 5.5：日常编程、复杂调试、多文件开发、电脑操作。
3. Sonnet 5.5：修 Bug、按需求开发、文档/PPT/表格、聊天、重复性任务。
4. Haiku 5.5：文件搜索、日志分析、信息提取、分类整理、简单子 Agent。

二、实用技巧

1. 日常开发：Opus 5.5 + medium effort。
2. 遇到难题：先让模型运行测试自检，再提高 effort，最后升级模型。超过 high 可以直接试更强模型的低 effort。
3. 多 Agent：Fable/Opus 当主 Agent，负责规划、决策和关键代码修改；Sonnet 并行处理明确的子任务；Haiku 负责找文件、读日志、跑测试。
4. 省钱：低 effort 先执行，失败的任务再提高 effort 重试。
5. 成本：Fable Token 单价是 Opus 的 2 倍，但部分高难度任务的总成本反而低约 50%。
6. Haiku：提示词超过 100K Token，单价上涨 5 倍。
7. 切换模型：先 /compact 或开新会话，减少缓存重建成本，跨模型切换还可能丢失之前的思考内容。
8. 多 Agent：简单任务别用，协调开销可能比节省的还多。
9. API 开发：注意 Thinking、工具调用和历史消息的兼容性，不能只换模型名称。
10. 最终选型：拿真实任务对比成功率和总成本，不要只看模型跑分。
