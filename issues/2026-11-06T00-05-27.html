01｜Claude Code 三模型分工架构

来源（X） · @HeLi8866 · 2026-11-05 09:19

这真的是一座金矿！

Anthropic 刚分享了一个 Claude Code 的超好用技巧。

思路很简单：同时跑 Sonnet、Haiku 5.5 和 Opus 5.5，每个模型只干自己最擅长的活。

效果更好，token 也省很多，因为每个任务都交给了最合适的模型。

启动 Claude Code 时这样写就行：

claude --model sonnet --advisor opus

分工是这样的：

→ Sonnet 5.5 负责主会话，写代码、改 bug

→ Haiku 5.5 并行扫整个代码库，负责搜索、grep 和检查改动

→ Opus 5.5 当顾问，只在关键决策时出手，最后审核改动

→ 不需要 Opus 的活，就不再浪费它的上下文

Opus 只在三个时候介入：

- 计划敲定之前

- 同一个错误出现第二次的时候

- 宣布完成之前

Sonnet 负责写，Haiku 负责查，Opus 负责审。

JEV 工程也是同样的思路，只是再往下一层：不需要动脑的小选择，比如用哪个文件、哪个工具、重试还是停止，交给 JEV 毫秒级处理，大模型只处理真正需要判断的问题。

完整结构：

> Sonnet 5.5 跑主会话，统筹整个任务

> search 用 Haiku 5.5 梳理代码库，只读不改

> grep 用 Haiku 5.5 查找调用位置，单独占一个上下文

> audit 用 Haiku 5.5 在临时工作区检查改动

> Opus 5.5 当顾问，在最终确认前审核汇总后的改动

> JEV 毫秒级处理小分支选择

把这个结构和下面这段提示词一起贴进 Claude Code：

"按这个结构重新配置我的 Claude Code：
1. 主会话用 Sonnet 5.5，Opus 5.5 当顾问。
2. 在 .claude/agents 里建三个 Haiku 5.5 子代理：search（梳理代码库）、grep（查找调用位置）、audit（检查改动）。
3. 给 audit 设置 worktree 隔离，让它的检查不碰我的工作分支。
4. 在 CLAUDE.md 里加一条规则：所有代码库搜索和测试都交给 Haiku 5.5 子代理，让主上下文保持精简。
5. 快速、确定性的小选择（选工具、选路径、重试）交给 JEV 处理。
所有改动先用 diff 给我看，我说开始之前不要动任何文件。"

官方文档：http://code.claude.com/docs/en/sub-agents

建议先收藏，迟早用得上。

03｜Claude Code 识破充电宝窃密

来源（X） · @ChrisSlacker · 2026-11-05 12:47

用户通过 Claude Code 在一个广州买的杂牌充电宝里发现了隐藏芯片。

每次给 iPhone 充电，它都在偷偷复制整部手机的数据。还会读取 Wi-Fi 密码，连接家庭网络，把所有信息发送到远程服务器。

这个充电宝 3 周前在机场花 19 美元买的，30000 mAh 标注，沉甸甸的没牌子。

首次插入时屏幕问'信任此计算机'，用户没想就点了信任，结果一键给了它读取所有数据的权限。

今早设置 Claude Code 监测文件读取，充电 10 秒后屏幕就闪黄红警告——数据在传输。

充电宝被识别为自带 64 GB 存储和网络连接的小电脑。

普通充电线只用电源线，这个同时用电源线和数据线，已复制：

→ 设备信息、1206 个通讯录号码
→ 全部应用含 2 个银行 app
→ 3912 张照片含护照
→ Wi-Fi 名称和密钥
→ 妻子 iPhone 照片

每次充电就用密钥上网发送新数据，3 周上传 19 次，最后一次昨晚 2:14 发送。

用户立即拔线，通过 Claude Code 阻止那个 IP，改了 Wi-Fi 密码和银行 app 登录信息。

04｜TikTok 逆向揭示推荐算法机制

来源（X） · @vista8 · 2026-11-05 23:37

我去，这个 TikTok逆向有点意思，对推荐算法有了新认知！

1. TikTok 手机端有 25+ 个 AI 模型。

用来判断什么内容能让用户持续刷下去。

2. 视频播放前已打好“推荐分”

服务器预先给每个视频计算“推荐分”，即预测用户“跳过、看完、点赞、打开评论、关注创作者” 的概率。

3. 实时采集用户状态（50+ 变量）

每次请求新一批视频时，App 会带：
① 陀螺仪/运动传感器，判断用户状态（走路、躺下、在车里）
② 电量、是否在充电、屏幕亮度、是否静音等 50+变量

甚至输入但没发送的消息也会被收集，因此吃中午饭和睡前躺床上刷的内容会不一样。

4. 用户可能流失时，模型会介入

① 有一个模型如果预测到你会跳过其他已加载视频，手机就会请求“紧急批次” 视频来重新吸引你。

② 如果扔持续跳过，TikTok 会标记为“失去专注”，最后手段是给你的信息流里推一条直播。

③ 会根据你多久没摸屏幕、是否躺着判断你是否打瞌睡。

④ 有模型预测你“下次打开 App 的时间”，以便提前后台启动、缓存视频做准备

内容来源于视频作者说法，未实测。

想想还挺追求极致的，比如预测下次打开提前缓存，牛逼！

但也不是那么黑盒，一些方法是能想到。

06｜kimi-k3-in-c 无显卡跑大模型

来源（X） · @Ryrenz · 2026-11-05 23:40

🤯 震惊，kimi-k3-in-c 居然能让一台没显卡的普通电脑，跑起 2.78 万亿参数的 Kimi K3 大模型。

kimi-k3-in-c 在 GitHub 三个月狂揽 1 万多 star，已经有人把它移植到 Mac、改写成 Rust、补上 Metal 后端，围着它长出一片周边。

以前想在本地碰一个顶配大模型，门槛是几块专业显卡加一柜子显存，个人根本玩不起。它用纯 C99 把整套推理重写了一遍，不依赖 BLAS、不依赖任何深度学习框架，编译出来的引擎才 176KB。

办法是把权重边读边算：稠密主干和专家分开流式加载，笔记本档位实测峰值内存压到 8.24GB，一台 16G 内存的机器就能慢慢跑，内存越大只是越快，不同档位输出逐字节都一样。

一个人用一门最朴素的语言，把「万亿参数必须上集群」这条常识给掀了。
