03｜pi-charter约束AI编程全流程

来源（X） · @AISuperDomain · 2026-11-13 23:05

AI 写代码最危险的，不是写不出来，而是它告诉你“已经完成”，却没有人真正验证！

pi-charter 是一个专为 Pi Coding Agent 打造的 Spec-driven 开发框架，试图解决 AI 编程中最重要的问题：如何让 AI 的开发过程真正可控、可验证。

它将开发拆成一条由代码强制执行的流水线：

需求定义：与 AI 共同编写 Brief 和 Spec，将需求拆成明确的验收标准。
人工审批：必须由你亲自批准，模型不能自我授权。
多 Agent 实现：独立 Agent 负责编码，自动运行测试、Lint 和类型检查。
独立审计：另一个 Agent 逐项验证验收标准，不能直接修改项目代码。
自动优化：可选 Refiner，在限定范围内简化代码。
结果报告：根据真实测试结果、审计证据和人工决策生成报告，而不是让 AI 自己宣布成功。

更重要的是，它支持 Spec 冻结、Git 检查点、自动回滚、失败修复预算和并行审计。

它真正想做的，不是让 AI 写更多代码，而是让 AI 编程从「相信模型」走向「用工程机制约束模型」。

GitHub：https://github.com/win4r/pi-charter

04｜leanrea轻量逆向省下token开销

来源（X） · @zg0820 · 2026-11-13 21:40

11 月 8 日那条「AI 逆向工具梳理」有 31K 曝光，但它只说了有什么。这篇写怎么用，下面每条命令都从各项目 GitHub README 抄下来对过。

先分清手上是什么，别一上来就装十个：APK / XAPK 走 Android 线，网页 JS 的混淆签名走前端线，原生二进制和 Electron 走通用底座，CTF 题走题型线，想复刻公开产品走产品分析线。常驻工具定义会吃掉上下文，装得越多每轮越贵。

1. 最轻的底座是 aicodeking/leanrea，一个 8KB 的 SKILL.md，不起 MCP 服务。npx skills add aicodeking/leanrea -g 装到用户级，npx skills add aicodeking/leanrea -g -a '*' -y 一次覆盖所有 agent，升级用 npx skills update leanrea。README 里给了对照：同任务它 34.5k tokens / $0.09，REA 带 MCP 是 400.7k tokens / $1.60，跑分 74/75 对 75/75。

2. 要跨目标、要证据链，再上 morluto/rea。npx rea-agents setup 是交互式，选完 agent、审完改动再批准，装完重启 agent；常用就 npm install --global rea-agents。单次分析不必装全局：npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json。它接得住 JS、Electron、原生二进制和 .NET，也会标出哪步是推断、哪步有实据。

零散查一次用 leanrea，长期跨目标反复查再上 REA，这个顺序别反。

07｜AWS七层插件化Agent参考架构

来源（X） · @snwiki238337 · 2026-11-13 18:33

AWS 发布了一套可插拔 agent 参考架构，有点像 dsh 的插件化理论。

这篇文章要解决的核心工程是为什么很多团队做出来的多 agent 原型演示时很顺利，但是生产环境容易出问题。

原因往往在于做原型时大家习惯把模型名称、子 agent 的调用地址、数据库查询逻辑全部写在业务代码里。

等到上生产需要控制成本换小模型、过安全合规审查或者排查线上故障时，修改一些地方容易导致一些不可言说的问题出现。

AWS 这套方案的核心思路，就是把智能体系统拆成七个插件化独立的层，层与层之间只通过固定的接口契约和配置中心通信，确保换掉任何一层的组件都不会影响其他模块。

根据他们给出的电商售后参考实现，可以很清楚地看到这套解耦思路是怎么一步步落地的。

第一步是把模型和业务逻辑拆开。在底层的数据和推理层，系统没有让后面的 Agent 直接去绑定某个厂商的 SDK，而是通过 LiteLLM 搭了一层统一推理接口，并把当前启用的模型 ID、退货政策知识库 ID 等全部注册到配置中心（SSM）。

后续无论是想把简单任务切给便宜的轻量模型，还是把推理后端从 AWS 原生服务换成第三方托管平台，只需要在配置层改一个字符串，上层的智能体代码一行都不用动。

第二步是在编排层解决总 agent 与子 agent之间的硬编码耦合。如果总 Agent 代码里写死了各个子 Agent 的地址，每次业务部门新加一个专职 Agent 都得去改总 agent 代码。

这里的做法是引入一个注册表和统一工具网关。各个专职子 Agent 部署后自己往注册表里登记能力，总 Agent 在收到用户请求时，通过运行时 harness 动态去注册表里发现可用的子 Agent 并通过 A2A 协议派发任务。

而子 Agent 去查数据库或知识库的底层工具调用，则全部收口到统一网关做精细的权限校验。这样一来，子 agent 的增删改就变成了热插拔。

第三步是怎么在不污染业务代码的前提下，把隐私和一些比如故障排查的善后工作加上去。

在真实售后场景里，底层工具从数据库查出订单详情后，里面往往带着用户的真实邮箱、电话和家庭住址，如果直接把这些原始数据塞回给总控大模型，很容易引发隐私泄露或提示词注入。

这套架构是在统一网关上挂了一个拦截器，就是说工具返回的数据在送达大模型之前，先在网关被拦截下来，自动过一遍把敏感隐私字段打码脱敏，再交给上层继续推理。

同时，由于所有跨层调用都遵循统一的接口，分布式追踪能把一次对话从前端入口、总控分发、网关拦截到数据库查询的耗时和 Token 账单完整链接起来。

一旦出现了某些问题的话，对于问题的排查就会很简单。顺着链路一眼就能看清到底是知识库没召回、模型算错了日期，还是说是别的问题。

github：https://github.com/aws-samples/sample-pluggable-agentic-ai-framework

原文：https://aws.amazon.com/cn/blogs/machine-learning/pluggable-agentic-ai-framework-a-seven-layer-composable-enterprise-agentic-ai-reference-architecture-on-amazon-bedrock-agentcore/

08｜Pi Extension自动路由多模型

来源（X） · @xiaomovps · 2026-11-13 17:09

Pi Agent 现在连模型切换都可以自动化了，而且用的还是国产模型🔥

最近 Hugging Face 联合创始人 Julien Chaumond 分享了一个挺有意思的玩法，通过 Pi 的 Virtual Models，把 Qwen、Kimi 和 GLM 三个模型整合到了一起

以前我们使用 Pi，基本都是根据任务自己手动切换模型，现在他直接做成了一套自动路由系统

整个思路其实很简单：

简单任务优先交给本地运行的 Qwen 3.8 27B，遇到比较复杂的问题，再自动切换到远程的 Kimi K3 或 GLM-5.3

甚至连电脑的运行状态都考虑进去了，如果本地负载比较高，就直接跳过 Qwen，把任务交给远程模型处理

最有意思的是，整个过程不需要修改 Pi 的核心代码，只需要通过 Extension 实现，最后把这些模型包装成一个 hybrid/auto 虚拟模型，正常选择使用就行

我平时使用 Pi，也经常在 GPT 和 DeepSeek 之间切换，主要就是为了兼顾模型效果和 Token 成本

其实以后完全可以参考这种思路，让 Pi 自动判断任务复杂度，简单任务用便宜模型，复杂任务再调用更强的模型

这也算是 Pi 极简架构的一个优势，很多功能不需要官方去做，社区通过 Extension 就能自己实现

不过最终到底能节省多少成本，还得看实际任务表现，自动切换也不一定就比固定模型更划算
