01｜Storybound单人开发月入10万

来源（X） · @Bengz168 · 2026-11-05 20:45

去年我用 67 天、一个人靠 Claude Code 做出了 AI 视频创作 SaaS，叫 Storybound。同一套东西跑了两条收入线：自己运营视频号，同时把软件当产品卖。

视频号从 1000 粉涨到 17 万粉，单月带货 GMV 14 万、佣金 7 万以上；软件公测前就有 73 个付费用户，累计订阅 3 万多元。第一次做到"自己跑号 + 卖软件"月入 10 万，投入产出比约 22 倍。

技术栈不复杂：Tauri 客户端 + Cloudflare Workers 服务端 + 一个管理后台，一个人就搭出了完整产品。省力主要靠一套工程化打法：用 CLAUDE.md 沉淀项目约定、用 Memory 记上下文、用 Subagent 拆任务、用 Skills 固化常用动作，再配合 Vibe Coding 快速试错。

商业上我走的是"一鸡两吃"：先自己 dogfooding，把工具用在真实业务里，验证价值后再包装成 SaaS 卖。这样产品方向和收费点都不是拍脑袋定的。

给想试的人三条建议：第一，先有一个自己每天在用的真实场景，再谈产品化；第二，让 AI 替代的不只是"写代码"，而是整个协作流程，把流程教给工具；第三，先用最小版本收第一批付费用户，再迭代。

02｜LangChain Agent异步化架构

来源（X） · @yibie · 2026-11-06 13:26

Agent 正在从同步变异步。过去一个 agent 跑在单条 ReAct loop 里：模型调一个工具，死等结果，再决定下一步。工具或子任务一跑就是几分钟，整条 loop 被堵死，你发的新消息只能在后面排队。

LangChain 这篇文章讲的变化，是把 agent 拆成前后台两层。一个编排者留在前台跟你对话，长任务丢给后台子 agent 跑。Claude Code 默认在后台跑子 agent，OpenAI 和 DeepSeek Harness 也是类似的路由加后台 worker 结构。

关键区别在调用方式。老式子 agent 像一行 await，不返回就卡住。async 子 agent 像 asyncio.create_task，或者一个没 await 的 Promise：调用立刻返回，活在独立线程跑，结果稍后回来。于是 agent 能同时接的工作量，跟着后台 worker 的数量涨，而不是被一条 loop 的长度限死。

编排者靠五个工具管住这些后台任务：start_async_task 启动，check_async_task 查状态和结果，update_async_task 发新指令，cancel_async_task 停掉，list_async_tasks 列出全部。

运行中改任务有两种策略。默认 interrupt 是打断当前运行、带着新指令重启，适合“改用 Postgres”这种纠正。enqueue 是把新指令攒着、等这轮跑完再执行，适合“跑完顺手把测试跑了”这种追加。

结果怎么回来也分情况。编排者正忙，它会在每次调模型前扫一遍未完成任务，中途把结果捡走。它闲着，子 agent 会唤醒一轮新运行。它正卡在等你审批，审批不动，等你答完结果才到。需要审批的子任务在自己线程里等，不打断前台；在 Slack 的 Managed Deep Agents 里，请求会发回原帖线程。

怎么用，其实就一个字段。在 Managed Deep Agents 里给子 agent 加 async: True：

subagents=[
{
"name": "researcher",
"description": "Researches a topic in the background.",
"async": True,
},
]

Python 和 JavaScript 版 Deep Agents 都已支持。每个托管 agent 还会自动得到一个通用子 agent 的 async 副本，运行时自己决定把活放前台还是后台。要注意任务通知还在 beta，API 可能变。

03｜Uber Spark写入提速至5.5倍

来源（X） · @shao__meng · 2026-11-06 16:44

Uber 如何加速 Spark：从查询计算，优化到数据写入

来自 Uber Engineering 分享的两条 Spark 加速路线：Gluten/Velox 已用于部分生产任务，Quanton 则进一步优化湖仓数据写入。后者在实验室测试中取得约 4.7—5.5 倍的稳态写入加速，但尚不能等同于生产收益。

# 为什么只加速 SQL 不够

Spark 是大规模数据处理引擎。Uber 仅将数据摄入湖仓，就需要超过 20 万个 CPU 核，因此小幅效率提升也可能带来可观收益。

问题在于，工作不只是执行 SQL，还包括读取旧数据、合并更新、写文件和维护表结构信息。Uber 约有 1.72 万张表使用 Hudi——一种支持数据湖增量更新的表格式，这些写入和维护环节同样需要优化。

# 两条路线有什么不同

Gluten/Velox 优化计算执行。 它将 Spark SQL 算子交给原生向量化引擎，一批数据一起处理，减少逐条执行的开销。Uber 报告，已迁移的生产负载运行速度约为原来的 3.5 倍，CPU 成本降至约 1/3.4。落地还涉及缺失功能补齐、兼容性和回退机制，并非直接替换即可。

Quanton 进一步优化数据读写。 这是 Onehouse 的商业 Spark 引擎，除向量化外，还针对湖表的读写、合并、索引和维护优化。虽然它支持 Hudi、Iceberg，Uber 本次只评测了 Hudi 写入路径，没有测通用 SQL 或读取性能。

# 关键结果该怎么看

相同计算资源配额下，Quanton 在插入为主的事实表上，稳态写入轮次的中位速度约为开源基线的 5.5 倍；更新为主的维表约为 4.7 倍。

但这些数字排除了周期性的元数据整理轮次；包含整理的轮次，加速约为 2.8 倍。收益也不均匀：数据表写入阶段约快 7.8 倍，去重和索引部分却略慢。

以上来自合成数据和受控集群。生产环境的正确性、兼容性、持续负载表现及故障恢复，仍需进一步验证。

06｜大模型三层缓存从KV到应用层

来源（X） · @Jerry_fsy · 2026-11-06 16:54

自底向上梳理一下常见的Cache
从最底层到最上层，常见的Cache有：
1.KV Cache
2.Prompt / Context Cache（提示/上下文缓存）
3.应用层缓存

下面具体讲解一下：
1.KV Cache：
Transformer 模型在处理每个 token 时计算出的注意力状态（Key/Value 张量）。有了这个KV Cache缓存后，在生成每一个新token的时候，模型不需要计算之前所有token的Key/Value值，因此将计算复杂度从近 O(n²) 降至 O(n)。
KV Cache是底层数据，上面的Prompt / Context Cache（提示/上下文缓存）是利用KV Cache的一种机制。

2.Prompt / Context Cache（提示/上下文缓存）：
可以跨请求复用相同提示词前缀的KV Cache结果，本质上是前缀缓存（Prefix Caching） 的产品化封装。假如多个请求的前缀相同时，可以复用这些Cache，从而减少首token的输出需要时间，优化体验。

3.应用层缓存：
这一层缓存至少有3种情况：
（1）应用层响应缓存
即达到一定的匹配条件后，直接复用已有的模型回复，而不用再调用大模型。
常见的匹配方法有：精确匹配缓存和语义缓存。前者是哈希值这种完全匹配才行，后者是语义相似度达到一定的阈值即可。
（2）嵌入缓存
缓存embedding模型的输出结果，让相同或者相似的输入复用已经获得的embedding模型输出。
（3）检索结果缓存
对于RAG服务，相同的查询复用已有的查询结果，减少重复查询需要的时间。
