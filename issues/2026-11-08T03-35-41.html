01｜音频接收模块改造老音箱上网播放

来源（X） · @mr_mr122497 · 2026-11-08 10:53

花不到二十块，我把家里那对吃了五年灰的老音箱救活了，现在它每天早上七点自己开口报天气。

起因是搬家，翻出一对有源音箱，2.0 那种，插根 3.5mm 就能响。扔了舍不得，接电脑又懒得专门拉一条线过去。后来花了不到二十块，买了块最小号的音频接收模块，塞进音箱后面原本装电池的空格里，供电直接从音箱自己的 USB 口取，连充电头都省了。

做起来就三步。第一步，把老音箱背后那块小盖板卸了，找到 AUX 输入线和供电脚，本质就是把它当成一个"哑巴喇叭"，音源我们自己喂。第二步，模块刷一段现成固件，连上家里 2.4G Wi-Fi（别连 5G，很多便宜模块不支持），设备名改成"客厅音箱"。第三步，手机、平板、电脑里随便哪个 App 放歌时，点一下输出设备就行，不用再摸线。

踩的坑有两个。一个是老音箱电源滤波太差，模块一接上就有一层很轻的电流声，后来在供电线上串了个小电感才安静下来；嫌麻烦的话就单独用一个充电头供电，隔离得更干净。第二个是音量映射，模块一推到底容易爆音，正确做法是把音箱自己的旋钮打到七成，让模块只负责"给信号"，音量交给音箱本体。

为什么不干脆买个新的智能音箱？因为这对箱子的喇叭单元一点没坏，我听过同价位的新品，中频比它糊。坏的不是硬件，是我们不再愿意拉那根线——这点小麻烦，二十块以内就能解决。现在它既是手机外放，也是床头电台，早上定点播新闻，晚上放白噪音，比我原来那台只能放歌的蓝牙音箱实用。

还有个意外收获：因为音源是网络设备，可以写个定时任务让它几点播什么都没问题，等于白捡了一个"语音管家"，只是一句话不说，直接开播。

想问问你们：家里那些"还能响、就是不方便接"的老音箱，你是直接扔了，还是留着塞在哪个角落吃灰？

03｜H3 Flash 13.7B模型单卡可跑

来源（X） · @servasyy_ai · 2026-11-08 10:43

卧槽，这帮神人居然真把 31B 的 MiniMax H3 给硬砍到 13.7B 了？？？

单张 4090 在本地就能直接跑这套模型，推理不用 CFG 引导，6 步采样就能直出 1080P 级音画同步视频，这下屯多卡机房的人真要麻了。

以前我们在本地跑 MiniMax H3 原版，31B 参数要占 62GB 权重，跑一条几秒的视频动辄需要几十步采样，单张消费级显卡基本只能干瞪眼。

我刚扒了下 Video Rebirth 团队放出的 HyperFlow H3 Flash，他们这次完全没靠加速 LoRA 糊弄事，直接对着 31B 底模动了三刀手术：

第一刀，他们做了结构剪枝加低秩分解。
他们直接砍掉冗余 Block，对上百个线性层做低秩分解，把 31B 的庞然大物硬生生压到了 13.7B。

第二刀，他们加了双时间步条件注入。
他们给每个 Token 同时喂入当前噪声步和终点步，直接废掉了传统的 CFG 引导。现在我们不用写负向提示词，把 CFG 锁死 1.0，跑 4 到 8 步（默认 6
步）就能跑出 1344x768 的 24 帧画面，还能同步直出 32kHz 立体声音轨。

第三刀，他们把 GGUF 与旋转 INT8 量化落地了。
他们放出了全套量化权重，我们接上 ComfyUI-GGUF
和专用节点就能把模型塞进现有工作流，直接跑文生音画（T2VA）、首尾帧控制（FL2VA）和多图参考（REF2VA）。

如果你准备在自己的 4090 或 5090 上拉下模型来跑，你有三个实操细节必须先排雷：

你千万别被 9.1GB 的权重体积骗了

Q4_K_M 的 9.1GB 只包含视频 Transformer 本体。我们把整条管线跑起来，还得外挂一个 Qwen3-VL-32B 的文本编码器（哪怕用 nvfp4_awq 量化版也要占
15.7GB），另外还要加载视频和音频两个 VAE。

4090 显存有一条真实水位线

24G 显存的 4090 跑 Q4_K_M，峰值显存基本顶在 22G 到 23G 的红线上。
如果你的机器系统内存只有 16G 或 32G，你启动 ComfyUI 时必须加上 --fast-disk参数，靠系统页面缓存做流式卸载才不会爆内存。

实测跑一段 5.2 秒的音画同步视频，4090 大概需要 130 到 150 秒，5090 能把耗时压进 92 秒左右。

GGUF 与 Python 包各自有不同的能力边界

你想用多参考模式（REF2VA）喂视频和音频参考素材，就必须走他们官方的 Python INT8 包；
目前 ComfyUI 的 GGUF路线在多参考模式下只吃图片输入（最多支持 9 张图，你在提示词里用 <Picture 1> 按顺序指代）。

手里有 4090 和 5090 的朋友赶紧先把仓库存下来去跑一轮。

05｜Claude 用做梦机制整理跨会话记忆

来源（X） · @dotey · 2026-11-08 11:21

Anthropic 拆解智能体记忆：Claude 边干边记，再靠“做梦”回头纠错整理

Anthropic 工程团队 11 月 6 日发文，讲他们怎么给 Claude 设计跨会话的记忆。难点在于：Claude 得在当下决定什么值得记，可它并不知道以后会用到什么。

他们的办法是加一个后台步骤，叫“做梦”（dreaming）：会话结束后，让 Claude 回头翻原始对话记录，改掉记错的笔记，把零散笔记整理成更好找的形式。这有点像人睡觉时大脑回放白天的经历，把一部分沉淀成长期知识。

• 新模型明显更会用记忆：在一个查数据库答题的测试里，Sonnet 4.6 有记忆只从 0.330 涨到 0.364，Opus 5 从 0.564 涨到 0.828（满分 1）
• 玩宝可梦红版，Sonnet 3.7 写了 413 个记忆文件，只拿到 1 枚徽章；Fable 5 只写了 10 个文件，拿到 4 枚
• 一条记错的笔记经“做梦”改正后，Claude 走出了月见山；没改的那次三次掉回原路，最后也没到下一座城

【记忆分四层】

文章给“智能体记忆”的定义是：Claude 从经历中学到、跨会话保留、存成以后能读的内容。改模型权重、单次对话里临时学到的东西、上下文快满时把旧对话压成摘要，这三种都不算。

按 Anthropic 的划分，记忆从下到上分四层：最底下是原始会话记录，可以搜索；往上是 Claude 自己写的记忆笔记；再往上是整理出来的结构，比如互相链接的 wiki；最顶层是每次开新会话就自动塞进上下文的内容。“做梦”负责把下层的东西核对、提炼，再往上送。

【会挑比记得多更重要】

宝可梦测试最能说明问题。Sonnet 3.7 觉得什么都可能有用，每场战斗、每个道具、每个路人都单独建文件，玩到 1 万步左右，记忆已有近 98 万字符。那时它开始建第四个“总”文件夹，接下来 17 步新建 6 个文件、删掉 9 个，一步游戏都没玩。

Fable 5 只记屏幕上看不到的东西。钱和位置每回合都能从画面读出来，记下来多余，还很快过期；策略和验证过的规律只有自己总结出来才存在。它用一个 global.md 当总控台，写着当前目标、打道馆的计划和自己的记忆规则。七个精灵球都没抓到鲤鱼王之后，它记下：“连续 3 球失败，就改变节奏，在菜单步骤之间多按几下等待。”Opus 5.5 用类似的小文件夹，边玩边改，最后通关。

数据库测试里，每道题都开新会话，只有记忆文件夹能带过去，答完会被告知正确答案。Sonnet 4.6 只会堆一堆没验证的猜测。Anthropic 说 Opus 5 是这批模型里第一个形成完整学习循环的：大多数笔记写了规则、怎么确认它成立、以前的答案，还有踩过的坑。

【给开发者的几条经验】

告诉 Claude 记忆是干什么的，别规定怎么记。只说一句“有个记忆文件夹可用”，Opus 4.7 和 Opus 5 就用得很好；加一条“只记录失败”，两者都丢掉了记忆带来的大部分提升。

老模型需要点拨。让 Sonnet 4.6 答题前先读记忆、并验证自己的猜测，得分从 0.364 涨到 0.641。Sonnet 5 不用提醒，10 次里有 9 次会自己先读。

自动加载的那一层要小。它每次都占 token，错一条会被带进每个会话，而且指令文件越长，模型越不容易照做。Claude Code 的自动记忆只加载 MEMORY.md 的前 200 行或 25KB，这部分当目录用，细节放在下层，留个链接。

多个 agent 并行时别写同一个文件。在一个收购合同测试里，四个 agent 同时往一张共享条款表里写，互相覆盖，57 条要点只留住 41 条。改成每份合同一页、一个 agent 负责、条款原文照抄，57 条全部保住。

【“做梦”还能建 wiki】

Anthropic 用 5 月收购的软件公司 Stainless 的约 35 万份内部文件（约 4.2 亿 token）做测试，让 Opus 5 分 128 次会话持续整理成 wiki，再回答 25 个问题。只靠 wiki，得分从 13% 涨到 48%；只靠搜索是 53%；wiki 加搜索从 54% 涨到 61%，每题还省约 2 万 token。

wiki 适合需要跨文档拼信息的问题。一组 24 题的并购问答，过半要综合多份文件，用 wiki 答对 87%，只用搜索是 73%。答案在单份文件里就能搜到的任务，wiki 没有明显帮助；有一次 wiki 写到 203KB，比 115KB 的原始文件还大。

【能不能用上】

“做梦”已经是 Claude Managed Agents（Anthropic 托管的 agent 运行服务）里的功能，目前是研究预览，要申请才能用；跨会话的记忆库功能是 beta。Anthropic 也放出了 cookbook，教开发者用自己的提示词和模型搭一套。

以上数字都来自 Anthropic 自己的测试，宝可梦的对比是每个模型各跑一次。文章也说，“做梦”要额外花算力，记忆该多久复查一次、在干活时记还是事后整理，都还没有定论。

06｜ReproBridge 打包实验复现步骤

来源（X） · @omarsar0 · 2026-11-07 23:14

中文译文

Google 的一篇很棒的论文，关于让 ML 实验对编码 agent 可复现。

（收藏一下）

如果你在研究代码上运行 agent，这篇值得你花时间。

他们发现，经过优化的产物将 agent 的复现成功率从 76.4% 提高到 92.6%（跨四个模型），并节省了 19.7% 的 API 开支。

ReproBridge 将一次成功的复现转化为一个包，供下一个 agent 重用。这个包包含清理后的代码、环境配置、启动每个实验的脚本以及一份书面指南。

一个新 agent 从该包中重新运行实验。然后一个独立的审计员检查运行是否真正发生过。

基准测试涵盖来自 36 篇论文的 1,029 个任务，每个任务有五个人工验证的参考分数。最好和最差模型之间的差距从 21.6 分缩小到 3.9 分。移除代码或环境配置会导致最大损失。

如果你的 agent 一直无法重新运行某个仓库，请在尝试更大的模型之前，先保存第一次成功运行的设置步骤。

https://arxiv.org/abs/2611.08452

与论文对话：https://academy.dair.ai/papers/reprobridge-building-reproducibility-into-ml-research-artifacts-2611.08452

原文

Great paper from Google on making ML experiments reproducible for coding agents.

(bookmark it)

If you run agents on research code, this one is worth your time.

They find that refined artifacts raise agent reproduction success from 76.4% to 92.6% across four models and cut API spending by 19.7%.

ReproBridge turns one successful reproduction into a package the next agent can reuse. The package holds the cleaned code, the environment setup, scripts that launch each experiment, and a written guide.

A new agent reruns the experiment from that package. A separate auditor then checks that the runs actually happened.

The benchmark covers 1,029 tasks from 36 papers, each with five human-verified reference scores. The gap between the best and worst model drops from 21.6 to 3.9 points. Removing the code or the environment setup causes the largest losses.

If your agents keep failing to rerun a repo, save the setup steps from the first successful run before trying a bigger model.

https://arxiv.org/abs/2611.08452

11｜Agent任务附效果截图供人工验收

来源（X） · @dotey · 2026-11-08 10:50

补充说明一下，这个截图或者录频重点是给人看的，Agent 要给验收的人类证明它把活干完了干好了。

比如今天有人报了个 Issue 说评论有问题，我把 Issue 直接发给 Agent 让它修，它修的时候也许自己也截图了，但是对我来说还是个黑盒子。

所以我需要它给我看“证据”，证明它修好了，当我看到这样的截图我就基本上可以确定它真的修好了没骗我。

引用内容

宝玉 @dotey

以前我团队有个员工做事比较粗心，也比较懒，每次让别人 Review PR 都不自己测，一审查就发现很多问题，后来我就让他提交 PR 的时候必须要带上相关功能修改的截屏，这样效果很好，至少去截图的时候得测试一遍。

现在我也把这一套应用在 AI 身上了，每次 Agent 任务完成，让它自己测试验证后，生成效果截图，让我看看效果。很多时候它自己截图的时候就发现问题，能顺手修复一下。
