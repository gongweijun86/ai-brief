04｜Google上线Harness工程课

来源（X） · @huxlab · 2026-11-19 20:49

Google 刚刚放出了一门近 2 小时的 Harness 工程完整课，直接教你从零搭出一套会7×24自己进化的 Agent 系统。

大多数人还在卷模型、复制粘贴 Prompt，但同一个模型，外层包裹的 Harness 不同，产出差距能拉开好几倍。

整门课最硬核的，是这四层工程递进：

1. 搭 Harness 底座：先定边界、工具、验证和记忆。让 Agent 靠谱的从来不是更长的指令，而是外层这套约束与支撑。

2. 做 Eval 工程：用Chief of Staff（幕僚长）的标准定义什么叫好，通过行为评测、横向对比和打分来验收，而不是看着“差不多对”就放行。

3. 跑通 Loop 闭环：告别“输入到输出”的一次性直线流程，让 Agent 自己跑、自己查、自己修，形成自纠错闭环。

4. 自进化图系统（Graph）：把真实失败自动沉淀为下一轮考题，让图结构持续迭代，实现 7×24 无人值守运行。

看完最大的体感是：

之前只调模型和 Prompt 的玩法其实很原始。

没有测试、评判、反馈和自动迭代，根本算不上工程闭环。

模型只会越来越强、越来越便宜。

真正拉开差距的，是谁先把 Harness、Eval 和 Loop 这三层跑通。

把“看起来对”变成“验证过、且能自己变好”。

以前这是顶级团队压箱底的工程心法，现在 Google 直接免费摊开讲透了。

05｜Agent权限由代码守住而非文档

来源（X） · @yymhxie · 2026-11-19 10:08

#FDE #自然语言 #权限

这两天又看到有人讨论 土豆姐的那场演讲。昨天说的是验证体系，今天 @akitabtc 抓了一个更具体的点：别对 AGENTS.md 这类自然语言约束期望过高。

这点我非常认同。
文档当然要写。项目背景、目录结构、最佳时间、常见问题，写清楚就能减少模型摸索的成本。但「告诉它不要做」和「让它做不了」，不是一回事。

你在文档里写「不能访问生产密钥」，如果执行环境里就有生产密钥，风险仍然存在。写「不能绕过测试」，如果 Agent 有权修改检查配置，最后能不能守住，还是取决于它有没有照做。

我一直坚持：确定性的规则逻辑放进代码，用测试守住；需要理解和推理的部分，再交给模型，用 eval 衡量。不能把所有东西都塞进提示词，最后靠模型每次自觉执行。

落地时，还得分清约束应该放在哪一层：
代码风格和禁用 API，可以用 lint、类型检查。
合并条件和回归要求，放到受保护的 CI 和分支规则里。
能访问哪些文件、能调用哪些接口、能否写生产数据，要靠执行环境、身份和权限控制。
对外发送、付款、删除这类动作，要有工具层的授权与审批。
本地 hook 很有用，但如果执行者可以跳过或者修改它，就不能当成最后一道保障。检查本身也要有边界，不能让被检查的改动顺手把检查关掉。

所以 Agent 每犯一次不该犯的错，不要只想到给文档追加一句话。先问：这是一个需要更好理解的判断问题，还是一个本来就能被系统拦住的规则问题？

前者补上下文、补评测；后者补程序约束。

原帖还提醒，不要轻易让长时间运行的 Agent 拿着过大的本机权限。这里我更看重的也不是「本机还是云端」这个标签，而是它实际能接触什么信息。

浏览器里也可能有敏感会话，远程环境里也可能有生产凭据。隔离环境、最小权限、短期凭据和可撤销授权，才是要检查的内容。长期运行意味着暴露时间更长，更不该默认给全套权限。

FDE在企业落地 Agent，一定要把两件事分开：哪些地方允许模型判断，哪些边界不允许模型自行决定。
文档负责把事说清楚，系统负责把边界守住。
