中文译文

我会第一个承认我在 Exploit 开发方面水平平庸，但我接触到了足够多极其出色的 Exploit 开发者，可以就此做出确定的判断：

任何声称他们用 AI"轻而易举"地生成了一个可用的 php2shell Exploit 的人，要么是：

a) 一个患有极度冒名顶替综合征的世界级 Exploit 开发者。

b) 正在看着某些听起来非常自信但完全错误的 LLM 输出。

基于我在 GitHub 上看到的 AI 幻觉 Exploit 的数量，我相当确信是后者。威胁行为者也在向我的蜜罐网络大量发送"php2shell"Exploit，这些不仅完全不可用，甚至和 Exploit 实际的工作原理相差十万八千里。

我在多个所谓的"php2shell Exploit"中看到了与附图相同的技术，包括 GitHub 上一个拥有超过100颗星的项目。问题在于，它既不是 php2shell，甚至根本不是一个漏洞。它是一种叫做"会话投毒"（session poisoning）的技术，可以用来利用 PHP 应用（不是 PHP 本身）中的本地文件包含（LFI）漏洞。

它与 CVE-2026-109618/CVE-2026-109619 唯一的共同点是两者都使用了"PHP_SESSION_UPLOAD_PROGRESS"功能。而两个问题的缓解建议都提到了将"session.upload_progress.enabled"设置为"Off"。

人们将漏洞的零散细节塞进 LLM，LLM 抓住了"PHP_SESSION_UPLOAD_PROGRESS"这个字符串，然后生成了与实际 CVE 毫无关系的会话投毒代码。而因为做这些事的人完全不知道自己在干什么，他们自信到把"概念验证 Exploit"发到 GitHub 并在社交媒体上分享。

所以如果你看到有人谈论"session poisoning + LFI"，很可能是他们的 LLM 基于 Orange Tsai 在2018年写的一篇关于本地文件包含攻击向量的博客文章幻觉出了一个 Exploit。

更糟糕的是，"安全研究人员"随后用 LLM 来分类这些利用尝试，同样陷入了同样的幻觉，然后确认存在正在进行的大规模利用（目前并不存在）。

真正的真实 Exploit 非常难以利用，到目前为止我还没有看到有人成功地在超过少数几个特定配置的 PHP 版本上将其运行起来。

LLM 在技术娴熟的专业人士手中是有用的工具，但对其他人来说，它们往往只是一个达克效应加速器。

原文

I'll be the first to admit I'm mediocre at exploit development, but I am in contact with enough extremely talented exploit developers to say this for certain:

Anyone claiming they were "easily" able to generate a working php2shell exploit with AI is either:

a) a world-class exploit developer with an extreme case of imposter syndrome.

b) currently looking at some very confident-sounding but wrong LLM output.

I'm rather certain it's the latter based on the number of AI-hallucinated exploits I've seen posted on GitHub. Threat actors are also blasting my honeypot network with "php2shell" exploits that not only don't work, but aren't even within 10,000 miles of anything to do with how the exploit actually works.

I've seen the same technique from the attached image in multiple alleged "php2shell exploits", including one on GitHub with over 100 stars. Problem is, it's not php2shell, nor is it even a vulnerability at all. It's a technique known as "session poisoning", which can be leveraged to exploit local file inclusion (LFI) vulnerabilities in PHP apps (not PHP itself).

The only thing it has in common with CVE-2026-109618/CVE-2026-109619 is they both use the "PHP_SESSION_UPLOAD_PROGRESS" feature. And mitigation advice for both issues reference setting "session.upload_progress.enabled" to "Off".

People are shoving loose details of the vulnerability into LLMs, the LLMs are keying in on the "PHP_SESSION_UPLOAD_PROGRESS" string, then generating session poisoning code that has nothing to do with the actual CVE. And because the people doing this have absolutely no idea what they're doing, they're confident enough to post their "proof of concept exploit" to GitHub and share it on social media.

So if you see people talking about "session poisoning + LFI" it's likely their LLM hallucinated an exploit based on a 2018 blog by Orange Tsai talking about a local file inclusion attack vector.

What's even worse is that "security researchers" are then using LLMs to triage these exploitation attempts, falling victim to the same hallucinations, then confirming there is ongoing mass-exploitation (there currently isn't).

The actual real exploit is very difficult to exploit, and so far I've not seen anyone successfully get it working on more than a handful of PHP version with highly-specific configurations.

LLMs are useful tools in the hands of skilled professionals, but for others, they're often just a Dunning-Kruger accelerator.

07｜Anthropic 将子智能体合并进主循环

来源（X） · @snwiki238337 · 2026-10-23 19:02

Anthropic 的这篇文章可以看看，《构建智能体：何时把子智能体合并回主智能体循环》

文里提出了一个观察就是我们目前的大多数公司的 Agent 架构，不知不觉就变成了公司内部组织架构图的翻版。

意思就是说比如做客服或企业中台，市场部、财务部、订单部各自造一个独立的 Subagent，然后中台团队在上面搭一个中央调度器。

其实在我们的视角来看的话是很好的，很清晰和完整的分类。但在实际生产中不是。

每个子 Agent 都有自己独立的 Prompt 和上下文，跨智能体转交任务就像玩传话游戏，每一次 handoff 都在丢失关键细节。

而且呢各个业务线为了向其中加入自己的规则，最后把系统提示词搞成了一个人格分裂的弗兰肯斯坦，而且呢架构中的多层嵌套的 LLM 循环直接让端到端延迟翻了整整一倍。

Anthropic 的应用 AI 团队在实际帮企业调优后给出了一种方法：他们把绝大多数调度器和 Subagent 砍掉，收进单一大模型的主循环里。

他们发现，随着 Opus 4.5 到 5.5 这代前沿模型自带的思考和自我修正能力大幅进化，原本靠外部复杂框架硬编码约束的很多繁琐环节，模型自己就能处理得很好。

他们把子智能体的业务经验降维沉淀为 Skill，把数据读写拆解为标准的 MCP Tools，主循环只加载极短的描述，只有在模型实际需要调用时才动态加载细节。

Anthropic 透露，他们自己用这套思路把 Claude Code 的系统提示词直接精简了 80% 以上。

当然官方并不是完全否定多智能体，对于多 agent ，官方认为可以依据一下来判断你是否需要保留多 agent 。

只有当单上下文确实出现了可量化的性能衰减、需要用完即弃的新上下文去并行跑多条完全独立的探索路径，或者指令出现不可调和的逻辑互斥时，才值得单独开一个 Subagent。

除此之外的绝大部分业务，单一共享上下文的效果反而更好，因为模型能够直接看到之前每一步真实的工具返回原始数据，而不是阅读被子智能体压缩失真后的总结。
其实这从我们日常写代码、做 Agent 时就能明显感受到，我相信很多动手搭过多智能体系统的人都有体会。

最开始大家觉得多智能体架构分工明确、图谱漂亮，但之后的链路调试，或者说子 Agent 等等的问题可以说是很折磨人。

我们的 agent 始终要向着效果看齐。能用少的开销，还有一个基本干净的的上下文能很好的把工作做好，其实就是我们所需要开发的 agent。

不要过度设计，把子智能体打散成按需加载的 Skills 和 Tools 是一个很好的轻量思路。

原文：https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop
