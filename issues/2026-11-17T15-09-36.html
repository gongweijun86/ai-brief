03｜Claude Code 三类测试验证代码

来源（X） · @hongming731 · 2026-11-17 20:52

Addy 分享了 Claude Code 团队内部的验证体系，很值得一读。这套方法论的精髓，就在于用确定性的工程制度，把充满概率不确定性的大模型关进质量笼子里。

一、 别再迷信单元测试：AI 时代最值得投入的三类测试
在给 AI 配备验证工具时，首先要避开两个致命陷阱：

一是不稳定的测试，这会训练出只会反复重试、不修真正漏洞的偷懒 AI；

二是运行过慢的测试，这会迫使 AI 积攒大量改动后才测一次，极难定位根因。

在此基础上，团队最推崇以下三种真正能卡住质量的测试手段：

1、端到端测试：给 AI 装上真实的「手和眼」单元测试全绿，线上功能依然可能崩掉，因为局部测试和 AI 往往都没有理解完整的业务全貌。端到端测试模拟真实用户的完整操作路径，比如加购、结账、跳转确认页，它极难被糊弄，功能要么通，要么不通。团队在代码库里沉淀了专门的验证技能，教会 AI 像真人测试工程师一样启动本地服务、拉起浏览器或手机模拟器真刀真枪跑一遍。一旦出错，AI 能直接看到页面截图和直观报错，自己迭代修复。

2、基于属性的测试：用海量随机输入打破「同源盲区」让写代码的 AI 顺手写单元测试，往往会陷入同样的思维盲区，漏掉极端边界条件。属性测试不针对具体用例，而是直接定义绝不能被打破的业务铁律，比如账户余额永不为负、数据编码再解码必须还原、接口重试多次结果一致，然后利用自动化测试库生成成千上万组极端输入去轰炸代码。在旧文档失真、重写核心逻辑时，这招尤其管用。

3、差分测试：把老系统当成「标准答案」在做大型系统迁移或语言重写时，与其人工编写海量断言，不如直接把老系统当作绝对真理。用随机输入或脱敏的真实生产流量，同时喂给新旧两套系统，只要两边输出不一致，就说明新代码引入了破坏性变更。

二、 把验证层当成核心系统来治理的工程铁律

光有测试工具还不够，Claude Code 团队围绕验证建立了一套严密的防作弊与自我进化机制：

1、三振出局，精准呼叫人类
遇到测试报错，AI 会自己尝试修复。但如果同一项检查连续改了三轮依然失败，AI 必须立刻停手并呼叫人类介入。这既防止算力在死胡同里空转，也把工程师的注意力精准聚焦在真正的硬骨头上。

2、基于代码变更动态匹配「踩坑清单」
团队维护了一份包含三十九条历史血泪教训的可靠性清单，比如恢复旧会话记录时，新增字段是否兼容缺失场景。审查时，AI 只读取本次代码变更，动态匹配命中条件的三到十条规则进行检查，既省去了把几百行规范全塞进上下文的算力浪费，又防住了历史故障重演。

3、物理防作弊：改动绝不能修改自己的「考卷」
审查代码时读取的规范文件，必须强制从主干分支拉取，绝不读取当前工作分支里的版本，防止 AI 为了通过审查而偷偷篡改验收标准。同时，低成本的代码格式和构建检查必须通过本地钩子拦在提交合并请求之前，绝不把低级错误带进公共流水线浪费资源。

4、像评估产品一样评估「审查者」
每次把线上回滚和人类找出的漏网之鱼，通过多智能体证伪后沉淀为新规则；新门禁上线先开观察模式统计误报率，调优后再切强制拦截；同时给审查意见打上必改、微瑕和历史遗留等标签，防止 AI 过度挑刺，并定期修剪冗余规则，保持整个验证体系轻快锋利。

04｜LoopForge 开源AI交付SOP

来源（X） · @berryxia · 2026-11-17 00:11

兄弟们，腾讯刚开源了 LoopForge，能自己部署的 AI 写代码交付平台，Claude Code、Codex、Cursor 都能接！

很多人以为 AI 写代码的瓶颈在模型，写得不够好。
腾讯在发布帖里的原话正好反过来：代码从来不是瓶颈，交接才是。

让 Agent「修个 bug」，跑一次靠运气：可能跳过计划，忘了测试，自己审自己的代码，跑到一半停了也没人发现。

LoopForge 的做法是把团队的交付流程写成 SOP，让 Agent 在云端按流程循环跑：

① 角色分开：计划、写代码、审代码、测试是四个不同的 Agent，写的人不审。

② 脚本说了算：编译和测试过没过，看退出码，不听 Agent 自己说「好了」。

③ 人来签字：关键节点停下来等你批，可以打回到任意一步重做。

④ 自己进化：官方说每次运行会打 0 到 100 分，复盘哪里出了问题，把改进建议写回 SOP，你审过再应用

执行的 Agent 可以换，README 里列了十个：CodeBuddy、Codex、Claude Code、OpenCode、Cursor CLI、Kimi Code、DeepSeek Harness 等。

MIT 协议，代码和密钥都留在你自己的服务器上。

不想搭服务器的，还有个本地版，在项目里跑一行：

npx -y loopforge-cli@latest install claude

装完在 Claude Code 里用 /start-devflow 加需求就能走内置流程。

说实话，需要注意的几点：

· 平台版要 Docker，模型的 key 要你自己出
· 对话工作台目前只有中文，管理页面是中英双语
· 现在还是 v0.3 版本；那个 0 到 100 分的自我进化，README 里没写细节，以发布帖为准

我的看法：一个人用 Claude Code 写代码的，先装本地版试试；
团队里已经好几个人在用 Agent 写代码、又管不住质量的，平台版值得搭一套。

仓库地址在原帖里👇

06｜aoa 实现可插拔常在线Agent内核

来源（X） · @ninthbit_ai · 2026-11-17 20:59

前几天看了 Claude 那篇关于如何构建 Always-on Agent 的博客之后，发现原文讲的非常详细，完全可以作为一份开发文档使用。于是我做了这样一个掐头去尾的东西，把这里的 inbox + worker 机制做成了一个头尾可插拔的kernel。我猜应该已经有大佬实现了，这里仅仅是作为自己使用记录一下。

1、可插拔的头部，其实原博客里只说了支持webhook 事件，来往 inbox 里来存任务，但其实我更希望这个可以像 grokbot 的那种交互形式，幕僚长+cloud agent。于是我就想把这个服务封装成 mcp 或者 skill，方便我在 claude code 里直接使用，这样一来其实也成了一种 orchestration 模式，用 claude code 来做 main agent。

2、可插拔的尾部，这个比较好理解，就是接入不同的harness 当 worker。但是有个问题是，当人不在 loop 时的权限问题，如果直接使用 harness 当作 worker 那很多权限处理是在harness内部的，无法让 kernel 感知到。所以我还是选择了 pi 自己构造了一个 built-in 的 worker，而harness 的权限还是交给它自己去控制。

3、多个 worker 的协作模式，我一开始比较简单的以为，多 worker 可能就是多个 worker 从同一个 inbox 里取得任务。但后面还是改成了，每个 agent 一个 inbox，这样的话 agent 之间进行交接的时候，可以通过 inbox 进行通信。这里不知道是不是设计的更复杂了，后面还需要在任务量多起来时多实践实践。
