01｜TrenTorch 从零实现 ML 算法

来源（X） · @Michaelzsguo · 2026-10-18 10:41

刷算法题有 LeetCode，刷 AI / ML 题有 TrenTorch！

学了那么多机器学习理论，真让你从零写一个 Softmax、反向传播，甚至 Transformer，你能写出来吗？

http://TrenTorch.com 免费提供 1600 多道题，从线性回归、神经网络，到强化学习、模型推理和底层 Kernel。

玩法和 LeetCode 一样：看题、写代码、提交，用隐藏测试验证结果。区别在于，LeetCode 考算法和数据结构，TrenTorch 考你能不能亲手实现机器学习算法。

比如平时一行代码就能调用的 Softmax、交叉熵损失，在这里都得从零实现，还要处理数值溢出、张量形状等细节。

准备 AI / ML 岗位面试可以拿它刷题，自学也能检验一下：那些看懂了的理论，自己到底能不能写出来。

网站展示的注册用户里，也有来自 OpenAI、Anthropic 等头部公司，以及哈佛、斯坦福等高校的学习者。

02｜VoiceStudio 本地语音克隆合成

来源（X） · @lxfater · 2026-10-18 09:30

配音、克隆声音，不一定要花钱了。

GitHub 上有个开源项目 VoiceStudio，能把一套语音工作台装进你自己的电脑。

它可以做什么？

→ 给一段参考录音，克隆已获授权的声音
→ 把文字生成旁白、口播和有声书
→ 给视频配上其他语言的语音
→ 把录音转成文字
→ 在不同语音模型之间切换

这些功能，一个应用搞定🤝。

选用兼容的本地模型后，语音生成就在自己的机器上完成，不用每生成一段音频都调用外部付费接口，数据也在本地😁，防止你做奇怪的事情。

做教程、短视频，文案改了就能重新生成旁白；想做有声书，也可以先拿一小段试试。

https://github.com/debpalash/VoiceStudio

04｜Codex Worktree 隔离并行任务

来源（X） · @sitinme · 2026-10-18 15:35

Codex同时开3个任务，代码越改越乱？Worktree这步别漏

给 Codex 同时派三个活，是一件很爽的事。

修登录、改后台页面、升级依赖，三个窗口一字排开，各干各的。

过一会儿，三个任务都说“完成了”。

然后你打开项目一看：修改全混在一起。改页面的任务跑测试时，读到了登录任务改到一半的文件；升级依赖的任务，又顺手动了大家都在用的配置。

问题出在哪？

聊天窗口分开了，代码没分开。

如果三个任务都选了 Local，它们其实在改同一份项目文件。

解决办法就是 Codex 里的 Worktree。但它也不是“开了就万事大吉”，有两件事它管不了。

这篇就拿这三个任务，把三件事讲清楚：

1.Worktree 到底把什么分开了；
2.哪些任务能并行，哪些必须排队；
3.任务说“完成”以后，结果怎么收回来。

引用内容

sitin @sitinme

很多人会把“分支”和“Worktree”混在一起。

简单理解：分支解决的是代码历史怎么分叉，Worktree 解决的是多个任务怎么同时拥有独立的工作目录。

分支是提交历史上的一条指针。

它回答的是“这组提交属于哪条开发线”，但不会自动创建第二份文件目录。你仍然只能在当前目录中切换分支。

Worktree 是同一个 Git 仓库关联的另一份工作目录。

它可以绑定到不同分支，让两个任务同时拥有各自的文件、依赖和终端窗口；提交对象和 Git 历史仍然共享，不需要复制一整份仓库。

一个实用的判断句是：只需要另一条提交线，用分支；需要同时打开另一份文件，用 Worktree。

05｜1873铁路崩盘类比AI投资潮

来源（X） · @MrPingChecks · 2026-10-18 12:21

卧槽，拿过普利策奖的金融史学家对当前AI 热潮下了判断：“我们肯定已经进入狂热阶段。”他还打了个比方：当年引爆 1873 年铁路大崩盘的那一幕，放到今天，就好比 OpenAI 突然宣布，承诺要筹的一万亿美元筹不齐了。

他叫艾哈迈德，当过二十多年投资经理，新书《1873》写的就是那次铁路崩盘和第一次大萧条。这周他上了 Prof G Markets，把 1873 年和今天逐条对了一遍。

1873 年是这么崩的。当时全球靠铁路这项新技术繁荣了 20 年，每年约 30 亿美元投进铁路，大约四分之三是借的。那年 9 月，美国最有名的金融家 Jay Cooke，总统的朋友，南北战争时靠卖国债筹了 20 亿美元，突然宣布：他给北太平洋铁路承诺的约 1 亿美元，相当于今天约 1000 亿，筹不齐了。其他铁路公司一看，连他都借不到钱，我还借什么。3 个月内全美铁路停工，1 年内四分之一的铁路公司违约。

他说今天和历史有三点相似。一是越建越多、越来越靠借债，而且债不透明，英伟达“本质上是在借钱给自己的客户”。二是利润被侵蚀，1872 年底只有四分之一的铁路公司还付得出股息，今天对应的是 token 价格一直在跌。三是借钱变贵，当年铁路发债利率从五六厘涨到 9%。

纳德拉说读了这本书，“我们会很小心”。艾哈迈德说他理解反了：每家公司单独看都很小心，合起来就是会建过头。这是囚徒困境，谁放慢谁丢市场份额，“大概没有解决办法”。

美国历史上四五次大的私人投资热潮，从 1870 年代、1920 年代、互联网泡沫到 2000 年代的房地产，都是投资多出 GDP 的 2% 到 4%，持续两到四年，最后产能过剩、利率飙升、崩盘。他说数据中心这一轮大概走了两年，“可能走到一半”，规模还没到历史极端。时点没法预测，可能还能再走一两年：“这种事拖得比你想的久，来的时候比你想的快。”

他真正担心的是另一件事。1873 年把一次普通的下行变成四年大萧条的，是货币政策的大错：德国和美国先后放弃白银，银价跌三四成，全球信用一下收紧。今天他担心两点：美股市值已是 GDP 的 250%，一跌就打消费；过去一年外国人买了约一万亿美元美股，这笔钱一撤、美元一跌，美联储降息救市就两头为难。

接下来会怎么崩？他列了三种：某个大玩家突然融不到钱，地缘政治出意外，中国开源模型让利润大面积缩水。问他谁会是今天的 Jay Cooke，他说不知道是 Anthropic 还是 OpenAI。

06｜Sweeney 70%编码工作被AI接管

来源（X） · @TimSweeneyEpic · 2026-10-18 09:39

中文译文

我在编写 Unreal Engine 1 的时候，时间大致是这样分配的：

- 大约 30% 用于对难题进行深度编码：汇编语言纹理映射器、C++ BSP 树、数据持久化、面向对象的系统设计以及网络。

- 大约 70% 只是打字和重构大量代码，这些代码是完成一个引擎的完整功能集所必需的。这并不难，在做这些的时候，我的心思大部分在更深层的编码问题上，思考和规划下一步要做什么。这跟今天的 vibe coding 感觉没什么不同，只不过是我自己坐在 IBM Model M 键盘前敲代码，而不是通过提示词让它来写然后审核结果。

所以，一旦 AI 能以跟我们差不多的质量标准（从来不是完美）来完成那 70%，我们依赖 AI 来做这部分工作就一直是顺理成章的事。经过几年 AI 模型的进化，它能够接管那 70% 的工作并把程序员的时间解放出来去做更有价值的任务，这并不令人意外。

更令人惊讶的是，AI 作为一种即时版 Carmack 的崛起——它能够相当巧妙、且往往是干净利落地解决困难的技术问题，而且它既可以通过操作工具，也可以通过直接理解原始数据文件来推理和处理复杂的 3D 场景。

我在 1998 年放弃了汇编语言，因为乱序执行 CPU 让更简单的 C/C++ 代码运行得更快，我从来没有怀念过它。如果通过架构文档、概念美术和设计方案来进行提示能够超越手敲代码和手动调整顶点，那将使开发者能够把时间花在更高层次、更高价值的技术和创造性任务上。

真正重要的是最终产品，无论它是一个游戏还是一个引擎。开发者能做的任何事情——尝试更多想法、更快地做出更好的软件和游戏——对所有人来说都是一种胜利。

原文

When I was writing Unreal Engine 1, my time was divided as follows:

- Around 30% went to seriously deep coding on hard problems: assembly language texture mappers, C++ BSP trees, data persistence, object oriented systems design, and networking.

- Around 70% was just typing and refactoring large bodies of code needed for a complete engine feature set. This was not hard, and while I was doing it my mind was mostly on the deeper coding topics, thinking and planning for what's next. It didn't feel much different from vibe coding today, except that it was just me typing code on an IBM Model M keyboard rather than prompting it and reviewing the results.

So, it has always seemed perfectly logical that we would rely on AI for that 70%, once the AI could do it with a similar quality standard as we could, which has never been perfection. It came as no surprise that, after a few years of AI model evolution, it was able to take the reigns on that 70% and free up programmers' time for more valuable tasks.

What's more of a surprise is the emergence of AI as a sort of insta-Carmack able to solve hard technical problems quite cleverly and often cleanly, and that it's able to reason about and work in complex 3D scenes both by operating the tools and by directly understanding the raw data files.

I abandoned assembly language in 1998 when out-of-order CPUs made much simpler C/C++ code faster, and never I missed it. If prompting through architectural documents, concept art, and design plans can transcend typing code and tweaking vertices, that will enable developers to spend their time on higher-level, higher value technical and creative tasks.

What matters is the end product, whether it's a game or an engine. Anything developers can do to try out more ideas and make better software and games faster is a win for everyone.
