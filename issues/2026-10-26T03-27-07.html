01｜小黑Skill为长文统一配手绘图

来源（X） · @Ryrenz · 2026-10-26 11:05

🖍️ 好家伙，ian-xiaohei-illustrations 能给一篇中文文章一口气配齐 4 到 8 张手绘插图，画风还统一。

ian-xiaohei-illustrations 今年 5 月底才发布，GitHub 已经 1.2 万 star，fork 也有 1400 多个。

写公众号、博客、Notion 文档的人都知道，最磨人的往往不是写字，是配图：自己画不会，AI 生图每张风格都不一样。这个 Codex Skill 的做法是先读你的文章，提炼出关键点，先给一份分镜清单，再逐张调用图像模型生成。

所有图都是同一套画风：纯白底、黑色手绘细线，配几笔红橙蓝的中文手写批注，主角是一个叫“小黑”的黑色小角色，白点眼、细腿、面无表情。每张图只讲一个动作或一个比喻，一组排下来像出自同一个画师之手。

作者也提醒了，AI 生图可能出错字、风格漂移，生成完要过一眼。

后来作者又做了小黑 2.0 版本 ian-xiaohei-scenes，也有 541 star，还有人照着小黑的路子做了自己的配图 skill。

写完文章，不用再为配图发愁了。

02｜Amp让Agent覆盖发版与生产观测

来源（X） · @shao__meng · 2026-10-26 10:09

How I Work with Agents：让 Agent 横向打通构建、发版与生产观测

@thorstenball (@AmpCode) 把「怎么用 Agent」总结成了一套可执行世界观：软件变便宜、变化速率必须进计划、「堆 slop」论已过时、prompt 写 what 不写 how；真正放大收益的是 Agent × 代码库可读性 × 流程 三角，并让 Agent 横向覆盖构建 → 发版 → CI/生产日志/feature flag/监控，不只替换编辑器里的打字。

他怎么看当下
· 修 bug、改功能、出原型的时间常数变了；feature flag、Grafana 等过去嫌麻烦的事，现在交给 Agent 反而划算。
· 不能只按「2026 年 10 月模型能做什么」定流程，要计入 token 降价与 frontier 约两周一更——可能处于「六个月后更便宜更快」的通缩期。
· 「不审每一行就会堆成不可维护 slop」他认为已不成立：会有 slop，但强模型也能帮你清；去年模型常迷糊，现在可丢给很脏的代码修。
· Prompt 升一层：不再强调文件 @ 提及与复杂排版；例：「把字节码编译器和 VM 提速一倍」「按这些截图做一个类似项目」。Amp Web/macOS/iOS 已去掉 @ mentioning。

三角：Agent · 代码库 · 流程
只把 Agent 塞进「以前文本编辑器那一格」，再照旧 push/review，GDP 不会涨。要让 Agent 竖向吃透前后端/库/基建之外，再 横向会部署、看 CI、读生产日志、拨 flag、看指标。Amp 自研叙事：约 200 万+ 行 monorepo、几乎全由 AI 做出；上 Orbs/云 Agent 后提交速度明显起来。

个人日常用法
· 永远用最强模型（点名 Opus 5.5）；便宜/开源模型适合固定工作负载，否则多轮纠错可能更贵。
· 口述在升温；不再手工管 context（handoff、thread map 等被弱化）。
· Agent 不写给人读的散文（Slack 人手写）；写机械文案：排障步骤、事故报告参数说明等。
· Automations/定时唤醒 成刚需：发版后两小时再查错误率；sidebar 用「snooze until next message」保持干净。
· 不要干等 Agent：异步推进；要改 UI 就一次要 多版变体 再点选，而不是来回迭代。
· 只审承重代码；边缘（如 CSS）容错更高。口头禅（来自 Quinn）：「给我无可辩驳的证据，证明这能跑。」——E2E、截图、录屏、测试矩阵；有了证明再进 review，心态完全不同。
· 约 8 周几乎不本地写代码；本机偶发杂务 / Pi 上跑 amp --no-tui 做家庭自动化。

团队：让代码库对 Agent「可读」
· 约 15 个 AGENTS.md + skills（dev server、gcloud、BigQuery、部署等）：能看见、能启动、能注入数据，才少幻觉。
· Threads 作共享记忆：Agent 可 read_thread 追到同事某次提交的讨论。
· All-in Orbs：一线程一临时机、空闲缩零；随便装依赖/FFmpeg/自建 slideshow。需要 macOS 特化时用 Runner，Orb 与本机线程互传文件与证明。
· 生产侧：canary、日志、专给 Agent 走的生产路径（类比「为测试改代码」）；插件拨 flag、查健康、读 bug 诊断包。
· 流程偏 AI-native：推 main、少/无 PR（避免 Orb 跑 20 分钟 CI 再远端重跑一遍）、设计师也在 Orb 里出原型与修代码、不用 Figma。
· Slack 一点开 bug → Agent 拉诊断 → 修 → 发邮件/发积分；事故用 get system health 类插件。
· 评测 Agent 友好度：改完 AGENTS.md 就 spawn 多个干净 Orb（含对照组）验证是否真走新脚本/插件，再合入。

案例：Orbs OOM
Slack 接报 → 起 Opus 线程查 top 内存进程与告警 → 查日志/BigQuery/相似 bug → 方案迭代 → feature flag 包起来 → 发版 → 人批准开 flag → 再 spawn Orb 人为吃内存验证 → 作者回传录屏确认。强调：小步发生产 + flag，在有 Agent 时比过去本地点点点便宜得多。

03｜Gemini 4 Argon长文不丢信息

来源（X） · @kk_shinkai · 2026-10-25 20:02

最近试了一下 Gemini 4 Argon，感觉它在沟通和措辞上比 Opus 5.5 还要好一个档次，在整理和理解复杂内容上很有效。我在重构代码的时候需要理解很多盘根错节的垃圾，Argon 基本能准确的把问题说清楚，描述也很清楚，很少需要我反复追问某个点到底是什么意思，反倒是 Opus 有时候内容压缩得太严重，需要我多问几轮。而且 Argon 在长上下文的情况下更少丢东西，所以体感上完全没有 Opus 那种时好时坏的起伏感。

Argon 最大的问题在于严重的讨好倾向，对于写代码来说这不是大毛病，因为我有能力判断它说的对错，只剩下在写作和沟通能力上的优点。但如果是在学习不熟悉的新东西，Argon 几乎是不可用的，因为它会无止境地夸赞你， 附和错误的说法，以至于你根本无法判断到底什么是对的。这点 Claude 系列模型做的都非常好，在对抗用户说的胡话这点上，Claude（包括 Sonnet）的水平比其他 SOTA 模型高了不止一个档次。

至于 GPT-6 Astra，我觉得它十分怪异。Astra 的推理能力很厉害，但是它的措辞非常糟糕，以至于我几乎完全无法理解它说的任何长篇幅的话。Astra 的 spec gaming 倾向也达到了一种灾难性的程度，如果你给它下达的指令有任何轻微的过约束，它就会立刻把你没有写在字面上的真实意图当作可放松的条件去除，甚至干脆把某条根本不应该纳入讨论的基础常识当作阻碍去掉，在这种荒谬的前提下继续工作。复杂问题是在探索和试错中完成的，但在真正把程序实现出来之前，几乎不可能穷尽边缘场景。要求实现前就给出没有细微矛盾的 spec 和思维是否缜密、能力高低无关，这违背了客观规律。

不过论订阅的价格和难度（再算上 reset 次数），Astra（在 Ultra 档位下）还是有些优势的，以至于我不得不绞尽脑汁思考如何驾驭这个怪胎。我意识到作为一个从人类语料训练出来的 SOTA 模型，它不可能不具备正确理解人类意图的能力，但糟糕的训练方式让这种能力被掩盖了。只要被任务逼着，这种能力就无法发挥，也无法用 prompt 缓解。但如果把 review 的部分单独拆出来，小心地挑选它能看到的上下文， 也没有苛刻的约束逼它，常识和真实意图有机会重新占据主导，让它正确地识别出荒谬性，重新拥有架构和工程意识。我设计了一套流程，虽然不可能解决模型内部的问题，但至少让 Astra 表现得稍微正常一点了，让它的推理能力和 Codex 的 Computer Use 发挥它们本应该有的效果，做出有价值的成果而不是纯粹地在腐化和污染代码库。当然，写作这部分我认为 Astra 确实没救了，我几乎不会阅读 Astra 说的话，要么直接复制丢给其他模型，要么干脆让其他模型调用 Codex CLI。

虽然这样要维护好几个订阅，在各种终端和 App 里来回切换和复制，让人很不舒服，但是目前这是唯一让我觉得能顺利推进复杂问题的工作流。

04｜出海网站SEO上线前自查清单

来源（X） · @liangzhu_AI · 2026-10-25 14:54

很多用 AI 几天搓出来的网站在 Google 搜不到，根本不是内容差，而是上线前漏了这 7 项。

Vibe Coding 确实快，但大部分人写完前端往 Vercel 一挂就以为万事大吉，
一个月过去后台展现量还是鸭蛋。

我给你整理了一份出海网站上线前必须打勾的 SEO 救命清单：
1. 检查是不是纯客户端渲染：必须配置 SSR（服务端渲染），确保爬虫抓到的是完整 HTML；
2. 生成动态 Sitemap.xml 并主动提交到 Google Search Console；
3. 检查 robots.txt：千万别手滑把 Googlebot 给拒之门外；
4. 全站全局搜一下 noindex 标签，很多脚手架测试环境默认带这个，上线前必须干掉；
5. 清除多重重定向死链，把 404 页面做优雅降级。

这 7 项自查加起来不到半小时，但决定了你几个月的心血能不能被搜索引擎正常索引。
建议做独立开发的朋友先收藏，每次新站上线前照着逐项对一遍。
